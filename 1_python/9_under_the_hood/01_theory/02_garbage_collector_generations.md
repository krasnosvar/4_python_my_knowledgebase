# Generational garbage collector

## Зачем нужен GC поверх refcounting

Refcounting (см. предыдущую тему) не может уничтожить объекты, участвующие
в цикле взаимных ссылок — их счётчик ссылок никогда не дойдёт до нуля сам
по себе. Модуль `gc` реализует **трассирующий** сборщик мусора,
специально для поиска и уничтожения таких недостижимых циклов.

## Поколения (generations)

Гипотеза генерационного GC: «большинство объектов умирают молодыми» —
если объект пережил одну проверку GC, вероятность, что он проживёт долго,
выше. CPython делит отслеживаемые объекты на 3 поколения:

- **Generation 0** — новые объекты. Проверяется чаще всего.
- **Generation 1** — объекты, пережившие хотя бы одну проверку gen 0.
- **Generation 2** — объекты, пережившие проверку gen 1. Проверяется реже
  всего.

```python
import gc

print(gc.get_threshold())   # например (700, 10, 10)
```

Тройка `(700, 10, 10)` означает: gen 0 проверяется, когда число
выделений минус освобождений превысит 700 с прошлой проверки; каждый раз,
когда gen 0 проверяется 10 раз, проверяется и gen 1; каждый раз, когда gen 1
проверяется 10 раз — проверяется gen 2.

## Не все объекты отслеживаются GC

Только объекты, которые **потенциально могут** участвовать в цикле
(контейнеры: `list`, `dict`, объекты пользовательских классов, `set` и
т.п.), регистрируются трассирующим сборщиком. Неизменяемые атомарные типы
(`int`, `str`, `tuple` из неизменяемых элементов) не могут содержать
цикл сами на себя и не отслеживаются:

```python
import gc

gc.is_tracked([1, 2])     # True — список может входить в цикл
gc.is_tracked((1, 2))     # False — кортеж из простых типов не может
gc.is_tracked("hello")    # False
```

## Как GC находит циклы

Упрощённо: для каждого отслеживаемого объекта в поколении вычисляется
"внешний" refcount (сколько ссылок приходит **извне** проверяемого
множества объектов). Если после вычитания внутренних ссылок (объекты
ссылаются друг на друга внутри множества) внешний refcount равен нулю —
всё множество недостижимо и уничтожается целиком, даже если внутри
множества объекты продолжают ссылаться друг на друга.

## __del__ и циклы: осторожно

До Python 3.4 объекты с `__del__` в цикле вообще не могли быть собраны
(GC не знал, в каком порядке вызывать деструкторы). С 3.4+ (PEP 442) это
исправлено — GC способен собирать такие циклы, но порядок вызова `__del__`
не гарантирован, и внутри `__del__` объект может увидеть уже частично
разрушенные связанные объекты — по возможности избегайте сложной логики
в `__del__`, особенно если класс участвует в циклах.

## Ручное управление GC

```python
import gc

gc.disable()          # отключить автоматический цикл GC (refcounting всё равно работает)
gc.collect()          # запустить сборку принудительно, вернёт число собранных объектов
gc.enable()

gc.get_stats()        # статистика по каждому поколению: collections, collected, uncollectable
```

Отключение GC иногда используют как оптимизацию в коротких CPU-bound
скриптах, которые создают много временных объектов без циклов (например,
загрузка большого числа объектов при старте) — избегая накладных расходов
на периодические проверки, но это осознанный компромисс, а не общая
рекомендация: без GC циклические структуры будут копиться в памяти.

## weakref как альтернатива борьбе с циклами

Вместо того чтобы полагаться на GC для разрыва циклов (родитель ↔
ребёнок, кэш ↔ значение), можно изначально не создавать сильную ссылку в
одном из направлений:

```python
import weakref

class Node:
    def __init__(self, parent=None):
        self.parent = weakref.ref(parent) if parent else None  # слабая ссылка
        self.children = []

root = Node()
child = Node(parent=root)
root.children.append(child)   # сильная ссылка родитель -> ребёнок
# child.parent — слабая ссылка, не увеличивает refcount root
```

`weakref.ref(obj)()` возвращает сам объект (или `None`, если он уже
уничтожен) — обращение к нему явное, в отличие от прозрачного цикла.
Это позволяет объекту быть уничтоженным через обычный refcounting сразу,
без ожидания generational GC.

## Практическое значение

- Утечки памяти в Python чаще всего — не "GC не сработал", а забытые
  сильные ссылки (глобальный список подписчиков на события, кэш без
  ограничения размера, замыкание, держащее ссылку на большой объект).
- `gc.collect()` полезен в тестах, если нужно детерминированно проверить
  вызов `__del__`/освобождение ресурса до следующей проверки.
- Для долгоживущих сервисов с высокой аллокацией мелких объектов —
  `gc.get_stats()` и `gc.set_threshold()` иногда используют для тюнинга
  под конкретный профиль нагрузки, но это редкая, узкоспециализированная
  оптимизация.
