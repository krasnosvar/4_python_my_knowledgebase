# Модель памяти CPython и подсчёт ссылок

## Всё — объект, у каждого объекта есть refcount

В CPython каждое значение — объект в куче с заголовком, который включает
поле `ob_refcnt` — счётчик количества ссылок на этот объект. Даже
маленькие целые числа и `None`/`True`/`False` — полноценные объекты.

**Куча (heap)** — область памяти процесса, из которой программа во время
работы выделяет память под объекты произвольного размера и времени жизни
и куда возвращает её, когда объект больше не нужен. (Не путать с
одноимённой структурой данных «куча» из `heapq` — это разные вещи.)
Переменная в Python хранит не сам объект, а **ссылку** на объект в куче;
`ob_refcnt` считает, сколько таких ссылок сейчас существует.

```python
import sys

x = [1, 2, 3]
print(sys.getrefcount(x))  # обычно 2: сама переменная x + временная ссылка
                             # внутри аргумента вызова getrefcount
```

Когда счётчик ссылок доходит до нуля, объект **немедленно** уничтожается
(вызывается `__del__`, память освобождается) — в отличие от языков с
трассирующим GC (Java, Go), где освобождение памяти откладывается до
следующего цикла сборки мусора.

## Когда меняется refcount

- Присваивание переменной, добавление в список/словарь, передача как
  аргумент функции — **increment**.
- Выход переменной из области видимости, `del x`, удаление из
  контейнера, перезапись переменной другим значением — **decrement**.

```python
a = [1, 2, 3]   # refcount = 1
b = a           # refcount = 2 (b ссылается на тот же объект)
del a           # refcount = 1
b = None        # refcount = 0 -> объект немедленно уничтожен
```

## Детерминированное освобождение ресурсов — следствие refcounting

Именно благодаря немедленному уничтожению при refcount == 0 в CPython
надёжно работает идиома "закрыть файл при выходе из области видимости"
для объектов с `__del__`, хотя контекстные менеджеры (`with`) всё равно
остаются правильным явным способом управления ресурсами — полагаться на
момент вызова `__del__` в общем случае не рекомендуется (в других
реализациях Python, например PyPy, `__del__` может вызываться заметно
позже).

## Почему refcounting не решает всё: циклические ссылки

Объекты, ссылающиеся друг на друга, никогда не дойдут до refcount == 0
сами по себе, даже если недостижимы извне:

```python
class Node:
    def __init__(self):
        self.other = None

a = Node()
b = Node()
a.other = b   # refcount(b) = 2 (b + a.other)
b.other = a   # refcount(a) = 2 (a + b.other)

del a
del b
# оба объекта всё ещё живы: у каждого refcount == 1 (взаимная ссылка),
# несмотря на то, что снаружи на них больше никто не ссылается
```

Для решения этой проблемы CPython использует **дополнительный**
generational garbage collector (см. следующую тему) — он находит и
уничтожает именно такие недостижимые циклы, которые refcounting
принципиально не может обработать.

## GIL и refcounting — прямая связь

`ob_refcnt` инкрементируется/декрементируется без блокировок на каждую
операцию (это было бы слишком дорого) — GIL как раз и есть механизм,
который делает эти операции безопасными без атомарных инструкций
процессора на каждый `incref`/`decref`. Это одна из причин, почему
free-threaded (no-GIL) сборки CPython (PEP 703) требуют существенной
переработки: без GIL нужен либо atomic refcounting (дороже), либо другая
схема управления памятью.

## sys.getsizeof и накладные расходы объектов

```python
import sys

sys.getsizeof(0)          # ~28 байт — даже маленькое int не "бесплатно"
sys.getsizeof([])         # ~56 байт — пустой список уже занимает память под заголовок
sys.getsizeof([1, 2, 3])  # больше — под сами элементы (точнее, под указатели на них)
```

Список в Python хранит не сами объекты подряд, а **указатели** на
объекты, разбросанные по куче — отсюда дополнительные накладные расходы
по сравнению с массивами примитивных типов в C/Go, но и универсальность
(список может содержать объекты разных типов).

## Кэширование мелких объектов в CPython

Для экономии памяти и времени аллокаций CPython заранее создаёт и
переиспользует некоторые часто встречающиеся неизменяемые объекты:

- **Малые целые числа от `-5` до `256`** существуют в единственном
  экземпляре на весь процесс.
- **Короткие строки**, похожие на идентификаторы (имена переменных,
  функций, атрибутов), автоматически **интернируются** (interning) —
  складываются во внутреннюю таблицу и переиспользуются.

```python
a = 100
b = 100
print(a is b)   # True — оба имени ссылаются на один кэшированный объект

x = 1000
y = 1000
print(x is y)   # в разных фреймах False — вне кэша создаются разные объекты
```

> ⚠️ Это деталь реализации CPython, а не гарантия языка Python. Никогда не
> сравнивайте числа или строки через `is` — используйте только `==`.

## Внутреннее устройство коллекций в CPython

### `list` — динамический массив указателей с over-allocation

Внутри CPython объект `list` состоит из заголовка (счётчик ссылок, текущая
длина `ob_size`, выделенная ёмкость `allocated`) и отдельного непрерывного
массива указателей `PyObject**` в куче.

- Доступ по индексу `lst[i]` — **O(1)**: адрес `i`-го указателя вычисляется
  одной арифметической операцией.
- При `lst.append(x)` CPython выделяет память под массив указателей **с
  запасом** (over-allocation, обычно с ростом примерно на 12.5%). Поэтому
  большинство вызовов `append()` просто записывают указатель в следующую
  свободную ячейку за **O(1)**, и лишь изредка массив перевыделяется и
  копируется (отсюда **амортизированное O(1)**).
- Вставка или удаление в начале/середине (`insert(0, x)`, `pop(0)`) требуют
  сдвинуть все последующие указатели в массиве на одну позицию — **O(n)**.

### `dict` и `set` — хеш-таблицы с открытой адресацией

`dict` и `set` хранят элементы в **хеш-таблице**, ячейки которой называют
**бакетами** (buckets / slots):

1. При вставке или поиске ключа `k` вызывается `hash(k)`.
2. Младшие биты хеша дают индекс бакета в таблице — поэтому поиск не
   требует перебора всех элементов и работает за **O(1) в среднем**.
3. Если у двух разных ключей совпал индекс бакета (**коллизия**), CPython
   использует **открытую адресацию (open addressing)**: проверяет следующие
   ячейки по псевдослучайной формуле, учитывающей старшие биты хеша, пока
   не найдёт свободную ячейку или равный ключ (`==`).
4. Когда таблица заполняется выше порога (**load factor** — около `2/3` от
   ёмкости), CPython выделяет таблицу большего размера и перекладывает
   элементы заново.
5. С Python 3.6+ `dict` использует компактную схему хранения (два массива:
   разреженная таблица индексов и плотный массив записей `(hash, key,
   value)` в порядке вставки). Это уменьшило расход памяти словарей и дало
   гарантированное сохранение порядка ключей (закреплено в стандарте языка
   с Python 3.7).
6. Для защиты от атак через преднамеренные коллизии хешей (Hash DoS) CPython
   сортирует соль хеширования строк и байтов при каждом старте процесса
   (управляется переменной окружения `PYTHONHASHSEED`). Поэтому значения
   `hash("hello")` меняются от запуска к запуску — их нельзя сохранять в
   базу данных или файлы.

## Практическое значение

- Понимание refcounting объясняет, почему `del obj` не всегда освобождает
  память немедленно (если есть другие ссылки) и почему циклические
  структуры (деревья с обратными ссылками на родителя, кэши с обратными
  указателями) нуждаются в `weakref` или explicit разрыве ссылок, если
  нужно освобождение сразу, не дожидаясь generational GC.
- `sys.getrefcount()` полезен при отладке "утечек" объектов, которые
  должны были быть уничтожены, но почему-то живы (обычно из-за забытой
  ссылки в каком-то глобальном кэше/списке слушателей событий).
