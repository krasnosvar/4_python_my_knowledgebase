# Event loop, корутины, async/await, задачи

## Корутина — это не поток и не функция

`async def` создаёт **coroutine function**. Вызов такой функции не выполняет
её тело — он возвращает объект-корутину:

```python
async def greet():
    print("hello")
    return 42

coro = greet()       # тело ещё НЕ выполнилось
print(type(coro))    # <class 'coroutine'>
```

Тело выполнится только тогда, когда корутину кто-то «продвинет» — либо
`await`, либо event loop через `asyncio.run`/`create_task`. Если создать
корутину и забыть про неё — Python выдаст предупреждение
`RuntimeWarning: coroutine 'greet' was never awaited`.

## await — точка возможного переключения

`await` делает две вещи:

1. Передаёт управление вложенному awaitable — объекту, который можно
   ждать через `await`: корутине, `Task` или `Future`. **`Future`** —
   «обещание результата»: объект-заглушка, в который результат (или
   исключение) будет положен позже, когда операция завершится; `Task` —
   частный случай `Future`, который сам выполняет корутину.
2. Если тот приостанавливается (например, ждёт I/O) — отдаёт управление
   **event loop**, который может в это время выполнять другие задачи.

Ключевое: переключение возможно **только** в точках `await` (или `yield` в
низкоуровневых генераторах). Между двумя `await` код одной корутины
выполняется атомарно — никто не может «влезть» посередине. Это упрощает
рассуждения о гонках по сравнению с потоками: shared state, к которому нет
`await` между операциями чтения/записи, не нуждается в блокировке.

## Event loop: как это устроено внутри

Event loop — это цикл, который:

1. Держит очередь готовых к выполнению callback'ов (готовые задачи).
2. На каждой итерации выполняет их по одному, пока каждый либо не завершится,
   либо не дойдёт до `await` и не приостановится.
3. Параллельно следит за I/O через `select`/`epoll`/`kqueue` (в зависимости
   от ОС) — когда сокет готов к чтению/записи, соответствующий callback
   добавляется в очередь готовых.
4. Обрабатывает таймеры (`asyncio.sleep`, таймауты) через отдельную
   упорядоченную по времени очередь.

```
┌─────────────────────────────────────────┐
│               Event Loop                 │
│  ┌───────────┐   ┌──────────────────┐    │
│  │ ready queue│──▶│ выполнить callback│   │
│  └───────────┘   └──────────────────┘    │
│        ▲                    │            │
│        │           await I/O / sleep     │
│        │                    ▼            │
│  ┌─────────────────────────────────┐     │
│  │ selector (epoll/kqueue) + timers │     │
│  └─────────────────────────────────┘     │
└─────────────────────────────────────────┘
```

Отсюда следствие: **если корутина не отдаёт управление** (нет `await`,
идёт долгий CPU-цикл), event loop не может обработать ничего другого —
ни другие задачи, ни таймауты, ни сетевые события. Это и есть причина,
почему блокирующий код в asyncio «замораживает» всё приложение.

## asyncio.run — точка входа

```python
async def main():
    await asyncio.sleep(1)
    print("done")

asyncio.run(main())
```

`asyncio.run`:

- создаёт новый event loop;
- запускает переданную корутину до завершения;
- по завершении закрывает loop и отменяет оставшиеся незавершённые задачи.

Нельзя вызвать `asyncio.run` изнутри уже работающего event loop (например,
внутри другой корутины) — получите `RuntimeError`. Внутри корутины
корутины запускают через `await`, а не через `asyncio.run`.

## Task — обёртка для конкурентного запуска

`await coro` выполняет корутину последовательно — это не конкурентность,
это просто вызов асинхронной функции. Чтобы запустить работу **конкурентно**
(запланировать в event loop прямо сейчас, не дожидаясь текущей точки), нужен
`asyncio.create_task`:

```python
async def worker(n: int) -> int:
    await asyncio.sleep(1)
    return n * 2

async def main():
    task1 = asyncio.create_task(worker(1))  # запланирована немедленно
    task2 = asyncio.create_task(worker(2))  # запланирована немедленно
    # к этому моменту обе корутины уже стартовали и спят внутри sleep(1) —
    # суммарное время ожидания ~1 секунда, а не 2
    r1 = await task1
    r2 = await task2
```

Разница с простым `await worker(1); await worker(2)`: без `create_task`
вторая корутина не начнёт выполняться, пока не завершится первая — это
последовательное, а не конкурентное исполнение.

## Важно: task нужно держать «живым»

```python
async def main():
    asyncio.create_task(worker(1))  # ссылка потеряна сразу после создания
    await asyncio.sleep(2)
```

CPython не гарантирует, что задача без сохранённой ссылки не будет собрана
сборщиком мусора до завершения — event loop хранит только слабую ссылку.
(**Слабая ссылка** — ссылка, которая *не* удерживает объект в памяти: если
других, обычных ссылок не осталось, объект удаляется, несмотря на неё.)
Официальная рекомендация: сохранять ссылку на task (в списке, множестве,
атрибуте объекта), пока она не завершится — это же паттерн для
background-задач (см. `07_concurrency_patterns.md`).

## Отмена (cancellation)

```python
task = asyncio.create_task(worker(1))
task.cancel()          # внутри корутины на следующем await бросится CancelledError
try:
    await task
except asyncio.CancelledError:
    print("отменено")
```

`CancelledError` в 3.8+ наследуется от `BaseException`, а не `Exception` —
случайный `except Exception` не проглотит отмену. Если внутри корутины
нужно освободить ресурсы при отмене — используйте `try/finally`, а не
`try/except CancelledError` с «глотанием» ошибки (иначе отмена не долетит
до вызывающего кода).
