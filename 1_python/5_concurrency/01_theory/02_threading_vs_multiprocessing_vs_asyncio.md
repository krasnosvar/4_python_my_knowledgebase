# threading vs multiprocessing vs asyncio: что выбрать

Три модели решают разные проблемы, и путаница между ними — источник большинства
проблем с производительностью в Python-коде.

Несколько терминов из таблицы ниже:

- **I/O-bound** — задача, которая в основном *ждёт* ввода-вывода (сеть,
  диск, БД); **CPU-bound** — задача, которая в основном *считает*.
- **IPC (inter-process communication)** — обмен данными между процессами.
  Раз у процессов раздельная память, данные приходится пересылать (через
  каналы/очереди ОС), и это заметно дороже, чем общая переменная у потоков.
- **Overhead** — накладные расходы: время и память, которые уходят не на
  саму задачу, а на её обслуживание (создание потока, переключение и т.п.).

## Таблица решений

| Задача | Инструмент | Почему |
|---|---|---|
| Много сетевых запросов / файлового I/O, простая логика | `asyncio` | Одна ОС-нить, тысячи «задач», минимальный overhead на переключение |
| Обёртка над блокирующей библиотекой (без async-версии) в конкурентном контексте | `threading` (или `run_in_executor`) | GIL отпускается на I/O, поток не блокирует остальных |
| Тяжёлые вычисления (парсинг, матанализ, сжатие) | `multiprocessing` | Обходит GIL — реальный параллелизм по ядрам |
| Вычисления + нужен доступ к shared state с низким overhead | C-расширение / numpy / переписать алгоритм | Threading не поможет из-за GIL, multiprocessing дорог на IPC |

## threading

- Настоящие ОС-потоки, `GIL` разделяется между ними.
- Хорош для I/O-bound: сеть, файлы, вызовы блокирующих C-библиотек, которые
  отпускают GIL.
- Overhead на поток разумный (мегабайты на стек), но тысячи потоков — уже
  дорого и неудобно для scheduler ОС.
- Общая память между потоками — удобно, но требует `Lock`/`RLock` для shared
  state (см. модуль `threading` — API почти зеркалит `asyncio` примитивы).

## multiprocessing

- Отдельные процессы, каждый со своим интерпретатором и своим GIL — реальный
  параллелизм по ядрам CPU.
- Дорогая цена: старт процесса, сериализация (`pickle`) аргументов и
  результатов между процессами, нет общей памяти «из коробки»
  (`multiprocessing.shared_memory`, `Value`, `Array` — для частных случаев).
  **Сериализация** — превращение объекта в последовательность байтов,
  которую можно передать другому процессу и там собрать обратно;
  `pickle` — встроенный в Python формат для этого. Не всё «пиклится»:
  например, открытое сетевое соединение или лямбду передать так нельзя.
- Хорош для CPU-bound задач, которые можно разбить на независимые куски
  (map/reduce): обработка изображений, парсинг больших файлов, численные
  расчёты без numpy.
- Способ создания процесса-потомка (start method) зависит от ОС. `fork` —
  ОС делает копию текущего процесса вместе со всей его памятью: старт
  быстрый, потомок сразу «знает» всё, что знал родитель. `spawn` —
  запускается новый чистый интерпретатор, который заново импортирует ваш
  модуль: старт дороже, а всё, что передаётся потомку, должно
  сериализоваться через `pickle`. Третий вариант, `forkserver`, — заранее
  запускается чистый процесс-«сервер», и новые потомки делаются копией
  уже его, а не вашего процесса. На Linux по умолчанию `fork` до Python
  3.13 включительно и `forkserver` начиная с 3.14; на macOS/Windows —
  `spawn`. Это частый источник различий в поведении между ОС и версиями.

```python
import multiprocessing as mp
mp.get_start_method()  # Linux: 'fork' (до 3.13) / 'forkserver' (3.14+); macOS/Windows: 'spawn'
```

## asyncio

- Один поток, **кооперативная** многозадачность: код сам отдаёт управление в
  точках `await`. Нет переключения контекста ОС, минимальный overhead —
  тысячи и десятки тысяч конкурентных задач реальны.
- Задачами управляет **event loop** (цикл событий) — диспетчер, который
  держит список задач и по очереди запускает ту, что готова продолжать,
  пока остальные ждут I/O. Синтаксис `async def`/`await` и устройство
  event loop подробно разбираются в следующем файле,
  [03_asyncio_event_loop_coroutines.md](./03_asyncio_event_loop_coroutines.md).
- Не даёт параллелизма по CPU (всё ещё один поток, один GIL) — только
  конкурентность на I/O.
- Требует, чтобы весь стек вызовов был async-совместимым: одна
  синхронная блокирующая функция (`time.sleep`, `requests.get`,
  «тяжёлый» CPU-цикл) без `await` останавливает **весь** event loop, а не
  только одну задачу.

## Практическое правило

1. Спросите: «я жду ответа от внешнего мира (сеть/диск/БД) или я считаю?»
2. Жду → I/O-bound → `asyncio` (если пишу код с нуля и есть async-библиотеки)
   или `threading` (если библиотека синхронная и не имеет async-обёртки).
3. Считаю → CPU-bound → `multiprocessing` или `concurrent.futures.ProcessPoolExecutor`,
   а ещё лучше — векторизация через numpy/переписать в C-расширении.
4. Смешанная нагрузка (немного I/O, немного CPU в одном сервисе) —
   `asyncio` для I/O-части + `loop.run_in_executor(ProcessPoolExecutor, ...)`
   для CPU-части, чтобы не блокировать event loop.

## Частая ошибка: asyncio не ускоряет CPU-bound код

> Синтаксис `async def`/`await`/`asyncio.gather` разбирается в следующем
> файле (`03`). Здесь достаточно понять идею: четыре «асинхронные» задачи,
> которые только считают, всё равно выполняются строго одна за другой. Если
> пример пока непонятен — вернитесь к нему после `03`.

```python
import asyncio, time

async def cpu_bound():
    return sum(i * i for i in range(10_000_000))

async def main():
    start = time.perf_counter()
    await asyncio.gather(*(cpu_bound() for _ in range(4)))
    print(time.perf_counter() - start)  # столько же, сколько 4 последовательных вызова

asyncio.run(main())
```

Корутина без `await` внутри выполняется от начала до конца без единой точки
переключения — event loop не может «вклиниться» в середину `sum(...)`.
Для такого кода нужен `run_in_executor` с `ProcessPoolExecutor` (см. тему
про executors ниже).
