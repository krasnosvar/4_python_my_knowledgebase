# GIL и модель исполнения CPython

## Сначала простыми словами: процесс, поток, конкурентность

- **Процесс** — запущенная программа. У каждого процесса своя отдельная
  память: два процесса не видят переменные друг друга. Команда
  `python script.py` создаёт один процесс.
- **Поток (thread)** — «линия выполнения» внутри процесса. В одном
  процессе может быть несколько потоков, и все они работают с **общей**
  памятью процесса (одними и теми же переменными и объектами).
- **Конкурентность** — программа ведёт несколько задач одновременно «по
  очереди»: пока одна задача ждёт (ответ сервера, чтение файла), другая
  продолжает работу. **Параллелизм** — задачи буквально выполняются в одно
  и то же мгновение на разных ядрах процессора. Конкурентность возможна и
  на одном ядре, параллелизм — нет.

Зачем это нужно: большая часть времени бэкенд-сервиса уходит на
**ожидание** — ответа БД, другого API, диска. Если обрабатывать запросы
строго по одному, процессор простаивает, пока идёт ожидание. Конкурентность
позволяет в это время заниматься другими запросами.

## Что такое GIL

Пара терминов, которые понадобятся ниже:

- **Байткод** — Python не исполняет ваш текст напрямую: сначала он
  переводит его в простые низкоуровневые инструкции (байткод), и уже их
  по одной выполняет интерпретатор (подробно — в
  `10_under_the_hood/01_theory/03_bytecode_and_dis.md`).
- **Мьютекс (lock, блокировка)** — «замок», который в каждый момент может
  держать только один поток; остальные ждут, пока он освободится.

**GIL (Global Interpreter Lock)** — один глобальный мьютекс на весь
интерпретатор CPython: байткод Python в любой момент выполняет только тот
поток, который держит GIL. Поэтому даже на многоядерной машине потоки
одного процесса выполняют Python-код по очереди, а не параллельно.

Почему так сделано. CPython следит, сколько переменных ссылается на каждый
объект (**счётчик ссылок, refcount**): когда счётчик падает до нуля, объект
больше никому не нужен и его память сразу освобождается (подробно — в
`10_under_the_hood/01_theory/01_memory_model_refcounting.md`). Если два
потока одновременно меняют этот счётчик без защиты, он может «сбиться» —
и объект удалится, пока им ещё пользуются. GIL — самый дешёвый способ
защитить все счётчики разом, вместо того чтобы ставить отдельную защиту на
каждое увеличение/уменьшение счётчика (`incref`/`decref`).

## Что это значит на практике

- **CPU-bound код** (вычисления: циклы, парсинг, математика на чистом Python)
  — `threading` не ускоряет его. Потоки будут по очереди отдавать GIL друг
  другу, суммарное время работы не уменьшится, а из-за переключений контекста
  может даже увеличиться.
- **I/O-bound код** (сеть, диск, ожидание ответа от БД) — GIL освобождается
  на время системного вызова (`socket.recv`, `file.read`, `time.sleep` и т.д.).
  Пока один поток ждёт I/O, другой может выполнять Python-байткод. Поэтому
  `threading` отлично ускоряет I/O-bound нагрузку.
- Расширения на C (numpy, часть stdlib на C) могут явно отпускать GIL на
  время тяжёлых вычислений (`Py_BEGIN_ALLOW_THREADS`) — поэтому `numpy` в
  потоках может параллелиться, а чистый Python-цикл — нет.

## Когда GIL переключается

Интерпретатор переключает GIL между потоками:

- каждые ~5 мс (настраивается через `sys.setswitchinterval`) по таймеру —
  «вытесняющее» переключение между CPU-bound потоками;
- немедленно при блокирующем системном вызове (I/O), пока поток ждёт ответ от ОС.

```python
import sys
print(sys.getswitchinterval())  # 0.005 по умолчанию
```

## Типичная ошибка

Использовать `threading.Thread` для ускорения вычислений и удивляться, что
несколько потоков работают не быстрее одного, а иногда и медленнее:

```python
import threading, time

def cpu_bound(n: int) -> int:
    return sum(i * i for i in range(n))

start = time.perf_counter()
threads = [threading.Thread(target=cpu_bound, args=(10_000_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(time.perf_counter() - start)  # примерно как один поток, а не в 4 раза быстрее
```

Правильный инструмент здесь — `multiprocessing` (отдельные процессы, у
каждого свой интерпретатор и свой GIL) или переписать горячий участок на C/Rust
(numpy, Cython, PyO3).

## GIL не защищает от гонок на уровне ваших операций

GIL гарантирует атомарность отдельных байткод-инструкций, но **не**
атомарность составных операций Python-уровня:

```python
counter = 0

def inc():
    global counter
    counter += 1  # это load + add + store — три байткода, между ними GIL может переключиться
```

(`global counter` говорит функции, что `counter` — переменная модуля, а не
новая локальная переменная функции; без него присваивание внутри функции
создало бы локальную переменную.)

`counter += 1` в многопоточном коде всё равно требует `threading.Lock`,
потому что состоит из нескольких шагов байткода, между которыми возможно
переключение потока.

## Будущее: subinterpreters и free-threaded CPython

- PEP 684 (3.12) — per-interpreter GIL: несколько суб-интерпретаторов в
  одном процессе, у каждого свой GIL (модуль `interpreters` для этого
  экспериментален).
- PEP 703 (3.13, экспериментальная сборка `--disable-gil` / free-threaded
  build) — CPython без GIL вообще. Пока это опциональная сборка, не
  дефолтная, и требует, чтобы C-расширения были совместимы (thread-safe).

На момент изучения этого раздела для 99% реального кода актуальна модель
«есть GIL» — из неё и исходят все решения ниже: threading для I/O,
multiprocessing или C-расширения для CPU, asyncio как альтернатива
threading для I/O с гораздо большим числом одновременных задач.
