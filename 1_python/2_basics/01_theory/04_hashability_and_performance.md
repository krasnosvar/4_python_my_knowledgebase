# Хешируемость и её влияние на скорость

Главный файл раздела. Отвечает на два практических вопроса: почему `list`
нельзя положить в `set` или сделать ключом словаря, и почему поиск в
`set`/`dict` быстрый, а в `list` — медленный.

## Что такое хеш

Встроенная функция `hash(x)` превращает значение в целое число — его
«отпечаток». Одинаковые значения всегда дают одинаковый отпечаток.

```python
hash("hello")     # какое-то целое число
hash((1, 2, 3))   # кортеж тоже можно
hash([1, 2, 3])   # ошибка TypeError: unhashable type: 'list'
```

`set` и `dict` используют отпечаток как адрес: по `hash(x)` сразу
вычисляют, в какой ячейке своей таблицы искать `x`, вместо того чтобы
перебирать все элементы. Значение, у которого можно взять хеш, называется
**хешируемым**.

## Почему список нехешируемый, а кортеж — хешируемый

Хеш вычисляется по содержимому. Представь, что у списка был бы хеш:

1. Кладём список `[1, 2]` в множество — оно запоминает его в ячейке,
   вычисленной по хешу `[1, 2]`.
2. Делаем `lst.append(3)` — содержимое стало `[1, 2, 3]`, хеш изменился.
3. Ищем список в множестве — Python вычисляет новый хеш, смотрит в другую
   ячейку и **не находит** объект, хотя тот там лежит.

Поэтому изменяемые `list`, `dict`, `set` нехешируемы. А неизменяемые
`tuple`, `frozenset`, `str`, `int` — хешируемы: их хеш никогда не
«протухнет» (у кортежа — при условии, что всё внутри тоже неизменяемо).

Практическое правило: **ключ словаря и элемент множества должны быть
неизменяемыми**.

```python
cache = {}
cache[("GET", "/users", 1)] = "cached response"   # кортеж — ОК
# cache[["GET", "/users", 1]] = "..."             # TypeError: список нельзя
```

## Почему `set`/`dict` ищут быстрее `list`

- `list`: `x in lst` — перебор по одному, **O(n)**: в худшем случае
  придётся сравнить `x` с каждым элементом.
- `set` / `dict`: `x in s` — вычисляется `hash(x)`, и сразу проверяется
  нужная ячейка, **O(1) в среднем**, независимо от размера.

```python
big_list = list(range(1_000_000))   # список чисел от 0 до 999999
big_set = set(big_list)             # те же числа во множестве

999_999 in big_list   # O(n) — переберёт почти весь список
999_999 in big_set    # O(1) в среднем — сразу в нужную ячейку
```

`list(...)` и `set(...)` здесь создают коллекцию из другой
последовательности; `1_000_000` — то же, что `1000000`, подчёркивания
только для читаемости.

На реальных данных разница заметна уже на тысячах элементов и критична на
миллионах: время поиска в списке растёт вместе с размером, а в множестве
остаётся почти постоянным.

## Итог

| Тип | Изменяемый | Хешируемый | Поиск `in` |
|---|---|---|---|
| `list` | да | нет | O(n) |
| `tuple` | нет | да (если элементы хешируемы) | O(n) — внутри тоже перебор! |
| `set` / `frozenset` | да / нет | нет / да | O(1) в среднем |
| `dict` (по ключам) | да | — | O(1) в среднем |

Обрати внимание: кортеж хешируем, но поиск `x in some_tuple` внутри него —
обычный перебор, O(n). Хешируемость ускоряет только поиск **самого
кортежа** как ключа/элемента в `dict`/`set`.

<details>
<summary>Для любопытных: правило «равные → равный хеш» и свои классы</summary>

Главное правило: **если `a == b`, то обязательно `hash(a) == hash(b)`**.
Обратное не обязательно: у разных объектов хеши иногда случайно совпадают
(это называется **коллизия**).

Когда ты пишешь свой класс (см. `4_oop`), за `==` отвечает метод `__eq__`,
а за `hash()` — метод `__hash__`. Если определить `__eq__`, но не
`__hash__`, Python делает объекты класса нехешируемыми: он не может сам
угадать хеш, согласованный с твоей логикой равенства. Упражнение
`03_exercises/02_hashable_key.py` — ровно про это.

</details>

<details>
<summary>Для любопытных: что происходит внутри хеш-таблицы</summary>

- Ячейки таблицы называют **бакетами** (bucket).
- Хеши строк меняются от запуска к запуску (защита от атак; управляется
  переменной окружения `PYTHONHASHSEED`) — не сохраняйте `hash()` строк
  между запусками программы.
- Когда таблица заполняется выше определённой доли (load factor), Python
  увеличивает её и раскладывает элементы заново. Это бывает редко,
  поэтому вставка тоже в среднем O(1).
- При коллизии CPython пробует другие ячейки по определённому правилу
  (open addressing). Это чуть замедляет конкретную операцию, но не меняет
  O(1) в среднем.

</details>
