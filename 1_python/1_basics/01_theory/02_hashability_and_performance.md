# Хешируемость и её влияние на производительность

Это ключевая тема раздела: почему `list` нельзя положить в `set` или использовать как ключ словаря, и почему `dict`/`set` в среднем работают за O(1), а список — за O(n).

## Протокол `hash()`

Любой объект, для которого определён `__hash__`, можно передать во встроенную функцию `hash()`. Она возвращает целое число — «отпечаток» объекта, который `dict`/`set` используют, чтобы сразу вычислить, в каком «бакете» (bucket) хеш-таблицы должен лежать объект, вместо того чтобы перебирать все элементы.

```python
hash("hello")     # некоторое целое число (зависит от PYTHONHASHSEED)
hash((1, 2, 3))   # кортежи хешируемы, если хешируемы все их элементы
hash([1, 2, 3])   # TypeError: unhashable type: 'list'
```

## Контракт `__hash__` / `__eq__`

Основное правило: **если `a == b`, то обязательно `hash(a) == hash(b)`**. Обратное необязательно (у разных объектов могут случайно совпадать хеши — коллизия, см. ниже). Если контракт нарушить (например, переопределить `__eq__`, но не `__hash__`), объект будет вести себя непредсказуемо в словарях и множествах — его можно «потерять» в хеш-таблице, даже если он там формально есть.

Именно поэтому в CPython, как только класс определяет `__eq__`, он **автоматически становится нехешируемым** (`__hash__` устанавливается в `None`), пока вы явно не определите свой `__hash__`. Интерпретатор не может сам вывести корректный хеш из вашей логики равенства — это ваша ответственность.

## Почему список/множество/словарь нехешируемы, а кортеж/frozenset/строка — хешируемы

* `list`, `dict`, `set` — **изменяемые**. Если бы у них был хеш, он был бы рассчитан по текущему содержимому. После `list.append(...)` хеш изменился бы, но объект остался бы «на месте» в том бакете хеш-таблицы, где был размещён по старому хешу — хеш-таблица оказалась бы сломана (объект физически не там, где его будут искать).
* `tuple`, `frozenset`, `str`, `int`, `bytes` — **неизменяемые** (при условии, что все их элементы тоже неизменяемы для составных типов). Хеш можно посчитать один раз и быть уверенным, что он не «протухнет».

Отсюда практическое правило: **если объект должен быть ключом словаря или элементом множества, он обязан быть хешируемым, а значит — неизменяемым по семантике** (или как минимум не изменяться, пока участвует в хеш-таблице).

```python
cache = {}
cache[("GET", "/users", 1)] = "cached response"   # кортеж — ОК, хешируем
# cache[["GET", "/users", 1]] = "..."             # TypeError: unhashable type: 'list'
```

## Почему `dict`/`set` быстрее `list` для проверки принадлежности

* `list`: `x in lst` — линейный поиск, **O(n)**: в худшем случае нужно сравнить `x` с каждым элементом.
* `set` / `dict`: `x in s` — вычисляется `hash(x)`, по хешу сразу находится нужный бакет, **O(1) в среднем** (амортизированно), независимо от размера коллекции.

```python
# Концептуально, без реального замера:
big_list = list(range(1_000_000))
big_set = set(big_list)

999_999 in big_list   # O(n) — переберёт почти весь список
999_999 in big_set    # O(1) в среднем — сразу попадёт в нужный бакет по хешу
```

На реальных данных разница становится заметна уже на тысячах элементов и критична на миллионах — с ростом `n` время поиска в списке растёт линейно, а в множестве остаётся практически постоянным.

## Амортизированный рост и коллизии — коротко

* Хеш-таблица CPython при заполнении выше определённого порога (load factor) увеличивает внутренний массив и перераспределяет элементы — это происходит нечасто и не на каждой вставке, поэтому вставка тоже в среднем O(1) (амортизированно).
* **Коллизия** — ситуация, когда у двух разных объектов совпал хеш (или бакет). CPython разрешает коллизии через open addressing (пробирование других слотов) — это чуть замедляет операции в конкретном бакете, но не меняет асимптотику в среднем случае.

## Итог

| Тип | Изменяемый | Хешируемый | Поиск `in` |
|---|---|---|---|
| `list` | да | нет | O(n) |
| `tuple` | нет | да (если элементы хешируемы) | O(n) — сам по себе тоже линейная структура! |
| `set` / `frozenset` | да / нет | нет / да | O(1) в среднем |
| `dict` (по ключам) | да | — | O(1) в среднем |

Обратите внимание: сам `tuple`, несмотря на хешируемость, при поиске `in` внутри него — обычная линейная структура, O(n). Хешируемость даёт выигрыш в скорости, только когда объект используется как **ключ/элемент** `dict`/`set`, а не при переборе последовательности.
