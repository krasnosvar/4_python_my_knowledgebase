# Ленивые вычисления и память

## Список — жадный, генератор — ленивый

Список материализует **все** элементы сразу и хранит их в памяти. Генератор хранит только состояние (текущую позицию + локальные переменные) и вычисляет следующее значение только тогда, когда его действительно запросили через `next()`.

Это можно измерить напрямую через `sys.getsizeof`:

```python
import sys

N = 1_000_000

lst = [x for x in range(N)]
gen = (x for x in range(N))

print(sys.getsizeof(lst))   # порядка 8 000 000+ байт — растёт линейно с N
print(sys.getsizeof(gen))   # порядка 200 байт — не зависит от N
```

Размер генератора не меняется, сколько бы элементов он ни должен был отдать в будущем — он не хранит будущие значения, только то, как их получить. Размер списка растёт линейно с числом элементов (плюс служебные накладные расходы на объект `int` для каждого элемента, если это не примитивный C-массив).

## Когда генератор — правильный выбор

* Обработка данных, которые **не помещаются в память целиком** (построчное чтение огромного лог-файла, потоковые данные из сети).
* **Пайплайны** обработки: `read -> filter -> transform -> write`, где данные проходят по одной «штуке» через всю цепочку, не создавая промежуточных списков на каждом этапе.
* **Бесконечные последовательности** (счётчики, генераторы событий) — список для них в принципе невозможен.
* Ситуации, где нужен только **один проход** и не важна повторная итерация.

## Когда список — правильный выбор, а не генератор

* Нужна **длина** (`len()`) — у генератора её нет и не может быть без полного прохода.
* Нужен **случайный доступ по индексу** (`data[5]`) — генератор поддерживает только последовательное продвижение вперёд.
* Данные нужно обойти **несколько раз** — генератор после первого прохода исчерпан, list можно обходить сколько угодно раз.
* Данные **и так уже целиком в памяти** и небольшие — оборачивать их в генератор не даст выигрыша, только косвенные расходы на вызовы `next()`.

## Итог

Генератор экономит память ценой того, что данные становятся «одноразовыми» и последовательными. Это типичный компромисс: пространство (память) против гибкости доступа (индексация, повторный проход, `len()`).
