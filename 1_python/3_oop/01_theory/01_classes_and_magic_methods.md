# Классы и магические методы

Магические методы (dunder-методы, от «double underscore») — это то, как Python подключает встроенное поведение (`+`, `len()`, `[]`, `print()`, сравнение) к пользовательским классам. Они не «синтаксический сахар для красоты» — интерпретатор вызывает их напрямую в конкретных ситуациях.

## `__init__` vs `__new__`

* `__new__(cls, ...)` — создаёт объект (аллоцирует память) и возвращает его. Вызывается первым.
* `__init__(self, ...)` — инициализирует уже созданный объект. Ничего не возвращает (точнее, обязан вернуть `None`).

На практике `__new__` переопределяют редко: неизменяемые типы (наследники `int`, `str`, `tuple`), синглтоны, метаклассы. В прикладном коде почти всегда достаточно `__init__`.

```python
class Point:
    def __init__(self, x: float, y: float) -> None:
        self.x = x
        self.y = y
```

## `__repr__` против `__str__`

* `__repr__` — однозначное, «для разработчика» представление. Идеал: строка, по которой можно воссоздать объект (`eval(repr(obj)) == obj`), либо хотя бы `<Point x=1 y=2>`.
* `__str__` — читаемое, «для пользователя» представление (например, для `print()`).

Если `__str__` не определён, Python **падает обратно на `__repr__`**. Поэтому `__repr__` стоит определять почти всегда, а `__str__` — только когда пользовательское представление действительно должно отличаться от отладочного.

```python
class Point:
    def __repr__(self) -> str:
        return f"Point(x={self.x!r}, y={self.y!r})"
```

`repr()` вызывается неявно везде, где Python показывает объект «сам по себе»: в интерактивной консоли, внутри `list`/`dict` при их печати, в трейсбеках.

## `__eq__` и хешируемость

По умолчанию класс сравнивается по идентичности (`is`), а хешируется по `id()`. Как только вы определяете `__eq__`, Python **автоматически убирает унаследованный `__hash__`**, выставляя его в `None` — объект становится нехешируемым (нельзя использовать как ключ словаря или элемент множества).

```python
class Point:
    def __eq__(self, other: object) -> bool:
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

p = Point(1, 2)
# hash(p)  # TypeError: unhashable type: 'Point'
```

Причина этого правила — инвариант хеш-таблиц: если `a == b`, то обязано быть `hash(a) == hash(b)`. Python не может гарантировать это автоматически для вашего кастомного `__eq__`, поэтому просто отключает хеш, пока вы явно не определите `__hash__` сами (или не используете `@dataclass(frozen=True)`, который сделает это за вас — см. [04_dataclasses.md](./04_dataclasses.md)).

Правило: если объект логически неизменяем и вы хотите класть его в `set`/`dict`, определяйте `__hash__` согласованно с `__eq__` (обычно как `hash()` от того же кортежа полей, что участвует в сравнении).

## `__len__`, `__getitem__`, `__setitem__`

Эти методы превращают объект в «контейнероподобный»:

* `__len__` — включает `len(obj)` и делает объект «truthy/falsy»-совместимым (пустой контейнер — `False` в булевом контексте, если `__bool__` не определён отдельно).
* `__getitem__(self, key)` — включает `obj[key]`, а также **автоматически даёт итерируемость** через последовательный перебор `obj[0], obj[1], ...` до `IndexError`, если `__iter__` не определён явно.
* `__setitem__(self, key, value)` — включает `obj[key] = value`.

```python
class Row:
    def __init__(self, values: list[int]) -> None:
        self._values = values

    def __len__(self) -> int:
        return len(self._values)

    def __getitem__(self, index: int) -> int:
        return self._values[index]
```

Это тот механизм, благодаря которому `for x in row` работает даже без явного итератора — подробнее в разделе [4_iterators_generators](../../4_iterators_generators/README.md).

## Перегрузка операторов

`__add__`, `__sub__`, `__mul__`, `__lt__`, `__contains__` и другие dunder-методы позволяют переопределить поведение операторов для собственных типов:

```python
class Vector:
    def __init__(self, x: float, y: float) -> None:
        self.x, self.y = x, y

    def __add__(self, other: "Vector") -> "Vector":
        return Vector(self.x + other.x, self.y + other.y)
```

Общее правило: перегружайте оператор только если он сохраняет интуитивную семантику из математики/встроенных типов. `__add__`, который втихую мутирует один из операндов или выполняет тяжёлый побочный эффект, — источник трудноуловимых багов.
