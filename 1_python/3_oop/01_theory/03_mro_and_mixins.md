# Множественное наследование, MRO и миксины

## Множественное наследование

Python, в отличие от Go и Java, разрешает классу наследоваться сразу от нескольких:

```python
class Flyer:
    def move(self) -> str:
        return "летит"

class Swimmer:
    def move(self) -> str:
        return "плывёт"

class Duck(Flyer, Swimmer):
    pass
```

Какой `move()` выберет `Duck`? Ответ даёт **порядок разрешения методов (MRO)**.

## C3-линеаризация

Python вычисляет MRO по алгоритму C3-линеаризации (используется также в Perl 6, Dylan). Не вдаваясь в формальный вывод, ключевая идея:

* Ребёнок всегда стоит в списке раньше своих родителей.
* Порядок родителей в объявлении класса (`class Duck(Flyer, Swimmer)`) сохраняется — `Flyer` будет проверен раньше `Swimmer`.
* Общий предок (обычно `object`) всегда оказывается в конце, после всех классов, которые от него зависят.

Посмотреть фактический порядок можно всегда:

```python
print(Duck.__mro__)
# (<class 'Duck'>, <class 'Flyer'>, <class 'Swimmer'>, <class 'object'>)
```

`Duck().move()` вернёт `"летит"`, потому что `Flyer` идёт первым в списке родителей и, соответственно, раньше в MRO.

## Ромбовидное наследование (diamond problem)

```python
class Base:
    def greet(self) -> str:
        return "Base"

class Left(Base):
    def greet(self) -> str:
        return "Left -> " + super().greet()

class Right(Base):
    def greet(self) -> str:
        return "Right -> " + super().greet()

class Child(Left, Right):
    pass
```

MRO для `Child`: `Child -> Left -> Right -> Base -> object`. Обратите внимание: `Base` встречается **один раз**, хотя формально в дерево наследования входит дважды (через `Left` и через `Right`). C3-линеаризация гарантирует, что каждый класс появляется в MRO ровно один раз, и это единственный порядок, непротиворечиво согласующий все ограничения (ребёнок раньше родителя, порядок объявления родителей сохраняется).

`Child().greet()` вернёт `"Left -> Right -> Base"` — потому что `super()` внутри `Left.greet` находит по MRO **не `Base`, а `Right`** (следующий класс после `Left`). Это именно то «кооперативное» поведение `super()`, о котором говорилось в [02_inheritance_and_super.md](./02_inheritance_and_super.md): каждый класс вызывает `super()`, доверяя, что MRO подставит следующего по цепочке, а не жёстко прописанного «родителя».

Если бы Python использовал наивный порядок «глубина, потом слева направо» (как в старом C++), `Base.greet()` вызвался бы дважды и цепочка `super()` оборвалась бы после первого попадания в `Base`.

## Миксины

Миксин — небольшой класс, добавляющий **одну конкретную возможность**, и не предназначенный для самостоятельного использования (обычно не создаётся напрямую, не имеет собственного `__init__` с обязательными аргументами). Конвенция именования — суффикс `Mixin`.

```python
class JSONSerializableMixin:
    def to_json(self) -> str:
        import json
        return json.dumps(self.__dict__)

class User(JSONSerializableMixin):
    def __init__(self, name: str) -> None:
        self.name = name
```

Отличие миксина от «обычного» родителя в многонаследовании — по замыслу, а не по синтаксису: миксин не участвует в основной иерархии `is-a`, а лишь примешивает поведение. Порядок в списке базовых классов имеет значение: миксины обычно ставят **перед** основным базовым классом (`class User(JSONSerializableMixin, Base)`), чтобы их методы имели приоритет в MRO при конфликте имён.

> Частый вопрос на собеседовании: чем миксин отличается от абстрактного базового класса? ABC описывает контракт «что класс обязан уметь» (см. [06_duck_typing_and_protocols.md](./06_duck_typing_and_protocols.md)), а миксин — это готовая, конкретная реализация одной возможности, которую можно «примешать» к разным несвязанным иерархиям.
