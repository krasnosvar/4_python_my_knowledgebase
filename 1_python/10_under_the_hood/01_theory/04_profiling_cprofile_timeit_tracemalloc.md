# Профилирование: cProfile, timeit, tracemalloc

## cProfile — профилирование по всей программе/функции

Показывает, сколько раз вызывалась каждая функция и сколько суммарного/
собственного времени заняла — находит "где горячо" на уровне функций.

```python
import cProfile
import pstats

def slow_function():
    total = 0
    for i in range(1_000_000):
        total += i ** 2
    return total

cProfile.run("slow_function()", "profile_output.prof")

stats = pstats.Stats("profile_output.prof")
stats.sort_stats("cumulative").print_stats(10)  # топ-10 по суммарному времени
```

Или без сохранения в файл — прямо в консоль:

```bash
python -m cProfile -s cumulative myscript.py
```

Ключевые колонки вывода:

- `ncalls` — сколько раз вызвана функция.
- `tottime` — время **внутри самой функции**, без учёта вложенных вызовов.
- `cumtime` — суммарное время, включая вложенные вызовы.

**Правило чтения**: сортировка по `tottime` находит функции, которые сами
по себе медленные; сортировка по `cumtime` находит "точки входа", где
накапливается больше всего суммарного времени (может быть из-за
множества вызовов дешёвой функции).

## timeit — точный замер маленьких фрагментов кода

`cProfile` даёт overhead на каждый вызов функции — для микробенчмарков
одной строчки/выражения точнее `timeit`, который сам подбирает число
повторений и минимизирует шум:

```python
import timeit

t1 = timeit.timeit("'-'.join(str(n) for n in range(100))", number=10_000)
t2 = timeit.timeit("'-'.join([str(n) for n in range(100)])", number=10_000)
print(f"генератор: {t1:.4f}s, list comprehension: {t2:.4f}s")
```

Из командной строки:

```bash
python -m timeit -s "data = list(range(1000))" "sum(data)"
```

**Важно**: `timeit` по умолчанию отключает автоматический GC на время
замера (`gc.disable()` внутри) — это специально, чтобы случайный запуск
цикла сборки мусора не исказил единичный замер. Для реалистичной оценки
поведения в проде (где GC работает) это стоит учитывать.

## tracemalloc — профилирование памяти

Отслеживает, где именно в коде были выделены объекты, всё ещё занимающие
память — находит утечки и неожиданно "тяжёлые" структуры данных.

```python
import tracemalloc

tracemalloc.start()

data = [str(i) * 100 for i in range(100_000)]  # намеренно тратим память

snapshot = tracemalloc.take_snapshot()
top_stats = snapshot.statistics("lineno")

for stat in top_stats[:5]:
    print(stat)
```

Вывод покажет конкретные файл:строка, где были выделены самые "тяжёлые"
по суммарному размеру объекты.

### Сравнение двух снапшотов — поиск утечки

```python
import tracemalloc

tracemalloc.start()
snapshot1 = tracemalloc.take_snapshot()

# ... код, который потенциально "утекает" ...
leaky_cache = [str(i) for i in range(50_000)]

snapshot2 = tracemalloc.take_snapshot()
diff = snapshot2.compare_to(snapshot1, "lineno")

for stat in diff[:5]:
    print(stat)   # строки с наибольшим ПРИРОСТОМ памяти между снапшотами
```

Этот паттерн — стандартный способ найти утечку в долгоживущем процессе:
снять снапшот, выполнить подозрительный участок много раз, снять снапшот
снова, сравнить.

## Какой инструмент когда

| Вопрос | Инструмент |
|---|---|
| Какая функция во всей программе съедает больше всего времени | `cProfile` |
| Что быстрее — вариант A или вариант B одной строчки кода | `timeit` |
| Где выделяется память, которая не освобождается | `tracemalloc` |
| Точное время одного интервала в работающем коде (не бенчмарк) | `time.perf_counter()` (см. `7_standard_library`) |

## Практический процесс

1. Заметили, что что-то медленно/жрёт память — не гадать, а сначала
   профилировать (`cProfile`/`tracemalloc`), чтобы найти реальное узкое
   место, а не оптимизировать код "на глаз".
2. Найдя горячую функцию — сравнить альтернативные реализации через
   `timeit` на реалистичных данных.
3. Оптимизировать именно то место, которое показал профайлер — часто
   узкое место оказывается не там, где интуитивно ожидалось.
