# Байткод и модуль dis

## Python компилируется, а не интерпретируется построчно "как есть"

CPython компилирует исходный код в промежуточный **байткод** (набор
инструкций для стековой виртуальной машины CPython), который затем
исполняется циклом интерпретатора (`ceval.c`). Это не JIT-компиляция в
машинный код (в отличие от PyPy) — байткод остаётся байткодом, но
компиляция в него избавляет от повторного парсинга исходного текста при
каждом исполнении.

```python
def add(a, b):
    return a + b

print(add.__code__.co_code)      # байты байткода — нечитаемо напрямую
```

## dis — человекочитаемое представление байткода

```python
import dis

def add(a, b):
    return a + b

dis.dis(add)
```

Вывод (формат может слегка отличаться между версиями Python):

```
  2           0 RESUME                   0
              2 LOAD_FAST                0 (a)
              4 LOAD_FAST                1 (b)
              6 BINARY_OP                0 (+)
             10 RETURN_VALUE
```

- `LOAD_FAST` — загрузить локальную переменную на стек виртуальной машины.
- `BINARY_OP` — снять два верхних значения со стека, применить операцию,
  положить результат обратно.
- `RETURN_VALUE` — вернуть значение с вершины стека.

CPython — стековая машина: почти все инструкции берут операнды с вершины
стека и кладут результат туда же, а не работают с именованными регистрами.

## Практическое применение: сравнение эффективности эквивалентного кода

```python
import dis

def concat_plus(a, b, c):
    return a + b + c

def concat_join(parts):
    return "".join(parts)

dis.dis(concat_plus)
```

`dis` показывает, сколько инструкций и промежуточных объектов
подразумевает та или иная формулировка — полезно, чтобы увидеть, что,
например, `x in (1, 2, 3)` компилируется в сравнение с константным
кортежем эффективнее, чем `x == 1 or x == 2 or x == 3` в отдельных
`BINARY_OP`/`JUMP` инструкциях для каждого сравнения.

## Различия между версиями Python

Формат и набор инструкций байткода **не стабилен** между минорными
версиями Python — `.pyc`-файлы одной версии несовместимы с другой
(отсюда номер версии в имени кэш-файла, например
`__pycache__/module.cpython-312.pyc`). CPython 3.11+ существенно
переработал байткод (specializing adaptive interpreter, PEP 659) —
одни и те же инструкции "специализируются" во время выполнения под
конкретные типы операндов, ускоряя горячий код без изменения исходного
текста программы.

```python
import dis
print(dis.opmap)  # словарь {имя_инструкции: числовой код} для текущей версии Python
```

## co_* атрибуты объекта кода

```python
def example(x, y=10):
    z = x + y
    return z

code = example.__code__
print(code.co_varnames)   # ('x', 'y', 'z') — локальные переменные
print(code.co_consts)     # константы, использованные в теле функции
print(code.co_argcount)   # число позиционных аргументов
```

Полезно для инструментов статического анализа, отладчиков и профилировщиков
— именно через `co_*` атрибуты и байткод строятся многие инструменты
трассировки выполнения.

## Когда реально нужен dis

- Понять, почему одна формулировка кода заметно быстрее другой
  (профилирование указало на горячую строку — `dis` показывает, что там
  происходит на уровне интерпретатора).
- Отладка тонких эффектов (например, разница между `is` и `==` на разных
  типах, поведение constant folding компилятора).
- Не для повседневного кода — `dis` инструмент диагностики, а не то, на
  что стоит ориентироваться при обычной разработке (микрооптимизация на
  уровне байткода почти никогда не окупается по сравнению с алгоритмическими
  улучшениями или переходом на C-расширения/numpy для горячих участков).
