# Конфликты, commit hygiene и отмена изменений

## Конфликты слияния

Конфликт возникает, когда Git не может автоматически объединить изменения —
обычно потому, что обе ветки поменяли **одни и те же строки** одного файла.
Git останавливает merge/rebase и размечает конфликтующие места прямо в файле:

```
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature/config-update
```

- Всё между `<<<<<<< HEAD` и `=======` — версия текущей ветки (куда мержим).
- Всё между `=======` и `>>>>>>> <branch>` — версия входящей ветки.

### Как решать

1. `git status` — покажет список файлов с конфликтами (`both modified`).
2. Открыть файл, вручную выбрать нужный код, **удалить маркеры**
   `<<<<<<<`, `=======`, `>>>>>>>` целиком.
3. `git add <file>` — пометить конфликт как разрешённый.
4. Завершить операцию:
   - при merge: `git commit` (сообщение уже подготовлено Git'ом);
   - при rebase: `git rebase --continue`.

Если решили, что разбираться не готовы — можно откатиться полностью:

```bash
git merge --abort
git rebase --abort
```

⚠️ Ловушка: `git add` не «разрешает» конфликт сам по себе — он просто
сообщает Git'у «я разобрался с этим файлом». Если случайно оставить маркеры
`<<<<<<<` в файле и закоммитить — код продолжит содержать мусор, и Git об
этом не предупредит.

### Инструменты

```bash
git diff                    # покажет конфликт в unified-формате с обеими версиями
git checkout --ours <file>   # взять полностью версию текущей ветки
git checkout --theirs <file> # взять полностью версию входящей ветки
git mergetool                 # запустить настроенный визуальный merge-инструмент
```

## Commit hygiene

- **Атомарные коммиты** — один коммит решает одну логическую задачу. Не
  смешивайте рефакторинг, форматирование и фичу в одном коммите. Это не
  эстетика: атомарные коммиты — это то, что делает работающими `git revert`
  (отменить ровно одну вещь), `git bisect` (найти коммит, сломавший тесты) и
  code review (проще понять, что и зачем менялось).
- **Сообщение коммита**: короткая строка в повелительном наклонении
  (`Add`, а не `Added`/`Adding`), до ~50 символов, при необходимости — пустая
  строка и подробное тело с объяснением **почему**, а не **что** (что видно
  из diff'а и так).

```
fix: retry Kafka consumer on connection reset

Consumer silently died on transient network errors instead of
reconnecting, causing message loss during deploys. Add exponential
backoff and reconnect loop.
```

- Многие команды используют префиксы в духе Conventional Commits
  (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`) — это не требование Git,
  а соглашение, которое включает автогенерацию changelog'ов.

## Отмена изменений: restore, reset, revert

Это три разные операции, которые новички часто путают:

| Команда | Что откатывает | Меняет ли историю коммитов | Где безопасно применять |
| :--- | :--- | :--- | :--- |
| `git restore` | Working directory / staging area | Нет | Всегда, локальные незакоммиченные изменения |
| `git reset` | Положение ветки (и, опционально, staging/working dir) | Да (удаляет коммиты из ветки) | Только для **локальных**, ещё не запушенных коммитов |
| `git revert` | Эффект конкретного коммита, новым коммитом | Нет (добавляет коммит) | Безопасно даже для **уже запушенной/публичной** истории |

### `git restore` — откат файлов

```bash
git restore <file>            # отменить незакоммиченные правки в файле
                                # (working dir -> вернуть как в последнем коммите)
git restore --staged <file>    # убрать файл из staging area, не трогая правки на диске
git restore --source=HEAD~2 -- <file>  # взять версию файла из более старого коммита
```

### `git reset` — три режима

```bash
git reset --soft HEAD~1   # откатить ветку на 1 коммит назад,
                            # изменения остаются в staging area
git reset --mixed HEAD~1   # (по умолчанию) откатить ветку,
                            # изменения остаются в working dir, но не застейджены
git reset --hard HEAD~1    # откатить ветку И стереть изменения в рабочей папке
                            # НЕОБРАТИМО для working dir
```

⚠️ `git reset --hard` безвозвратно уничтожает незакоммиченные изменения в
рабочей папке. Сами коммиты, впрочем, обычно ещё какое-то время живут в
`git reflog` — это единственная страховочная сетка:

```bash
git reflog                  # список всех перемещений HEAD, включая "потерянные" коммиты
git reset --hard <sha>       # можно вернуться к состоянию до неудачного reset
```

### `git revert` — безопасная отмена для общей истории

```bash
git revert <commit-sha>     # создать новый коммит, отменяющий изменения указанного
git revert -n <sha1> <sha2>  # отменить несколько коммитов без автокоммита каждого
```

**Правило выбора**: коммит уже запушен и потенциально виден/затянут другими —
используйте `revert`. Коммит существует только у вас локально — можно
`reset`. Причина простая: `reset` меняет то, на что указывает ветка, а
`revert` добавляет новый коммит поверх существующей истории, ничего не
переписывая — поэтому он не ломает чужие локальные копии репозитория.

### `git commit --amend` — исправление последнего коммита

```bash
git commit --amend                 # изменить сообщение последнего коммита
git add forgotten_file.py
git commit --amend --no-edit        # добавить файл в последний коммит без изменения сообщения
```

`--amend` тоже **переписывает SHA** последнего коммита — по сути это
частный случай rebase на один коммит. То же золотое правило: амендить можно
только то, что ещё не запушено (или запушено только в вашу личную ветку, о
которой точно никто больше не знает).
