# Ветвление и слияние: branch, merge, rebase

## Ветка — это просто указатель

Ветка в Git — не копия файлов, а **лёгкий указатель на коммит** (файл на 41
байт с SHA внутри `.git/refs/heads/`). Поэтому создание и переключение веток
почти мгновенное — Git не копирует историю.

`HEAD` — это указатель на указатель: обычно он ссылается на текущую ветку,
которая в свою очередь ссылается на коммит.

```bash
git branch                     # список локальных веток
git branch feature/login        # создать ветку (без переключения)
git switch feature/login         # переключиться на неё
git switch -c feature/login      # создать и сразу переключиться (аналог checkout -b)

git branch -d feature/login      # удалить смёрженную ветку
git branch -D feature/login      # принудительно удалить (даже несмёрженную)
```

`git switch` и `git restore` (Git ≥ 2.23) разделили когда-то перегруженную
команду `git checkout` на две понятные: переключение веток и восстановление
файлов. Старый `checkout` продолжает работать, но в новых скриптах лучше
использовать `switch`/`restore` — меньше риск случайно перепутать «переключить
ветку» и «затереть файл».

## Merge: fast-forward vs three-way

Когда сливаете `feature` в `main`, возможны два сценария:

- **Fast-forward** — если в `main` не было новых коммитов с момента создания
  `feature`, Git просто **двигает указатель `main`** вперёд, до коммита
  `feature`. Merge-коммит не создаётся, история остаётся линейной.
- **Three-way merge** — если обе ветки успели разойтись, Git создаёт новый
  **merge-коммит с двумя родителями**, объединяющий изменения.

```bash
git switch main
git merge feature/login          # fast-forward, если возможно
git merge --no-ff feature/login  # всегда создавать merge-коммит,
                                   # даже если fast-forward возможен
```

⚠️ Ловушка: fast-forward merge **не оставляет следа**, что ветка вообще
существовала — история выглядит так, будто коммиты сделаны прямо в `main`. В
командах, где важно видеть границы фич в логе, осознанно используют
`--no-ff`.

## Rebase: переписывание истории

`git rebase` берёт коммиты вашей ветки и **накатывает их заново** поверх
другого коммита (обычно — актуального `main`), создавая для каждого коммита
**новый SHA**.

```bash
git switch feature/login
git rebase main         # переносим feature на актуальный main
```

Результат — линейная история без merge-коммитов, как будто вы начали ветку
от свежего `main`. Это делает `git log` чище и упрощает `git bisect`.

### Rebase vs merge: что выбрать

| | `merge` | `rebase` |
| :--- | :--- | :--- |
| Меняет существующие коммиты | Нет | Да (новые SHA) |
| История | Нелинейная, с merge-коммитами | Линейная |
| Безопасность для чужих веток | Безопасно всегда | Опасно для запушенных веток |
| Когда использовать | Публичные/общие ветки (`main`, `develop`) | Локальные фичи перед созданием PR |

**PR (pull request, в GitLab — merge request)** — запрос на сервере
(GitHub/GitLab) «влейте мою ветку в `main`»: коллеги смотрят изменения,
оставляют комментарии, запускаются автоматические проверки, и только после
одобрения ветка сливается. Так в командах устроено ревью кода.

**Золотое правило rebase**: никогда не переписывайте историю коммитов,
которые уже запушены и могут быть у кого-то ещё в локальном репозитории.
После `rebase` SHA меняются, и следующий `git push` потребует `--force`,
что перезапишет чужую историю на сервере и может привести к потере чужих
коммитов.

```bash
# Если ветка уже была запушена и вы её перебазировали ЛОКАЛЬНО — единственно верный шаг:
git push --force-with-lease   # безопаснее чем --force: не даст затереть
                                # чужие коммиты, о которых вы не знали
```

### Конфликт во время rebase

Конфликт при rebase решается так же, как обычный merge-конфликт (см.
`03_conflicts_and_hygiene.md`), но команды продолжения/отмены другие:

```bash
# после ручного разрешения конфликта в файлах:
git add <resolved-file>
git rebase --continue

git rebase --abort     # полностью откатить rebase, вернуться к состоянию до него
git rebase --skip       # пропустить текущий коммит целиком (редко нужно)
```

### Interactive rebase (кратко)

`git rebase -i` позволяет переупорядочить, объединить (`squash`) или
переписать сообщения последних N коммитов перед тем, как поделиться веткой:

```bash
git rebase -i HEAD~3    # интерактивно отредактировать последние 3 коммита
```

Типичный сценарий — «причесать» серию коммитов вида `wip`, `fix typo`,
`actual feature` в один осмысленный коммит перед открытием PR.

## Визуализация истории

```bash
git log --oneline --graph --all --decorate
```

Полезно держать эту команду под рукой (или алиасом `git lg`), чтобы видеть
реальную топологию веток и merge-коммитов, а не гадать по плоскому логу.
