# Решение: 05_restore_reset_revert

```bash
# 1. Отменить незакоммиченную правку в scratch.py
git restore scratch.py

# 2. Создать draft.py, застейджить и снять со стейджа, не удаляя файл
echo "TEMP = 1" > draft.py
git add draft.py
git restore --staged draft.py

# 3. Найти коммит "report v3" и отменить его эффект через revert,
#    НЕ трогая сам коммит в истории (git log --oneline покажет позицию)
git log --oneline
git revert --no-edit HEAD~1   # HEAD~1 = "feat: report v3 (bug: ...)"
```

Почему `HEAD~1`, а не `HEAD~2`: на момент решения `HEAD` — это
`chore: add scratch module`, значит `HEAD~1` — это как раз коммит с багом.
Если ошибиться со смещением, `git revert` либо откатит не тот коммит, либо
(если задетый файл пересекается с более новыми изменениями) покажет
конфликт — тогда проще всего `git revert --abort` и попробовать снова с
верным указателем на коммит (можно просто указать сам SHA коммита вместо
`HEAD~N`, это надёжнее).

После `revert`: `report.py` снова возвращает `"report v2"`, а сам коммит
`feat: report v3 ...` остаётся в `git log` — revert не переписывает историю,
а добавляет новый коммит, отменяющий её эффект. Именно поэтому revert
безопасен для уже опубликованной истории, а `reset` — нет.
