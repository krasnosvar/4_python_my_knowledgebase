# Dockerfile: основные инструкции

## Минимальный Dockerfile для Python-приложения

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Python-специфичные вещи в этом примере (сам Python — дальше, в `1_python`):

- **`pip`** — стандартный установщик Python-библиотек; `pip install -r
  requirements.txt` ставит все библиотеки из списка. Подробнее — в
  [01_environments_and_packaging](../../../other/01_environments_and_packaging/README.md).
- **`requirements.txt`** — текстовый файл со списком библиотек (и их
  версий), которые нужны приложению.
- **`uvicorn`** — веб-сервер, который запускает Python веб-приложение
  (`main:app` — «объект `app` из файла `main.py`»); разбирается в
  `3_web_frameworks`.

## Инструкции по порядку

| Инструкция | Назначение |
| :--- | :--- |
| `FROM` | Базовый образ. Всегда первая инструкция (кроме `ARG` перед ней). |
| `WORKDIR` | Рабочая директория внутри образа — создаётся, если не существует. Лучше, чем `RUN cd ...` (который не сохраняется между слоями). |
| `COPY` | Копирует файлы с хоста в образ. |
| `ADD` | Как `COPY`, но ещё умеет распаковывать архивы и качать по URL — из-за неочевидного поведения обычно **предпочитают `COPY`**, если не нужна именно распаковка. |
| `RUN` | Выполняет команду **во время сборки** и коммитит результат новым слоем. |
| `ENV` | Переменная окружения, доступна и во время сборки, и в запущенном контейнере. |
| `ARG` | Переменная, доступна **только во время сборки** (через `--build-arg`), в контейнер не попадает. |
| `EXPOSE` | Только документация: какой порт слушает процесс. **Не публикует порт наружу** — публикация делается флагом `-p` у `docker run` или секцией `ports` в compose. |
| `CMD` | Команда по умолчанию при `docker run` без аргументов команды. Переопределяется аргументом командной строки. |
| `ENTRYPOINT` | Команда, которая выполняется всегда; аргументы `docker run image ARGS` добавляются к ней, а не заменяют её. |
| `USER` | От чьего имени выполняется процесс — по умолчанию `root`, что для прод-контейнеров считается плохой практикой. |
| `.dockerignore` | Не инструкция Dockerfile, а отдельный файл — исключает файлы из **контекста сборки** (см. ниже). |

## CMD vs ENTRYPOINT

```dockerfile
ENTRYPOINT ["python", "manage.py"]
CMD ["runserver"]
```

(`manage.py` — стандартный скрипт управления Django-проектом:
`runserver` запускает сервер разработки, `shell` — интерактивную консоль.)

`docker run myimage runserver` → выполнит `python manage.py runserver`.
`docker run myimage shell` → выполнит `python manage.py shell` (CMD
переопределён аргументом). Комбинация `ENTRYPOINT` + `CMD` — стандартный
способ дать образу "команду по умолчанию", которую можно переопределить
одним аргументом, не переписывая всю команду.

## Shell form vs exec form — сигналы

```dockerfile
CMD python app.py          # shell form: команда выполняется через /bin/sh -c "..."
CMD ["python", "app.py"]   # exec form: команда выполняется напрямую, без обёртки шелла
```

⚠️ Неочевидная, но важная деталь: в **shell form** процесс приложения — это
**не PID 1** в контейнере (PID 1 — сам `/bin/sh`). Docker при `docker stop`
отправляет `SIGTERM` в PID 1. Если приложение не PID 1, оно может вообще не
получить сигнал и контейнер остановится только по истечении таймаута через
`SIGKILL` — то есть без штатного graceful shutdown. **Exec form** делает
процесс приложения PID 1 напрямую и должен использоваться, если приложению
важно перехватывать сигналы (веб-серверы, воркеры очередей — то есть
практически весь backend).

## .dockerignore

Работает как `.gitignore`, но исключает файлы из **build context** — того,
что клиент Docker отправляет демону перед сборкой:

```
.git
__pycache__/
*.pyc
.venv/
.env
tests/
```

Без `.dockerignore` в контекст сборки (и, при неосторожном `COPY . .`, в
итоговый образ) может утечь `.git` целиком, локальный `.venv`, секреты из
`.env` — и просто раздуть размер контекста, что замедляет каждую сборку.

## Кэш и порядок инструкций

```dockerfile
# ХОРОШО: зависимости отдельно от исходного кода
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# ПЛОХО: любое изменение любого файла инвалидирует кэш pip install
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
```

Слой с `pip install` пересобирается только когда меняется
`requirements.txt`, а не при любом изменении исходников — это может
сэкономить минуты на каждой пересборке.

## Multi-stage builds

Многоэтапная сборка позволяет использовать один образ для **сборки**
(с компиляторами, dev-зависимостями) и другой, минимальный — для **запуска**:

```dockerfile
# --- этап сборки ---
FROM python:3.12 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --target=/deps -r requirements.txt

# --- финальный этап ---
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /deps /usr/local/lib/python3.12/site-packages
COPY . .
CMD ["python", "main.py"]
```

Итоговый образ не содержит компиляторов и промежуточных артефактов сборки —
только то, что реально нужно для запуска. Для компилируемых зависимостей
(например, пакетов с C-расширениями) это может уменьшить размер образа в
разы. Рабочий пример — в `../02_examples/Dockerfile.multistage`.
