# venv, pip и зачем нужны виртуальные окружения

## Зачем изолировать окружение

Без виртуального окружения `pip install` ставит пакеты глобально — в
системный Python. Проблемы, которые это создаёт:

- Два проекта на одной машине требуют разных (несовместимых) версий одной
  библиотеки — глобально одновременно установлена может быть только одна.
- `pip install` от имени обычного пользователя в системный Python может
  требовать `sudo` или упираться в пакеты, управляемые менеджером пакетов ОС
  (современные дистрибутивы вообще блокируют это — `error: externally
  managed environment`).
- Нет воспроизводимости: непонятно, какие пакеты на самом деле нужны
  именно этому проекту, а какие — случайно оказались в системе.

**Виртуальное окружение** — это отдельная папка с собственной копией
интерпретатора (точнее, символьными ссылками) и собственной `site-packages`,
полностью изолированной от системного Python и от других окружений.

## venv: базовые команды

```bash
python3 -m venv .venv         # создать окружение в папке .venv
source .venv/bin/activate      # активировать (Linux/macOS)
.venv\Scripts\activate          # активировать (Windows)

deactivate                       # выйти из окружения

pip install requests             # ставится ТОЛЬКО в .venv, не глобально
pip list                          # что установлено в текущем активном окружении
pip show requests                  # версия, зависимости, где установлен пакет
```

⚠️ Активация окружения — это просто временное изменение `PATH` и
переменных окружения в текущей сессии шелла. Она ничего не сохраняет
навсегда и не действует в других открытых терминалах или в CI без
повторной активации.

`.venv/` **никогда** не коммитится в git — добавляйте в `.gitignore` (см.
[../../../0_tooling_and_workflow/01_git_essentials](../../../0_tooling_and_workflow/01_git_essentials/)).
Она воссоздаётся из `requirements.txt`/`pyproject.toml` на любой машине.

## requirements.txt

```
# requirements.txt
requests==2.32.3
click>=8.1,<9
```

```bash
pip install -r requirements.txt      # установить всё из файла
pip freeze > requirements.txt          # зафиксировать ТЕКУЩЕЕ состояние окружения
```

⚠️ Ловушка: `pip freeze` пишет в файл **абсолютно все** пакеты в текущем
окружении, включая транзитивные зависимости зависимостей — файл быстро
превращается в нечитаемую простыню, где непонятно, что вы поставили
осознанно, а что подтянулось само. Более управляемый подход — разделять
"прямые" зависимости (то, что вы реально импортируете) и "полный слепок"
(то, что реально ставится):

```
requirements.in           # то, что вы решили использовать (пишете руками)
requirements.txt           # сгенерированный полный слепок с точными версиями
```

Инструменты вроде `pip-tools` (`pip-compile requirements.in`) автоматизируют
второй файл из первого. Подробнее про современный подход через
`pyproject.toml`/poetry — в
[02_pyproject_and_poetry.md](./02_pyproject_and_poetry.md).

## Зачем пиновать версии

- `requests` (без версии) — при следующей установке может подтянуться
  новая мажорная версия с breaking changes, и ничто не гарантирует, что
  код продолжит работать.
- `requests==2.32.3` — точная версия, максимально воспроизводимо, но
  требует ручного апдейта.
- `requests>=2.32,<3` — компромисс: позволяет патч/минорные обновления
  (багфиксы, новые фичи без breaking changes по семверу), но не даёт
  случайно перепрыгнуть на несовместимую мажорную версию.

Для приложений (не библиотек) обычно фиксируют точные версии всего дерева
зависимостей через lock-файл — это то, что делают `pip-tools`, `poetry` и
`pdm` по умолчанию.
