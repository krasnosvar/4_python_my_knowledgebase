# Type hints и mypy

## Аннотации типов ничего не проверяют сами по себе

Python остаётся динамически типизированным языком **во время выполнения**.
Аннотации типов (PEP 484) — это метаданные, которые интерпретатор
в большинстве случаев просто игнорирует:

```python
def add(a: int, b: int) -> int:
    return a + b

add("2", "3")   # выполнится без ошибок и вернёт "23" — аннотации не проверяются в рантайме
```

Пользу аннотации приносят только вместе со **статическим анализатором**
(mypy, pyright) и с автодополнением/подсказками в IDE. Без анализатора это
просто документация, которая может незаметно разойтись с реальностью.

## Базовый синтаксис (модуль `typing`)

```python
from typing import Optional, Union

def greet(name: str) -> str:
    return f"Hello, {name}!"

def find_user(user_id: int) -> Optional[dict]:      # то же самое, что dict | None
    ...

def parse(value: str | int) -> float:                 # современный синтаксис (3.10+), без typing.Union
    ...

names: list[str] = []          # начиная с 3.9 — встроенные generic-типы, typing.List не обязателен
mapping: dict[str, int] = {}
```

## Основные конструкции

| Конструкция | Назначение |
| :--- | :--- |
| `Optional[X]` / `X \| None` | Значение может быть `None`. |
| `Union[X, Y]` / `X \| Y` | Одно из нескольких типов. |
| `list[X]`, `dict[K, V]`, `tuple[X, ...]` | Параметризованные коллекции. |
| `Callable[[int, str], bool]` | Функция с сигнатурой `(int, str) -> bool`. |
| `TypeVar` | Обобщённые (generic) функции/классы: тип входа связан с типом выхода. |
| `Protocol` | Структурная типизация ("duck typing" с проверкой): не важно, от чего унаследован класс, важно — какие методы у него есть. |
| `TypedDict` | Типизированный словарь с фиксированным набором ключей — полезно для JSON-подобных структур. |
| `Any` | "Выключить" проверку типов для конкретного места — использовать точечно, не как способ "заткнуть" mypy глобально. |

```python
from typing import TypeVar, Protocol

T = TypeVar("T")

def first(items: list[T]) -> T:
    return items[0]

class SupportsClose(Protocol):
    def close(self) -> None: ...

def cleanup(resource: SupportsClose) -> None:
    resource.close()
```

## mypy: запуск и что он реально ловит

```bash
mypy src/
mypy --strict src/    # включает почти все проверки: без Any по умолчанию,
                        # обязательные аннотации, запрет неявных Optional и т.д.
```

Что mypy ловит **до** запуска кода:

- Передачу аргумента не того типа (`add("2", "3")` из примера выше — mypy
  сообщит об ошибке).
- Обращение к несуществующему атрибуту/методу.
- Забытую обработку `None` (`Optional[X]` без проверки перед использованием).
- Несовместимые типы при переопределении методов в наследниках (нарушение
  принципа подстановки Лисков).

## Неочевидные ловушки

- `Any` "заразен": если функция возвращает `Any`, всё, что из неё
  вычисляется дальше, тоже становится `Any` — тип-чек молча перестаёт
  что-либо проверять по всей цепочке использования этого значения.
- Аннотации в сигнатуре функции **не проверяются** реальными значениями в
  рантайме — для этого нужны отдельные инструменты (`pydantic`,
  `typeguard`) или библиотеки валидации на границах системы (например,
  входящий HTTP-запрос).
- `# type: ignore` подавляет ошибку **на конкретной строке** — легко
  использовать как способ "заткнуть" mypy вместо того, чтобы разобраться с
  реальной проблемой; используйте `# type: ignore[code]` с конкретным
  кодом ошибки, а не голый `# type: ignore`, чтобы не скрыть заодно другие,
  несвязанные проблемы в этой же строке в будущем.
- Постепенное внедрение типов в существующий проект обычно начинают не с
  `--strict` сразу, а с `mypy` в дефолтном режиме на конкретных модулях,
  постепенно расширяя охват (`[[tool.mypy.overrides]]` в `pyproject.toml`
  позволяет включать строгость по модулям точечно).
