# Упражнения: Kafka и RabbitMQ

Перед началом:

1. Прочитай `../01_theory/README.md` (особенно разделы 2.1-2.3 про Kafka
   и 3.1-3.4, 4 про RabbitMQ/DLQ - без этого решать бессмысленно).
2. Подними стенд из `../02_examples/`:
   ```bash
   cd ../02_examples
   docker compose up -d

   pip install -r requirements.txt
   ```

   `# TODO:`. Открой файл, дочитай комментарии до конца, реализуй недостающие

   только после собственной попытки.

## Упражнение 1 - партиционирование и порядок сообщений (Kafka)

Файлы: `ex1_kafka_ordering/producer.py`, `ex1_kafka_ordering/consumer.py`

Задача: создать новый topic `events` с 3 партициями, отправить в него события
с ключом `user_id` и на практике убедиться, что:

- события ОДНОГО пользователя (один и тот же `user_id`) всегда приходят
  в одну и ту же партицию и читаются в том порядке, в котором были отправлены;
- события РАЗНЫХ пользователей могут оказаться в разных партициях, и
  гарантии порядка МЕЖДУ ними нет.

Что нужно реализовать (см. `# TODO` в файлах):

1. В `producer.py` - создать topic `events` с 3 партициями (если ещё не
   существует) через `AIOKafkaAdminClient`, затем отправить не менее 9 событий
   для 3 разных `user_id`, используя `user_id` как ключ сообщения.
2. В `consumer.py` - прочитать все сообщения из topic'а и вывести для каждого
   `partition`, `key`, порядковый номер события внутри пользователя. Убедиться
   (глазами, по логу), что для каждого `user_id` номера идут строго по возрастанию
   в пределах партиции.

Проверка: запусти `producer.py`, затем `consumer.py` (или в Kafka UI на
http://localhost:8080 открой topic `events` -> Messages, отсортируй по
партициям) и убедись, что все сообщения одного `user_id` лежат в одной партиции
и в правильном порядке.

## Упражнение 2 - manual commit offset'а (Kafka)

Файлы: `ex2_manual_commit/producer.py`, `ex2_manual_commit/consumer.py`

Задача: реализовать consumer с топиком `manual-commit-demo`, который коммитит
offset ТОЛЬКО после успешной обработки сообщения, а не по таймеру.

Что нужно реализовать:

1. `producer.py` - отправить 10 последовательных сообщений с номерами 0..9
   (ключ можно не использовать - для этого упражнения важна только
   последовательность, а не партиционирование).
2. `consumer.py` - создать consumer с `enable_auto_commit=False`, вызывать
   `process_message()` (уже дан в файле, он бросает исключение для сообщения
   с номером 5, имитируя сбой обработки), и коммитить offset вручную только
   при успешной обработке.
3. В комментарии над функцией commit (`# TODO: объясни...`) написать своими
   словами, что именно сломалось бы, если бы вместо manual commit был
   включён `enable_auto_commit=True` - какое конкретно сообщение и почему
   было бы потеряно или обработано неправильно в сценарии с падением на
   сообщении номер 5.

Проверка: убедись, что consumer не коммитит offset сообщения №5 (в логе должно
быть явно видно "ошибка обработки, offset НЕ закоммичен") и после этого
останавливается, а не продолжает обрабатывать 6, 7, 8, 9 (если бы он продолжил
и закоммитил успешную обработку number=6, это сдвинуло бы committed offset
и мимо number=5 - подробнее см. комментарий в файле). После перезапуска
consumer'а сообщение №5 должно быть прочитано снова, а не пропущено.

## Упражнение 3 - topic exchange с двумя очередями (RabbitMQ)

Файлы: `ex3_rabbitmq_routing/producer.py`, `ex3_rabbitmq_routing/consumer_a.py`,
`ex3_rabbitmq_routing/consumer_b.py`

Задача: сервисы публикуют логи с routing key вида `logs.<service>.<level>`,
например `logs.auth.error`, `logs.billing.warning`, `logs.auth.info`.
Нужно завести exchange `logs_topic` (type=topic) и две очереди с РАЗНЫМИ
паттернами биндинга:

- `errors_queue` - должна получать ВСЕ сообщения уровня `error`, от какого бы
  сервиса они ни пришли (binding key должен использовать `*` на месте service);
- `auth_service_queue` - должна получать ВСЕ сообщения от сервиса `auth`,
  независимо от уровня (binding key должен использовать `#` на месте level).

Что нужно реализовать:

1. `producer.py` - объявить exchange `logs_topic`, опубликовать не менее
   6 сообщений с разными комбинациями `service`/`level` (минимум 2 разных
   сервиса и минимум 2 разных уровня, включая `error`).
2. `consumer_a.py` - объявить `errors_queue` с правильным binding key
   и подтверждать сообщения (manual ack).
3. `consumer_b.py` - объявить `auth_service_queue` с правильным binding key
   и подтверждать сообщения (manual ack).

Проверка: запусти оба consumer'а, затем producer, и убедись по логам, что:
- `errors_queue` получила все `*.error` сообщения и ни одного `warning`/`info`
  от сервисов, не относящихся к `error`-логам;
- `auth_service_queue` получила ВСЕ сообщения от `auth` (любого уровня) и ни
  одного сообщения от других сервисов;
- сообщение `logs.auth.error` должно быть доставлено В ОБЕ очереди
  (это не взаимоисключающие фильтры, а независимые подписки).

## Упражнение 4 - DLQ с retry-with-backoff (RabbitMQ)

Файлы: `ex4_dlq_retry/producer.py`, `ex4_dlq_retry/consumer.py`

Задача: реализовать полный цикл dead-lettering: сообщение, которое не
обрабатывается N попыток подряд (с задержкой между попытками), должно
оказаться в отдельной DLQ-очереди - без единой строчки кода, вручную
перекладывающей сообщение между очередями (только конфигурация
`x-dead-letter-exchange` на основной очереди, как в `02_examples/rabbitmq/consumer.py`).

Что нужно реализовать:

1. `consumer.py` - объявить основную очередь `payments_queue` с
   `x-dead-letter-exchange`, указывающим на отдельный DLX `payments_dlx`,
   к которому привязана очередь `payments_dlq`.
2. Использовать декоратор `retry_with_backoff` из `../../02_examples/retry_with_backoff.py`
   для оборачивания обработчика с не менее чем 3 попытками.
3. При исчерпании попыток (`RetryExhaustedError`) - `nack` с `requeue=False`.
4. `producer.py` - опубликовать несколько нормальных сообщений и минимум одно
   "ядовитое" (например, с отрицательной суммой `amount`, которую обработчик
   обязан отвергать как невалидную).

Проверка: в RabbitMQ management UI (http://localhost:15672) убедись, что
"ядовитое" сообщение оказалось в очереди `payments_dlq`, а нормальные
сообщения были успешно обработаны (подтверждены, из очереди `payments_queue`
исчезли) без единого попадания в DLQ.
