# Kafka: гарантии доставки

На уровне промышленного проекта здесь не абстрактная теория, а конкретные
настройки producer'а и consumer'а.

```
┌──────────────────────────────────────────────────────────────────┐
│ At-most-once — сообщение может потеряться, но не задублируется   │
├──────────────────────────────────────────────────────────────────┤
│ Producer: acks=0 (не ждать подтверждения от брокера)              │
│ Consumer: commit offset ДО обработки (или auto-commit с коротким  │
│           интервалом и обработкой, которая может не успеть)       │
│                                                                    │
│ Плюс: максимальная скорость, минимальная задержка                 │
│ Минус: потеря данных при сбое сети/брокера/consumer'а             │
│ Когда уместно: метрики, non-critical логи — где потерять          │
│                 несколько точек дешевле, чем тормозить систему     │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ At-least-once — сообщение не потеряется, но может задублироваться│
├──────────────────────────────────────────────────────────────────┤
│ Producer: acks=all (ждать подтверждения от всех in-sync реплик)   │
│           + retries > 0                                           │
│ Consumer: commit offset ПОСЛЕ успешной обработки (manual commit)  │
│                                                                    │
│ Плюс: данные не теряются                                          │
│ Минус: обработчик обязан быть идемпотентным (обработка одного и   │
│        того же сообщения дважды не должна портить состояние)      │
│ Когда уместно: подавляющее большинство бизнес-событий              │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ Exactly-once — сообщение обработано ровно один раз                │
├──────────────────────────────────────────────────────────────────┤
│ Producer: enable.idempotence=true (у Confluent/aiokafka —          │
│           idempotent producer, дедупликация по producer id +      │
│           sequence number на стороне брокера)                     │
│           + транзакции, если пишем в несколько партиций/топиков   │
│           атомарно вместе с коммитом offset'а                      │
│ Consumer: читает только committed-сообщения транзакций             │
│           (isolation.level=read_committed)                        │
│                                                                    │
│ Плюс: не нужно думать о дубликатах вообще                          │
│ Минус: заметный оверхед на координацию транзакций, ниже throughput,│
│        сложнее эксплуатация; и это exactly-once ТОЛЬКО в рамках    │
│        Kafka (запись в топик + коммит офсета атомарно). Если       │
│        consumer, обработав сообщение, пишет результат во внешнюю   │
│        систему (БД, HTTP-вызов) — гарантия немедленно откатывается │
│        к at-least-once, потому что запись во внешнюю систему и     │
│        коммит offset'а — это уже две разные операции, между        │
│        которыми процесс может упасть                              │
│ Когда уместно: финансовые операции, платежи, где дубль или потеря  │
│                стоят дороже сложности                              │
└──────────────────────────────────────────────────────────────────┘
```

Почему exactly-once — это дорого и сложно в общем случае, а не просто «ещё одна
галочка в конфиге»: сама Kafka может гарантировать эту семантику только для
операций целиком внутри себя (consume-transform-produce в рамках одного
кластера, через транзакции). Как только в цепочке появляется внешняя система без
поддержки двухфазного коммита с Kafka — а это почти всегда так (Postgres,
внешний HTTP API, файловое хранилище) — единственный практичный вариант это
**at-least-once на транспорте + идемпотентность на уровне бизнес-логики**
(например, `INSERT ... ON CONFLICT DO NOTHING` по уникальному `event_id`, или
проверка «это событие уже обработано» перед применением эффекта). Именно поэтому
в реальных системах чаще инвестируют не в exactly-once Kafka-транзакции, а в
идемпотентные consumer'ы.
