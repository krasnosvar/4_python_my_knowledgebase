## 1. Зачем вообще нужны брокеры сообщений

Самый простой способ связать два сервиса — сделать прямой синхронный вызов: сервис A
вызывает HTTP/gRPC у сервиса B и ждёт ответа. Это работает, пока система маленькая.
Проблемы начинаются, когда сервисов становится много, а нагрузка — неравномерной.

```
Без брокера (прямые вызовы):

  Order Service ──HTTP──► Inventory Service
       │
       ├──HTTP──► Payment Service
       │
       └──HTTP──► Shipping Service

Проблемы:
  - Order Service должен знать адреса всех трёх сервисов
  - если Shipping Service тормозит — тормозит и Order Service (он ждёт ответа)
  - если Payment Service упал — заказ не оформить вообще, хотя товар и доставка
    были бы готовы
  - добавили Notification Service — надо менять код Order Service
```

Брокер сообщений решает три конкретные задачи, а не просто «модно».

**Decoupling (развязка производителя и потребителя).** Producer ничего не знает о том,
кто и сколько consumer'ов читает сообщение. Он публикует событие один раз, а сколько
сервисов на него подписано — 0, 1 или 10 — для него не видно. Это позволяет добавлять
новых потребителей события (например, Notification Service), не трогая код Order
Service вообще.

```
С брокером:

  Order Service ──► [ Broker: topic "orders" ] 
                            │
                 ┌──────────┼──────────┐
                 ▼          ▼          ▼
           Inventory   Payment    Shipping
           Service     Service    Service

  Order Service публикует "OrderCreated" и не ждёт,
  пока все три сервиса его обработают.
```

**Buffering / сглаживание нагрузки (backpressure absorption).** Если consumer
временно медленнее producer'а (пиковая нагрузка, деплой, GC-пауза, временная
недоступность БД, в которую пишет consumer), сообщения не теряются и не роняют
producer — они складываются в очередь/партицию и дожидаются, пока consumer их
разберёт. Без брокера пришлось бы либо ронять запросы, либо городить собственную
очередь в памяти (которая пропадёт при рестарте).

```
Пиковая нагрузка 10x:

  Producer:  ██████████████████████████████████  (шлёт быстро)
  Broker:    [буферизует в очереди/партиции]
  Consumer:  ████████                              (обрабатывает в своём темпе)

  Без брокера consumer либо не успевает и роняет запросы,
  либо накапливает бэклог в памяти и падает по OOM.
  С брокером бэклог живёт на диске брокера — consumer нагонит,
  когда сможет, ничего не потеряно.
```

**Асинхронная обработка.** Producer не обязан ждать, пока сообщение будет
полностью обработано, чтобы продолжить свою работу. «Отправить письмо», «пересчитать
рекомендации», «обновить поисковый индекс» — это не обязано блокировать ответ
пользователю. Producer публикует событие и сразу возвращает управление вызывающему.

Отсюда и стандартная плата за использование брокера: **дополнительная инфраструктура**
(кластер, мониторинг, эксплуатация), **eventual consistency** вместо мгновенной
согласованности (consumer обработает событие чуть позже, а не в момент публикации)
и необходимость думать о доставке сообщений (что если consumer упал в середине
обработки? что если сообщение обработано дважды?). Дальше в этом документе — как
Kafka и RabbitMQ решают эти вопросы каждый по-своему.

## 2. Apache Kafka

Kafka — это распределённый **лог событий** (append-only log), а не классическая
очередь. Сообщение, попав в Kafka, не удаляется после прочтения — оно хранится
согласно политике retention (например, 7 дней) независимо от того, прочитал его
кто-то или нет. Это ключевое архитектурное отличие определяет всё остальное:
партиции, консьюмер-группы, офсеты.

### 2.1 Партиции

**Topic** в Kafka — это именованный поток событий (например, `orders`). Физически
topic разбит на одну или несколько **партиций** — независимых, строго упорядоченных
логов.

Партиции существуют по двум причинам:

- **Параллелизм.** Один диск/поток может писать и читать с ограниченной скоростью.
  Если partition одна — весь topic упирается в производительность одного лога.
  Разбив topic на N партиций, можно писать в них параллельно (разные партиции могут
  жить на разных брокерах) и параллельно же читать (см. consumer-группы ниже).
- **Масштабирование.** Партиция — это единица распределения по брокерам кластера.
  Чем больше партиций, тем больше consumer'ов одновременно смогут работать с topic'ом
  и тем выше потенциальный throughput.

Расплата за это: **порядок сообщений гарантирован только внутри одной партиции**,
но не между партициями. Если для бизнес-логики важно, чтобы события по одному
пользователю обрабатывались строго по порядку (например, `created` не должен
обогнать `updated`), все события этого пользователя обязаны попадать в одну и ту же
партицию.

```
Topic "orders" (3 партиции):

  Partition 0:  [m0][m3][m6][m9] ...     ← порядок m0,m3,m6,m9 гарантирован
  Partition 1:  [m1][m4][m7]     ...     ← порядок m1,m4,m7 гарантирован
  Partition 2:  [m2][m5][m8]     ...     ← порядок m2,m5,m8 гарантирован

  Но: между Partition 0 и Partition 1 порядок НЕ гарантирован —
  m1 вполне может быть обработан раньше m0.
```

**Как сообщение попадает в конкретную партицию.** Если у сообщения задан ключ (key),
Kafka вычисляет `hash(key) % num_partitions` — все сообщения с одним и тем же ключом
всегда попадут в одну и ту же партицию (пока число партиций не меняется). Если ключа
нет, используется round-robin (или sticky-партиционер в современных клиентах, который
батчит подряд идущие сообщения в одну партицию для эффективности, а затем переключается).

```
                 Есть key?
                     │
        ┌────────────┴────────────┐
       ДА                        НЕТ
        │                          │
        ▼                          ▼
hash(key) % N партиций      round-robin / sticky
        │                          │
        ▼                          ▼
Все сообщения с этим key    Сообщения размазываются
всегда идут в одну          по партициям без привязки
и ту же партицию            к порядку между собой

Пример: key="user-42" → всегда Partition 1
        key="user-7"  → всегда Partition 2
        без key        → Partition 0, 1, 2, 0, 1, 2 ...
```

Практический вывод: если нужна гарантия порядка «все события заказа №123 обработаны
в порядке публикации» — используйте `order_id` как ключ. Если порядок не важен (метрики,
независимые события) — ключ не нужен, это даёт более равномерное распределение нагрузки.

### 2.2 Consumer-группы

Consumer сам по себе просто читает партиции. **Consumer-группа** — это несколько
consumer'ов, которые объединены общим `group_id` и совместно разбирают партиции topic'а,
не пересекаясь друг с другом.

Правило одно и оно жёсткое: **в рамках одной группы одну партицию читает не более
одного consumer'а одновременно**. Это то, что даёт горизонтальное масштабирование
чтения без дублирования обработки внутри группы.

```
Topic "orders" (4 партиции), группа "billing-service" (2 consumer'а):

  P0    P1    P2    P3
   │     │     │     │
   └──┬──┘     └──┬──┘
      │           │
 ┌────▼───┐  ┌────▼───┐
 │Consumer1│  │Consumer2│
 └────────┘  └────────┘

  Consumer1 читает P0 и P1, Consumer2 читает P2 и P3.
  Ни одна партиция не читается двумя consumer'ами сразу.
```

Отсюда прямое следствие для планирования capacity: **число активных consumer'ов
в группе, приносящих пользу, ограничено числом партиций**. 4 партиции и 6 consumer'ов
в группе — 2 consumer'а будут простаивать (idle), у Kafka просто нет для них партиций.
Поэтому число партиций планируют исходя из ожидаемого максимума параллелизма чтения,
а не только из throughput на запись.

**Rebalancing.** Когда consumer присоединяется к группе или выходит из неё (упал,
задеплоился заново, завис на обработке дольше `max.poll.interval.ms`), группа
перераспределяет партиции между оставшимися consumer'ами.

```
Было: 2 consumer'а, 4 партиции — по 2 партиции на каждого.

Добавили Consumer3 → REBALANCE:
  P0→C1   P1→C2   P2→C3   P3→C1 (например)

Consumer2 упал → REBALANCE:
  P0→C1   P1→C3   P2→C3   P3→C1

Во время rebalance обработка приостанавливается (stop-the-world для группы),
поэтому слишком частые рестарты consumer'ов или слишком долгая обработка одного
батча (что триггерит kick из группы по таймауту) — это ощутимая эксплуатационная
проблема, а не мелочь.
```

Разные группы полностью независимы друг от друга: группа `analytics` и группа
`notifications`, подписанные на один и тот же topic, читают его каждая по-своему,
не мешая друг другу и не деля партиции между собой — это два параллельных потока
чтения одного и того же лога.

### 2.3 Офсеты

**Offset** — это порядковый номер сообщения внутри конкретной партиции (0, 1, 2, ...).
Он не глобален для topic'а — это позиция строго в рамках одной партиции.

Consumer хранит два разных числа, и разница между ними принципиальна:

- **current position** — до какого сообщения consumer уже дочитал локально
  (in-memory), не факт, что это сохранено где-то на случай падения;
- **committed offset** — то, что зафиксировано в Kafka (в служебном topic'е
  `__consumer_offsets`) как «эта группа гарантированно обработала всё до этой точки».
  Именно committed offset используется при рестарте consumer'а, чтобы понять,
  с какого места продолжать.

```
Partition 0 топика "orders":

  offset:  0    1    2    3    4    5    6    7
           x    x    x    x    ^    ^
                          committed  current position
                          (зафиксировано) (уже прочитано,
                                            но не закоммичено)

  Если consumer упадёт прямо сейчас — при рестарте он начнёт с offset 4,
  а не с offset 6. Сообщения 4 и 5 будут обработаны повторно.
```

**Auto-commit vs manual commit — это не техническая деталь, а решение о семантике
доставки.**

Auto-commit (по умолчанию в большинстве клиентов, коммит раз в N миллисекунд)
коммитит offset по таймеру, независимо от того, успела ли обработка завершиться.
Это создаёт окно, в котором offset уже закоммичен, а обработка ещё не закончена —
упав в этот момент, consumer при рестарте начнёт со следующего offset и **потеряет**
недообработанные сообщения. Плюс auto-commit — простота и минимальный код.

Manual commit коммитит offset explicitly, кодом, **после** того как обработка
сообщения гарантированно завершена (записана в БД, отправлена дальше и т.д.).
Это даёт at-least-once: при падении между обработкой и коммитом сообщение будет
обработано повторно после рестарта — но не потеряно никогда. Плата — код должен
быть готов к повторной обработке (идемпотентность на стороне consumer'а) и коммит
надо вызывать явно в нужный момент, а не забывать об этом.

**Replay — уникальная для лог-модели возможность, которой нет у классической очереди.**
Поскольку сообщение не удаляется после прочтения, а живёт в партиции согласно
retention, можно перемотать committed offset consumer-группы назад (или указать
`earliest` при первом запуске новой группы) и **перечитать историю заново** —
например, чтобы пересчитать агрегаты после исправления бага в обработчике, или
чтобы поднять новый сервис, которому нужна вся история событий с нуля. В RabbitMQ
после ack сообщение физически удалено из очереди — такой возможности нет.

### 2.4 Гарантии доставки

На уровне промышленного проекта здесь не абстрактная теория, а конкретные настройки
producer'а и consumer'а.

```
┌──────────────────────────────────────────────────────────────────┐
│ At-most-once — сообщение может потеряться, но не задублируется   │
├──────────────────────────────────────────────────────────────────┤
│ Producer: acks=0 (не ждать подтверждения от брокера)              │
│ Consumer: commit offset ДО обработки (или auto-commit с коротким  │
│           интервалом и обработкой, которая может не успеть)       │
│                                                                    │
│ Плюс: максимальная скорость, минимальная задержка                 │
│ Минус: потеря данных при сбое сети/брокера/consumer'а             │
│ Когда уместно: метрики, non-critical логи — где потерять          │
│                 несколько точек дешевле, чем тормозить систему     │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ At-least-once — сообщение не потеряется, но может задублироваться│
├──────────────────────────────────────────────────────────────────┤
│ Producer: acks=all (ждать подтверждения от всех in-sync реплик)   │
│           + retries > 0                                           │
│ Consumer: commit offset ПОСЛЕ успешной обработки (manual commit)  │
│                                                                    │
│ Плюс: данные не теряются                                          │
│ Минус: обработчик обязан быть идемпотентным (обработка одного и   │
│        того же сообщения дважды не должна портить состояние)      │
│ Когда уместно: подавляющее большинство бизнес-событий              │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│ Exactly-once — сообщение обработано ровно один раз                │
├──────────────────────────────────────────────────────────────────┤
│ Producer: enable.idempotence=true (у Confluent/aiokafka —          │
│           idempotent producer, дедупликация по producer id +      │
│           sequence number на стороне брокера)                     │
│           + транзакции, если пишем в несколько партиций/топиков   │
│           атомарно вместе с коммитом offset'а                      │
│ Consumer: читает только committed-сообщения транзакций             │
│           (isolation.level=read_committed)                        │
│                                                                    │
│ Плюс: не нужно думать о дубликатах вообще                          │
│ Минус: заметный оверхед на координацию транзакций, ниже throughput,│
│        сложнее эксплуатация; и это exactly-once ТОЛЬКО в рамках    │
│        Kafka (запись в топик + коммит офсета атомарно). Если       │
│        consumer, обработав сообщение, пишет результат во внешнюю   │
│        систему (БД, HTTP-вызов) — гарантия немедленно откатывается │
│        к at-least-once, потому что запись во внешнюю систему и     │
│        коммит offset'а — это уже две разные операции, между        │
│        которыми процесс может упасть                              │
│ Когда уместно: финансовые операции, платежи, где дубль или потеря  │
│                стоят дороже сложности                              │
└──────────────────────────────────────────────────────────────────┘
```

Почему exactly-once — это дорого и сложно в общем случае, а не просто «ещё одна
галочка в конфиге»: сама Kafka может гарантировать эту семантику только для операций
целиком внутри себя (consume-transform-produce в рамках одного кластера, через
транзакции). Как только в цепочке появляется внешняя система без поддержки
двухфазного коммита с Kafka — а это почти всегда так (Postgres, внешний HTTP API,
файловое хранилище) — единственный практичный вариант это **at-least-once на транспорте
+ идемпотентность на уровне бизнес-логики** (например, `INSERT ... ON CONFLICT DO
NOTHING` по уникальному `event_id`, или проверка «это событие уже обработано» перед
применением эффекта). Именно поэтому в реальных системах чаще инвестируют не в
exactly-once Kafka-транзакции, а в идемпотентные consumer'ы.

## 3. RabbitMQ

RabbitMQ — классический брокер очередей на основе протокола AMQP 0-9-1. В отличие от
Kafka, здесь нет понятия «лог с retention»: сообщение живёт в очереди до тех пор, пока
consumer его не подтвердит (ack), после чего оно физически удаляется. Зато у RabbitMQ
гораздо более гибкая модель маршрутизации сообщений — через **exchange**.

### 3.1 Exchange и его типы

Producer в RabbitMQ никогда не публикует напрямую в очередь — он публикует в
**exchange**, а exchange, руководствуясь своим типом и **routing key** сообщения,
решает, в какие очереди это сообщение попадёт (или не попадёт ни в одну).

```
   Producer ──► [ Exchange ] ──► Queue A
                     │      └──► Queue B
                     └──────────► Queue C

   Какие именно очереди получат сообщение — решает тип exchange
   и routing key, с которым отправлено сообщение.
```

**direct** — точное совпадение routing key с binding key очереди. Простейший тип:
подходит, когда есть фиксированный набор «каналов» (например, routing key = уровень
логирования `error`, `warning`, `info`, и для каждого — своя очередь).

**topic** — routing key и binding key — это точки-разделённые слова (`orders.eu.created`),
и binding key может содержать wildcard-подстановки: `*` заменяет ровно одно слово,
`#` — ноль или более слов. Это самый гибкий и самый часто используемый в реальных
системах тип, потому что позволяет разным consumer'ам подписываться на разные срезы
одного потока событий без изменения producer'а.

**fanout** — routing key полностью игнорируется, сообщение уходит во **все** очереди,
привязанные к этому exchange. Используется для широковещательной рассылки:
«разослать всем интересующимся сервисам, что конфиг обновился» — без необходимости
знать заранее список подписчиков и придумывать для них routing key.

**headers** — маршрутизация не по routing key, а по совпадению произвольных
заголовков сообщения (с `x-match: all` — все заголовки должны совпасть — или
`x-match: any` — хотя бы один). Используется реже всего: routing key почти всегда
выразительнее и дешевле по CPU, headers-exchange оправдан, только когда критерии
маршрутизации многомерны и плохо ложатся в одну строку routing key.

```
┌───────────────────────────────────────────────────────────────┐
│ Тип       │ Критерий маршрутизации      │ Типичный случай      │
├───────────┼──────────────────────────────┼──────────────────────┤
│ direct    │ routing_key == binding_key  │ фиксированный набор  │
│           │ (точное совпадение)          │ каналов/очередей     │
│ topic     │ routing_key matches pattern  │ подписка на срез     │
│           │ с * и # в binding_key         │ событий по паттерну  │
│ fanout    │ routing key игнорируется,    │ broadcast всем        │
│           │ уходит во все bound-очереди   │ подписчикам           │
│ headers   │ совпадение произвольных      │ многомерная           │
│           │ заголовков сообщения          │ маршрутизация         │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 Очереди и биндинги

**Queue** — это то, откуда фактически читает consumer; это FIFO-буфер сообщений
(с оговорками про приоритеты и quorum-очереди, но базовая модель — FIFO).
**Binding** — это связь между exchange и очередью с конкретным binding key
(«эта очередь хочет получать сообщения, чей routing key совпадает вот с таким
шаблоном»). Одна очередь может быть привязана к exchange несколькими биндингами
сразу (подписка сразу на несколько шаблонов), и несколько очередей могут быть
привязаны с одинаковым или разным binding key — тогда подходящее сообщение
доставляется в каждую из них по копии.

### 3.3 Ack/Nack

RabbitMQ не удаляет сообщение из очереди в момент, когда его забрал consumer —
оно помечается как «доставлено, но не подтверждено» и физически остаётся в очереди
(и будет повторно доставлено, если consumer оборвёт соединение, не подтвердив).
Подтверждение — явное действие consumer'а:

- **ack** — «обработано успешно, можно удалить из очереди»;
- **nack / reject с `requeue=True`** — «обработка не удалась, но верни сообщение
  в очередь на повторную попытку» (осторожно: если ошибка систематическая — это
  сообщение немедленно будет отдано следующему consumer'у и снова провалится,
  создавая busy loop, если не сочетать с ограничением числа попыток);
- **nack / reject с `requeue=False`** — «обработка не удалась, и повторять смысла
  нет (или лимит попыток исчерпан) — не возвращай в очередь». Если для очереди
  настроен dead-letter-exchange (см. раздел 4), сообщение уходит именно туда;
  если DLX не настроен — сообщение теряется безвозвратно.

Это ручное подтверждение (manual ack) — сознательный выбор для надёжности:
auto-ack (подтверждение сразу при доставке, до обработки) экономит один
round-trip, но означает, что упавший посреди обработки consumer теряет сообщение
без следа — RabbitMQ уже посчитал его доставленным.

### 3.4 Routing key на практике

Разберём на примере: сервис публикует события заказов с routing key вида
`orders.<страна>.<событие>`, например `orders.eu.created`, `orders.us.cancelled`,
`orders.eu.shipped`.

```
Exchange "orders_topic" (type=topic)

  Producer публикует:
    routing_key = "orders.eu.created"
    routing_key = "orders.us.cancelled"
    routing_key = "orders.eu.shipped"

  Queue "eu_orders"      binding_key = "orders.eu.*"
    → получит "orders.eu.created" и "orders.eu.shipped"
    → НЕ получит "orders.us.cancelled" (не eu)

  Queue "all_cancellations"  binding_key = "orders.*.cancelled"
    → получит "orders.us.cancelled"
    → НЕ получит "orders.eu.created" (последнее слово не cancelled)

  Queue "audit_log"      binding_key = "orders.#"
    → получит ВСЕ три сообщения (# — ноль или более слов после "orders")
```

`*` — ровно одно слово на этой позиции, `#` — произвольное число слов (в т.ч. ноль).
Именно эта возможность — подписаться сразу на семантический срез потока событий,
не трогая producer и не создавая отдельный topic на каждую комбинацию — то, ради
чего topic exchange выбирают чаще direct: новый consumer с новым паттерном
подписки добавляется без единой строчки изменений у producer'а.

## 4. Dead Letter Queue и retry с backoff

Рано или поздно какое-то сообщение не обработается успешно раз за разом: баг
в данных («битая» запись, не проходящая валидацию), временная недоступность
внешней зависимости, которая не восстанавливается в разумный срок, или логическая
ошибка в самом обработчике. Такие сообщения называют **poison message** — они
не единичный сбой, а систематически не проходят обработку. Проблема в том, что
без специального механизма они либо теряются молча, либо блокируют всю очередь.

### Почему наивный «retry на месте до победного» опасен

Если при ошибке просто возвращать сообщение в начало очереди/партиции и пробовать
снова немедленно, возникает **head-of-line blocking**: одно проблемное сообщение
не даёт очереди продвинуться, потому что consumer раз за разом получает именно
его (для очереди FIFO) или зависает на одной и той же позиции (для Kafka —
partition вообще не может пропустить неподтверждённое сообщение и продолжить
дальше, потому что offset один на партицию, а не на сообщение). Все сообщения,
стоящие за проблемным, ждут, пока проблемное либо будет обработано, либо
исключено из потока — а если ошибка не временная, это не произойдёт никогда,
и вся партиция/очередь фактически встаёт.

```
Без DLQ (наивный retry-в-цикле):

  [msg_bad][msg2][msg3][msg4] ...
      │
      ▼ обработка падает
      │
   retry немедленно
      │
      ▼ падает снова
      │
   retry немедленно ... (бесконечно)

  msg2, msg3, msg4 никогда не будут обработаны,
  пока consumer зациклен на msg_bad.
```

### Почему сообщения оказываются в DLQ

- превышено число попыток обработки (retry limit исчерпан);
- истёк TTL сообщения (протухшая задача уже не актуальна);
- переполнена очередь (`x-max-length` в RabbitMQ) — новые сообщения при
  заполненной очереди могут настраиваться на dead-letter вместо отбрасывания;
- явный reject/nack от бизнес-логики («это сообщение в принципе не может быть
  обработано» — например, не проходит валидацию схемы).

### Retry с exponential backoff

Правильный паттерн — не ретраить мгновенно, а с растущей паузой между попытками,
и **не блокируя** при этом обработку остальных сообщений. Задержка растёт
экспоненциально (1с, 2с, 4с, 8с, ...), обычно с ограничением сверху (cap) и
случайным джиттером, чтобы много упавших одновременно consumer'ов не долбили
внешнюю зависимость синхронной волной запросов.

```
Попытка 1: ошибка → подождать ~1s  (+ jitter)
Попытка 2: ошибка → подождать ~2s  (+ jitter)
Попытка 3: ошибка → подождать ~4s  (+ jitter)
Попытка 4: ошибка → подождать ~8s  (+ jitter)
Попытка 5: ошибка → исчерпан лимит → в DLQ
```

Ключевая деталь: пауза между попытками не должна останавливать обработку
остальных сообщений. Поэтому «retry» реализуют не как sleep внутри цикла чтения
основной очереди, а как **отдельный retry-топик/retry-очередь с задержкой**:
сообщение, провалившее попытку, уходит не обратно в голову основной очереди,
а в отдельное место, откуда попадёт обратно в обработку только через нужный
интервал — основной поток при этом продолжает разбирать следующие сообщения
без пауз.

### Как это устроено в Kafka (уровень приложения)

У Kafka нет встроенного механизма DLQ — это паттерн, который реализуется поверх
топиков силами приложения:

```
   topic "orders"
        │
        ▼
  ┌─────────────┐
  │  Consumer   │──── успех ────► commit offset, следующее сообщение
  └──────┬──────┘
         │ ошибка
         ▼
  topic "orders-retry-1"  (consumer этого топика ждёт backoff-интервал
         │                 перед обработкой, например через заголовок
         │                 "retry-after" в сообщении, и только потом
         │                 пробует снова)
         │ снова ошибка
         ▼
  topic "orders-retry-2"  (больше интервал)
         │ снова ошибка, лимит попыток исчерпан
         ▼
  topic "orders-dlq"   ← сообщение + причина ошибки, для ручного разбора
```

Основной consumer при этом не простаивает: он не блокируется на проблемном
сообщении, а сразу коммитит его offset (обработка «переложена» в retry-топик)
и переходит к следующему сообщению партиции.

### Как это устроено в RabbitMQ (нативный DLX)

В RabbitMQ dead-lettering — встроенная возможность очереди, а не самодельный
паттерн. При объявлении очереди указывается:

- `x-dead-letter-exchange` — куда переслать сообщение при dead-letter-событии;
- `x-dead-letter-routing-key` — с каким routing key (по умолчанию сохраняется
  оригинальный).

Сообщение становится dead-lettered автоматически (без кода приложения) в трёх
случаях: `nack`/`reject` с `requeue=False`, истечение TTL, переполнение очереди
по `x-max-length`.

Задержку между попытками реализуют классическим RabbitMQ-паттерном
«retry-очередь с TTL»: вместо `time.sleep()` в коде consumer'а сообщение
публикуется в отдельную очередь `retry_queue` с TTL, равным нужной задержке
backoff, и без собственных consumer'ов — единственное, что происходит с
сообщениями в ней, это истечение TTL, после которого RabbitMQ сам
dead-letter'ит их дальше — но уже обратно в основной exchange, откуда они
снова попадают в основную очередь на повторную обработку.

```
   Основная очередь "orders_queue"
   (x-dead-letter-exchange = "retry_exchange")
        │
        ▼ nack(requeue=False) после ошибки обработки
   Exchange "retry_exchange"
        │
        ▼
   Queue "retry_queue_5s"   TTL = 5000ms, без consumer'ов
   (x-dead-letter-exchange = "orders_topic",
    x-dead-letter-routing-key = исходный routing key)
        │
        ▼ TTL истёк → RabbitMQ сам пересылает дальше
   Exchange "orders_topic"
        │
        ▼
   Queue "orders_queue"   ← сообщение снова доступно для обработки,
                            спустя ровно 5 секунд, без единой строки
                            sleep() в коде consumer'а

   Если лимит попыток (хранится, например, в заголовке x-death или
   в счётчике в самом сообщении) исчерпан — вместо повторной публикации
   в retry_exchange сообщение уходит в финальную DLQ-очередь для
   ручного разбора.
```

Разница по сути одна: у Kafka DLQ/retry — это соглашение на уровне приложения
(отдельные топики, ваш код решает, когда и куда переложить сообщение), у
RabbitMQ — встроенный механизм брокера (`x-dead-letter-exchange`, TTL), который
можно собрать почти без кода, чистой конфигурацией очередей.

## 5. Сценарии применения

**Event-driven взаимодействие микросервисов.** Сервис публикует событие домена
(`OrderCreated`, `PaymentCompleted`) не зная, кто на него подписан — Inventory,
Notification, Analytics могут подписываться и отписываться независимо. Если нужна
гибкая маршрутизация («только заказы из EU», «только отменённые») — удобнее
RabbitMQ с topic exchange. Если поток высокий и часть подписчиков должна уметь
переиграть историю с нуля (например, новый сервис аналитики строит агрегаты
с первого дня) — удобнее Kafka с его retention и replay.

**Централизованное логирование / агрегация логов.** Огромный, постоянный поток
записей от сотен инстансов приложений, который нужно надёжно и с высокой
пропускной способностью довезти до Elasticsearch/ClickHouse/S3, при этом порядок
между разными источниками не важен, а объём — десятки и сотни тысяч сообщений
в секунду. Это классический сценарий для Kafka: партиционирование по
source/host даёт параллелизм записи и чтения, retention позволяет «пересчитать»
индекс заново при сбое sink-коннектора, а строгая маршрутизация не нужна —
все читают один и тот же поток целиком.

**Real-time аналитика / стриминговая обработка.** Подсчёт метрик в скользящих
окнах, детекция аномалий, агрегация кликов — там, где важны throughput,
возможность нескольких независимых consumer-групп читать один и тот же поток
с разной скоростью (одна группа считает метрики онлайн, другая пишет сырые данные
в data lake), и возможность переиграть окно при исправлении бага в расчёте.
Это тоже домен Kafka (плюс Kafka Streams/Flink поверх него) — RabbitMQ для
таких объёмов и такой модели повторного чтения не предназначен.

**Task queue / фоновые задачи и RPC-подобные паттерны.** Когда нужно поставить
задачу в очередь («отправить письмо», «сгенерировать PDF», «обработать загруженный
файл») с гарантией, что задача будет выполнена ровно одним воркером, с приоритетами,
TTL на задачу и встроенным DLQ на случай неудачи — это классический RabbitMQ:
модель «одна задача — один consumer, удалить после ack» ложится сюда естественно,
а конфигурация ретраев и dead-letter'а не требует отдельной инфраструктуры,
как в случае Kafka.

## 6. Kafka vs RabbitMQ

Это не вопрос «что лучше» — это разные модели данных, оптимизированные под разные
задачи.

```
┌────────────────────┬───────────────────────────┬───────────────────────────┐
│ Критерий            │ Kafka                     │ RabbitMQ                  │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Модель данных        │ append-only лог,          │ очередь: сообщение        │
│                      │ сообщение хранится по     │ удаляется после ack       │
│                      │ retention независимо      │                            │
│                      │ от прочтения               │                            │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Throughput           │ очень высокий              │ высокий, но обычно ниже,  │
│                      │ (сотни МБ/с на кластер)    │ чем у Kafka на сравнимом  │
│                      │                            │ железе (за счёт per-msg   │
│                      │                            │ трекинга состояния)       │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Маршрутизация        │ базовая: топик + партиция  │ гибкая: direct/topic/     │
│                      │ по ключу                  │ fanout/headers exchange,  │
│                      │                            │ wildcard-биндинги         │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Replay (перечитать   │ да, встроенно — сместить   │ нет — сообщение физически │
│ историю заново)      │ committed offset назад     │ удалено после ack         │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Порядок сообщений    │ гарантирован строго внутри │ гарантирован в рамках     │
│                      │ партиции, не между ними    │ одной очереди с одним     │
│                      │                            │ consumer'ом               │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Per-message          │ нет "удалить одно          │ да — ack/nack на уровне   │
│ гарантии/состояние   │ сообщение навсегда", только│ каждого сообщения,        │
│                      │ сдвиг offset               │ приоритеты сообщений      │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ DLQ / retry          │ паттерн уровня приложения  │ встроенный механизм       │
│                      │ (отдельные топики)          │ (x-dead-letter-exchange)  │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Задержка (latency)   │ единицы миллисекунд при     │ обычно ниже при малых     │
│                      │ батчировании; батчирование  │ сообщениях и низкой       │
│                      │ ради throughput добавляет    │ нагрузке — нет           │
│                      │ микро-задержку               │ обязательного батчинга    │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Эксплуатационная      │ выше: KRaft/ZooKeeper,      │ ниже для небольших      │
│ сложность             │ партиции, репликация,       │ инсталляций — один узел  │
│                      │ ребалансировка — заметный   │ management UI поднимается│
│                      │ порог входа                 │ и настраивается быстро   │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Типичные кейсы        │ event streaming высокого   │ task queue, сложная       │
│                      │ объёма, агрегация логов,    │ маршрутизация событий,    │
│                      │ event sourcing, аналитика,   │ RPC-подобные паттерны,    │
│                      │ нужен replay                │ где не нужен масштаб Kafka│
└────────────────────┴───────────────────────────┴───────────────────────────┘
```

Конкретные ориентиры для выбора:

- **Нужно пересчитать историю с нуля** (новый consumer должен обработать всё,
  что произошло за последние 30 дней) — это Kafka; RabbitMQ такую историю
  физически не хранит.
- **Нужна гибкая маршрутизация по многим независимым критериям** (страна,
  тип события, приоритет) без раздувания числа топиков — это RabbitMQ
  с topic/headers exchange; в Kafka пришлось бы либо создавать топик под
  каждую комбинацию, либо фильтровать на стороне consumer'а вручную.
- **Объём — сотни тысяч сообщений в секунду с множеством независимых
  consumer-групп**, читающих один и тот же поток целиком с разной скоростью —
  Kafka: партиционирование и модель "не удалять после прочтения" именно под
  это спроектированы.
- **Нужна простая инсталляция для команды из нескольких человек**, без
  выделенной инфраструктурной экспертизы под Kafka-кластер — RabbitMQ
  поднимается и эксплуатируется существенно проще на таких масштабах.
- **Нужен встроенный, конфигурацией (а не кодом) реализуемый DLQ с TTL-based
  retry** — это нативная возможность RabbitMQ; в Kafka тот же результат
  потребует спроектировать и поддерживать отдельные retry/DLQ-топики руками.
- **Задача — классическая task queue** («выполнить эту работу ровно одним
  воркером, с приоритетом, TTL, dead-letter при неудаче») — RabbitMQ ближе
  к этой модели «из коробки»; Kafka как task queue использовать можно, но
  это не то, для чего она спроектирована (в Kafka нет понятия «удалить одно
  сообщение из середины партиции», только сдвиг offset).

Не редкость и комбинация: Kafka как центральная шина событий между
микросервисами (с retention и replay), а RabbitMQ — там, где конкретному
сервису нужна task-queue-модель с тонкой маршрутизацией и мгновенным DLQ
поверх уже полученных из Kafka событий.
