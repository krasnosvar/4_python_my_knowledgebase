# Kafka: партиции

## Kafka — лог событий, а не очередь

Kafka — это распределённый **лог событий** (append-only log), а не классическая
очередь. Сообщение, попав в Kafka, не удаляется после прочтения — оно хранится
согласно политике retention (например, 7 дней) независимо от того, прочитал его
кто-то или нет. Это ключевое архитектурное отличие определяет всё остальное:
партиции, консьюмер-группы, офсеты.

**Важно про слово «брокер».** В
[01_why_message_brokers.md](./01_why_message_brokers.md) «брокер сообщений» —
это вся система-посредник целиком. В терминах Kafka **брокер** — это один
отдельный сервер кластера Kafka. Кластер обычно состоит из нескольких таких
брокеров, и данные топиков распределены между ними. Дальше в уроках про Kafka
«брокер» означает именно отдельный сервер кластера.

## Что такое партиция

**Topic** в Kafka — это именованный поток событий (например, `orders`).
Физически topic разбит на одну или несколько **партиций** — независимых, строго
упорядоченных логов.

Партиции существуют по двум причинам:

- **Параллелизм.** Один диск/поток может писать и читать с ограниченной
  скоростью. Если partition одна — весь topic упирается в производительность
  одного лога. Разбив topic на N партиций, можно писать в них параллельно
  (разные партиции могут жить на разных брокерах) и параллельно же читать (см.
  [03_kafka_consumer_groups.md](./03_kafka_consumer_groups.md)).
- **Масштабирование.** Партиция — это единица распределения по брокерам
  кластера. Чем больше партиций, тем больше consumer'ов одновременно смогут
  работать с topic'ом и тем выше потенциальный throughput.

Расплата за это: **порядок сообщений гарантирован только внутри одной
партиции**, но не между партициями. Если для бизнес-логики важно, чтобы события
по одному пользователю обрабатывались строго по порядку (например, `created` не
должен обогнать `updated`), все события этого пользователя обязаны попадать в
одну и ту же партицию.

```
Topic "orders" (3 партиции):

  Partition 0:  [m0][m3][m6][m9] ...     ← порядок m0,m3,m6,m9 гарантирован
  Partition 1:  [m1][m4][m7]     ...     ← порядок m1,m4,m7 гарантирован
  Partition 2:  [m2][m5][m8]     ...     ← порядок m2,m5,m8 гарантирован

  Но: между Partition 0 и Partition 1 порядок НЕ гарантирован —
  m1 вполне может быть обработан раньше m0.
```

**Как сообщение попадает в конкретную партицию.** Если у сообщения задан ключ
(key), Kafka вычисляет `hash(key) % num_partitions` — все сообщения с одним и
тем же ключом всегда попадут в одну и ту же партицию (пока число партиций не
меняется). Если ключа нет, используется round-robin (или sticky-партиционер в
современных клиентах, который батчит подряд идущие сообщения в одну партицию для
эффективности, а затем переключается).

```
                 Есть key?
                     │
        ┌────────────┴────────────┐
       ДА                        НЕТ
        │                          │
        ▼                          ▼
hash(key) % N партиций      round-robin / sticky
        │                          │
        ▼                          ▼
Все сообщения с этим key    Сообщения размазываются
всегда идут в одну          по партициям без привязки
и ту же партицию            к порядку между собой

Пример: key="user-42" → всегда Partition 1
        key="user-7"  → всегда Partition 2
        без key        → Partition 0, 1, 2, 0, 1, 2 ...
```

Практический вывод: если нужна гарантия порядка «все события заказа №123
обработаны в порядке публикации» — используйте `order_id` как ключ. Если порядок
не важен (метрики, независимые события) — ключ не нужен, это даёт более
равномерное распределение нагрузки.
