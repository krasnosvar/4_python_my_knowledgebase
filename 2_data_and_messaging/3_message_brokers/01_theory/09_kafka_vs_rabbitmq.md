# Kafka vs RabbitMQ

Это не вопрос «что лучше» — это разные модели данных, оптимизированные под
разные задачи.

```
┌────────────────────┬───────────────────────────┬───────────────────────────┐
│ Критерий            │ Kafka                     │ RabbitMQ                  │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Модель данных        │ append-only лог,          │ очередь: сообщение        │
│                      │ сообщение хранится по     │ удаляется после ack       │
│                      │ retention независимо      │                            │
│                      │ от прочтения               │                            │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Throughput           │ очень высокий              │ высокий, но обычно ниже,  │
│                      │ (сотни МБ/с на кластер)    │ чем у Kafka на сравнимом  │
│                      │                            │ железе (за счёт per-msg   │
│                      │                            │ трекинга состояния)       │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Маршрутизация        │ базовая: топик + партиция  │ гибкая: direct/topic/     │
│                      │ по ключу                  │ fanout/headers exchange,  │
│                      │                            │ wildcard-биндинги         │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Replay (перечитать   │ да, встроенно — сместить   │ нет — сообщение физически │
│ историю заново)      │ committed offset назад     │ удалено после ack         │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Порядок сообщений    │ гарантирован строго внутри │ гарантирован в рамках     │
│                      │ партиции, не между ними    │ одной очереди с одним     │
│                      │                            │ consumer'ом               │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Per-message          │ нет "удалить одно          │ да — ack/nack на уровне   │
│ гарантии/состояние   │ сообщение навсегда", только│ каждого сообщения,        │
│                      │ сдвиг offset               │ приоритеты сообщений      │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ DLQ / retry          │ паттерн уровня приложения  │ встроенный механизм       │
│                      │ (отдельные топики)          │ (x-dead-letter-exchange)  │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Задержка (latency)   │ единицы миллисекунд при     │ обычно ниже при малых     │
│                      │ батчировании; батчирование  │ сообщениях и низкой       │
│                      │ ради throughput добавляет    │ нагрузке — нет           │
│                      │ микро-задержку               │ обязательного батчинга    │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Эксплуатационная      │ выше: KRaft/ZooKeeper,      │ ниже для небольших      │
│ сложность             │ партиции, репликация,       │ инсталляций — один узел  │
│                      │ ребалансировка — заметный   │ management UI поднимается│
│                      │ порог входа                 │ и настраивается быстро   │
├────────────────────┼───────────────────────────┼───────────────────────────┤
│ Типичные кейсы        │ event streaming высокого   │ task queue, сложная       │
│                      │ объёма, агрегация логов,    │ маршрутизация событий,    │
│                      │ event sourcing, аналитика,   │ RPC-подобные паттерны,    │
│                      │ нужен replay                │ где не нужен масштаб Kafka│
└────────────────────┴───────────────────────────┴───────────────────────────┘
```

Конкретные ориентиры для выбора:

- **Нужно пересчитать историю с нуля** (новый consumer должен обработать всё,
  что произошло за последние 30 дней) — это Kafka; RabbitMQ такую историю
  физически не хранит.
- **Нужна гибкая маршрутизация по многим независимым критериям** (страна,
  тип события, приоритет) без раздувания числа топиков — это RabbitMQ
  с topic/headers exchange; в Kafka пришлось бы либо создавать топик под
  каждую комбинацию, либо фильтровать на стороне consumer'а вручную.
- **Объём — сотни тысяч сообщений в секунду с множеством независимых
  consumer-групп**, читающих один и тот же поток целиком с разной скоростью —
  Kafka: партиционирование и модель "не удалять после прочтения" именно под
  это спроектированы.
- **Нужна простая инсталляция для команды из нескольких человек**, без
  выделенной инфраструктурной экспертизы под Kafka-кластер — RabbitMQ
  поднимается и эксплуатируется существенно проще на таких масштабах.
- **Нужен встроенный, конфигурацией (а не кодом) реализуемый DLQ с TTL-based
  retry** — это нативная возможность RabbitMQ; в Kafka тот же результат
  потребует спроектировать и поддерживать отдельные retry/DLQ-топики руками.
- **Задача — классическая task queue** («выполнить эту работу ровно одним
  воркером, с приоритетом, TTL, dead-letter при неудаче») — RabbitMQ ближе
  к этой модели «из коробки»; Kafka как task queue использовать можно, но
  это не то, для чего она спроектирована (в Kafka нет понятия «удалить одно
  сообщение из середины партиции», только сдвиг offset).

Не редкость и комбинация: Kafka как центральная шина событий между
микросервисами (с retention и replay), а RabbitMQ — там, где конкретному
сервису нужна task-queue-модель с тонкой маршрутизацией и мгновенным DLQ
поверх уже полученных из Kafka событий.
