# Упражнения: реляционные базы данных (PostgreSQL + Python)

Упражнения выполняются на стенде из `../02_examples/` (тот же
`docker-compose.yml`, та же `schema.sql`). Перед началом:

```bash
cd ../02_examples
docker compose up -d
docker compose exec -T postgres psql -U kb_user -d kb_shop -v ON_ERROR_STOP=1 < schema.sql
```

Задания идут от простого к сложному. Решения (полные, рабочие) лежат в
`../04_exercises_answers/` под теми же именами файлов -- заглядывайте туда
только после собственной попытки.

Файлы с `# TODO:` / `-- TODO:` -- это заготовки, их нужно дописать. Пустых
файлов "с нуля" в задании нет специально, чтобы не тратить время на
boilerplate вместо сути темы.

## Задание 04. Перевод денег с корректной транзакцией (Python)

Файл: `04_transfer.py`

В файле есть сигнатура функции `transfer_money(conn, from_name, to_name,
amount)` и подготовленные вспомогательные функции. Нужно дописать саму
функцию так, чтобы:

- списание и зачисление выполнялись в одной транзакции;
- при недостатке средств на счёте отправителя транзакция откатывалась
  целиком, и функция поднимала `InsufficientFundsError`, не изменив ни
  одной строки;
- если исключение произойдёт ПОСЛЕ списания, но ДО зачисления (в файле
  есть переключатель `simulate_crash_after_debit`, имитирующий сбой
  приложения на середине операции) -- после отлова исключения в базе не
  должно остаться частичного состояния (баланс отправителя должен
  вернуться к значению до попытки перевода).

В конце файла есть блок проверки (`if __name__ == "__main__":`), который
запускает несколько сценариев и печатает балансы до/после -- используйте
его, чтобы убедиться, что сумма по счетам всегда сохраняется.

## Задание 06 (опционально). Pessimistic vs optimistic locking

Файл: `06_locking.py`

Сценарий: несколько параллельных "покупателей" одновременно пытаются
списать 1 единицу товара со склада (таблица `products`, столбец `stock`).
Нужно реализовать два варианта одной и той же операции:

1. `decrement_stock_pessimistic` -- через `SELECT ... FOR UPDATE`: строка
   товара блокируется на время транзакции, конкурентные вызовы ждут своей
   очереди.
2. `decrement_stock_optimistic` -- через столбец `version`: читаем
   `stock` и `version`, затем `UPDATE ... WHERE id = %s AND version =
   %s`; если обновилось 0 строк -- значит, кто-то опередил, и вызывающий
   код должен повторить попытку (TODO: реализовать retry с ограничением
   числа попыток).

В обоих случаях нужно гарантировать инвариант: `stock` никогда не должен
уйти в минус, даже при гонке нескольких потоков/процессов (проверка есть
и на уровне Python, и как `CHECK (stock >= 0)` в схеме -- на случай, если
логика в коде где-то ошибётся).

В файле есть заготовка `run_concurrent_demo`, которая запускает несколько
потоков на общий товар и в конце печатает итоговый `stock` -- используйте
её, чтобы вручную проверить, что оба варианта дают корректный результат
(отличаться будет только поведение под нагрузкой: у пессимистичного
варианта потоки ждут друг друга, у оптимистичного -- часть из них уходит
в retry).
