# Индексы

## Зачем нужен индекс

Без индекса поиск строки по условию — это `Seq Scan`: PostgreSQL читает
таблицу целиком, строку за строкой, и проверяет условие на каждой. Для
таблицы из 200 000 строк это 200 000 сравнений даже если подходит одна
строка. Индекс — это отдельная структура данных, которая хранит
отсортированные (или хэшированные) значения столбца вместе со ссылкой
(`ctid`) на физическое место строки в таблице, что позволяет находить нужные
строки без полного перебора.

Два термина PostgreSQL, которые дальше будут встречаться:

- **heap** (куча) — основной файл таблицы, где лежат сами строки, без
  какого-либо порядка. Индекс — отдельный файл рядом с ним.
- **`ctid`** — физический адрес строки в heap: пара «номер страницы, номер
  строки на странице», например `(42,7)`. Индекс хранит именно `ctid`, чтобы
  по найденному значению сразу перейти к нужной строке в heap.

## B-Tree: как устроен и почему это индекс "по умолчанию"

B-Tree (сбалансированное B-дерево) — структура, в которой корневой узел
ссылается на внутренние узлы, а те — на листовые, при этом внутри каждого
узла ключи отсортированы:

```
                  [ 50 | 90 ]
                 /     |     \
          [10|30]   [60|75]  [95|120]
          /  |  \    /  |  \    /  |  \
        ... leaf nodes (отсортированы, связаны в цепочку) ...
```

Поиск спускается от корня к листу за `O(log n)` сравнений — для миллиона
строк это порядка 20 шагов вместо миллиона. Листовые узлы связаны в цепочку
(двусвязный список), поэтому B-Tree одинаково хорошо обслуживает:

- точное равенство (`= значение`);
- диапазоны (`>`, `<`, `BETWEEN`) — потому что данные физически
  отсортированы, можно "войти" в дерево в нужную точку и идти по цепочке
  листьев вправо/влево;
- сортировку (`ORDER BY`) — тот же обход по отсортированной цепочке листьев
  без отдельной сортировки в памяти;
- префиксный поиск (`LIKE 'абв%'`).

Цена индекса — не только память на диске (обычно 5-20% от размера таблицы
на индекс, у составных индексов больше), но и замедление записи: при каждом
`INSERT`/`UPDATE`/`DELETE` нужно поддерживать в актуальном состоянии не
только таблицу, но и каждый висящий на ней индекс. Чем больше индексов —
тем дороже запись. Это фундаментальный компромисс: индексы ускоряют чтение
за счёт замедления записи, поэтому индексировать стоит столбцы, которые
реально участвуют в `WHERE`/`JOIN`/`ORDER BY`, а не "всё подряд на всякий
случай".

## Hash-индекс: когда он выигрывает у B-Tree

Hash-индекс хранит не отсортированные ключи, а хэш от значения столбца —
это даёт `O(1)` (в среднем) доступ при точном совпадении, без необходимости
спускаться по дереву. Для чисто точечного поиска (`WHERE email = '...'`,
без диапазонов и сортировки) Hash-индекс теоретически быстрее B-Tree и
компактнее на очень длинных ключах, потому что хранит не сами значения,
а их хэш.

Но у Hash-индекса в PostgreSQL есть жёсткое ограничение — он **не
поддерживает** ни диапазонные условия (`>`, `<`, `BETWEEN`), ни `ORDER BY`,
ни `LIKE`: хэш-функция намеренно "перемешивает" порядок значений, так что
по хэшам нельзя восстановить исходную сортировку.

```sql
CREATE INDEX idx_users_email_hash ON users USING HASH (email);

-- Использует индекс:
SELECT * FROM users WHERE email = 'ivan@mail.ru';

-- НЕ может использовать hash-индекс (нужен B-Tree):
SELECT * FROM users WHERE email > 'i';
SELECT * FROM users ORDER BY email;
```

| Критерий                    | B-Tree                          | Hash                        |
|------------------------------|----------------------------------|------------------------------|
| Точное равенство (`=`)       | O(log n)                        | O(1) в среднем               |
| Диапазоны (`>`,`<`,`BETWEEN`)| да                               | нет                           |
| `ORDER BY` по индексу        | да                               | нет                           |
| `LIKE 'prefix%'`             | да                               | нет                           |
| Размер на диске              | умеренный                       | обычно компактнее на длинных ключах |
| Where использовать           | универсальный выбор по умолчанию | узкая ниша: только точечные lookup, когда диапазоны точно не понадобятся |

На практике в подавляющем большинстве случаев выбирают B-Tree просто потому,
что он покрывает и точечные, и диапазонные запросы, а прирост Hash-индекса
на чистом равенстве в современных версиях PostgreSQL (начиная с 10, когда
Hash-индексы стали WAL-логируемыми и безопасными для репликации) заметен
только на очень специфичных нагрузках. Явно выбирать Hash имеет смысл,
только когда точно известно, что диапазонные запросы и сортировка по этому
столбцу никогда не понадобятся.

## Составные и частичные индексы

Составной индекс покрывает несколько столбцов сразу и работает по принципу
"левого префикса": индекс `(city, status)` ускоряет фильтр по `city` и по
`(city, status)` вместе, но не по одному `status` без `city`.

```sql
CREATE INDEX idx_orders_city_status ON orders (city, status);

-- использует индекс полностью:
SELECT * FROM orders WHERE city = 'Moscow' AND status = 'paid';
-- использует индекс частично (только по city):
SELECT * FROM orders WHERE city = 'Moscow';
-- НЕ использует этот индекс:
SELECT * FROM orders WHERE status = 'paid';
```

Частичный индекс строится не по всей таблице, а только по строкам,
удовлетворяющим условию — он компактнее и дешевле в поддержке, если
основная масса запросов всегда фильтрует по этому же условию:

```sql
-- Если 95% запросов ищут только неотменённые заказы,
-- нет смысла тащить в индекс и отменённые
CREATE INDEX idx_orders_active ON orders (order_date)
WHERE status <> 'cancelled';
```
