# Блокировки

Когда два конкурентных процесса пытаются изменить одну и ту же строку,
нужен механизм, не позволяющий им "затоптать" правки друг друга. Есть два
принципиально разных подхода.

## Pessimistic locking: SELECT ... FOR UPDATE

Пессимистичный подход исходит из предположения "конфликты вероятны, лучше
заблокировать заранее". `SELECT ... FOR UPDATE` берёт блокировку строки на
уровне строки сразу при чтении — любая другая транзакция, пытающаяся
изменить (или тоже заблокировать через `FOR UPDATE`) ту же строку, будет
ждать, пока первая транзакция не завершится (`COMMIT`/`ROLLBACK`).

```sql
BEGIN;

SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- строка заблокирована: другая транзакция, делающая то же самое
-- по id=42, будет ждать здесь

UPDATE products SET stock = stock - 1 WHERE id = 42;

COMMIT;  -- блокировка снимается
```

Плюс — гарантированная корректность без необходимости обрабатывать retry:
конкурент просто подождёт своей очереди. Минус — при высокой конкуренции
за одни и те же строки (горячий товар на распродаже) транзакции выстраиваются
в очередь, и общая пропускная способность падает; если транзакция внутри
блокировки "зависла" (долгий внешний вызов, забытый `COMMIT`), все
конкуренты будут ждать её целиком.

## Optimistic locking: столбец версии

Оптимистичный подход исходит из обратного предположения: "конфликты редки,
не будем блокировать заранее — проверим на выходе". Для этого в таблицу
добавляют столбец `version` (или используют `updated_at`), и `UPDATE`
проверяет, что версия не изменилась с момента чтения:

```sql
-- Прочитали строку вместе с текущей версией
SELECT stock, version FROM products WHERE id = 42;
-- допустим, получили stock=10, version=5

-- Пытаемся обновить, проверяя, что version не "уехала"
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 42 AND version = 5;

-- Если другая транзакция успела обновить строку первой (version уже 6),
-- этот UPDATE затронет 0 строк. Приложение обязано это проверить
-- (rowcount == 0) и либо повторить операцию, либо вернуть ошибку конфликта.
```

Плюс — никаких блокировок, конкуренты не ждут друг друга, что даёт лучшую
пропускную способность при низкой вероятности реального конфликта. Минус —
логику "проверить rowcount и повторить" нужно писать руками в приложении, и
при высокой конкуренции за одну строку (тот же горячий товар) большая доля
попыток будет проигрывать гонку и уходить в retry, что при особо высокой
контенции может оказаться даже хуже, чем просто отстоять очередь в
пессимистичном варианте.

**Когда что выбирать:** пессимистичная блокировка лучше подходит, когда
конфликты часты и предсказуемы (списание со склада популярного товара,
финансовые операции с одним и тем же счётом), а транзакции короткие.
Оптимистичная — когда конфликты редки, а строки читаются и правятся долго
относительно частоты записи (формы редактирования, где пользователь
несколько минут смотрит на данные перед сохранением, и блокировать строку
всё это время неприемлемо).

## Deadlock: как возникает и как избежать

Взаимная блокировка (deadlock) возникает, когда транзакция A ждёт блокировку,
которую держит транзакция B, а B в это же время ждёт блокировку, которую
держит A — круг замкнулся, и без вмешательства обе будут ждать вечно.

```
Транзакция A:                    Транзакция B:
BEGIN;                           BEGIN;
UPDATE accounts                  UPDATE accounts
  SET ... WHERE id = 1;            SET ... WHERE id = 2;
  (заблокировала строку 1)         (заблокировала строку 2)

UPDATE accounts                  UPDATE accounts
  SET ... WHERE id = 2;            SET ... WHERE id = 1;
  (ждёт: строку 2 держит B)        (ждёт: строку 1 держит A)

              --- DEADLOCK ---
```

PostgreSQL умеет обнаруживать такие циклы (сервис deadlock detector) и сам
прерывает одну из транзакций с ошибкой `deadlock detected`, чтобы разорвать
цикл — но для приложения это всё равно означает потерянную транзакцию,
которую нужно перезапустить.

Лучший способ не допустить deadlock — соблюдать **единый порядок
блокировок** во всех местах кода: если несколько транзакций трогают строки
1 и 2, пусть все они всегда блокируют сначала строку с меньшим `id`, потом
с большим. Тогда цикл ожидания в принципе невозможен — кто-то один всегда
захватит первую блокировку раньше остальных и продолжит движение по тому
же маршруту, что и все.

```python
# Пример: перед переводом денег всегда лочим счета в порядке возрастания id,
# независимо от того, кто "откуда" и "куда" переводит
lo_id, hi_id = sorted([from_id, to_id])
cur.execute("SELECT * FROM accounts WHERE id = %s FOR UPDATE", (lo_id,))
cur.execute("SELECT * FROM accounts WHERE id = %s FOR UPDATE", (hi_id,))
```
