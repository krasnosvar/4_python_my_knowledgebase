# Транзакции и ACID

## Почему перевод денег без транзакции ломается

Возьмём классический пример: перевести 200 у Alice к Bob.

```sql
UPDATE accounts SET balance = balance - 200 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 200 WHERE name = 'Bob';
```

Если выполнить это как два независимых автокоммитных запроса (каждый
коммитится сам по себе сразу после выполнения), возникает целый набор
проблем:

1. **Сбой между запросами.** Приложение упало, оборвалась сеть, процесс
   перезапустился — ровно между первым и вторым `UPDATE`.
   Результат: у Alice списали 200, Bob не получил ничего. Деньги пропали.
2. **Гонка при параллельном чтении.** Другой запрос, читающий балансы между
   этими двумя `UPDATE`, увидит промежуточное состояние: у Alice уже минус
   200, у Bob ещё без изменений. Сумма по системе на мгновение "теряет" 200 —
   для отчёта, банковской сверки или дашборда это уже неверные данные.
3. **Нет отката при бизнес-ошибке.** Если бы мы сначала проверяли баланс
   Alice, а потом слали второй `UPDATE`, и уже после первого `UPDATE`
   выяснилось, что что-то пошло не так (например, счёт Bob заблокирован) —
   без транзакции механически "вернуть как было" нужно вручную и с риском
   ошибиться.

Транзакция решает всё это, оборачивая обе операции в одну атомарную единицу:

```sql
BEGIN;

UPDATE accounts SET balance = balance - 200 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 200 WHERE name = 'Bob';

COMMIT;
-- или ROLLBACK, если что-то пошло не так до COMMIT
```

Если между `BEGIN` и `COMMIT` произойдёт сбой (обрыв соединения, падение
процесса, `ROLLBACK` по ошибке в коде), PostgreSQL откатит оба `UPDATE`, как
будто их не было. Другие транзакции, работающие на уровне изоляции по
умолчанию (Read Committed), либо вообще не увидят изменений до `COMMIT`,
либо увидят их только целиком, разом — частично применённого перевода
снаружи транзакции не бывает.

## Что даёт каждая буква ACID

- **Atomicity (атомарность).** "Всё или ничего": набор операций внутри
  транзакции применяется либо целиком, либо не применяется вовсе. Если хотя
  бы одна операция не может выполниться (нарушение constraint, deadlock,
  явный `ROLLBACK`), откатываются вообще все изменения транзакции.
- **Consistency (согласованность).** После коммита база остаётся в состоянии,
  которое не нарушает объявленные ограничения — `CHECK`, `NOT NULL`,
  `FOREIGN KEY`, уникальные индексы. Это не "магия", а следствие того, что
  СУБД физически не даст закоммитить транзакцию, нарушающую constraint (в
  примере с переводом — `CHECK (balance >= 0)` не даст увести баланс в
  минус).
- **Isolation (изолированность).** Конкурентные транзакции не видят "грязных"
  промежуточных состояний друг друга настолько, насколько это гарантирует
  выбранный уровень изоляции (см. ниже — это не бинарное свойство,
  а спектр компромиссов).
- **Durability (долговечность).** После успешного `COMMIT` изменения
  переживут любой сбой сервера — отключение питания, падение процесса
  `postgres`. Гарантируется физической записью в WAL до подтверждения
  коммита клиенту (см. [10_wal.md](./10_wal.md)).

## Уровни изоляции и аномалии

Полная изоляция (Serializable) — самая безопасная, но и самая дорогая по
пропускной способности: транзакции по сути выполняются так, как будто идут
строго одна за другой. Более слабые уровни допускают определённые аномалии
ради параллелизма. Три классические аномалии:

- **Dirty read** — транзакция читает данные, которые другая транзакция ещё
  не закоммитила (и которые могут потом откатиться).
- **Non-repeatable read** — в рамках одной транзакции один и тот же `SELECT`
  по тому же условию возвращает разные значения строки, потому что между
  двумя чтениями другая транзакция успела закоммитить `UPDATE`.
- **Phantom read** — в рамках одной транзакции один и тот же диапазонный
  запрос (`WHERE age > 30`) второй раз возвращает другой НАБОР строк,
  потому что другая транзакция успела вставить/удалить подходящую строку.

Перед таблицей — один термин, который в ней встречается. **MVCC**
(Multiversion Concurrency Control, многоверсионность) — способ, которым
PostgreSQL изолирует транзакции без блокировки читателей: `UPDATE` не
перезаписывает строку на месте, а создаёт её новую версию, старая какое-то
время продолжает существовать. Каждая транзакция видит **снимок** (snapshot) —
те версии строк, которые были закоммичены к определённому моменту. Поэтому
читатель не ждёт писателя и никогда не видит его незакоммиченных изменений.

| Уровень изоляции   | Dirty read | Non-repeatable read | Phantom read | Комментарий для PostgreSQL |
|--------------------|:----------:|:--------------------:|:-------------:|------------------------------|
| Read Uncommitted   | возможен   | возможен             | возможен      | В PostgreSQL это синоним Read Committed — грязного чтения нет никогда |
| Read Committed     | нет        | возможен             | возможен      | Уровень по умолчанию в PostgreSQL |
| Repeatable Read    | нет        | нет                  | нет*          | В PostgreSQL реализован через MVCC-снимок на старте транзакции; классический phantom невозможен, но возможна ошибка сериализации при конфликте записи |
| Serializable       | нет        | нет                  | нет           | Полная сериализуемость (SSI); может завершить транзакцию ошибкой `could not serialize access`, требуется retry на уровне приложения |

Почему PostgreSQL вообще не даёт грязного чтения даже на "Read Uncommitted":
в основе лежит MVCC (см. определение выше) — читатели видят
согласованный снимок закоммиченных версий строк, а не "сырые" изменения
чужой незакоммиченной транзакции. Это отличает PostgreSQL от, например,
классического поведения некоторых других СУБД, где Read Uncommitted
действительно читает грязные данные.

Практический вывод для Python-разработчика: по умолчанию (Read Committed)
достаточно для подавляющего большинства CRUD-операций, но если код читает одну и
ту же строку дважды в рамках бизнес-транзакции и принимает решение на основе
обоих чтений (например, "прочитать остаток, посчитать, обновить"), либо
используйте `SELECT ... FOR UPDATE` (пессимистичная блокировка, см.
[07_locking.md](./07_locking.md)), либо повышайте уровень изоляции до Repeatable
Read/Serializable и оборачивайте операцию в retry-цикл на конфликт сериализации.

```python
# psycopg3: явно задать уровень изоляции для транзакции
import psycopg

with psycopg.connect(dsn) as conn:
    conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
    with conn.cursor() as cur:
        ...
    conn.commit()
```
