# Реляционная модель

## Таблицы и связи

Реляционная модель хранит данные в виде таблиц (отношений): фиксированный
набор столбцов (атрибутов) и произвольное число строк (кортежей). Смысл
модели — не просто "положить данные в клетки", а разложить предметную
область так, чтобы каждый факт хранился ровно в одном месте, и связи между
фактами выражались через значения, а не через физическое расположение.

Есть три базовых вида связей между таблицами:

**1:1 (один к одному).** Каждой строке таблицы A соответствует не более одной
строки таблицы B. На практике так выносят редко используемые или "тяжёлые"
столбцы в отдельную таблицу (например, `users` и `user_profiles_extended`
с большим текстовым полем биографии), либо разделяют данные по правам
доступа (публичная и приватная часть профиля).

```sql
CREATE TABLE users (
    id   SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE user_settings (
    user_id  INT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    theme    VARCHAR(20) DEFAULT 'light',
    locale   VARCHAR(10) DEFAULT 'ru'
);
```

Обратите внимание: `user_id` в `user_settings` — одновременно и первичный,
и внешний ключ. Именно это (а не просто "одна строка на другую") гарантирует
1:1: без `PRIMARY KEY`/`UNIQUE` на внешнем ключе получилась бы связь 1:N.

**1:N (один ко многим).** Самая частая связь: один автор написал много книг,
один клиент сделал много заказов. Внешний ключ живёт на стороне "многих".

```sql
CREATE TABLE authors (
    id   SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE books (
    id        SERIAL PRIMARY KEY,
    author_id INT NOT NULL REFERENCES authors(id) ON DELETE CASCADE,
    title     VARCHAR(255) NOT NULL
);
```

**N:M (многие ко многим).** Например, у книги может быть несколько авторов,
а у автора — несколько книг. Такая связь не выражается одним внешним ключом:
нужна промежуточная (association) таблица, где каждая строка — это одна
пара "автор-книга".

```sql
CREATE TABLE book_authors (
    book_id   INT NOT NULL REFERENCES books(id)   ON DELETE CASCADE,
    author_id INT NOT NULL REFERENCES authors(id) ON DELETE CASCADE,
    PRIMARY KEY (book_id, author_id)
);
```

Составной первичный ключ `(book_id, author_id)` тут не формальность: он же
работает как уникальный индекс, не давая добавить одну и ту же пару дважды,
и ускоряет JOIN в обе стороны.

## Первичные и внешние ключи

Первичный ключ (PRIMARY KEY) — это гарантия, что строку можно однозначно
идентифицировать и что таких идентификаторов не бывает два одинаковых
(PostgreSQL реализует это через уникальный индекс + `NOT NULL`). Внешний ключ
(FOREIGN KEY) — это ограничение целостности: значение в дочерней таблице
обязано существовать в родительской. Без FK ничего не мешает вставить в
`books.author_id` значение `9999`, которого нет в `authors` — база потеряет
связность, и рано или поздно это всплывёт в проде как "book без автора" в
отчёте.

`ON DELETE`-политика определяет, что делать с дочерними строками при удалении
родителя:

| Политика       | Поведение                                              | Когда уместна |
|----------------|---------------------------------------------------------|---------------|
| `CASCADE`      | Дочерние строки удаляются вместе с родителем             | Владение (книги без автора не имеют смысла) |
| `SET NULL`     | Внешний ключ обнуляется                                  | Связь необязательная (заказ без менеджера, если менеджер уволился) |
| `RESTRICT`/`NO ACTION` | Удаление родителя запрещено, пока есть дочерние строки | Нужно явное подтверждение, что зависимости учтены |

## Нормализация: зачем и до какой степени

Нормализация — это процесс разложения таблиц так, чтобы каждый факт
хранился один раз, а не дублировался в разных строках. Три первые
нормальные формы решают конкретные проблемы:

- **1NF** — каждая ячейка хранит одно атомарное значение (не список телефонов
  через запятую в одной колонке). Без этого нельзя нормально ни
  фильтровать, ни индексировать такие данные.
- **2NF** — устраняет частичную зависимость: неключевой атрибут должен
  зависеть от всего составного ключа, а не от его части.
- **3NF** — устраняет транзитивную зависимость: неключевой атрибут не должен
  зависеть от другого неключевого атрибута. Классический пример — если в
  таблице `orders` хранить `customer_name` и `customer_city` напрямую, то
  при переезде клиента в другой город придётся исправлять его во всех
  заказах, и при первой же забытой строке данные разъедутся.

Зачем это в реальности: нормализация убирает аномалии обновления (update
anomaly — правишь в одном месте, забываешь про дубликат), вставки (insert
anomaly — не можешь добавить факт, пока нет "хозяина" для него) и удаления
(delete anomaly — удаляя последний заказ клиента, случайно теряешь и данные
о самом клиенте, если они хранились только в строке заказа).

Цена нормализации — больше JOIN'ов при чтении. Поэтому на практике решение
всегда компромиссное:

- OLTP-нагрузка (много мелких транзакций, важна целостность) — нормализуют
  почти всегда до 3NF.
- Аналитика/отчётность (read-heavy, данные пакетно перезаписываются) —
  осознанно денормализуют (звезда/снежинка в хранилищах, материализованные
  представления, дублирующие "толстые" колонки) ради меньшего числа JOIN'ов.

Денормализация — это не "ошибка", а осознанный компромисс "скорость чтения
против риска рассинхронизации данных", который стоит применять точечно и
осознанно, а не по умолчанию.
