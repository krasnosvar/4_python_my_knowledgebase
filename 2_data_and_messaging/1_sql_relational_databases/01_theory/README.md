## 1. Реляционная модель <a name="relational-model"></a>

### Таблицы и связи

Реляционная модель хранит данные в виде таблиц (отношений): фиксированный
набор столбцов (атрибутов) и произвольное число строк (кортежей). Смысл
модели — не просто "положить данные в клетки", а разложить предметную
область так, чтобы каждый факт хранился ровно в одном месте, и связи между
фактами выражались через значения, а не через физическое расположение.

Есть три базовых вида связей между таблицами:

**1:1 (один к одному).** Каждой строке таблицы A соответствует не более одной
строки таблицы B. На практике так выносят редко используемые или "тяжёлые"
столбцы в отдельную таблицу (например, `users` и `user_profiles_extended`
с большим текстовым полем биографии), либо разделяют данные по правам
доступа (публичная и приватная часть профиля).

```sql
CREATE TABLE users (
    id   SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE user_settings (
    user_id  INT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    theme    VARCHAR(20) DEFAULT 'light',
    locale   VARCHAR(10) DEFAULT 'ru'
);
```

Обратите внимание: `user_id` в `user_settings` — одновременно и первичный,
и внешний ключ. Именно это (а не просто "одна строка на другую") гарантирует
1:1: без `PRIMARY KEY`/`UNIQUE` на внешнем ключе получилась бы связь 1:N.

**1:N (один ко многим).** Самая частая связь: один автор написал много книг,
один клиент сделал много заказов. Внешний ключ живёт на стороне "многих".

```sql
CREATE TABLE authors (
    id   SERIAL PRIMARY KEY,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE books (
    id        SERIAL PRIMARY KEY,
    author_id INT NOT NULL REFERENCES authors(id) ON DELETE CASCADE,
    title     VARCHAR(255) NOT NULL
);
```

**N:M (многие ко многим).** Например, у книги может быть несколько авторов,
а у автора — несколько книг. Такая связь не выражается одним внешним ключом:
нужна промежуточная (association) таблица, где каждая строка — это одна
пара "автор-книга".

```sql
CREATE TABLE book_authors (
    book_id   INT NOT NULL REFERENCES books(id)   ON DELETE CASCADE,
    author_id INT NOT NULL REFERENCES authors(id) ON DELETE CASCADE,
    PRIMARY KEY (book_id, author_id)
);
```

Составной первичный ключ `(book_id, author_id)` тут не формальность: он же
работает как уникальный индекс, не давая добавить одну и ту же пару дважды,
и ускоряет JOIN в обе стороны.

### Первичные и внешние ключи

Первичный ключ (PRIMARY KEY) — это гарантия, что строку можно однозначно
идентифицировать и что таких идентификаторов не бывает два одинаковых
(PostgreSQL реализует это через уникальный индекс + `NOT NULL`). Внешний ключ
(FOREIGN KEY) — это ограничение целостности: значение в дочерней таблице
обязано существовать в родительской. Без FK ничего не мешает вставить в
`books.author_id` значение `9999`, которого нет в `authors` — база потеряет
связность, и рано или поздно это всплывёт в проде как "book без автора" в
отчёте.

`ON DELETE`-политика определяет, что делать с дочерними строками при удалении
родителя:

| Политика       | Поведение                                              | Когда уместна |
|----------------|---------------------------------------------------------|---------------|
| `CASCADE`      | Дочерние строки удаляются вместе с родителем             | Владение (книги без автора не имеют смысла) |
| `SET NULL`     | Внешний ключ обнуляется                                  | Связь необязательная (заказ без менеджера, если менеджер уволился) |
| `RESTRICT`/`NO ACTION` | Удаление родителя запрещено, пока есть дочерние строки | Нужно явное подтверждение, что зависимости учтены |

### Нормализация: зачем и до какой степени

Нормализация — это процесс разложения таблиц так, чтобы каждый факт
хранился один раз, а не дублировался в разных строках. Три первые
нормальные формы решают конкретные проблемы:

- **1NF** — каждая ячейка хранит одно атомарное значение (не список телефонов
  через запятую в одной колонке). Без этого нельзя нормально ни
  фильтровать, ни индексировать такие данные.
- **2NF** — устраняет частичную зависимость: неключевой атрибут должен
  зависеть от всего составного ключа, а не от его части.
- **3NF** — устраняет транзитивную зависимость: неключевой атрибут не должен
  зависеть от другого неключевого атрибута. Классический пример — если в
  таблице `orders` хранить `customer_name` и `customer_city` напрямую, то
  при переезде клиента в другой город придётся исправлять его во всех
  заказах, и при первой же забытой строке данные разъедутся.

Зачем это в реальности: нормализация убирает аномалии обновления (update
anomaly — правишь в одном месте, забываешь про дубликат), вставки (insert
anomaly — не можешь добавить факт, пока нет "хозяина" для него) и удаления
(delete anomaly — удаляя последний заказ клиента, случайно теряешь и данные
о самом клиенте, если они хранились только в строке заказа).

Цена нормализации — больше JOIN'ов при чтении. Поэтому на практике решение
всегда компромиссное:

- OLTP-нагрузка (много мелких транзакций, важна целостность) — нормализуют
  почти всегда до 3NF.
- Аналитика/отчётность (read-heavy, данные пакетно перезаписываются) —
  осознанно денормализуют (звезда/снежинка в хранилищах, материализованные
  представления, дублирующие "толстые" колонки) ради меньшего числа JOIN'ов.

Денормализация — это не "ошибка", а осознанный компромисс "скорость чтения
против риска рассинхронизации данных", который стоит применять точечно и
осознанно, а не по умолчанию.

## 2. Транзакции и ACID <a name="acid"></a>

### Почему перевод денег без транзакции ломается

Возьмём классический пример: перевести 200 у Alice к Bob.

```sql
UPDATE accounts SET balance = balance - 200 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 200 WHERE name = 'Bob';
```

Если выполнить это как два независимых автокоммитных запроса (каждый
коммитится сам по себе сразу после выполнения), возникает целый набор
проблем:

1. **Сбой между запросами.** Приложение упало, оборвалась сеть, под
   перезапустили в Kubernetes — ровно между первым и вторым `UPDATE`.
   Результат: у Alice списали 200, Bob не получил ничего. Деньги пропали.
2. **Гонка при параллельном чтении.** Другой запрос, читающий балансы между
   этими двумя `UPDATE`, увидит промежуточное состояние: у Alice уже минус
   200, у Bob ещё без изменений. Сумма по системе на мгновение "теряет" 200 —
   для отчёта, банковской сверки или дашборда это уже неверные данные.
3. **Нет отката при бизнес-ошибке.** Если бы мы сначала проверяли баланс
   Alice, а потом слали второй `UPDATE`, и уже после первого `UPDATE`
   выяснилось, что что-то пошло не так (например, счёт Bob заблокирован) —
   без транзакции механически "вернуть как было" нужно вручную и с риском
   ошибиться.

Транзакция решает всё это, оборачивая обе операции в одну атомарную единицу:

```sql
BEGIN;

UPDATE accounts SET balance = balance - 200 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 200 WHERE name = 'Bob';

COMMIT;
-- или ROLLBACK, если что-то пошло не так до COMMIT
```

Если между `BEGIN` и `COMMIT` произойдёт сбой (обрыв соединения, падение
процесса, `ROLLBACK` по ошибке в коде), PostgreSQL откатит оба `UPDATE`, как
будто их не было. Другие транзакции, работающие на уровне изоляции по
умолчанию (Read Committed), либо вообще не увидят изменений до `COMMIT`,
либо увидят их только целиком, разом — частично применённого перевода
снаружи транзакции не бывает.

### Что даёт каждая буква ACID

- **Atomicity (атомарность).** "Всё или ничего": набор операций внутри
  транзакции применяется либо целиком, либо не применяется вовсе. Если хотя
  бы одна операция не может выполниться (нарушение constraint, deadlock,
  явный `ROLLBACK`), откатываются вообще все изменения транзакции.
- **Consistency (согласованность).** После коммита база остаётся в состоянии,
  которое не нарушает объявленные ограничения — `CHECK`, `NOT NULL`,
  `FOREIGN KEY`, уникальные индексы. Это не "магия", а следствие того, что
  СУБД физически не даст закоммитить транзакцию, нарушающую constraint (в
  примере с переводом — `CHECK (balance >= 0)` не даст увести баланс в
  минус).
- **Isolation (изолированность).** Конкурентные транзакции не видят "грязных"
  промежуточных состояний друг друга настолько, насколько это гарантирует
  выбранный уровень изоляции (см. ниже — это не бинарное свойство,
  а спектр компромиссов).
- **Durability (долговечность).** После успешного `COMMIT` изменения
  переживут любой сбой сервера — отключение питания, падение процесса
  `postgres`. Гарантируется физической записью в WAL до подтверждения
  коммита клиенту (см. раздел про WAL).

### Уровни изоляции и аномалии

Полная изоляция (Serializable) — самая безопасная, но и самая дорогая по
пропускной способности: транзакции по сути выполняются так, как будто идут
строго одна за другой. Более слабые уровни допускают определённые аномалии
ради параллелизма. Три классические аномалии:

- **Dirty read** — транзакция читает данные, которые другая транзакция ещё
  не закоммитила (и которые могут потом откатиться).
- **Non-repeatable read** — в рамках одной транзакции один и тот же `SELECT`
  по тому же условию возвращает разные значения строки, потому что между
  двумя чтениями другая транзакция успела закоммитить `UPDATE`.
- **Phantom read** — в рамках одной транзакции один и тот же диапазонный
  запрос (`WHERE age > 30`) второй раз возвращает другой НАБОР строк,
  потому что другая транзакция успела вставить/удалить подходящую строку.

| Уровень изоляции   | Dirty read | Non-repeatable read | Phantom read | Комментарий для PostgreSQL |
|--------------------|:----------:|:--------------------:|:-------------:|------------------------------|
| Read Uncommitted   | возможен   | возможен             | возможен      | В PostgreSQL это синоним Read Committed — грязного чтения нет никогда |
| Read Committed     | нет        | возможен             | возможен      | Уровень по умолчанию в PostgreSQL |
| Repeatable Read    | нет        | нет                  | нет*          | В PostgreSQL реализован через MVCC-снимок на старте транзакции; классический phantom невозможен, но возможна ошибка сериализации при конфликте записи |
| Serializable       | нет        | нет                  | нет           | Полная сериализуемость (SSI); может завершить транзакцию ошибкой `could not serialize access`, требуется retry на уровне приложения |

Почему PostgreSQL вообще не даёт грязного чтения даже на "Read Uncommitted":
в основе лежит MVCC (Multiversion Concurrency Control) — читатели видят
согласованный снимок закоммиченных версий строк, а не "сырые" изменения
чужой незакоммиченной транзакции. Это отличает PostgreSQL от, например,
классического поведения некоторых других СУБД, где Read Uncommitted
действительно читает грязные данные.

Практический вывод для Python-разработчика: по умолчанию (Read Committed)
достаточно для подавляющего большинства CRUD-операций, но если код читает
одну и ту же строку дважды в рамках бизнес-транзакции и принимает решение
на основе обоих чтений (например, "прочитать остаток, посчитать, обновить"),
либо используйте `SELECT ... FOR UPDATE` (пессимистичная блокировка, см.
раздел 6), либо повышайте уровень изоляции до Repeatable Read/Serializable
и оборачивайте операцию в retry-цикл на конфликт сериализации.

```python
# psycopg3: явно задать уровень изоляции для транзакции
import psycopg

with psycopg.connect(dsn) as conn:
    conn.isolation_level = psycopg.IsolationLevel.SERIALIZABLE
    with conn.cursor() as cur:
        ...
    conn.commit()
```

## 3. Индексы <a name="indexes"></a>

### Зачем нужен индекс

Без индекса поиск строки по условию — это `Seq Scan`: PostgreSQL читает
таблицу целиком, строку за строкой, и проверяет условие на каждой. Для
таблицы из 200 000 строк это 200 000 сравнений даже если подходит одна
строка. Индекс — это отдельная структура данных, которая хранит
отсортированные (или хэшированные) значения столбца вместе со ссылкой
(`ctid`) на физическое место строки в таблице, что позволяет находить нужные
строки без полного перебора.

### B-Tree: как устроен и почему это индекс "по умолчанию"

B-Tree (сбалансированное B-дерево) — структура, в которой корневой узел
ссылается на внутренние узлы, а те — на листовые, при этом внутри каждого
узла ключи отсортированы:

```
                  [ 50 | 90 ]
                 /     |     \
          [10|30]   [60|75]  [95|120]
          /  |  \    /  |  \    /  |  \
        ... leaf nodes (отсортированы, связаны в цепочку) ...
```

Поиск спускается от корня к листу за `O(log n)` сравнений — для миллиона
строк это порядка 20 шагов вместо миллиона. Листовые узлы связаны в цепочку
(двусвязный список), поэтому B-Tree одинаково хорошо обслуживает:

- точное равенство (`= значение`);
- диапазоны (`>`, `<`, `BETWEEN`) — потому что данные физически
  отсортированы, можно "войти" в дерево в нужную точку и идти по цепочке
  листьев вправо/влево;
- сортировку (`ORDER BY`) — тот же обход по отсортированной цепочке листьев
  без отдельной сортировки в памяти;
- префиксный поиск (`LIKE 'абв%'`).

Цена индекса — не только память на диске (обычно 5-20% от размера таблицы
на индекс, у составных индексов больше), но и замедление записи: при каждом
`INSERT`/`UPDATE`/`DELETE` нужно поддерживать в актуальном состоянии не
только таблицу, но и каждый висящий на ней индекс. Чем больше индексов —
тем дороже запись. Это фундаментальный компромисс: индексы ускоряют чтение
за счёт замедления записи, поэтому индексировать стоит столбцы, которые
реально участвуют в `WHERE`/`JOIN`/`ORDER BY`, а не "всё подряд на всякий
случай".

### Hash-индекс: когда он выигрывает у B-Tree

Hash-индекс хранит не отсортированные ключи, а хэш от значения столбца —
это даёт `O(1)` (в среднем) доступ при точном совпадении, без необходимости
спускаться по дереву. Для чисто точечного поиска (`WHERE email = '...'`,
без диапазонов и сортировки) Hash-индекс теоретически быстрее B-Tree и
компактнее на очень длинных ключах, потому что хранит не сами значения,
а их хэш.

Но у Hash-индекса в PostgreSQL есть жёсткое ограничение — он **не
поддерживает** ни диапазонные условия (`>`, `<`, `BETWEEN`), ни `ORDER BY`,
ни `LIKE`: хэш-функция намеренно "перемешивает" порядок значений, так что
по хэшам нельзя восстановить исходную сортировку.

```sql
CREATE INDEX idx_users_email_hash ON users USING HASH (email);

-- Использует индекс:
SELECT * FROM users WHERE email = 'ivan@mail.ru';

-- НЕ может использовать hash-индекс (нужен B-Tree):
SELECT * FROM users WHERE email > 'i';
SELECT * FROM users ORDER BY email;
```

| Критерий                    | B-Tree                          | Hash                        |
|------------------------------|----------------------------------|------------------------------|
| Точное равенство (`=`)       | O(log n)                        | O(1) в среднем               |
| Диапазоны (`>`,`<`,`BETWEEN`)| да                               | нет                           |
| `ORDER BY` по индексу        | да                               | нет                           |
| `LIKE 'prefix%'`             | да                               | нет                           |
| Размер на диске              | умеренный                       | обычно компактнее на длинных ключах |
| Where использовать           | универсальный выбор по умолчанию | узкая ниша: только точечные lookup, когда диапазоны точно не понадобятся |

На практике в подавляющем большинстве случаев выбирают B-Tree просто потому,
что он покрывает и точечные, и диапазонные запросы, а прирост Hash-индекса
на чистом равенстве в современных версиях PostgreSQL (начиная с 10, когда
Hash-индексы стали WAL-логируемыми и безопасными для репликации) заметен
только на очень специфичных нагрузках. Явно выбирать Hash имеет смысл,
только когда точно известно, что диапазонные запросы и сортировка по этому
столбцу никогда не понадобятся.

### Составные и частичные индексы

Составной индекс покрывает несколько столбцов сразу и работает по принципу
"левого префикса": индекс `(city, status)` ускоряет фильтр по `city` и по
`(city, status)` вместе, но не по одному `status` без `city`.

```sql
CREATE INDEX idx_orders_city_status ON orders (city, status);

-- использует индекс полностью:
SELECT * FROM orders WHERE city = 'Moscow' AND status = 'paid';
-- использует индекс частично (только по city):
SELECT * FROM orders WHERE city = 'Moscow';
-- НЕ использует этот индекс:
SELECT * FROM orders WHERE status = 'paid';
```

Частичный индекс строится не по всей таблице, а только по строкам,
удовлетворяющим условию — он компактнее и дешевле в поддержке, если
основная масса запросов всегда фильтрует по этому же условию:

```sql
-- Если 95% запросов ищут только неотменённые заказы,
-- нет смысла тащить в индекс и отменённые
CREATE INDEX idx_orders_active ON orders (order_date)
WHERE status <> 'cancelled';
```

## 4. EXPLAIN ANALYZE <a name="explain"></a>

`EXPLAIN` показывает план выполнения запроса — как планировщик собирается
его выполнить и во сколько это ему обходится по его собственной модели
"стоимости". `EXPLAIN ANALYZE` идёт дальше: реально выполняет запрос и
добавляет к оценкам фактические цифры (сколько строк, сколько времени).

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 777;
```

Пример вывода (форматирование упрощено для читаемости):

```
Seq Scan on orders  (cost=0.00..4553.00 rows=97 width=42)
                     (actual time=0.021..38.500 rows=103 loops=1)
  Filter: (customer_id = 777)
  Rows Removed by Filter: 199897
Planning Time: 0.112 ms
Execution Time: 38.541 ms
```

После `CREATE INDEX idx_orders_customer_id ON orders (customer_id);`:

```
Index Scan using idx_orders_customer_id on orders
                     (cost=0.29..8.45 rows=97 width=42)
                     (actual time=0.018..0.095 rows=103 loops=1)
  Index Cond: (customer_id = 777)
Planning Time: 0.098 ms
Execution Time: 0.121 ms
```

### Как читать основные узлы плана

- **Seq Scan** — последовательное чтение всей таблицы с фильтрацией "на
  лету". Нормально для маленьких таблиц или когда выборка почти вся
  таблица (тогда индекс не помог бы — читать всё равно пришлось бы
  почти всё). Тревожный сигнал — когда так читается большая таблица ради
  небольшой выборки.
- **Index Scan** — по индексу находятся конкретные `ctid` (адреса строк), и
  для каждого идёт отдельное обращение к самой таблице (heap), чтобы достать
  остальные столбцы. Быстро при небольшом числе совпадений.
- **Index Only Scan** — то же самое, но все нужные запросу столбцы уже есть
  в самом индексе, поэтому обращение к таблице не требуется вовсе (кроме
  проверки видимости строки через `visibility map`). Быстрее обычного
  Index Scan.
- **Bitmap Heap Scan** (обычно в паре с **Bitmap Index Scan**) — план сначала
  строит в памяти битовую карту подходящих страниц таблицы по индексу, а
  затем читает эти страницы таблицы уже последовательно в физическом
  порядке. Хорош, когда совпадений много (больше, чем оправдывает Index
  Scan построчно), но всё ещё не вся таблица.

### На что смотреть в цифрах

- **cost=0.29..8.45** — не миллисекунды, а условные единицы "стоимости"
  по внутренней модели планировщика: первое число — цена до получения
  первой строки, второе — до получения всех строк.
- **rows=97** (в cost) — оценка планировщика по статистике; **rows=103**
  (в actual) — что получилось по факту. Большое расхождение (например,
  оценка 10, а по факту 100 000) — прямой сигнал, что статистика устарела
  и планировщику нужен `ANALYZE`.
- **actual time=0.018..0.095** — реальное время в миллисекундах: от начала
  выполнения узла до первой строки и до последней.
- **loops=1** — сколько раз этот узел плана выполнялся (для узлов внутри
  вложенных циклов, `Nested Loop`, может быть больше 1 — тогда actual time
  нужно домножать на loops, чтобы понять реальный вклад узла).

### Почему индекс может не использоваться

1. **Несоответствие типов.** `WHERE customer_id = '777'` (строка) при
   целочисленном столбце может помешать использованию индекса или
   потребовать неявного приведения типа на каждой строке.
2. **Функция поверх индексированного столбца.** `WHERE lower(email) = ...`
   не использует обычный индекс на `email`, потому что индекс хранит
   исходные значения, а не результат функции. Решение — функциональный
   индекс: `CREATE INDEX ON users (lower(email));`.
3. **Низкая селективность.** Если условие отбирает половину таблицы,
   планировщик резонно посчитает Seq Scan дешевле, чем Index Scan вперемешку
   со случайными обращениями к диску по каждому совпадению.
4. **Устаревшая статистика.** Если после массовой загрузки данных не
   выполнить `ANALYZE`, планировщик будет опираться на старые (или пустые)
   оценки количества строк и может ошибочно выбрать Seq Scan вместо
   Index Scan или наоборот.

## 5. Проблема N+1 <a name="n-plus-one"></a>

N+1 — это когда код делает 1 запрос, чтобы получить список родительских
объектов, а затем ещё по одному дополнительному запросу **на каждый**
объект этого списка, чтобы получить связанные данные — итого `1 + N`
запросов там, где логически достаточно одного-двух.

```python
# Антипаттерн: N+1
authors = session.scalars(select(Author)).all()   # 1 запрос
for author in authors:
    print(author.name, len(author.books))          # ещё по 1 запросу на автора
```

Возникает это почти всегда из-за **ленивой загрузки** (lazy loading) связей
в ORM: обращение к `author.books` внутри цикла не "просто читает атрибут
объекта из памяти" — оно триггерит отдельный SQL-запрос в БД в этот самый
момент, и так на каждой итерации.

### Почему это незаметно в коде и заметно в проде

На локальной базе с десятком авторов разница между 1 и 11 запросами не
видна на глаз. В проде с десятками тысяч авторов это дополнительные
десятки тысяч round-trip'ов к базе — каждый со своей сетевой задержкой,
даже если сам SQL-запрос простой. Именно поэтому N+1 — классическая
"тихая" проблема производительности: код проходит ревью и тесты (там мало
данных), а в проде превращается в деградацию под нагрузкой.

### Как обнаружить

- Включить логирование SQL (`echo=True` в SQLAlchemy) или `django-debug-toolbar`
  в Django и визуально посчитать количество запросов на один HTTP-запрос.
- Программный счётчик через события драйвера — например, слушатель
  `before_cursor_execute` в SQLAlchemy (см. `02_examples/04_n_plus_one_problem.py`):
  так число запросов можно проверять автоматически в тестах, а не глазами.
- APM/трейсинг (Sentry, Datadog) в проде — характерный паттерн "десятки
  однотипных SELECT подряд внутри одной транзакции/запроса".

### Как исправить: eager loading

Идея исправления одна — заранее сказать ORM, что связанные данные тоже
понадобятся, чтобы она забрала их за один-два запроса вместо N.

В SQLAlchemy 2.0 есть два основных варианта, у каждого свой компромисс:

```python
from sqlalchemy.orm import selectinload, joinedload

# selectinload: 2 запроса всего (авторы, затем IN (...) по их id для книг).
# Хорош, когда "хвост" (books) большой, а строк в "голове" (authors) немного:
# не размножает строки JOIN'ом.
stmt = select(Author).options(selectinload(Author.books))

# joinedload: 1 запрос через LEFT JOIN.
# Хорош для связей 1:1 или небольших 1:N, но при 1:N дублирует строки
# родителя в результате JOIN (нужен .unique() при чтении).
stmt = select(Author).options(joinedload(Author.books))
```

Для контраста: в Django ORM та же идея выражается через
`Author.objects.prefetch_related("books")` (аналог `selectinload` — отдельный
запрос + склейка в Python) и `select_related("publisher")` (аналог
`joinedload` — один SQL-запрос через JOIN, годится для `ForeignKey`/`OneToOne`
в прямом направлении).

Итог: eager loading не бесплатен (тянет больше данных за раз, требует
заранее знать, что понадобится), но почти всегда дешевле, чем N лишних
round-trip'ов к базе.

## 6. Блокировки <a name="locking"></a>

Когда два конкурентных процесса пытаются изменить одну и ту же строку,
нужен механизм, не позволяющий им "затоптать" правки друг друга. Есть два
принципиально разных подхода.

### Pessimistic locking: SELECT ... FOR UPDATE

Пессимистичный подход исходит из предположения "конфликты вероятны, лучше
заблокировать заранее". `SELECT ... FOR UPDATE` берёт блокировку строки на
уровне строки сразу при чтении — любая другая транзакция, пытающаяся
изменить (или тоже заблокировать через `FOR UPDATE`) ту же строку, будет
ждать, пока первая транзакция не завершится (`COMMIT`/`ROLLBACK`).

```sql
BEGIN;

SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- строка заблокирована: другая транзакция, делающая то же самое
-- по id=42, будет ждать здесь

UPDATE products SET stock = stock - 1 WHERE id = 42;

COMMIT;  -- блокировка снимается
```

Плюс — гарантированная корректность без необходимости обрабатывать retry:
конкурент просто подождёт своей очереди. Минус — при высокой конкуренции
за одни и те же строки (горячий товар на распродаже) транзакции выстраиваются
в очередь, и общая пропускная способность падает; если транзакция внутри
блокировки "зависла" (долгий внешний вызов, забытый `COMMIT`), все
конкуренты будут ждать её целиком.

### Optimistic locking: столбец версии

Оптимистичный подход исходит из обратного предположения: "конфликты редки,
не будем блокировать заранее — проверим на выходе". Для этого в таблицу
добавляют столбец `version` (или используют `updated_at`), и `UPDATE`
проверяет, что версия не изменилась с момента чтения:

```sql
-- Прочитали строку вместе с текущей версией
SELECT stock, version FROM products WHERE id = 42;
-- допустим, получили stock=10, version=5

-- Пытаемся обновить, проверяя, что version не "уехала"
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 42 AND version = 5;

-- Если другая транзакция успела обновить строку первой (version уже 6),
-- этот UPDATE затронет 0 строк. Приложение обязано это проверить
-- (rowcount == 0) и либо повторить операцию, либо вернуть ошибку конфликта.
```

Плюс — никаких блокировок, конкуренты не ждут друг друга, что даёт лучшую
пропускную способность при низкой вероятности реального конфликта. Минус —
логику "проверить rowcount и повторить" нужно писать руками в приложении, и
при высокой конкуренции за одну строку (тот же горячий товар) большая доля
попыток будет проигрывать гонку и уходить в retry, что при особо высокой
контенции может оказаться даже хуже, чем просто отстоять очередь в
пессимистичном варианте.

**Когда что выбирать:** пессимистичная блокировка лучше подходит, когда
конфликты часты и предсказуемы (списание со склада популярного товара,
финансовые операции с одним и тем же счётом), а транзакции короткие.
Оптимистичная — когда конфликты редки, а строки читаются и правятся долго
относительно частоты записи (формы редактирования, где пользователь
несколько минут смотрит на данные перед сохранением, и блокировать строку
всё это время неприемлемо).

### Deadlock: как возникает и как избежать

Взаимная блокировка (deadlock) возникает, когда транзакция A ждёт блокировку,
которую держит транзакция B, а B в это же время ждёт блокировку, которую
держит A — круг замкнулся, и без вмешательства обе будут ждать вечно.

```
Транзакция A:                    Транзакция B:
BEGIN;                           BEGIN;
UPDATE accounts                  UPDATE accounts
  SET ... WHERE id = 1;            SET ... WHERE id = 2;
  (заблокировала строку 1)         (заблокировала строку 2)

UPDATE accounts                  UPDATE accounts
  SET ... WHERE id = 2;            SET ... WHERE id = 1;
  (ждёт: строку 2 держит B)        (ждёт: строку 1 держит A)

              --- DEADLOCK ---
```

PostgreSQL умеет обнаруживать такие циклы (сервис deadlock detector) и сам
прерывает одну из транзакций с ошибкой `deadlock detected`, чтобы разорвать
цикл — но для приложения это всё равно означает потерянную транзакцию,
которую нужно перезапустить.

Лучший способ не допустить deadlock — соблюдать **единый порядок
блокировок** во всех местах кода: если несколько транзакций трогают строки
1 и 2, пусть все они всегда блокируют сначала строку с меньшим `id`, потом
с большим. Тогда цикл ожидания в принципе невозможен — кто-то один всегда
захватит первую блокировку раньше остальных и продолжит движение по тому
же маршруту, что и все.

```python
# Пример: перед переводом денег всегда лочим счета в порядке возрастания id,
# независимо от того, кто "откуда" и "куда" переводит
lo_id, hi_id = sorted([from_id, to_id])
cur.execute("SELECT * FROM accounts WHERE id = %s FOR UPDATE", (lo_id,))
cur.execute("SELECT * FROM accounts WHERE id = %s FOR UPDATE", (hi_id,))
```

## 7. Репликация <a name="replication"></a>

### Master-replica (асинхронная)

В типичной схеме есть один узел на запись (primary/master) и один или
несколько узлов только на чтение (replica), которые непрерывно применяют
у себя поток изменений, полученный от primary. В асинхронном режиме
primary подтверждает `COMMIT` клиенту, не дожидаясь, пока реплика
подтвердит применение изменений у себя — отсюда возможен **replication
lag**: реплика в любой момент времени немного "отстаёт" от primary.

```
Primary  ---(поток WAL)--->  Replica
  |                              |
  COMMIT подтверждён клиенту     |
  клиенту сразу                 применяет изменения
                                 чуть позже (лаг: мс - секунды,
                                 иногда больше при нагрузке/сети)
```

Лаг возникает из-за задержки сети, нагрузки на реплику (она параллельно
обслуживает читающие запросы) или отставания в применении WAL, если поток
изменений на primary временно превышает скорость применения на реплике.

**К чему это приводит:** stale reads — клиент записал данные на primary и
сразу же читает их с реплики, но реплика ещё не успела применить эту
запись, и клиент видит старое состояние. Классический сценарий: "сохранил
профиль -> тут же обновил страницу -> увидел старые данные", если чтение
профиля идёт с реплики.

**Паттерн read replicas.** Несмотря на лаг, реплики — стандартный способ
масштабировать чтение: пишущая нагрузка идёт на единственный primary, а
читающая (обычно её на порядок больше) размазывается по нескольким
репликам. Работает хорошо для нагрузок, терпимых к небольшой несвежести
данных (списки, витрины, отчёты), и требует аккуратности там, где нужна
свежесть сразу после записи — такие запросы явно направляют на primary
("read your own writes"), а не на реплику.

### Synchronous vs asynchronous: компромисс

Синхронная репликация решает проблему лага ценой задержки записи: primary
не подтверждает `COMMIT` клиенту, пока хотя бы одна (настраиваемо — сколько)
синхронная реплика не подтвердит получение данных. Это даёт нулевую потерю
данных при отказе primary (реплика гарантированно не отстаёт на момент
коммита), но каждый `COMMIT` теперь ждёт сетевого round-trip до реплики —
это дороже по латентности и уязвимее к недоступности реплики (если
единственная синхронная реплика недоступна, запись может встать).
Асинхронная репликация — обратный компромисс: быстрее запись, но при
отказе primary до применения последних изменений на реплике эти последние
транзакции могут быть потеряны при переключении (failover). В PostgreSQL
можно настроить гибрид (`synchronous_commit`, `synchronous_standby_names`)
и держать синхронной только часть реплик, балансируя между надёжностью и
задержкой под конкретную нагрузку.

## 8. WAL (Write-Ahead Log) <a name="wal"></a>

### Зачем нужен WAL

Write-Ahead Log — это принцип "прежде чем менять данные на диске, запиши
намерение об этом изменении в отдельный последовательный лог". PostgreSQL
не переписывает страницы данных на диске при каждом `UPDATE` немедленно —
это было бы дорого (случайная запись по всему файлу данных). Вместо этого
он дописывает компактную запись в WAL-файл (последовательная запись —
дёшево), и только эту запись обязан гарантированно сохранить на диск перед
тем, как подтвердить `COMMIT` клиенту.

```
UPDATE в транзакции:
  1. Изменение применяется к странице данных в разделяемой памяти (shared buffers)
  2. Запись об этом изменении дописывается в WAL
  3. WAL физически сбрасывается на диск (fsync) --> COMMIT можно подтвердить клиенту
  4. Сама страница данных на диске обновляется ПОЗЖЕ, во время checkpoint
     (не обязательно сразу после коммита)
```

### Durability и восстановление после сбоя

Если сервер упадёт (отключение питания) между шагом 3 и физической записью
страницы данных на диск, данные страницы на диске могут быть ещё старыми —
но это не проблема, потому что при старте PostgreSQL сначала проигрывает
(replay) WAL с последней контрольной точки (checkpoint) и досоздаёт все
изменения, которые были подтверждены клиентам, но ещё не долетели до
основных файлов данных. Именно эта операция (WAL replay) при старте
и обеспечивает Durability: раз `COMMIT` был подтверждён, значит
соответствующая запись гарантированно уже физически лежит в WAL на диске,
и её не потеряет никакой сбой процесса или отключение питания (при условии,
что сам диск/fsync не соврал).

### Checkpoint

Checkpoint — это момент, когда PostgreSQL гарантированно сбрасывает на
диск все "грязные" (изменённые в памяти, но ещё не записанные) страницы
данных, и после этого WAL до этой точки больше не нужен для восстановления
— его можно переиспользовать/архивировать. Чем реже checkpoint, тем больше
WAL-файлов копится и тем дольше будет replay при аварийном восстановлении,
но тем меньше случайной записи на диск в моменте; чем чаще — тем короче
recovery, но выше постоянная фоновая нагрузка на диск. Это ещё один
настраиваемый компромисс (`checkpoint_timeout`, `max_wal_size`).

### Связь WAL с репликацией

Физическая репликация в PostgreSQL (`streaming replication`) — это, по
сути, непрерывная трансляция того же самого потока WAL с primary на
реплику: реплика получает те же WAL-записи, что записал бы на диск
primary, и проигрывает (replay) их у себя, поддерживая свою копию данных в
актуальном состоянии. Поэтому реплика — это, концептуально, узел, который
непрерывно выполняет ту же процедуру восстановления после сбоя (WAL
replay), что и primary делал бы после падения, только без остановки, в
режиме реального времени. Отсюда и природа replication lag (раздел 7): это
буквально задержка между тем, когда WAL-запись появилась на primary, и
когда реплика успела её принять и проиграть.

## 9. Планировщик запросов <a name="planner"></a>

### Cost-based optimizer

PostgreSQL не выполняет запрос "как написано" — сначала планировщик строит
несколько альтернативных планов выполнения (какой индекс использовать,
в каком порядке соединять таблицы, `Nested Loop` или `Hash Join`) и выбирает
план с наименьшей оценочной стоимостью (`cost`). Стоимость считается по
модели, учитывающей: количество строк в таблицах, селективность условий,
случайные vs последовательные обращения к диску, доступную память
(`work_mem`) и текущие настройки стоимости (`random_page_cost`,
`seq_page_cost` и т.д.).

### Почему один и тот же запрос выполняется по-разному на разном объёме данных

Оценка "количество строк" берётся не из реального подсчёта (это было бы
дорого делать на каждый запрос), а из статистики, которую PostgreSQL
собирает заранее и хранит в `pg_statistic` — гистограммы распределения
значений, количество уникальных значений (`n_distinct`), процент `NULL`.
Именно поэтому:

- на маленькой таблице (скажем, 500 строк) планировщик часто предпочитает
  `Seq Scan` даже при наличии индекса — прочитать всю таблицу целиком
  дешевле, чем "прыгать" по диску между индексом и таблицей на каждую
  строку;
- на большой таблице (200 000+ строк) тот же по тексту запрос с тем же
  индексом уже выберет `Index Scan`/`Bitmap Heap Scan`, потому что
  выигрыш от избегания полного скана начинает перевешивать накладные
  расходы на обращения по индексу;
- если статистика устарела (например, сразу после массовой загрузки
  данных, до автовакуума), планировщик может принять решение на основе
  старых пропорций и выбрать неоптимальный план для актуального объёма
  данных.

### Зачем ANALYZE и автовакуум

`ANALYZE` явно пересчитывает статистику по таблице (распределение значений,
число строк, селективность столбцов) и обновляет `pg_statistic` — без этого
шага планировщик работает по устаревшим или отсутствующим данным.
Автовакуум (`autovacuum`) в фоне делает две вещи одновременно: убирает
"мёртвые" версии строк, оставшиеся от MVCC после `UPDATE`/`DELETE` (без
этого таблица и индексы разрастаются мёртвым весом — это называется
bloat), и по мере накопления изменений сам инициирует `ANALYZE`, чтобы
статистика не расходилась слишком сильно с реальностью. Поэтому в проде
типичная рекомендация — не отключать автовакуум "для производительности":
без него планировщик со временем начинает принимать решения по всё более
неверным данным, и симптомы (внезапно "поглупевшие" планы на запросах,
которые раньше работали быстро) проявляются не сразу, а с накоплением
изменений.

Практический вывод: если после массовой загрузки данных (например, той
самой вставки 200 000 строк через `generate_series` для примеров в этом
разделе) `EXPLAIN ANALYZE` показывает неожиданно "глупый" план — первое,
что стоит проверить, это выполнялся ли `ANALYZE` по таблице, а не сразу
чинить индексы или переписывать запрос.
