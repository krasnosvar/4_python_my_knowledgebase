# Redis — шпаргалка

Подробности — в [01_theory/](./01_theory/README.md). Команды — в синтаксисе
`redis-cli`; ⚠️ — частая ловушка.

## Когда Redis, а когда нет

Подробнее: [01_what_is_redis.md](./01_theory/01_what_is_redis.md).

| Подходит | Не подходит |
| :--- | :--- |
| Кеш рядом с основной БД | Основное хранилище данных, которые нельзя терять |
| Сессии, счётчики, rate-limit окна | Датасет больше RAM |
| Лидерборды, «последние N» | JOIN, произвольная фильтрация, агрегации как в SQL |

| Персистентность | Что теряется при падении |
| :--- | :--- |
| RDB (снимок) | Всё после последнего снимка |
| AOF (журнал команд) | Обычно не больше секунды записей; файл надо сжимать |

- ⚠️ Команды выполняются в одном потоке: `KEYS *` или `SORT` на большой
  коллекции блокирует всех клиентов.

## Структуры данных

Подробнее: [02_data_structures.md](./01_theory/02_data_structures.md).

| Тип | Команды | Для чего |
| :--- | :--- | :--- |
| String | `SET k v` · `GET k` · `INCR k` · `INCRBY k 10` · `SETEX k 1800 v` | Кеш ответа целиком, счётчики, флаги |
| Hash | `HSET user:100 name "Alice" age 25` · `HGET` · `HGETALL` · `HINCRBY user:100 login_count 1` | Объект с атомарным обновлением одного поля |
| List | `LPUSH` · `RPOP` · `BRPOP q 5` · `LRANGE k 0 9` · `LTRIM k 0 9` | Простая очередь, «последние N» (`LPUSH` + `LTRIM`) |
| Set | `SADD` · `SISMEMBER` (O(1)) · `SMEMBERS` · `SINTER a b` | Теги, уникальные посетители, пересечения |
| Sorted Set | `ZADD lb 1100 alice` · `ZREVRANGE lb 0 2 WITHSCORES` · `ZREVRANK` · `ZINCRBY` · `ZREMRANGEBYSCORE` · `ZCARD` | Лидерборд (score = очки), sliding window (score = timestamp) |

- ⚠️ JSON в String: обновление поля = GET → parse → SET, не атомарно; для
  частичных обновлений берите Hash.

## TTL и eviction

Подробнее: [03_ttl_expiration_eviction.md](./01_theory/03_ttl_expiration_eviction.md).

| Задача | Команда / настройка |
| :--- | :--- |
| Значение с TTL | `SET k v EX 3600` (redis-py: `r.set(k, v, ex=3600)`) |
| Добавить TTL существующему ключу | `EXPIRE k 60` |
| Ограничить память | `maxmemory 2gb` + `maxmemory-policy allkeys-lru` |

| `maxmemory-policy` | Вытесняет | Когда |
| :--- | :--- | :--- |
| `noeviction` (по умолчанию) | Ничего, запись → ошибка | Есть данные, которые нельзя терять молча |
| `allkeys-lru` | Давно не использованный ключ | Дефолт для инстанса «только кеш» |
| `allkeys-lfu` | Редко используемый ключ | Горячие ключи вымываются редкими сканами |
| `volatile-lru` / `volatile-lfu` | То же, только ключи с TTL | Кеш + данные без TTL в одном инстансе |
| `volatile-ttl` | Ключ с наименьшим оставшимся TTL | То же, предсказуемый порядок |
| `allkeys-random` | Случайный ключ | Доступ равномерно случаен |

- ⚠️ Истёкший ключ удаляется лениво (при обращении) и выборочно (активный
  цикл раз в 100 мс) — не точно в момент истечения TTL.
- ⚠️ `volatile-*` без ключей с TTL ведёт себя как `noeviction`.

## Паттерны кеширования

Подробнее: [04_caching_patterns.md](./01_theory/04_caching_patterns.md).

| Паттерн | Запись | Плюс | Минус | Когда |
| :--- | :--- | :--- | :--- | :--- |
| Cache-aside | Приложение: MISS → БД → `SET ... ex=TTL` | Кеш можно потерять целиком | Устаревание в окне TTL, dogpile | Дефолт для веб-приложений |
| Write-through | Одновременно в кеш и БД | Кеш всегда свежий | Запись дороже, кешируется непрочитанное | Чтение сразу после записи критично |
| Write-behind | Сначала в кеш, в БД — асинхронно батчами | Быстрая запись, батчинг | Потеря данных при падении сбрасывающего процесса | Счётчики, аналитика — не деньги |

| Защита от dogpile (thundering herd) | Как |
| :--- | :--- |
| Jitter в TTL | `ex=3600 + random.randint(-300, 300)` |
| Лок на пересчёт | `SET lock:product:42 1 NX EX 10` — пересчитывает только получивший лок |
| Упреждающее обновление (XFetch) | Пересчитать с вероятностью, растущей к концу TTL |

## Инвалидация

Подробнее: [05_cache_invalidation.md](./01_theory/05_cache_invalidation.md).

| Стратегия | Как | Минус |
| :--- | :--- | :--- |
| По TTL | `SET k v EX 3600` | Данные устаревают на всё окно TTL |
| Delete-on-write | `UPDATE` в БД → `DEL k` | Каждый путь записи обязан удалять ключ |
| По событию | Событие об изменении → каждый инстанс чистит свою копию | Нужна доставка событий, дубли/потери |

- ⚠️ При записи — `DEL`, а не `SET` нового значения: проще и не проигрывает гонку.
- ⚠️ Гонка читателя и писателя может вернуть старое значение в кеш после `DEL` —
  TTL обязателен даже при delete-on-write.

## Rate limiting

Подробнее: [06_rate_limiting.md](./01_theory/06_rate_limiting.md).

| | Fixed window | Sliding window (ZSet) |
| :--- | :--- | :--- |
| Команды | `INCR ratelimit:{user}:{minute}` + `EXPIRE k 60` при значении 1 | `ZREMRANGEBYSCORE k -inf now-60` · `ZADD k now req_id` · `ZCARD k` · `EXPIRE k 60` |
| Точность | До 2× лимита на границе окна | Точная |
| Стоимость | O(1), одно число | O(log N), элемент на запрос |
| Когда | Защита от случайного злоупотребления | Платный API, брутфорс, DDoS |

## Очередь и Pub/Sub

Подробнее: [07_redis_as_queue.md](./01_theory/07_redis_as_queue.md),
[08_pubsub.md](./01_theory/08_pubsub.md).

| Задача | Как | Гарантии |
| :--- | :--- | :--- |
| Простая очередь внутри сервиса | `LPUSH q msg` / `BRPOP q 5` | Нет ack: упал воркер после `BRPOP` — сообщение потеряно |
| Лог с consumer groups | Redis Streams: `XADD` / `XREADGROUP` | Частично закрывает разрыв с брокерами |
| Разослать всем подписанным сейчас | `PUBLISH ch msg` / `SUBSCRIBE ch` | Fire-and-forget: нет подписчиков — сообщение пропало |
| Нужны ack, replay, fan-out группами | Kafka / RabbitMQ — [../3_message_brokers/](../3_message_brokers/) | — |
