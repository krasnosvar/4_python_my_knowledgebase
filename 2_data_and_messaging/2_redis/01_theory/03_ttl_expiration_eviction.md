# TTL: expiration и eviction

Для кеша TTL — не опция, а основной механизм: он гарантирует, что забытый
ключ рано или поздно освободит память и не будет отдавать данные вечно.

## Как Redis узнаёт, что ключ "истёк"

Redis не заводит таймер на каждый ключ с TTL (миллионы таймеров — это сама
по себе дорогая структура). Вместо этого работают два независимых
механизма одновременно:

```
1. Lazy expiration (ленивое удаление)
   ┌───────────────────────────────────────────┐
   │ Клиент делает GET/любую команду над ключом │
   │        │                                   │
   │        ▼                                   │
   │  TTL этого ключа истёк?                    │
   │   ├─ да  → удалить ключ, вести себя так,   │
   │   │        будто его не было (nil)          │
   │   └─ нет → вернуть значение как обычно      │
   └───────────────────────────────────────────┘
   + не тратит CPU на ключи, к которым никто не обращается
   - если к ключу никто не обращается, память не освобождается сразу

2. Active expiration cycle (активное удаление)
   Каждые 100 мс Redis:
   ┌───────────────────────────────────────────┐
   │ берёт случайную выборку ключей с TTL       │
   │ (по умолчанию 20 штук)                     │
   │ удаляет из них истёкшие                    │
   │ если истёкших > 25% выборки → повторить    │
   │ немедленно (не ждать следующий тик)        │
   └───────────────────────────────────────────┘
   + постепенно чистит "забытые" ключи, к которым не обращаются
   - не гарантирует, что ключ исчезнет ровно в момент истечения TTL
```

Вывод для практики: если приложению важно, что данные "не старше TTL", не
полагайтесь на факт удаления ключа как на сигнал — читающий код должен сам
относиться к TTL как к контракту ("если ключ есть — доверяем", а не
"если ключ есть — он гарантированно не старше выставленного TTL с точностью
до миллисекунды").

## Eviction policies: что делать, когда `maxmemory` достигнут

Без ограничения памяти (`maxmemory`) Redis будет расти, пока не займёт всю
доступную RAM и не начнёт падать по OOM или тормозить систему через swap.
Поэтому в проде `maxmemory` всегда выставлен, а `maxmemory-policy` решает,
что происходит, когда лимит достигнут и нужно освободить место под новую
запись.

```
maxmemory 2gb
maxmemory-policy allkeys-lru
```

| Политика | Что вытесняет | Когда выбрать для кеша |
| :--- | :--- | :--- |
| `noeviction` (по умолчанию) | Ничего — новые записи отклоняются с ошибкой | Почти никогда для чистого кеша: приложение начнёт получать ошибки записи вместо деградации. Уместно, если в этом же инстансе лежат не-кешируемые данные, потерю которых нельзя допустить молча. |
| `allkeys-lru` | Наименее недавно используемый ключ (approximate LRU) среди **всех** ключей | Хороший дефолт для инстанса, целиком используемого как кеш: "то, что давно не спрашивали — не жалко выкинуть". |
| `allkeys-lfu` | Наименее **часто** используемый ключ среди всех ключей | Когда есть явные "горячие" и "холодные" ключи и важно не терять горячие из-за случайного всплеска обращений к холодным (например, фоновый обход/скан по многим ключам один раз не должен вымыть по-настоящему популярные данные — LRU на это уязвим, LFU устойчивее). |
| `volatile-lru` / `volatile-lfu` | То же самое, но только среди ключей **с выставленным TTL** | Когда в одном инстансе соседствуют кеш (с TTL) и что-то ещё без TTL, что вытеснять нельзя ни в коем случае. Если подходящих ключей с TTL не найдётся — Redis ведёт себя как noeviction (ошибка на запись). |
| `volatile-ttl` | Ключ с TTL, у которого **меньше всего времени осталось** | Похожий смешанный сценарий, но с более предсказуемым порядком вытеснения — "кто и так скоро умрёт, пусть уйдёт первым". |
| `allkeys-random` | Случайный ключ | Редко осознанный выбор; имеет смысл, если доступ к ключам равномерно случаен и поддержка LRU/LFU метаданных не оправдывает своих накладных расходов. |

Практическое правило: для инстанса, который используется **только** как
кеш (это большинство случаев в веб-приложении), берите `allkeys-lru` как
безопасный дефолт и переходите на `allkeys-lfu`, если видите, что LRU
вымывает горячие ключи из-за редких "широких" обращений (батчевые job'ы,
прогрев, экспорт).
