# Redis для rate limiting

Ограничение частоты запросов — классическая задача, где sorted set и
инкременты закрывают ~все практические случаи.

## Fixed window counter (INCR + EXPIRE)

Идея: посчитать запросы в текущем "окне" времени (например, текущая
минута) и сбрасывать счётчик в начале следующего окна.

```
key = f"ratelimit:{user_id}:{current_minute}"

INCR key            # атомарный инкремент, возвращает новое значение
                     # если это первый INCR для ключа (значение стало 1) —
EXPIRE key 60        # выставить TTL, чтобы ключ сам исчез к следующему окну

if INCR-результат > limit:
    отклонить запрос
```

Просто и дёшево (O(1), одна строка на пользователя), но у fixed window есть
структурный изъян — **всплеск на границе окна**:

```
Лимит: 100 запросов / минуту

Окно [12:00:00 – 12:00:59]         Окно [12:01:00 – 12:01:59]
                            │
   ...100 запросов в        │        100 запросов в
   12:00:59.9               │        12:01:00.1
                            │
        └──────── реально это 200 запросов за 0.2 секунды! ────────┘
```

Клиент, зная о такой реализации, может сознательно "выстрелить" лимитом
дважды подряд вплотную к границе окна — фиксированное окно этого не видит,
потому что считает каждое окно независимо от соседнего.

## Sliding window (sorted set с timestamp'ами)

Idea: каждый запрос — это отдельный элемент множества со score = его
timestamp; лимит проверяется по количеству элементов **в скользящем окне
последних N секунд**, а не в "календарном" окне.

```
Key: "ratelimit:user:100"

Score = timestamp запроса      Member = уникальный id запроса
┌─────────────────────────────────────────────┐
│  1755780001.100  →  "req-a1"                 │
│  1755780001.250  →  "req-a2"                 │
│  1755780001.900  →  "req-a3"                 │
└─────────────────────────────────────────────┘
                     │
    окно "последние 60 секунд от текущего момента"
    сдвигается вместе с текущим временем —
    не привязано к границам "минута ровно"
```

```
now = текущий unix-timestamp
window_start = now - 60

ZREMRANGEBYSCORE ratelimit:user:100 -inf window_start   # выкинуть старое
ZADD ratelimit:user:100 now request_id                  # зафиксировать запрос
count = ZCARD ratelimit:user:100                        # сколько в окне сейчас
EXPIRE ratelimit:user:100 60                             # чтобы неактивный
                                                          # ключ сам исчез

if count > limit:
    отклонить запрос (и, как правило, удалить только что добавленный member)
```

Такое окно "едет" вместе со временем непрерывно, а не скачками — граничного
всплеска не возникает: в любой произвольный момент `ZCARD` честно отвечает
"сколько запросов было за последние 60 секунд, считая от прямо сейчас".

## Trade-off между двумя подходами

| | Fixed window | Sliding window (ZSet) |
| :--- | :--- | :--- |
| Точность на границе окна | Есть изъян (до 2x лимита) | Точная |
| Стоимость операции | O(1) (`INCR`) | O(log N) (`ZADD`/`ZREMRANGEBYSCORE`) |
| Память на пользователя | Одно число | Один элемент на каждый запрос в окне |
| Простота реализации | Минимальная | Чуть выше, но всё ещё несложно |

На практике: если лимиты не критичны для безопасности (защита от
случайного злоупотребления, а не от целенаправленной атаки) — fixed window
обычно достаточно и дешевле. Если нужна точность (платный API, защита от
DDoS/брутфорса) — sorted set оправдывает свою чуть большую стоимость.
Существует и промежуточный вариант — "sliding window counter" (взвешенное
среднее между текущим и предыдущим fixed-window счётчиком), который даёт
O(1) стоимость fixed window почти без её погрешности, но не рассматривается
здесь подробно.
