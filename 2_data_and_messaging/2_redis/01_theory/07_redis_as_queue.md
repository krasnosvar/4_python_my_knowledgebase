# Redis как простая очередь

`LPUSH`/`RPOP` (или блокирующий `BRPOP`) превращают List в базовую FIFO
очередь:

```
Producer:  LPUSH queue:emails "<email payload>"
Consumer:  BRPOP queue:emails 5     # ждать до 5 секунд, пока появится элемент
```

Этого достаточно, когда:
- очередь внутри одного сервиса (простой воркер-пул фоновых задач);
- потеря сообщения при падении воркера **между** `BRPOP` (элемент уже
  удалён из списка) и завершением обработки — приемлемый риск;
- не нужно несколько независимых групп потребителей, читающих одни и те
  же сообщения (fan-out), replay истории или гарантированная доставка
  "at-least-once" с подтверждением (ack).

Как только появляется требование "сообщение не должно теряться даже если
воркер упал посреди обработки", "нужно несколько независимых consumer
group", "нужен replay/аудит истории сообщений" или "нужна упорядоченная
доставка с партиционированием при высокой нагрузке" — это уже зона
полноценных брокеров сообщений (Kafka, RabbitMQ), с их протоколами
подтверждения, персистентным логом и consumer groups "из коробки". Redis
Streams (`XADD`/`XREADGROUP`) частично закрывает этот разрыв (append-only
лог с consumer groups), но подробный разбор брокеров сообщений — тема
отдельного модуля базы знаний, не этого раздела.
