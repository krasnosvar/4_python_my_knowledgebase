# Redis: in-memory кеш для ускорения ответов

Этот раздел рассматривает Redis узко и прагматично: как **in-memory кеш**,
который стоит перед медленным источником данных (обычно реляционной БД) и
ускоряет типичные операции чтения в веб-приложении на Python. Redis умеет
гораздо больше (pub/sub, streams, модули типа RediSearch/RedisJSON,
использование как основной БД в нишевых случаях), но это не тема данного
раздела — pub/sub и очереди сообщений затронуты только вскользь, потому что
полноценный разбор брокеров сообщений (Kafka/RabbitMQ) — отдельный модуль
базы знаний.

## 1. Что такое Redis и почему он быстрый

Redis (**RE**mote **DI**ctionary **S**erver) — сервер структур данных,
который хранит всё рабочее множество данных в оперативной памяти (RAM). Это
не побочная деталь, а главное архитектурное решение, из которого вытекает
всё остальное.

### Почему это быстро

```
Обычная БД (диск)                       Redis (RAM)
────────────────────                    ────────────────────
Application                             Application
    │ запрос                                │ запрос
    ▼                                        ▼
 Database engine                          Redis
    │ читает страницы с диска                │ читает из RAM
    ▼                                        ▼
 SSD/HDD  ~0.1–5 мс на операцию           RAM  ~0.0001 мс на операцию
    │ (даже на SSD — I/O, page cache,        │ (адресация в памяти —
    │  возможные seek'и, WAL fsync)          │  никакого round-trip к диску)
```

Ключевых причин скорости несколько, и важно понимать, что они складываются:

1. **Нет диска на горячем пути.** Чтение/запись — это операции над
   структурами данных в памяти процесса. Диск (RDB/AOF) используется только
   для персистентности "на всякий случай", а не для обслуживания запроса.
2. **Однопоточное исполнение команд (event loop).** Redis обрабатывает
   команды одну за другой в одном потоке (в терминах одного шарда/инстанса).
   Это звучит как ограничение, но на практике даёт выигрыш:
   - не нужны блокировки (locks/mutexes) на структуры данных — команда
     выполняется от начала до конца атомарно, без переключений контекста
     посреди неё;
   - нет накладных расходов на конкурентный доступ (contention, context
     switching), которые в многопоточной системе съедают заметную часть CPU;
   - сама по себе операция над структурой данных в памяти занимает
     микросекунды, поэтому один поток успевает обслуживать сотни тысяч
     операций в секунду — параллелизм здесь просто не нужен для скорости.

   Сетевой I/O (приём/отправка байт по сокетам) при этом мультиплексируется
   через epoll/kqueue, а начиная с Redis 6 есть опциональные I/O-threads для
   чтения/записи сокетов — но **исполнение самих команд** над данными
   остаётся однопоточным. Это сознательный trade-off простоты и
   предсказуемости в обмен на то, что одна "тяжёлая" команда (например,
   `KEYS *` или `SORT` на большой коллекции) блокирует всех остальных
   клиентов, пока не выполнится.
3. **Простой протокол (RESP).** Текстовый протокол с минимальным парсингом,
   дешёвый в кодировании/декодировании на клиенте и сервере.
4. **Структуры данных заточены под быстрые операции.** Хеш-таблицы,
   skip-list'ы и т.д. дают O(1)/O(log n) на большинство операций — сложность
   алгоритма подобрана так, чтобы соответствовать ожиданиям "это должно быть
   мгновенно".

### Когда НЕ использовать Redis

Из "всё в RAM" следует набор ограничений, которые нужно проговаривать
осознанно, а не натыкаться на них в проде:

```
НЕ подходит как:
- Основное хранилище (primary datastore) для данных, которые нельзя
  терять. Персистентность в Redis (RDB/AOF) — это подстраховка на случай
  рестарта, а не полноценная гарантия durability уровня "закоммиченная
  транзакция никогда не потеряется", как в PostgreSQL с WAL.
- Хранилище для датасета, который не помещается в RAM. Нет прозрачного
  вытеснения "холодных" данных на диск с сохранением работоспособности —
  либо всё в памяти, либо вы упираетесь в maxmemory и получаете отказы или
  агрессивное вытеснение (см. раздел 3).
- Источник для сложных запросов: JOIN, произвольная фильтрация по многим
  полям, агрегации "как в SQL". Redis даёт быстрый доступ по ключу и
  несколько специализированных структур — это не замена реляционной модели
  и не движок запросов общего назначения.
```

Практический вывод: Redis почти всегда стоит **рядом** с "настоящей" БД
(PostgreSQL, MySQL и т.п.), а не вместо неё — как слой ускорения чтений и
как место для эфемерных/производных данных (сессии, счётчики, rate-limit
окна, кеш вычислений), потеря которых неприятна, но не катастрофична.

## 2. Основные структуры данных

Ниже — пять структур, которые реально используются в кешировании веб-
приложений на Python. Команды даны в виде `redis-cli`-синтаксиса (в
`02_examples/01_data_structures.py` те же операции показаны через `redis-py`).

### String

Простейший тип: ключ → строка байт (до 512 МБ). "Просто значение", но с
атомарными числовыми операциями.

```
"user:100:name"  →  "Alice"
"views:article:42" → "1532"
```

```
SET user:100:name "Alice"
GET user:100:name
INCR views:article:42          # атомарный инкремент, без race condition
INCRBY views:article:42 10
SETEX session:abc 1800 "<данные сессии>"   # SET + TTL одной командой
```

**Use cases:**
- Кеш готового HTML/JSON-ответа целиком (например, отрендеренная страница
  или сериализованный ответ API).
- Счётчики (просмотры, лайки, лимиты запросов).
- Простые флаги/feature-toggle.

### Hash

Коллекция пар `field → value` под одним ключом — аналог словаря/объекта.

```
Key: "user:100"
┌─────────────────────────────┐
│ name   → "Alice"            │
│ email  → "alice@example.com"│
│ age    → "25"                │
└─────────────────────────────┘
```

```
HSET user:100 name "Alice" email "alice@example.com" age 25
HGET user:100 name
HGETALL user:100
HINCRBY user:100 login_count 1
```

**Почему Hash, а не JSON-строка целиком.** Если хранить объект как один
JSON в String, обновление одного поля требует GET → parse → изменить поле →
serialize → SET — пять шагов и не атомарно (между GET и SET кто-то другой
может успеть записать своё значение). Hash даёт `HSET user:100 age 26` —
одна атомарная операция, без чтения и парсинга всего объекта. Это особенно
заметно, если объект большой, а меняется в нём одно поле (например,
счётчик логинов), и на объект идёт параллельная запись из разных мест.

**Use cases:**
- Кеш объекта (пользователь, товар, конфигурация) без сериализации целиком.
- Частичные обновления структуры без риска "потерять" параллельно
  записанные соседние поля.

### List

Двусвязный список строк — упорядоченная последовательность с быстрыми
операциями на обоих концах.

```
Key: "recent:searches:user:100"
HEAD                                    TAIL
 ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │ q4 │←─→│ q3 │←─→│ q2 │←─→│ q1 │
 └────┘   └────┘   └────┘   └────┘
LPUSH добавляет сюда              RPOP забирает отсюда
```

```
LPUSH queue:tasks "task1"
RPOP queue:tasks
LRANGE recent:searches:user:100 0 9    # последние 10 элементов, без удаления
LTRIM recent:searches:user:100 0 9     # обрезать список до первых 10
BRPOP queue:tasks 5                    # блокирующий pop с таймаутом 5с
```

**Use cases:**
- Простая FIFO/LIFO очередь (подробнее — раздел 7).
- Лента "последних N событий/поисков/действий" пользователя: `LPUSH` новое
  значение + `LTRIM 0 N-1`, чтобы список никогда не рос неограниченно.
- Буфер "последние просмотренные товары".

### Set

Неупорядоченная коллекция **уникальных** строк с быстрой проверкой
принадлежности и операциями над множествами.

```
Key: "tags:article:42"
┌────────────────────┐
│ "redis"            │
│ "caching"          │
│ "python"           │   ← порядок не гарантирован,
└────────────────────┘     дубликаты невозможны
```

```
SADD tags:article:42 "redis" "caching" "python"
SISMEMBER tags:article:42 "redis"     # 1 (true) — O(1) проверка
SMEMBERS tags:article:42
SINTER user:1:interests user:2:interests   # общие интересы двух пользователей
```

**Use cases:**
- Теги/категории сущности с быстрой проверкой "есть ли тег X".
- Множество уникальных значений: посетители страницы за день, ID
  пользователей, видевших уведомление (защита от повторной обработки).
- Пересечение/объединение множеств "на лету" (общие подписки, друзья друзей).

### Sorted Set (ZSet)

Множество уникальных элементов, но с числовым `score`, по которому Redis
**поддерживает элементы отсортированными** автоматически (реализовано на
skip-list + hash-таблице — вставка и чтение диапазона одинаково быстры).

```
Key: "leaderboard"
Score    Member
1100  →  "alice"     ← ZREVRANGE отдаёт в этом порядке
 950  →  "bob"
 920  →  "charlie"
```

```
ZADD leaderboard 1100 "alice" 950 "bob" 920 "charlie"
ZREVRANGE leaderboard 0 2 WITHSCORES     # топ-3 по убыванию score
ZREVRANK leaderboard "alice"             # позиция игрока (0 = первое место)
ZINCRBY leaderboard 50 "bob"             # начислить очки, не читая текущий score
ZRANGEBYSCORE ratelimit:1.2.3.4 <старая_граница> +inf
ZREMRANGEBYSCORE ratelimit:1.2.3.4 -inf <старая_граница>
```

Ключевая идея, которую стоит унести: **score не обязан быть "очками"** — это
просто число, по которому нужна сортировка/диапазонный запрос. Отсюда два
разных, но одинаково естественных применения:

**Use cases:**
- **Leaderboard** — score = очки игрока, `ZREVRANGE` даёт топ-N мгновенно,
  без сортировки на клиенте или в SQL (`ORDER BY score DESC LIMIT N`
  каждый раз пересчитывать не нужно — структура уже отсортирована).
- **Rate limiting по времени** — score = timestamp запроса. `ZREMRANGEBYSCORE`
  выкидывает записи старше окна, `ZCARD` считает, сколько осталось —
  готовый sliding window (подробно — раздел 6).

## 3. TTL: expiration и eviction

Для кеша TTL — не опция, а основной механизм: он гарантирует, что забытый
ключ рано или поздно освободит память и не будет отдавать данные вечно.

### Как Redis узнаёт, что ключ "истёк"

Redis не заводит таймер на каждый ключ с TTL (миллионы таймеров — это сама
по себе дорогая структура). Вместо этого работают два независимых
механизма одновременно:

```
1. Lazy expiration (ленивое удаление)
   ┌───────────────────────────────────────────┐
   │ Клиент делает GET/любую команду над ключом │
   │        │                                   │
   │        ▼                                   │
   │  TTL этого ключа истёк?                    │
   │   ├─ да  → удалить ключ, вести себя так,   │
   │   │        будто его не было (nil)          │
   │   └─ нет → вернуть значение как обычно      │
   └───────────────────────────────────────────┘
   + не тратит CPU на ключи, к которым никто не обращается
   - если к ключу никто не обращается, память не освобождается сразу

2. Active expiration cycle (активное удаление)
   Каждые 100 мс Redis:
   ┌───────────────────────────────────────────┐
   │ берёт случайную выборку ключей с TTL       │
   │ (по умолчанию 20 штук)                     │
   │ удаляет из них истёкшие                    │
   │ если истёкших > 25% выборки → повторить    │
   │ немедленно (не ждать следующий тик)        │
   └───────────────────────────────────────────┘
   + постепенно чистит "забытые" ключи, к которым не обращаются
   - не гарантирует, что ключ исчезнет ровно в момент истечения TTL
```

Вывод для практики: если приложению важно, что данные "не старше TTL", не
полагайтесь на факт удаления ключа как на сигнал — читающий код должен сам
относиться к TTL как к контракту ("если ключ есть — доверяем", а не
"если ключ есть — он гарантированно не старше выставленного TTL с точностью
до миллисекунды").

### Eviction policies: что делать, когда `maxmemory` достигнут

Без ограничения памяти (`maxmemory`) Redis будет расти, пока не займёт всю
доступную RAM и не начнёт падать по OOM или тормозить систему через swap.
Поэтому в проде `maxmemory` всегда выставлен, а `maxmemory-policy` решает,
что происходит, когда лимит достигнут и нужно освободить место под новую
запись.

```
maxmemory 2gb
maxmemory-policy allkeys-lru
```

| Политика | Что вытесняет | Когда выбрать для кеша |
| :--- | :--- | :--- |
| `noeviction` (по умолчанию) | Ничего — новые записи отклоняются с ошибкой | Почти никогда для чистого кеша: приложение начнёт получать ошибки записи вместо деградации. Уместно, если в этом же инстансе лежат не-кешируемые данные, потерю которых нельзя допустить молча. |
| `allkeys-lru` | Наименее недавно используемый ключ (approximate LRU) среди **всех** ключей | Хороший дефолт для инстанса, целиком используемого как кеш: "то, что давно не спрашивали — не жалко выкинуть". |
| `allkeys-lfu` | Наименее **часто** используемый ключ среди всех ключей | Когда есть явные "горячие" и "холодные" ключи и важно не терять горячие из-за случайного всплеска обращений к холодным (например, фоновый обход/скан по многим ключам один раз не должен вымыть по-настоящему популярные данные — LRU на это уязвим, LFU устойчивее). |
| `volatile-lru` / `volatile-lfu` | То же самое, но только среди ключей **с выставленным TTL** | Когда в одном инстансе соседствуют кеш (с TTL) и что-то ещё без TTL, что вытеснять нельзя ни в коем случае. Если подходящих ключей с TTL не найдётся — Redis ведёт себя как noeviction (ошибка на запись). |
| `volatile-ttl` | Ключ с TTL, у которого **меньше всего времени осталось** | Похожий смешанный сценарий, но с более предсказуемым порядком вытеснения — "кто и так скоро умрёт, пусть уйдёт первым". |
| `allkeys-random` | Случайный ключ | Редко осознанный выбор; имеет смысл, если доступ к ключам равномерно случаен и поддержка LRU/LFU метаданных не оправдывает своих накладных расходов. |

Практическое правило: для инстанса, который используется **только** как
кеш (это большинство случаев в веб-приложении), берите `allkeys-lru` как
безопасный дефолт и переходите на `allkeys-lfu`, если видите, что LRU
вымывает горячие ключи из-за редких "широких" обращений (батчевые job'ы,
прогрев, экспорт).

## 4. Паттерны кеширования

### Cache-aside (lazy loading)

Это доминирующий паттерн в Python веб-приложениях: **кеш не является
источником истины и ничего не знает о записи** — приложение явно проверяет
кеш и явно его наполняет.

```
                    ┌──────────────┐
                    │ Application  │
                    └──────┬───────┘
                           │ GET user:100
                           ▼
                    ┌──────────────┐
                    │    Redis     │
                    └──────┬───────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
              HIT (есть)         MISS (нет / истёк)
                 │                   │
                 ▼                   ▼
        вернуть из кеша      прочитать из БД
        (~0.1 мс)            (~5-50 мс)
                                     │
                                     ▼
                             записать в кеш с TTL
                                     │
                                     ▼
                              вернуть результат
```

**Разбор на примере `get_user(user_id)`:**

```python
def get_user(user_id: int) -> dict:
    cache_key = f"user:{user_id}"

    cached = redis_client.get(cache_key)
    if cached is not None:
        return json.loads(cached)          # cache HIT

    user = db.fetch_user(user_id)          # cache MISS — идём в БД
    redis_client.set(cache_key, json.dumps(user), ex=3600)
    return user
```

Полная рабочая версия с замером времени и инвалидацией — в
`02_examples/03_cache_aside_pattern.py`.

**Почему это удобно:** кеш можно потерять целиком (перезапуск, сбой,
`FLUSHALL` по ошибке) — приложение просто начнёт с MISS на каждый запрос и
само перезаполнит кеш. Кеш строго вторичен по отношению к БД, и это делает
его безопасным по умолчанию.

**Trade-off 1: устаревшие данные (staleness).** Между записью в БД и
истечением TTL (или явной инвалидацией) кеш может отдавать старое значение.
Это осознанный компромисс: вы выбираете TTL так, чтобы "окно
рассинхронизации" было приемлемым для конкретных данных (профиль
пользователя — можно и 10 минут, баланс на счёте — уже сомнительно).

**Trade-off 2: dogpile / thundering herd.** Если один и тот же ключ очень
горячий (высокая частота запросов) и он истекает — в момент истечения
десятки или сотни параллельных запросов одновременно получают MISS и все
одновременно бьют в БД тем же самым запросом:

```
Ключ "product:42" истёк в T=0

T=0.001с  ┬─ запрос 1 → MISS → идёт в БД ─┐
T=0.002с  ├─ запрос 2 → MISS → идёт в БД ─┤
T=0.003с  ├─ запрос 3 → MISS → идёт в БД ─┼─► БД получает N одинаковых
T=0.004с  ├─ запрос 4 → MISS → идёт в БД ─┤    тяжёлых запросов разом,
   ...    │        ...                    │    вместо одного
T=0.050с  ┴─ запрос N → MISS → идёт в БД ─┘
```

Для одного горячего товара это неприятно, но для многих одновременно
истекающих ключей (например, все они были прогреты одним batch-job'ом в
одну и ту же секунду) — это лавинообразная нагрузка на БД ровно в момент,
когда БД меньше всего к ней готова.

Практические способы смягчить это:

- **Jitter в TTL.** Вместо `ex=3600` для всех ключей ставить
  `ex=3600 + random.randint(-300, 300)` — тогда массово прогретые ключи
  истекают не одномоментно, а размазанно по 10-минутному окну.
- **Короткая блокировка на пересчёт (lock/mutex через `SET key val NX EX`).**
  Первый запрос, получивший MISS, ставит короткий лок `lock:product:42`, идёт
  в БД и обновляет кеш; остальные запросы, видя MISS и уже существующий лок,
  либо ждут (retry с небольшой паузой), либо отдают чуть устаревшее значение,
  если оно ещё доступно (see "stale-while-revalidate" ниже).
- **Вероятностное упреждающее обновление (probabilistic early expiration,
  он же алгоритм XFetch).** Чем ближе текущее время к моменту истечения TTL,
  тем выше вероятность, что именно этот (а не следующий) запрос сам
  пересчитает значение заранее — так пересчёт "размазывается" по времени
  перед реальным истечением, и почти никогда не происходит массовый MISS
  ровно в момент T=0.

### Write-through

Запись идёт **одновременно** в кеш и в БД (обычно синхронно, в рамках
одного вызова на стороне приложения или через прослойку, которая сама
управляет этим):

```
Application → write(value)
                 │
        ┌────────┴────────┐
        ▼                 ▼
      Redis              БД
   (сразу актуален)   (сразу актуальна)
```

- Плюс: кеш никогда не бывает рассинхронизирован с БД — прочитанное после
  записи всегда свежее, не нужно думать про TTL/инвалидацию для этого ключа.
- Минус: каждая запись становится дороже (два round-trip'а вместо одного),
  и в кеш попадают в том числе данные, которые никогда не будут прочитаны —
  в отличие от cache-aside, здесь нет "лени", кешируется всё, что пишется.

### Write-behind (write-back)

Запись идёт **сначала** в кеш (быстрый ответ клиенту), а в БД сбрасывается
**асинхронно**, обычно батчами:

```
Application → write(value) → Redis (мгновенный ACK клиенту)
                                 │
                                 │ асинхронно, позже, батчем
                                 ▼
                                БД
```

- Плюс: минимальная задержка на запись и возможность объединять/сжимать
  много обновлений в одну запись в БД (например, инкременты счётчика).
- Минус: если процесс, отвечающий за сброс в БД, упадёт до того, как данные
  реально записаны — эти данные потеряны безвозвратно, даже если Redis
  сам по себе не упал. Это компромисс "скорость записи" против
  "гарантия сохранности", и его стоит применять только там, где потеря
  последних N секунд обновлений действительно допустима (аналитика,
  счётчики просмотров), а не для денег на счету пользователя.

## 5. Инвалидация кеша

Фраза Фила Карлтона "в Computer Science есть только две сложные вещи:
инвалидация кеша и называние переменных" — не шутка ради шутки. Сложность
именно в том, что "правильный момент удалить/обновить кеш" плохо
определён и легко ловит гонки состояний (race conditions).

### Три стратегии

```
1. TTL-based (по времени)
   SET key value EX 3600
   + просто, не требует связи между сервисом-писателем и кешем
   - данные могут быть устаревшими всё окно TTL — принятие риска, а не
     решение проблемы

2. Explicit delete-on-write (явное удаление при записи)
   UPDATE в БД → DEL cache_key
   (Следующий GET получит MISS → перечитает из БД → положит свежее значение)
   + следующий читатель всегда видит актуальные данные
   - требует, чтобы каждый путь записи в БД не забыл удалить ключ

3. Event-based (по событию)
   UPDATE в БД → публикация события об изменении → все узлы/инстансы,
   держащие свою копию кеша, инвалидируют у себя ключ
   + работает, когда кеш не один (несколько инстансов приложения с
     локальным in-process кешем поверх Redis, несколько дата-центров)
   - требует инфраструктуры доставки событий и обработки "at least once"
     (событие может продублироваться или не дойти)
```

Почему **delete**, а не **update** кеша при записи — практический нюанс:
удаление проще и безопаснее, чем запись нового значения в кеш из
write-пути. Если писать новое значение сразу в кеш, нужно быть уверенным,
что именно это значение — самое свежее (а не потерявшее гонку с другой
параллельной записью), и придётся заново его сериализовать в
write-обработчике. Удаление же ключа гарантированно корректно в любом
случае: следующий читатель просто перечитает актуальное состояние из БД по
правилам cache-aside.

### Race condition между записью в БД и обновлением кеша

Даже "простой" delete-on-write не спасает от гонки, если конкурентно идёт
чтение того же ключа:

```
Поток A (читатель, cache-aside)      Поток B (писатель)
──────────────────────────────       ──────────────────
GET user:100 → MISS
                                      UPDATE users SET age=26 WHERE id=100
GET age из БД → видит age=25          (ещё коммитится / реплика не догнала)
  (устаревшее значение, т.к. читает
   до применения UPDATE или из
   отстающей read-реплики)
                                      DEL user:100   ← инвалидация ПОСЛЕ
                                                        того, как A уже
                                                        прочитал старое
SET user:100 = {age: 25}   ← кладёт устаревшее значение В КЕШ
                              ПОСЛЕ того, как поток B его удалил!
```

Итог: в кеше застревает устаревшее значение `age=25`, и **ничто больше не
инициирует его удаление** — следующий читатель будет получать HIT с этим
неверным значением вплоть до истечения TTL. Отсюда практический вывод:
TTL — это не просто "оптимизация ускорения", а страховочный трос от именно
такого сценария: даже если инвалидация "сломалась" из-за гонки, TTL
гарантирует, что неверное значение не проживёт вечно. **Не выставлять TTL
вообще, полагаясь только на delete-on-write, — рискованная практика.**

### Thundering herd — см. раздел 4

Отдельный частный случай "инвалидации, идущей не так, как хотелось бы" —
массовое одновременное истечение TTL у горячего ключа (или у многих ключей
разом). Разобран подробно в разделе про cache-aside вместе со
способами смягчения (jitter, короткий лок, вероятностное упреждение).

## 6. Redis для rate limiting

Ограничение частоты запросов — классическая задача, где sorted set и
инкременты закрывают ~все практические случаи.

### Fixed window counter (INCR + EXPIRE)

Идея: посчитать запросы в текущем "окне" времени (например, текущая
минута) и сбрасывать счётчик в начале следующего окна.

```
key = f"ratelimit:{user_id}:{current_minute}"

INCR key            # атомарный инкремент, возвращает новое значение
                     # если это первый INCR для ключа (значение стало 1) —
EXPIRE key 60        # выставить TTL, чтобы ключ сам исчез к следующему окну

if INCR-результат > limit:
    отклонить запрос
```

Просто и дёшево (O(1), одна строка на пользователя), но у fixed window есть
структурный изъян — **всплеск на границе окна**:

```
Лимит: 100 запросов / минуту

Окно [12:00:00 – 12:00:59]         Окно [12:01:00 – 12:01:59]
                            │
   ...100 запросов в        │        100 запросов в
   12:00:59.9               │        12:01:00.1
                            │
        └──────── реально это 200 запросов за 0.2 секунды! ────────┘
```

Клиент, зная о такой реализации, может сознательно "выстрелить" лимитом
дважды подряд вплотную к границе окна — фиксированное окно этого не видит,
потому что считает каждое окно независимо от соседнего.

### Sliding window (sorted set с timestamp'ами)

Idea: каждый запрос — это отдельный элемент множества со score = его
timestamp; лимит проверяется по количеству элементов **в скользящем окне
последних N секунд**, а не в "календарном" окне.

```
Key: "ratelimit:user:100"

Score = timestamp запроса      Member = уникальный id запроса
┌─────────────────────────────────────────────┐
│  1755780001.100  →  "req-a1"                 │
│  1755780001.250  →  "req-a2"                 │
│  1755780001.900  →  "req-a3"                 │
└─────────────────────────────────────────────┘
                     │
    окно "последние 60 секунд от текущего момента"
    сдвигается вместе с текущим временем —
    не привязано к границам "минута ровно"
```

```
now = текущий unix-timestamp
window_start = now - 60

ZREMRANGEBYSCORE ratelimit:user:100 -inf window_start   # выкинуть старое
ZADD ratelimit:user:100 now request_id                  # зафиксировать запрос
count = ZCARD ratelimit:user:100                        # сколько в окне сейчас
EXPIRE ratelimit:user:100 60                             # чтобы неактивный
                                                          # ключ сам исчез

if count > limit:
    отклонить запрос (и, как правило, удалить только что добавленный member)
```

Такое окно "едет" вместе со временем непрерывно, а не скачками — граничного
всплеска не возникает: в любой произвольный момент `ZCARD` честно отвечает
"сколько запросов было за последние 60 секунд, считая от прямо сейчас".

### Trade-off между двумя подходами

| | Fixed window | Sliding window (ZSet) |
| :--- | :--- | :--- |
| Точность на границе окна | Есть изъян (до 2x лимита) | Точная |
| Стоимость операции | O(1) (`INCR`) | O(log N) (`ZADD`/`ZREMRANGEBYSCORE`) |
| Память на пользователя | Одно число | Один элемент на каждый запрос в окне |
| Простота реализации | Минимальная | Чуть выше, но всё ещё несложно |

На практике: если лимиты не критичны для безопасности (защита от
случайного злоупотребления, а не от целенаправленной атаки) — fixed window
обычно достаточно и дешевле. Если нужна точность (платный API, защита от
DDoS/брутфорса) — sorted set оправдывает свою чуть большую стоимость.
Существует и промежуточный вариант — "sliding window counter" (взвешенное
среднее между текущим и предыдущим fixed-window счётчиком), который даёт
O(1) стоимость fixed window почти без её погрешности, но не рассматривается
здесь подробно.

## 7. Redis как простая очередь

`LPUSH`/`RPOP` (или блокирующий `BRPOP`) превращают List в базовую FIFO
очередь:

```
Producer:  LPUSH queue:emails "<email payload>"
Consumer:  BRPOP queue:emails 5     # ждать до 5 секунд, пока появится элемент
```

Этого достаточно, когда:
- очередь внутри одного сервиса (простой воркер-пул фоновых задач);
- потеря сообщения при падении воркера **между** `BRPOP` (элемент уже
  удалён из списка) и завершением обработки — приемлемый риск;
- не нужно несколько независимых групп потребителей, читающих одни и те
  же сообщения (fan-out), replay истории или гарантированная доставка
  "at-least-once" с подтверждением (ack).

Как только появляется требование "сообщение не должно теряться даже если
воркер упал посреди обработки", "нужно несколько независимых consumer
group", "нужен replay/аудит истории сообщений" или "нужна упорядоченная
доставка с партиционированием при высокой нагрузке" — это уже зона
полноценных брокеров сообщений (Kafka, RabbitMQ), с их протоколами
подтверждения, персистентным логом и consumer groups "из коробки". Redis
Streams (`XADD`/`XREADGROUP`) частично закрывает этот разрыв (append-only
лог с consumer groups), но подробный разбор брокеров сообщений — тема
отдельного модуля базы знаний, не этого раздела.

## 8. Pub/Sub — коротко

Pub/Sub (`PUBLISH`/`SUBSCRIBE`) — механизм "разослать сообщение всем
подписанным прямо сейчас":

```
Publisher → PUBLISH "notifications:user:100" "у вас новое сообщение"
                          │
              Redis рассылает всем текущим подписчикам канала
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
          Подписчик 1  Подписчик 2  (никого нет — сообщение
          получает     получает      просто теряется, Redis
          немедленно   немедленно    его нигде не хранит)
```

Это **fire-and-forget**: если в момент `PUBLISH` подписчиков нет — сообщение
исчезает безвозвратно, история не сохраняется, гарантий доставки нет
никаких. Это уместно только там, где сама природа данных делает "потерять
и не заметить" приемлемым: индикатор "собеседник печатает", live-обновление
счётчика на дашборде, широковещательное уведомление об инвалидации
локального кеша на других инстансах приложения (см. раздел 5) — если
инстанс временно недоступен, для него это не критично, он и так не мог
показать пользователю устаревший UI, пока был недоступен.

Полноценное сравнение Pub/Sub с persistent-очередями и брокерами сообщений
(Kafka/RabbitMQ), consumer groups, гарантии доставки — предмет отдельного
модуля базы знаний про брокеры сообщений, здесь эта тема сознательно не
раскрывается глубже.
