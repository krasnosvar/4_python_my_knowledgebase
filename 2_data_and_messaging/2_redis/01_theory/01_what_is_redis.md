# Что такое Redis и почему он быстрый

Redis (**RE**mote **DI**ctionary **S**erver) — сервер структур данных,
который хранит всё рабочее множество данных в оперативной памяти (RAM). Это
не побочная деталь, а главное архитектурное решение, из которого вытекает
всё остальное.

## Почему это быстро

```
Обычная БД (диск)                       Redis (RAM)
────────────────────                    ────────────────────
Application                             Application
    │ запрос                                │ запрос
    ▼                                        ▼
 Database engine                          Redis
    │ читает страницы с диска                │ читает из RAM
    ▼                                        ▼
 SSD/HDD  ~0.1–5 мс на операцию           RAM  ~0.0001 мс на операцию
    │ (даже на SSD — I/O, page cache,        │ (адресация в памяти —
    │  возможные seek'и, WAL fsync)          │  никакого round-trip к диску)
```

Ключевых причин скорости несколько, и важно понимать, что они складываются:

1. **Нет диска на горячем пути.** Чтение/запись — это операции над
   структурами данных в памяти процесса. Диск используется только для
   персистентности "на всякий случай", а не для обслуживания запроса.
   Способов сохранить данные на диск два:
   - **RDB** (снимок) — Redis периодически целиком записывает содержимое
     памяти в файл. Дёшево, но всё, что изменилось после последнего снимка,
     при падении теряется;
   - **AOF** (append-only file, журнал) — Redis дописывает в файл каждую
     команду записи, а при рестарте проигрывает журнал заново. Теряется
     меньше (обычно не больше секунды записей), но файл растёт и его
     приходится периодически сжимать.
2. **Однопоточное исполнение команд (event loop).** Redis обрабатывает
   команды одну за другой в одном потоке (в терминах одного шарда/инстанса).
   Это звучит как ограничение, но на практике даёт выигрыш:
   - не нужны блокировки (locks/mutexes) на структуры данных — команда
     выполняется от начала до конца атомарно, без переключений контекста
     посреди неё;
   - нет накладных расходов на конкурентный доступ (contention, context
     switching), которые в многопоточной системе съедают заметную часть CPU;
   - сама по себе операция над структурой данных в памяти занимает
     микросекунды, поэтому один поток успевает обслуживать сотни тысяч
     операций в секунду — параллелизм здесь просто не нужен для скорости.

   Сетевой I/O (приём/отправка байт по сокетам) при этом мультиплексируется
   через epoll/kqueue (механизмы ОС Linux и macOS/BSD, которые позволяют одному
   потоку следить сразу за тысячами сетевых соединений и обрабатывать только те,
   где пришли данные), а начиная с Redis 6 есть опциональные I/O-threads для
   чтения/записи сокетов — но **исполнение самих команд** над данными остаётся
   однопоточным. Это сознательный trade-off простоты и предсказуемости в обмен
   на то, что одна "тяжёлая" команда (например, `KEYS *` или `SORT` на большой
   коллекции) блокирует всех остальных клиентов, пока не выполнится.
3. **Простой протокол (RESP).** RESP (REdis Serialization Protocol) — формат,
   в котором клиент и сервер обмениваются командами и ответами по сети.
   Текстовый протокол с минимальным парсингом, дешёвый в
   кодировании/декодировании на клиенте и сервере.
4. **Структуры данных заточены под быстрые операции.** Хеш-таблицы,
   skip-list'ы (упорядоченный связный список с дополнительными уровнями
   «ссылок через несколько элементов», по которым поиск идёт почти как
   бинарный) и т.д. дают O(1)/O(log n) на большинство операций — сложность
   алгоритма подобрана так, чтобы соответствовать ожиданиям "это должно быть
   мгновенно".

## Когда НЕ использовать Redis

Из "всё в RAM" следует набор ограничений, которые нужно проговаривать
осознанно, а не натыкаться на них в проде:

```
НЕ подходит как:
- Основное хранилище (primary datastore) для данных, которые нельзя
  терять. Персистентность в Redis (RDB/AOF) — это подстраховка на случай
  рестарта, а не полноценная гарантия durability уровня "закоммиченная
  транзакция никогда не потеряется", как в PostgreSQL с WAL.
- Хранилище для датасета, который не помещается в RAM. Нет прозрачного
  вытеснения "холодных" данных на диск с сохранением работоспособности —
  либо всё в памяти, либо вы упираетесь в maxmemory и получаете отказы или
  агрессивное вытеснение (см. урок 03_ttl_expiration_eviction.md).
- Источник для сложных запросов: JOIN, произвольная фильтрация по многим
  полям, агрегации "как в SQL". Redis даёт быстрый доступ по ключу и
  несколько специализированных структур — это не замена реляционной модели
  и не движок запросов общего назначения.
```

Практический вывод: Redis почти всегда стоит **рядом** с "настоящей" БД
(PostgreSQL, MySQL и т.п.), а не вместо неё — как слой ускорения чтений и
как место для эфемерных/производных данных (сессии, счётчики, rate-limit
окна, кеш вычислений), потеря которых неприятна, но не катастрофична.
