# Инвалидация кеша

Фраза Фила Карлтона "в Computer Science есть только две сложные вещи:
инвалидация кеша и называние переменных" — не шутка ради шутки. Сложность
именно в том, что "правильный момент удалить/обновить кеш" плохо
определён и легко ловит гонки состояний (race conditions).

## Три стратегии

```
1. TTL-based (по времени)
   SET key value EX 3600
   + просто, не требует связи между сервисом-писателем и кешем
   - данные могут быть устаревшими всё окно TTL — принятие риска, а не
     решение проблемы

2. Explicit delete-on-write (явное удаление при записи)
   UPDATE в БД → DEL cache_key
   (Следующий GET получит MISS → перечитает из БД → положит свежее значение)
   + следующий читатель всегда видит актуальные данные
   - требует, чтобы каждый путь записи в БД не забыл удалить ключ

3. Event-based (по событию)
   UPDATE в БД → публикация события об изменении → все узлы/инстансы,
   держащие свою копию кеша, инвалидируют у себя ключ
   + работает, когда кеш не один (несколько инстансов приложения с
     локальным in-process кешем поверх Redis, несколько дата-центров)
   - требует инфраструктуры доставки событий и обработки "at least once"
     (событие может продублироваться или не дойти)
```

Почему **delete**, а не **update** кеша при записи — практический нюанс:
удаление проще и безопаснее, чем запись нового значения в кеш из
write-пути. Если писать новое значение сразу в кеш, нужно быть уверенным,
что именно это значение — самое свежее (а не потерявшее гонку с другой
параллельной записью), и придётся заново его сериализовать в
write-обработчике. Удаление же ключа гарантированно корректно в любом
случае: следующий читатель просто перечитает актуальное состояние из БД по
правилам cache-aside.

## Race condition между записью в БД и обновлением кеша

Даже "простой" delete-on-write не спасает от гонки, если конкурентно идёт
чтение того же ключа:

```
Поток A (читатель, cache-aside)      Поток B (писатель)
──────────────────────────────       ──────────────────
GET user:100 → MISS
                                      UPDATE users SET age=26 WHERE id=100
GET age из БД → видит age=25          (ещё коммитится / реплика не догнала)
  (устаревшее значение, т.к. читает
   до применения UPDATE или из
   отстающей read-реплики)
                                      DEL user:100   ← инвалидация ПОСЛЕ
                                                        того, как A уже
                                                        прочитал старое
SET user:100 = {age: 25}   ← кладёт устаревшее значение В КЕШ
                              ПОСЛЕ того, как поток B его удалил!
```

Итог: в кеше застревает устаревшее значение `age=25`, и **ничто больше не
инициирует его удаление** — следующий читатель будет получать HIT с этим
неверным значением вплоть до истечения TTL. Отсюда практический вывод:
TTL — это не просто "оптимизация ускорения", а страховочный трос от именно
такого сценария: даже если инвалидация "сломалась" из-за гонки, TTL
гарантирует, что неверное значение не проживёт вечно. **Не выставлять TTL
вообще, полагаясь только на delete-on-write, — рискованная практика.**
