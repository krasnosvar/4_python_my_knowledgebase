# Основные структуры данных

Ниже — пять структур, которые реально используются в кешировании веб-
приложений на Python. Команды даны в виде `redis-cli`-синтаксиса (в
`02_examples/01_data_structures.py` те же операции показаны через `redis-py`).

## String

Простейший тип: ключ → строка байт (до 512 МБ). "Просто значение", но с
атомарными числовыми операциями.

```
"user:100:name"  →  "Alice"
"views:article:42" → "1532"
```

```
SET user:100:name "Alice"
GET user:100:name
INCR views:article:42          # атомарный инкремент, без race condition
INCRBY views:article:42 10
SETEX session:abc 1800 "<данные сессии>"   # SET + TTL одной командой
```

**Use cases:**
- Кеш готового HTML/JSON-ответа целиком (например, отрендеренная страница
  или сериализованный ответ API).
- Счётчики (просмотры, лайки, лимиты запросов).
- Простые флаги/feature-toggle.

## Hash

Коллекция пар `field → value` под одним ключом — аналог словаря/объекта.

```
Key: "user:100"
┌─────────────────────────────┐
│ name   → "Alice"            │
│ email  → "alice@example.com"│
│ age    → "25"                │
└─────────────────────────────┘
```

```
HSET user:100 name "Alice" email "alice@example.com" age 25
HGET user:100 name
HGETALL user:100
HINCRBY user:100 login_count 1
```

**Почему Hash, а не JSON-строка целиком.** Если хранить объект как один
JSON в String, обновление одного поля требует GET → parse → изменить поле →
serialize → SET — пять шагов и не атомарно (между GET и SET кто-то другой
может успеть записать своё значение). Hash даёт `HSET user:100 age 26` —
одна атомарная операция, без чтения и парсинга всего объекта. Это особенно
заметно, если объект большой, а меняется в нём одно поле (например,
счётчик логинов), и на объект идёт параллельная запись из разных мест.

**Use cases:**
- Кеш объекта (пользователь, товар, конфигурация) без сериализации целиком.
- Частичные обновления структуры без риска "потерять" параллельно
  записанные соседние поля.

## List

Двусвязный список строк — упорядоченная последовательность с быстрыми
операциями на обоих концах.

```
Key: "recent:searches:user:100"
HEAD                                    TAIL
 ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │ q4 │←─→│ q3 │←─→│ q2 │←─→│ q1 │
 └────┘   └────┘   └────┘   └────┘
LPUSH добавляет сюда              RPOP забирает отсюда
```

```
LPUSH queue:tasks "task1"
RPOP queue:tasks
LRANGE recent:searches:user:100 0 9    # последние 10 элементов, без удаления
LTRIM recent:searches:user:100 0 9     # обрезать список до первых 10
BRPOP queue:tasks 5                    # блокирующий pop с таймаутом 5с
```

**Use cases:**
- Простая FIFO/LIFO очередь (подробнее —
  [07_redis_as_queue.md](./07_redis_as_queue.md)).
- Лента "последних N событий/поисков/действий" пользователя: `LPUSH` новое
  значение + `LTRIM 0 N-1`, чтобы список никогда не рос неограниченно.
- Буфер "последние просмотренные товары".

## Set

Неупорядоченная коллекция **уникальных** строк с быстрой проверкой
принадлежности и операциями над множествами.

```
Key: "tags:article:42"
┌────────────────────┐
│ "redis"            │
│ "caching"          │
│ "python"           │   ← порядок не гарантирован,
└────────────────────┘     дубликаты невозможны
```

```
SADD tags:article:42 "redis" "caching" "python"
SISMEMBER tags:article:42 "redis"     # 1 (true) — O(1) проверка
SMEMBERS tags:article:42
SINTER user:1:interests user:2:interests   # общие интересы двух пользователей
```

**Use cases:**
- Теги/категории сущности с быстрой проверкой "есть ли тег X".
- Множество уникальных значений: посетители страницы за день, ID
  пользователей, видевших уведомление (защита от повторной обработки).
- Пересечение/объединение множеств "на лету" (общие подписки, друзья друзей).

## Sorted Set (ZSet)

Множество уникальных элементов, но с числовым `score`, по которому Redis
**поддерживает элементы отсортированными** автоматически (реализовано на
skip-list (см. [01_what_is_redis.md](./01_what_is_redis.md)) + hash-таблице —
вставка и чтение диапазона одинаково быстры).

```
Key: "leaderboard"
Score    Member
1100  →  "alice"     ← ZREVRANGE отдаёт в этом порядке
 950  →  "bob"
 920  →  "charlie"
```

```
ZADD leaderboard 1100 "alice" 950 "bob" 920 "charlie"
ZREVRANGE leaderboard 0 2 WITHSCORES     # топ-3 по убыванию score
ZREVRANK leaderboard "alice"             # позиция игрока (0 = первое место)
ZINCRBY leaderboard 50 "bob"             # начислить очки, не читая текущий score
ZRANGEBYSCORE ratelimit:1.2.3.4 <старая_граница> +inf
ZREMRANGEBYSCORE ratelimit:1.2.3.4 -inf <старая_граница>
```

Ключевая идея, которую стоит унести: **score не обязан быть "очками"** — это
просто число, по которому нужна сортировка/диапазонный запрос. Отсюда два
разных, но одинаково естественных применения:

**Use cases:**
- **Leaderboard** — score = очки игрока, `ZREVRANGE` даёт топ-N мгновенно,
  без сортировки на клиенте или в SQL (`ORDER BY score DESC LIMIT N`
  каждый раз пересчитывать не нужно — структура уже отсортирована).
- **Rate limiting по времени** — score = timestamp запроса. `ZREMRANGEBYSCORE`
  выкидывает записи старше окна, `ZCARD` считает, сколько осталось — готовый
  sliding window (подробно — [06_rate_limiting.md](./06_rate_limiting.md)).
