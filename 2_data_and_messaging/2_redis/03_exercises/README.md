# Упражнения: Redis как кеш

Все упражнения используют Redis, поднятый через `../02_examples/docker-compose.yml`
(тот же самый инстанс подходит):

```bash
cd ../02_examples
docker compose up -d
cd ../03_exercises
pip install -r ../02_examples/requirements.txt
```

Каждый файл — самостоятельный скрипт: реализуйте отмеченные `# TODO:`
места и запустите его напрямую (`python 01_cache_aside.py` и т.д.) — внутри
уже есть проверки/демонстрация, которая покажет, работает ли решение.
Когда закончите — сверьтесь с `../04_exercises_answers/`.

Упражнения расположены от простого к более сложному.

---

## 1. `01_cache_aside.py` — cache-aside обёртка

Дана "медленная" функция `slow_fetch_product(product_id)` (имитирует поход
в БД через `time.sleep`). Нужно реализовать `cached_get_product(product_id)`,
которая:

1. Проверяет Redis по ключу `product:{product_id}`.
2. При промахе (cache miss) идёт в `slow_fetch_product`, кладёт результат в
   кеш с TTL и возвращает его.
3. При попадании (cache hit) возвращает значение из кеша, не трогая
   "медленную" функцию вообще.

Также нужно реализовать `invalidate_product(product_id)` — удаление ключа
из кеша (delete-on-write), которое вызывается после гипотетического
обновления товара в БД.

В конце скрипта уже есть демонстрация: холодный вызов, тёплый вызов,
инвалидация, снова холодный вызов. Ваша задача — чтобы вывод показывал
резкую разницу во времени между холодным и тёплым вызовом.

## 2. `02_ttl_invalidation.py` — TTL-инвалидация с обоснованным сроком

Сценарий: кешируем курс обмена валют, полученный от внешнего API
(`slow_fetch_exchange_rate`, тоже с искусственной задержкой). Внешний API
публикует новый курс не чаще одного раза в 5 минут.

Нужно:

1. Выбрать константу `EXCHANGE_RATE_TTL_SECONDS` и **прокомментировать в
   коде**, почему выбрано именно это значение (слишком маленький TTL —
   теряем весь смысл кеширования и бьём во внешний API чаще, чем он
   обновляет данные; слишком большой — рискуем отдавать курс, устаревший
   на десятки минут).
2. Реализовать `get_exchange_rate(base, target)` в стиле cache-aside с
   этим TTL.

Демонстрация в конце скрипта должна показать: TTL действительно
установлен на ключе (`TTL` возвращает значение, близкое к выбранному), и
что после истечения короткого тестового TTL (скрипт временно использует
уменьшенный TTL для теста, чтобы не ждать 5 минут по-настоящему) кеш
самостоятельно "забывает" значение и следующий вызов снова идёт в
`slow_fetch_exchange_rate`.

## 3. `03_rate_limiter.py` — sliding window rate limiter для эндпоинта

Нужно реализовать класс `SlidingWindowRateLimiter` с методом
`allow(client_id: str) -> bool`, ограничивающий количество запросов от
одного клиента через sorted set (см. `sliding_window_allow` в
`02_examples/04_rate_limiting.py` как отправную точку, но здесь это
оформлено как класс с `limit` и `window_seconds`, заданными в конструкторе).

Требование к демонстрации/тесту в конце файла: при `limit=3` и
`window_seconds=5`, отправить 4 запроса подряд от одного и того же
`client_id` и **явно проверить (assert)**, что первые 3 разрешены, а
**4-й (N+1-й) заблокирован**. Скрипт должен завершаться без
`AssertionError`, если лимитер реализован корректно, и падать с понятным
сообщением, если нет.

## 4. `04_recent_searches.py` — выбор структуры данных

Задача: нужно хранить **10 последних поисковых запросов** каждого
пользователя, в порядке "от нового к старому", без неограниченного роста
истории.

Сначала ответьте (в комментарии в начале файла) на вопрос: **какая
структура данных Redis для этого естественна и почему** — сравните хотя бы
с одной неподходящей альтернативой (например, "почему не Set" или "почему
не String с JSON-массивом внутри").

Затем реализуйте:

- `record_search(user_id: int, query: str) -> None` — записывает новый
  поисковый запрос, гарантируя, что хранится не больше 10 последних.
- `get_recent_searches(user_id: int) -> list[str]` — возвращает последние
  запросы, от самого нового к самому старому.

Демонстрация в конце файла должна показать, что после 15 вызовов
`record_search` для одного пользователя `get_recent_searches` возвращает
ровно 10 самых свежих запросов в правильном порядке.
