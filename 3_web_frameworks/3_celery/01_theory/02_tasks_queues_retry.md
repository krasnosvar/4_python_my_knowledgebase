# Задачи, очереди, retry

## Объявление задачи

Задача — обычная функция, помеченная декоратором `@app.task`:

```python
from app.celery_app import app


@app.task
def add(x: int, y: int) -> int:
    return x + y
```

`app` здесь — экземпляр `Celery(...)`, настроенный с адресом брокера и result
backend. Декоратор регистрирует функцию в реестре задач под именем вида
`app.tasks.add` — именно это имя (а не сама функция) кладётся в сообщение
брокера, поэтому worker должен явно импортировать модуль с задачами.

## `.delay()` vs `.apply_async()`

```python
add.delay(2, 3)
```

`.delay(*args, **kwargs)` — короткая форма для «обычного» вызова: положить
задачу в очередь по умолчанию и сразу вернуть управление. Для большинства
случаев этого достаточно.

```python
add.apply_async(
    args=(2, 3),
    countdown=10,        # выполнить не раньше чем через 10 секунд
    queue="fast",         # положить в конкретную очередь
    retry=True,
)
```

`.apply_async()` — полная форма, нужна, когда требуется что-то за пределами
«просто выполнить как можно скорее»:

- `countdown` — отложить выполнение на N секунд;
- `eta` — выполнить не раньше конкретного времени (`datetime`);
- `queue` — явно указать очередь, в которую положить задачу;
- retry-политика для самой постановки в очередь (не путать с retry самой
  задачи, см. ниже).

Оба вызова возвращают объект `AsyncResult`, через который можно спросить
статус и результат:

```python
result = add.delay(2, 3)
result.status   # 'PENDING' / 'SUCCESS' / 'FAILURE' / ...
result.get(timeout=5)  # дождаться результата (блокирующий вызов!)
```

`result.get()` в веб-обработчике — почти всегда плохая идея: он снова
блокирует запрос до готовности задачи, обнуляя весь смысл вынесения работы
в фон. `.get()` уместен в скриптах, тестах, других задачах — но не в
HTTP-хендлере.

## Несколько очередей и маршрутизация

Одна очередь на все задачи работает, пока задач мало и они однородны. На
практике задачи бывают очень разной «тяжести»: быстрая задача (например,
отправка одного email) и тяжёлая (например, генерация большого отчёта или
обработка видео) не должны конкурировать за одних и тех же worker-ов —
иначе тяжёлая задача, попавшая в очередь первой, заблокирует обработку
десятков лёгких задач, которые физически могли бы выполниться мгновенно.

Решение — несколько именованных очередей и маршрутизация задач по ним:

```python
# celery_app.py
app.conf.task_routes = {
    "app.tasks.send_report": {"queue": "heavy"},
    "app.tasks.add": {"queue": "fast"},
}
```

Дальше запускаются отдельные worker-процессы, каждый слушающий свою очередь:

```bash
celery -A app.celery_app worker -Q fast --concurrency=8 --loglevel=info
celery -A app.celery_app worker -Q heavy --concurrency=2 --loglevel=info
```

Так «быстрый» пул worker-ов с высокой конкурентностью не простаивает,
дожидаясь, пока освободится ресурс, занятый тяжёлой задачей — у тяжёлых
задач свой изолированный пул.

## Retry-логика

Задачи выполняются в отдельном процессе, который может упасть, а внешние
сервисы (API, сети, БД) — временно быть недоступны. Retry — встроенный
механизм Celery для повторных попыток:

```python
@app.task(
    bind=True,
    autoretry_for=(ConnectionError,),
    retry_backoff=True,      # экспоненциальная задержка между попытками
    retry_backoff_max=60,    # верхняя граница задержки в секундах
    max_retries=5,
)
def call_external_api(self, payload: dict) -> dict:
    return external_client.send(payload)
```

`autoretry_for` — Celery сам перехватит перечисленные исключения и
запланирует повтор. `retry_backoff=True` включает экспоненциальную задержку
(1s, 2s, 4s, 8s, ...) вместо мгновенного повтора — это важно, чтобы не
«забомбить» и без того недоступный внешний сервис лавиной немедленных
ретраев.

Для более тонкого контроля используется ручной `self.retry()` (требует
`bind=True`, чтобы у задачи был доступ к `self`):

```python
@app.task(bind=True, max_retries=3)
def fetch_data(self, url: str) -> dict:
    try:
        return http_get(url)
    except TimeoutError as exc:
        raise self.retry(exc=exc, countdown=2 ** self.request.retries)
```

## Идемпотентность — обязательное требование

Retry означает, что тело задачи может выполниться больше одного раза для
одного логического вызова. Если задача не идемпотентна — например,
`charge_customer(order_id)`, которая просто списывает деньги без проверки,
не списаны ли они уже — повторная попытка после сетевого сбоя (когда первая
попытка на самом деле уже успела списать деньги, но ответ не дошёл) спишет
деньги дважды.

Практические приёмы для идемпотентности:

- проверять состояние перед действием («уже обработано? тогда выходим»);
- использовать уникальный ключ операции (idempotency key) и хранить факт
  выполнения в БД в той же транзакции, что и сам эффект;
- делать операции естественно идемпотентными там, где это возможно
  (`UPSERT` вместо `INSERT`, установка абсолютного значения вместо
  относительного инкремента).

Если задача не идемпотентна и в ней включён retry — это не гипотетический
риск, а вопрос времени, когда двойное выполнение произойдёт на проде.
