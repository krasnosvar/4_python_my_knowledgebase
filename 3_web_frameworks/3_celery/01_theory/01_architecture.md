# Архитектура Celery: зачем выносить работу «за кадр»

## Проблема

HTTP-запрос должен отвечать быстро. Если внутри обработчика запроса вызвать
что-то тяжёлое или медленное — отправку письма, генерацию отчёта, обработку
видео, вызов внешнего API с непредсказуемой задержкой — пользователь будет
ждать ответа секунды, а то и минуты. Веб-процесс всё это время занят одним
запросом и не может обслуживать другие (или расходует воркер/поток впустую).

Решение: не делать тяжёлую работу синхронно внутри запроса. Вместо этого —
быстро отдать пользователю ответ («задача принята, id = ...»), а саму работу
выполнить отдельно, асинхронно по отношению к HTTP-циклу. Celery — один из
стандартных инструментов для этого в Python-экосистеме.

## Три компонента

**Broker (брокер сообщений).** Очередь, куда попадают задачи на выполнение.
Обычно это Redis или RabbitMQ. Веб-процесс не выполняет задачу сам — он
сериализует вызов (имя задачи + аргументы) и кладёт сообщение в очередь
брокера. Дальше веб-процесс свободен и может обрабатывать следующий запрос.

**Worker.** Отдельный процесс (или несколько процессов на одной или разных
машинах), который подключён к брокеру, забирает оттуда задачи и исполняет их.
Worker — это не часть веб-приложения, а самостоятельный процесс, который
запускается отдельной командой (`celery -A app worker`) и живёт своей жизнью
независимо от того, жив ли в данный момент веб-сервер.

**Result backend.** Хранилище, куда worker пишет результат выполнения задачи
и её статус (`PENDING`, `STARTED`, `SUCCESS`, `FAILURE`). Клиент, который
поставил задачу в очередь, может прийти позже с `task_id` и спросить: «готово?
что вернулось?». Result backend тоже часто на Redis, но это концептуально
отдельная система от брокера.

## Поток целиком

```
клиент → API-процесс
             │
             │ 1. кладёт задачу (имя + аргументы) в очередь брокера
             ▼
          broker (Redis / RabbitMQ)
             │
             │ 2. worker слушает очередь и забирает задачу
             ▼
          worker (отдельный процесс)
             │
             │ 3. выполняет функцию-задачу
             │ 4. пишет результат/статус
             ▼
        result backend (например, Redis)
             │
             │ 5. клиент по task_id опрашивает статус/результат
             ▼
          клиент получает результат
```

API-процесс после шага 1 сразу возвращает ответ клиенту (обычно
`202 Accepted` с `task_id`) и не ждёт выполнения задачи.

## Почему broker и result backend можно (и стоит) разносить

Ничто не мешает использовать Redis сразу и как брокер, и как result backend —
это самый частый вариант для небольших/средних проектов: одна система,
меньше инфраструктуры. Но у брокера и result backend разная нагрузка и разные
требования к надёжности:

- брокер должен гарантированно не терять сообщения о постановке задачи
  (иначе задача просто исчезнет и никогда не выполнится);
- result backend хранит результаты, которые часто нужны недолго (пока клиент
  не заберёт ответ), и потеря одного результата не так критична, как потеря
  самой задачи.

В более требовательных системах брокер держат на RabbitMQ (сильные гарантии
доставки, подтверждения обработки), а result backend — на Redis или в базе
данных. Для учебных целей и для большинства реальных небольших проектов
связка «Redis как и то, и другое» — нормальный старт.
