# Структура Django-проекта

Django разделяет код на два уровня: **project** (проект целиком) и
**apps** (приложения внутри проекта). Это разделение — не формальность,
а способ держать код переиспользуемым и не превращать всё в одну большую
папку.

## Project: конфигурация, а не логика

Пакет проекта (обычно называется `config` или по имени проекта) отвечает
за то, как приложение запускается и настраивается, а не за бизнес-логику:

- `settings.py` — вся конфигурация: подключение к БД, список приложений
  (`INSTALLED_APPS`), middleware, статика, секреты (через переменные
  окружения, а не хардкод);
- `urls.py` — корневая маршрутизация, обычно просто подключает `urls.py`
  каждого приложения через `include()`;
- `wsgi.py` / `asgi.py` — точки входа для продакшен-серверов (Gunicorn,
  Uvicorn/Daphne для async). WSGI — синхронный интерфейс «сервер ↔
  приложение», ASGI — его асинхронный преемник (подробнее — в
  [FastAPI: HTTP и первое приложение](../../1_fastapi/01_theory/01_http_and_first_app.md)).

## App: единица бизнес-логики

Приложение (app) — это модуль с моделями, view-функциями и своей
маршрутизацией вокруг одной предметной области (`users`, `orders`,
`library`). Типичная структура:

- `models.py` — модели (таблицы БД);
- `views.py` — обработчики запросов;
- `urls.py` — маршруты именно этого приложения;
- `admin.py` — регистрация моделей в Django Admin;
- `migrations/` — история изменений схемы (генерируется автоматически,
  но коммитится в git — это часть кода, а не мусор);
- `apps.py` — конфиг приложения (`AppConfig`), обычно трогать не нужно.

## Модель и ORM: минимальный пример

**ORM** (Object-Relational Mapping) — слой, который позволяет работать с
таблицами базы данных как с обычными Python-классами, без ручного
написания SQL. В Django каждая таблица описывается **моделью** — классом,
унаследованным от `models.Model`, где каждый атрибут класса — колонка:

```python
# library/models.py
from django.db import models


class Book(models.Model):
    title = models.CharField(max_length=200)   # колонка VARCHAR(200)
    published_year = models.IntegerField()     # колонка INTEGER
```

Из этого описания Django сам сгенерирует таблицу (через миграции, см.
ниже) с колонками `id` (добавляется автоматически), `title` и
`published_year`.

Запросы к таблице делаются через **менеджер** — объект `Book.objects`,
который Django добавляет в каждую модель:

```python
Book.objects.all()                              # все книги
Book.objects.filter(published_year=2001)        # WHERE published_year = 2001
Book.objects.filter(published_year__gte=2000)   # WHERE published_year >= 2000
```

Двойное подчёркивание в `published_year__gte` — синтаксис **lookup'ов**
Django: слева имя поля, справа операция сравнения. `gte` — «greater than
or equal» (`>=`), есть также `gt` (`>`), `lt` (`<`), `lte` (`<=`),
`contains`, `in` и другие. Через `__` можно и переходить по связям
между моделями: `author__name="Unknown"` — «у связанного автора имя
равно Unknown».

Результат `filter()` — **QuerySet**, описание запроса, которое ещё не
выполнено. Почему это важно и к каким ошибкам приводит — в следующем
уроке, [02_lazy_querysets.md](./02_lazy_querysets.md).

## Зачем вообще делить на приложения

Разделение по смыслу (а не всё в одном `models.py` на 2000 строк) даёт:
- независимое тестирование и переиспользование модуля в другом проекте;
- явные границы ответственности — понятно, где искать код про заказы, а
  где про пользователей;
- возможность подключать/отключать приложение через `INSTALLED_APPS`, не
  трогая остальной проект.

Приложение регистрируется в `settings.py`:

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    # ...стандартные django.contrib.*
    "library",   # наше приложение
]
```

Без этой строчки Django не увидит модели приложения и не создаст под них
миграции.

## manage.py: основные команды

`manage.py` — точка входа для служебных команд:

- `python manage.py runserver` — локальный dev-сервер;
- `python manage.py makemigrations` — сгенерировать файлы миграций на
  основе изменений в `models.py`;
- `python manage.py migrate` — применить миграции к базе;
- `python manage.py shell` — интерактивная Python-консоль с загруженными
  настройками Django (удобно, чтобы поиграться с ORM руками);
- `python manage.py createsuperuser` — создать администратора для
  `/admin/`.

Порядок `makemigrations` -> `migrate` важен: первая команда только
описывает изменения в файле миграции (его нужно закоммитить), вторая —
реально применяет их к базе.
