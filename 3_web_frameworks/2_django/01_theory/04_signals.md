# Сигналы (signals)

Django позволяет подписаться на события жизненного цикла моделей и
получать уведомление, когда что-то произошло — например, объект был
сохранён или удалён.

## Основные сигналы

- `pre_save` / `post_save` — до/после сохранения объекта (`Model.save()`);
- `pre_delete` / `post_delete` — до/после удаления объекта;
- `m2m_changed` — изменение состава `ManyToMany`-связи (добавление,
  удаление, очистка).

Подключаются через декоратор `@receiver`:

```python
from django.db.models.signals import post_save
from django.dispatch import receiver

from .models import Book, ReadingStats


@receiver(post_save, sender=Book)
def create_reading_stats(sender, instance: Book, created: bool, **kwargs) -> None:
    if created:
        ReadingStats.objects.create(book=instance)
```

Такой обработчик обычно регистрируют в `apps.py` (метод `ready()`) или
импортируют в отдельном модуле `signals.py`, который явно подключается
при старте приложения.

## Для чего годятся

- побочные эффекты при создании/изменении объекта (создать связанную
  запись, отправить событие);
- инвалидация кэша при изменении данных;
- аудит/логирование изменений без изменения кода, который сохраняет
  объект.

## Почему использовать осторожно

Главная проблема сигналов — **неявность**. Код, который вызывает
`book.save()`, ничего не знает о том, что где-то в другом файле проекта
подписан обработчик, который что-то ещё сделает при сохранении. Это
усложняет:

- **чтение кода** — чтобы понять полный эффект `save()`, нужно знать обо
  всех подписчиках, а они могут быть раскиданы по разным приложениям;
- **тестирование** — юнит-тест модели неожиданно тянет за собой побочные
  эффекты сигнала, если явно их не отключить;
- **отладку** — порядок выполнения нескольких обработчиков на один сигнал
  не всегда очевиден, а падение внутри обработчика может неожиданно
  сорвать основную операцию.

Во многих случаях явный вызов метода или сервисной функции — надёжнее и
понятнее сигнала:

```python
# вместо сигнала на post_save
def create_book_with_stats(**fields) -> Book:
    book = Book.objects.create(**fields)
    ReadingStats.objects.create(book=book)
    return book
```

Так весь эффект операции виден в одном месте, его легко тестировать и
следить за порядком выполнения. Сигналы стоит оставлять для случаев,
когда вызывающий код принципиально не может (и не должен) знать о
побочном эффекте — например, интеграция с кодом сторонней библиотеки,
которую нельзя изменить напрямую.
