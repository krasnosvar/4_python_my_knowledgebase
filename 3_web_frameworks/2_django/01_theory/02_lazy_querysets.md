# Django ORM: ленивые (lazy) QuerySet'ы

## QuerySet не выполняет запрос сразу

`QuerySet` — это не результат запроса, а его описание. Каждый вызов `.filter()`,
`.exclude()`, `.order_by()`, `.annotate()` не бьёт в базу — он строит SQL-запрос
и возвращает новый `QuerySet` с обновлённым описанием. Так можно свободно
"цеплять" условия одно за другим:

```python
qs = Book.objects.filter(published_year__gte=2000)
qs = qs.exclude(author__name="Unknown")
qs = qs.order_by("-published_year")
# до этой строки в БД не ушло ни одного запроса
```

Запрос реально выполняется только в момент, когда QuerySet нужно превратить
в конкретные данные:

- итерация (`for book in qs`);
- приведение к списку (`list(qs)`);
- проверка на пустоту (`bool(qs)`, `if qs:`);
- срез с шагом или `len(qs)` (обычный slice `qs[:10]` остаётся ленивым —
  превращается в `LIMIT`/`OFFSET` и не выполняется сам по себе, а вот `len()`
  уже дергает базу);
- `repr()` в Django shell (когда QuerySet просто печатается).

## Почему это важно

Ленивость — это фича: она позволяет собирать запрос по частям (например,
базовый QuerySet в одном месте, дополнительную фильтрацию — в другом,
ближе к вызову), не тратя лишние обращения к БД.

Но у неё есть обратная сторона: **обращение к related-полю объекта — это
тоже "исполнение запроса"**, просто отдельного и неявного. Если запрос выше
не подгрузил связанные данные, каждое обращение к `book.author` внутри
цикла — это самостоятельный SQL-запрос к базе.

```python
books = Book.objects.all()          # SQL пока не ушёл

for book in books:                   # первый запрос: SELECT * FROM book
    print(book.author.name)          # +1 запрос на КАЖДУЮ книгу
```

Если книг 100 — это 101 запрос вместо одного-двух. Это и есть проблема
N+1, к которой ленивость QuerySet имеет прямое отношение: код выглядит
невинно (`book.author.name`), но за ним скрывается поход в БД.

## Как увидеть реальные SQL-запросы

Самый надёжный способ посчитать запросы — `CaptureQueriesContext`
(работает независимо от `DEBUG`):

```python
from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as ctx:
    for book in Book.objects.all():
        _ = book.author.name

print(len(ctx.captured_queries))
```

Более простой, но менее надёжный вариант — `connection.queries` (список
последних выполненных запросов), однако он наполняется только при
`settings.DEBUG = True`. Для отладки в браузере удобен пакет
`django-debug-toolbar` — он показывает панель с полным списком SQL-запросов
и их числом на каждой странице.

## Итог

- QuerySet ленив: цепочка фильтров ничего не стоит, пока её не начали
  "читать".
- Каждое обращение к related-объекту в цикле без предзагрузки — это
  отдельный запрос. Про то, как избежать этого — см.
  [03_select_related_prefetch_related.md](./03_select_related_prefetch_related.md).
