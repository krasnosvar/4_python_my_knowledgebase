# select_related vs prefetch_related

Оба метода решают одну проблему — N+1 запросы при обращении к related-полям
(см. [02_lazy_querysets.md](./02_lazy_querysets.md)), но делают это
принципиально по-разному, и от этого зависит, когда какой метод уместен.

## select_related: один запрос через SQL JOIN

`select_related` разворачивается в `JOIN` — Django добавляет связанную
таблицу прямо в исходный SQL-запрос и забирает все данные за один поход
в БД:

```python
books = Book.objects.select_related("author")

for book in books:
    print(book.author.name)   # данные уже в памяти, доп. запросов нет
```

Работает только для связей, где "внешний ключ смотрит наружу" из текущей
модели — `ForeignKey` и `OneToOneField` **в прямом направлении** (у Book
есть `author_id`, поэтому от Book к Author можно сделать JOIN). Для
обратных связей (`Author` -> его книги) и `ManyToMany` JOIN дал бы
дублирование строк (одна строка Author на каждую его книгу), поэтому
`select_related` для них не подходит.

Можно проходить через несколько связей: `select_related("author",
"publisher__country")`.

## prefetch_related: отдельный запрос + склейка в Python

`prefetch_related` выполняет **дополнительный самостоятельный запрос**
(обычно один, но может быть больше — для `Prefetch`-объектов с кастомной
логикой) и затем сам, в Python, раскладывает результаты по нужным объектам:

```python
books = Book.objects.prefetch_related("reviews")

for book in books:
    print(book.reviews.count())   # это уже данные из памяти, не новый запрос
```

Под капотом это два запроса: `SELECT * FROM book`, затем `SELECT * FROM
review WHERE book_id IN (...)`, после чего Django сам сопоставляет отзывы
с книгами по `book_id`. Общее число запросов не зависит от количества книг —
оно фиксировано (2, а не N+1).

`prefetch_related` — единственный вариант для:
- обратных `ForeignKey` (`author.books.all()`);
- `ManyToMany` (`book.tags.all()`);
- случаев, когда JOIN был бы неэффективен из-за огромного объёма
  дублирующихся строк (например, у книги тысячи отзывов — JOIN размножил
  бы строку книги тысячу раз).

## Как выбирать

| Тип связи                                   | Метод              |
|----------------------------------------------|--------------------|
| ForeignKey / OneToOne, прямое направление     | `select_related`   |
| Обратный ForeignKey (`related_name`)          | `prefetch_related` |
| ManyToMany (в любом направлении)              | `prefetch_related` |

Типичные ошибки:
- **выбрать не тот метод** — например, попытаться `select_related("tags")`
  для M2M: Django поднимет ошибку, потому что JOIN тут не применим;
- **забыть предзагрузку** — код работает и на тестовых данных с парой
  строк выглядит нормально, а на проде с тысячами записей превращается в
  тысячи запросов;
- **добавить лишнюю предзагрузку** — вызвать `prefetch_related` для поля,
  которое в шаблоне/сериализаторе не используется: это лишний запрос и
  лишняя память без всякой пользы.

## Как измерить эффект

Самый честный способ оценки — сравнить число SQL-запросов до и после,
через `CaptureQueriesContext` (см. пример в
[02_lazy_querysets.md](./02_lazy_querysets.md)). Именно так это сделано в
`02_examples/library/management/commands/demo_n_plus_one.py`: одна и та же
логика прогоняется дважды — наивно и с предзагрузкой — и печатается
разница в количестве запросов.
