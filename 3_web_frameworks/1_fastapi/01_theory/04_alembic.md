# Alembic: миграции схемы поверх SQLAlchemy

SQLAlchemy описывает схему БД в виде Python-классов (моделей), но сам по себе
не умеет менять уже существующую БД со временем — создать таблицу один раз
через `Base.metadata.create_all()` достаточно только для игрушечных примеров.
В реальном проекте схема меняется постепенно (добавили колонку, поменяли тип,
добавили индекс), и БД должна эволюционировать вместе с кодом, без потери
данных. Для этого используется Alembic — инструмент миграций для SQLAlchemy.

## Идея

Каждое изменение схемы фиксируется как отдельная **миграция** — файл с двумя
функциями: `upgrade()` (применить изменение) и `downgrade()` (откатить его).
Миграции пронумерованы/связаны в цепочку (каждая знает предыдущую), поэтому
Alembic всегда может понять, какие миграции уже применены к конкретной БД, а
какие ещё нет, и накатить/откатить именно недостающие.

## Инициализация проекта

```bash
alembic init alembic
```

Создаёт:

```
alembic.ini          # конфигурация, включая строку подключения к БД
alembic/
  env.py              # точка входа: как Alembic подключается к БД и откуда берёт метаданные моделей
  script.py.mako        # шаблон, по которому генерируются новые файлы миграций
  versions/            # сами файлы миграций
```

В `env.py` нужно один раз указать Alembic, где искать метаданные моделей —
обычно это `target_metadata = Base.metadata` из модуля с SQLAlchemy-моделями.
Именно отсюда Alembic узнаёт, как выглядит "целевая" схема при автогенерации.

## Создание миграции: autogenerate

```bash
alembic revision --autogenerate -m "create items table"
```

Alembic сравнивает текущее состояние `target_metadata` (то есть то, что описано
в Python-моделях) с реальной схемой БД (к которой подключается через
`alembic.ini`), и генерирует файл миграции с найденной разницей:

```python
def upgrade() -> None:
    op.create_table(
        "items",
        sa.Column("id", sa.Integer(), primary_key=True),
        sa.Column("name", sa.String(length=100), nullable=False),
        sa.Column("price", sa.Float(), nullable=False),
    )


def downgrade() -> None:
    op.drop_table("items")
```

Autogenerate — это помощник, а не гарантия правильности: сгенерированный файл
нужно прочитать и проверить перед применением.

## Применение миграций

```bash
alembic upgrade head      # накатить все миграции до последней
alembic upgrade +1        # накатить одну следующую миграцию
alembic downgrade -1      # откатить одну миграцию назад
alembic downgrade base    # откатить всё
alembic current            # какая миграция сейчас применена к БД
alembic history             # список всех миграций в порядке цепочки
```

## Когда autogenerate не справляется

Alembic сравнивает структуру таблиц, но не понимает намерение разработчика.
Есть случаи, где autogenerate либо ошибается, либо не видит изменения вообще:

- **Переименование колонки/таблицы.** Autogenerate увидит это как "удалили
  одну колонку, добавили другую" — то есть предложит `drop_column` +
  `add_column`, что в проде означает **потерю данных** в этой колонке. Нужно
  вручную заменить сгенерированный код на `op.alter_column(..., new_column_name=...)`
  (или `op.rename_table`).
- **Data migrations.** Alembic отслеживает только структуру схемы (DDL), но не
  данные. Если новая колонка должна быть заполнена вычисленным значением для
  существующих строк (например, разбить одно поле на два) — это пишется
  вручную через `op.execute("UPDATE ...")` внутри той же миграции, отдельным
  шагом после изменения структуры.
- **Смена типа данных с потерей точности** (например, `Float` → `Integer`) —
  Alembic сгенерирует `alter_column`, но не проверит и не предупредит, что
  часть данных может округлиться или не сконвертироваться. Такие миграции
  стоит проверять на копии продовых данных перед применением.
- **Сложные constraints** (составные уникальные ограничения, частичные
  индексы, `CHECK`) — autogenerate поддерживает не все диалекты БД одинаково
  полно; иногда такие вещи проще дописать в миграцию руками через `op.execute`.

Практическое правило: autogenerate — это черновик. Перед `alembic upgrade`
файл миграции всегда стоит прочитать целиком, особенно раздел `downgrade()` —
именно он часто получается некорректным или неполным при автогенерации.
