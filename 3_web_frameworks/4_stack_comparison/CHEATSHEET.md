## FastAPI vs Django vs Celery

Подробно: [01_fastapi_vs_django.md](./01_theory/01_fastapi_vs_django.md),
[02_where_celery_fits.md](./01_theory/02_where_celery_fits.md).
Celery не альтернатива фреймворку, а слой поверх любого из них.

| Критерий | Django | FastAPI | Celery |
| :--- | :--- | :--- | :--- |
| Что решает | HTTP-запрос → ответ | HTTP-запрос → ответ | работа, которая не должна блокировать ответ |
| Подход | batteries included | минималистичное async-first ядро | очередь + отдельные worker'ы |
| Интерфейс | WSGI (ASGI есть, ORM синхронная) | ASGI | брокер (Redis / RabbitMQ) |
| ORM, миграции | встроены | SQLAlchemy + Alembic руками | использует модели приложения |
| Админка | из коробки | нет | — |
| Auth, права, формы | встроены | руками | — |
| Валидация, OpenAPI | DRF | Pydantic + `/docs` автоматически | — |
| DI | нет явного DI, неявные механизмы | явный `Depends` | — |
| Лучше всего для | монолит, CRM/ERP, много сущностей | API-сервис, BFF, ML-инференс, шлюз; I/O-bound нагрузка | долгие/ненадёжные операции, retry, расписание |
| Цена | «магия», async «прибит сверху» | больше решений на старте, дисциплина async | брокер + worker'ы + beat в эксплуатации |

## Проект → стек

Подробно: [03_choosing_by_project_type.md](./01_theory/03_choosing_by_project_type.md).

| Проект | Стек | Фон |
| :--- | :--- | :--- |
| Маленький сервис, прототип, MVP без админки | FastAPI + SQLAlchemy (SQLite/PostgreSQL) | `BackgroundTasks`, Celery пока не нужен |
| Монолит с админкой, разнородными сущностями, бизнес-логикой | Django + Django ORM + admin (+ DRF для API) | Celery для тяжёлых/фоновых операций |
| Высоконагруженный async API, много одновременных I/O-ожиданий | FastAPI + async-драйверы БД и HTTP-клиенты | Celery для всего, что не должно идти внутри запроса |
| Высоконагруженный API + внутренняя админка | FastAPI снаружи + отдельный небольшой Django-сервис для админки | по потребности |

## Быстрый чек-лист

| Вопрос | Да → |
| :--- | :--- |
| Нужны админка / формы / права из коробки прямо сейчас? | Django |
| Нагрузка I/O-bound и важна async-производительность на масштабе? | FastAPI |
| Операции дольше таймаута HTTP, ненадёжные внешние вызовы, нужны retry/расписание? | Celery — при любом фреймворке |
| Команда глубоко знает один фреймворк, жёстких требований к масштабу нет? | тот, что команда знает |
| Потеря фоновой задачи при деплое допустима? | `BackgroundTasks` / `asyncio.create_task`, без Celery |

- ⚠️ «Async-first» ≠ «всегда быстрее»: CPU-bound работа (парсинг, шифрование, отчёты) не ускоряется event loop'ом.
- ⚠️ Блокирующий вызов в `async def` FastAPI роняет производительность всех запросов — см. [02_async_endpoints.md](../1_fastapi/01_theory/02_async_endpoints.md).
- ⚠️ Django ради 3 эндпоинтов и одной таблицы — платите настройкой за неиспользуемые батарейки.
- ⚠️ `asyncio.create_task` вместо Celery для критичной задачи — она пропадёт при рестарте процесса.
