# Критерии выбора по типу проекта

Ниже — практический ориентир: какой стек брать в зависимости от формы
проекта, а не от личных предпочтений. Критерии работают вместе, а не
по отдельности — редко бывает так, что решает только один пункт.

## Маленький сервис / прототип / MVP без сложной админки

**Стек: FastAPI (+ SQLite/PostgreSQL через SQLAlchemy, без Celery, пока
не понадобится)**

- Быстро поднимается, минимум инфраструктуры.
- Автогенерируемая OpenAPI-документация полезна, когда сервис будут
  дергать другие команды/фронтенд с первого дня.
- Если фоновой тяжёлой работы нет или она тривиальна (отправить одно
  письмо) — `BackgroundTasks` из FastAPI достаточно, отдельный брокер
  не нужен.
- Добавлять Django ради 3 эндпоинтов и одной таблицы избыточно: платите
  сложностью настройки (settings.py, apps, миграции Django ORM) за
  батарейки, которыми не пользуетесь.

## Монолит с админкой, разнородными сущностями, командой из бизнес-логики

**Стек: Django (+ Django ORM, admin, DRF если нужен API) + Celery для
тяжёлых/фоновых операций**

- Готовая админка экономит месяцы на внутренних CRUD-интерфейсах для
  нетехнических пользователей (менеджеров, поддержки).
- Встроенные auth/permissions, формы, миграции снижают количество
  архитектурных решений, которые иначе пришлось бы принимать и
  поддерживать вручную.
- Как только появляется тяжёлая или ненадёжная операция (генерация
  отчёта, рассылка, интеграция с внешним API с непредсказуемой
  задержкой) — подключается Celery поверх, без изменения архитектуры
  веб-слоя.
- Синхронная природа Django обычно не является узким местом для этого
  класса проектов: нагрузка чаще CPU/DB-bound на конкретных операциях,
  а не на масштабе "десятки тысяч одновременных долгоживущих
  I/O-ожиданий".

## Высоконагруженный async API (много одновременных I/O-bound запросов)

**Стек: FastAPI (async-драйверы БД, async HTTP-клиенты) + Celery для
всего, что не должно исполняться внутри запроса**

- Когда сервис держит много одновременных соединений, которые
  преимущественно ждут (внешние API, БД, очереди), async-модель
  FastAPI даёт лучшую утилизацию процесса на тех же ресурсах, чем
  синхронный WSGI-стек.
- Критично соблюдать дисциплину: никаких блокирующих синхронных
  вызовов внутри `async def` — иначе весь выигрыш от async теряется
  (см. `1_fastapi/01_theory/02_async_endpoints.md`).
- Тяжёлые/долгие операции (не «дождаться I/O», а «посчитать 30 секунд»
  или «сделать что-то ненадёжное, что может не получиться с первого
  раза») уводятся в Celery — иначе они точно так же будут держать
  event loop, только по CPU, а не по ожиданию.
- Если проекту всё же нужна админка/внутренние CRUD-инструменты —
  ничего не мешает держать отдельный небольшой Django-сервис для
  внутренней админки рядом с высоконагруженным FastAPI-сервисом снаружи
  — это не взаимоисключающие вещи, а разные сервисы под разные задачи.

## Быстрый чек-лист для принятия решения

1. Нужна ли готовая админка/формы/права из коробки прямо сейчас? →
   Django.
2. Нагрузка преимущественно I/O-bound и важна async-производительность
   на масштабе? → FastAPI.
3. Есть операции дольше типичного таймаута HTTP-запроса, ненадёжные
   внешние вызовы, нужны ретраи/расписание? → Celery, независимо от
   выбора веб-фреймворка.
4. Команда уже глубоко знает один из фреймворков и проект не предъявляет
   жёстких требований по производительности/масштабу? → идти с тем, что
   команда знает — скорость разработки на старте обычно важнее
   теоретической оптимальности стека.
