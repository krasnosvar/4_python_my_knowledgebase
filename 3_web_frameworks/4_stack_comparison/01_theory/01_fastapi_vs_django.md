# FastAPI vs Django: async-first против batteries-included

Оба фреймворка решают одну и ту же базовую задачу — принять HTTP-запрос и
вернуть ответ, — но исходят из разных философий, и это определяет, где
каждый из них ощущается естественно, а где превращается в борьбу с
инструментом.

## Django: batteries included

Django изначально проектировался как фреймворк "для всего": ORM, система
миграций, админка, аутентификация и права доступа, формы и их валидация,
шаблонизатор, защита от CSRF/XSS из коробки, i18n. Всё это идёт единым
пакетом и спроектировано так, чтобы работать вместе без дополнительной
сборки.

Плюсы такого подхода:

- Не нужно принимать десятки мелких архитектурных решений (какой ORM,
  какая система миграций, как делать админку) — за тебя их уже приняли
  разработчики Django, и решения проверены годами эксплуатации.
- Огромная экосистема пакетов (`django-rest-framework`,
  `django-allauth`, `django-cms` и т.д.), рассчитанных на конкретно эту
  батарейную модель.
- Админка `django.contrib.admin` — это готовая CRUD-панель по моделям,
  которая в большинстве внутренних инструментов и MVP закрывает
  потребность в отдельном админ-фронтенде.

Минусы:

- Django исторически синхронный (WSGI — синхронный интерфейс между
  сервером и приложением, один запрос держит поток до конца; ASGI — его
  асинхронный преемник, см.
  [HTTP и первое приложение](../../1_fastapi/01_theory/01_http_and_first_app.md)).
  Поддержка `async def` view и ASGI появилась, но большая часть экосистемы (ORM, множество
  сторонних пакетов) остаётся синхронной — асинхронность получается
  "прибитой сверху", а не пронизывающей фреймворк насквозь.
- Больше "магии" и соглашений (conventions over configuration) — это
  ускоряет разработку, пока ты идёшь по проторенной дороге, и мешает,
  когда нужно что-то нестандартное.

## FastAPI: async-first, минималистичное ядро

FastAPI — это тонкий слой поверх Starlette (ASGI) и Pydantic. Сам
фреймворк не диктует, какую ORM использовать, как хранить данные, как
делать админку — это осознанно оставлено разработчику.

Плюсы:

- Построен вокруг `async`/`await` с самого начала — `async def`-роуты,
  async-зависимости, async-драйверы БД (`asyncpg`, `asyncmy`) работают
  без обходных путей. Для I/O-bound нагрузки (много одновременных
  запросов, которые ждут ответа от БД/внешних API) это даёт заметно
  лучшую пропускную способность на тех же ресурсах, чем классический
  синхронный WSGI-процесс с пулом воркеров.
- Автоматическая валидация входных данных и генерация OpenAPI-схемы
  (Swagger UI/ReDoc) прямо из type hints и Pydantic-моделей — почти
  бесплатно получаешь контракт API и документацию.
- Явная Dependency Injection (`Depends`) вместо неявных механизмов
  Django — проще тестировать и переиспользовать логику.

Минусы:

- "Батареек" нет: ORM, миграции, аутентификация, права — всё это
  подключается руками (обычно SQLAlchemy + Alembic + свои
  security-схемы). Больше решений на старте проекта, больше шаблонного
  кода, который в Django уже написан за тебя.
- Нет готовой админки. Если внутреннему инструменту нужен CRUD-интерфейс
  "из коробки" — его придётся либо писать самому, либо тащить отдельный
  пакет.
- Асинхронность — это не бесплатный бонус, а требование дисциплины:
  один блокирующий синхронный вызов внутри `async def` (обычный
  `requests.get`, синхронный драйвер БД, `time.sleep`) стопорит весь
  event loop и роняет производительность всех запросов одновременно, а
  не только текущего. Команде нужно понимать эту модель, иначе async
  превращается в источник трудноуловимых деградаций.

## Сравнение по критериям

То же самое, что выше, сведённое в таблицу. Celery в последней колонке —
не третий кандидат на выбор, а слой, который добавляется к любому из двух
(подробно — в [02_where_celery_fits.md](./02_where_celery_fits.md)).

| Критерий | Django | FastAPI | Роль Celery |
| :--- | :--- | :--- | :--- |
| Философия | batteries included, conventions over configuration | минималистичное ядро (Starlette + Pydantic), стек собираете сами | отдельный слой инфраструктуры для фоновой работы |
| Интерфейс | исторически WSGI; `async def` view и ASGI есть, но ORM и много пакетов синхронные | ASGI, async-first насквозь | не HTTP: worker'ы читают очередь брокера |
| ORM и миграции | встроены (Django ORM, `makemigrations`/`migrate`) | нет: обычно SQLAlchemy + Alembic | задачи переиспользуют модели веб-приложения |
| Админка | `django.contrib.admin` из коробки | нет: писать самому или отдельный пакет | — |
| Auth и права | встроены | подключаются руками (свои security-схемы) | — |
| Валидация и документация API | формы; для API — DRF | Pydantic + OpenAPI/Swagger из type hints автоматически | — |
| Внедрение зависимостей | неявные механизмы (в т.ч. сигналы) | явный `Depends`, легко подменить в тестах | — |
| Сильная сторона | монолит с бизнес-логикой и множеством сущностей, быстрый старт по проторенной дороге | много одновременных I/O-bound запросов на тех же ресурсах | тяжёлая, долгая, ненадёжная работа вне запроса: retry, расписание, отдельное масштабирование |
| Цена / риск | «магия» мешает нестандартному; async «прибит сверху» | больше решений и шаблонного кода на старте; блокирующий вызов в `async def` стопорит весь event loop | брокер, worker'ы, beat — отдельно деплоить и мониторить |
| CPU-bound нагрузка | не решает | не решает (async помогает только ожиданию) | выносит в отдельные процессы/машины |

## Async-first не значит "всегда быстрее"

Важно не путать "async-first архитектура" с "автоматически более
высокой производительностью". Если нагрузка CPU-bound (парсинг,
шифрование, генерация отчётов в процессе) — async не помогает вообще,
там важны процессы/потоки и распараллеливание вычислений, а не event
loop. FastAPI даёт выгоду именно там, где много одновременных
операций, которые преимущественно *ждут* (сеть, диск, БД), а не
считают.

## Когда что выбирать

- **Django** — когда нужен монолит с бизнес-логикой, админкой,
  пользователями/правами и вы хотите двигаться быстро по проторенной
  дороге: внутренние CRM/ERP, платформы с большим количеством
  разнородных сущностей, где админка экономит месяцы разработки.
- **FastAPI** — когда сервис — это в первую очередь API (микросервис,
  BFF, ML-инференс, интеграционный шлюз), важна async-производительность
  под I/O-bound нагрузкой, и вы готовы сами собрать стек (ORM, миграции,
  auth) под конкретные нужды, не платя за то, чем не пользуетесь.

Ни один из вариантов не является "правильным по умолчанию" — выбор
определяется формой проекта, а не личными предпочтениями к синтаксису.
