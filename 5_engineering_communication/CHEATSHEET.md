## 01. Документирование работы

Подробнее: [01_documenting_your_work/01_theory/README.md](./01_documenting_your_work/01_theory/README.md)

| Шаг | Что написать | Пример |
| :--- | :--- | :--- |
| Проблема | что было не так или что было нужно | «в пик обработка заказов отставала на 15–20 минут» |
| Решение | что сделано и каким способом, ключевые решения | «параллельные воркеры, батчи по 50, дедупликация на входе» |
| Эффект | что изменилось, измеримо или наблюдаемо | «отставание в пик — 1–2 минуты, дубли исчезли» |

| Проверка | Вопрос к фразе |
| :--- | :--- |
| Конкретность | без контекста понятно, что именно изменилось? можно спросить «насколько?» |
| Влияние, а не стек | если убрать названия технологий, смысл остаётся? |
| Честность | нет точной цифры — опишите наблюдаемый эффект, не выдумывайте метрику |

| Аудитория | Что давать |
| :--- | :--- |
| Техническая | компоненты, архитектурные решения, компромиссы, почему так |
| Нетехническая | скорость, надёжность, стоимость, риски, время; реализация — максимум одно предложение |
| Смешанная | «слоями»: первое предложение — эффект, второе — как достигнуто |

- ⚠️ «Оптимизировал», «улучшил», «участвовал», «занимался поддержкой» без результата.
- ⚠️ «Стек: Kafka, Postgres» отдельным пунктом вместо роли инструмента в решении.

## 02. Объяснение технической работы

Подробнее: [02_explaining_technical_work/01_theory/README.md](./02_explaining_technical_work/01_theory/README.md)

| Объяснение за минуту (30–60 с) | Содержание |
| :--- | :--- |
| Что это | одно предложение в терминах слушателя |
| Зачем | какую проблему решает, какую возможность даёт |
| Что это даёт | эффект для пользователя, команды, системы |

| Слушатель | Что ему нужно |
| :--- | :--- |
| Нетехнический стейкхолдер | эффект и риски, без механизма |
| Коллега из смежной команды | контракты API, форматы данных, зависимости — то, что касается границы |
| Новый член команды | «почему так исторически сложилось» и привычные в команде термины |

| Сигнал | Значит |
| :--- | :--- |
| Переспрашивает базовые термины | слишком сложно |
| Спрашивает то, что вы уже сказали обобщённо | слишком просто, нужны детали |

- Термин для незнакомой аудитории — с расшифровкой в скобках при первом использовании.
- ⚠️ Метафора, искажающая суть, хуже термина с пояснением.

## 03. Диалог под давлением

Подробнее: [03_professional_dialogue/01_theory/README.md](./03_professional_dialogue/01_theory/README.md)

| Вместо | Говорить |
| :--- | :--- |
| «Я не мог знать, никто не предупредил» (оправдание) | факт → причина → следующий шаг: «оценка не учла рост в N раз, пересматриваю лимиты с запасом» |
| Выдуманный ответ наугад | «я не проверял этот случай, уточню и вернусь с ответом» |
| Немедленный ответ на неоднозначный вопрос | уточняющий вопрос: «вы про пиковую нагрузку или средний случай?» |

| Признание ошибки | Содержание |
| :--- | :--- |
| Факт | что произошло, без преуменьшения и самобичевания |
| Причина | на уровне процесса или решения |
| Следующий шаг | как исправить последствия и не повторить |

- ⚠️ Объяснять контекст до того, как прозвучал вопрос, — признак защитной позиции.
- ⚠️ Уточняющие вопросы как тактика затягивания, когда вопрос уже ясен.

## 04. Переговоры об условиях

Подробнее: [04_negotiation_basics/01_theory/README.md](./04_negotiation_basics/01_theory/README.md)

| Понятие | Суть | Пример |
| :--- | :--- | :--- |
| Позиция | что заявлено | «нужно к пятнице» |
| Интерес | зачем это нужно | «к пятнице демо для партнёра» |
| BATNA | что будет без соглашения; нижняя граница | «возьму задачу — выпадет X из плана; или в следующий спринт» |
| Аргумент через ценность | вариант лучше решает интерес другой стороны | «без тестов граничных случаев риск багов дороже недели задержки» |
| Аргумент через давление ⚠️ | статус, эмоция, ультиматум | «иначе откажусь от задачи» |

| Вопросы, вскрывающие интерес |
| :--- |
| «Что случится, если это будет не в пятницу, а во вторник?» |
| «Зачем именно к этой дате?» |

Переговоры без поражений: прояснить интересы обеих сторон → отделить людей
от проблемы → несколько вариантов → выбор по объективным критериям. Вместо
«да»/«нет» — встречный вариант.

- Продумайте и свою BATNA, и предполагаемую BATNA собеседника.

## 05. Конфликты

Подробнее: [05_conflict_resolution/01_theory/README.md](./05_conflict_resolution/01_theory/README.md)

| Вид конфликта | О чём |
| :--- | :--- |
| По существу | как лучше сделать: подход, приоритеты, риск |
| Отношений | раздражение, неуважение, недоверие — сюда соскальзывает неразрешённый первый |

| Шаг NVC | Вместо | Говорить |
| :--- | :--- | :--- |
| Наблюдение | «ты вечно опаздываешь» | «в последних трёх ревью правки пришли после дедлайна» |
| Чувство | «ты меня бесишь» | «меня это беспокоит» |
| Потребность | — | «мне важно укладываться в план спринта» |
| Просьба | — | «можешь предупреждать заранее, если не успеваешь?» |

| Принцип | Как |
| :--- | :--- |
| О проблеме, не о человеке | «подход создаёт риск X», а не «ты всегда предлагаешь рискованное» |
| Признать позицию до возражения | показать, что поняли аргумент |
| Фокус на будущем | «что делаем дальше», а не «кто был прав» |

| Эскалация | Здорово | Токсично ⚠️ |
| :--- | :--- | :--- |
| Что эскалировать | факт и разногласие: «нужна третья точка зрения» | жалобу на человека |
| Вторая сторона | предупреждена заранее | узнаёт постфактум, «за спиной» |
| Когда | после попыток договориться | первой же реакцией |

## 06. Метод STAR

Подробнее: [06_structured_self_presentation/01_theory/README.md](./06_structured_self_presentation/01_theory/README.md)

| Блок | Содержание | Объём |
| :--- | :--- | :--- |
| Situation | контекст и почему это важно | 2–3 предложения |
| Task | что требовалось лично от вас (или команды) | 1–2 предложения |
| Action | конкретные шаги, решения, компромиссы; ваша роль | ядро рассказа |
| Result | измеримый итог + вывод на будущее | честно, даже если успех частичный |

| Где применять | Что даёт |
| :--- | :--- |
| Ретроспектива | реальная задача и что сработало, вместо хронологии |
| Самооценка за период | структура эпизода вместо списка активностей |
| Презентация проекта | контекст до технических деталей |

- ⚠️ Situation длиннее Action и Result вместе.
- ⚠️ «Мы сделали» без своей роли: «команда решила X, я отвечал за Y».
- ⚠️ Result без вывода на будущее или с натянутым успехом.
