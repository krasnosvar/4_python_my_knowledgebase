# Практика: объяснение технической работы разной аудитории

## Чек-лист перед важным объяснением

- [ ] Есть заготовка на 30–60 секунд: что это, зачем, что это даёт — без ухода в детали реализации.
- [ ] Уровень абстракции выбран под конкретного слушателя, а не «по умолчанию технический» или «по умолчанию упрощённый».
- [ ] Специальные термины либо знакомы слушателю, либо кратко расшифрованы при первом использовании.
- [ ] Объяснение не превратилось в лекцию: слушателю оставлено пространство задать уточняющий вопрос и получить дополнительный уровень детализации по запросу.
- [ ] Эффект сформулирован в терминах, значимых именно для этого слушателя (пользователь, смежная команда, бизнес-метрика).
- [ ] Проверена «обратная связь понимания»: слушатель может своими словами повторить суть или задаёт вопросы по существу, а не переспрашивает базовые термины.

## Сценарии для отработки

Для каждого сценария сформулируйте объяснение вслух или письменно на 3–5 предложений, затем сверьтесь с подходом.

**Сценарий 1.** Нетехнический стейкхолдер спрашивает, чем вы занимались последний месяц, работая над миграцией системы хранения данных на новую технологию.

*Как подойти*: начните с эффекта и риска, а не с названия технологии — «мы переносим хранение данных на более надёжное решение, это снижает риск потери данных при сбоях и ускоряет отклик системы; миграция идёт поэтапно, чтобы не остановить работу сервиса». Название конкретной технологии дайте только если спросят, и без деталей внутреннего устройства.

**Сценарий 2.** Коллега из смежной команды спрашивает, что изменилось в API, которым пользуется его сервис, после вашего рефакторинга.

*Как подойти*: сфокусируйтесь строго на границе взаимодействия — что изменилось в контракте (форматы запросов/ответов, коды ошибок, поведение при граничных случаях), что осталось неизменным, что ему нужно сделать (если что-то нужно). Внутреннюю реализацию по вашу сторону границы упоминать не нужно, если она не влияет на его код.

**Сценарий 3.** Новый член команды спрашивает, почему в проекте используется нестандартное или на первый взгляд избыточное решение (например, самодельная обёртка вместо стандартной библиотеки).

*Как подойти*: дайте исторический контекст без оправданий и без излишней критики прошлых решений — «когда это делалось, стандартное решение не поддерживало X, поэтому появилась обёртка; сейчас ограничение, возможно, уже снято, но переход не был приоритетом» — и по возможности обозначьте, стоит ли это пересматривать.

**Сценарий 4.** Вам нужно объяснить одно и то же архитектурное решение дважды за один день: сначала на техническом ревью инженерам, затем в статусе для нетехнического руководителя. Составьте оба варианта объяснения для одного и того же решения.

*Как подойти*: сохраните одинаковыми пункты «зачем» и «что это даёт» в обеих версиях — эффект не должен противоречить сам себе для разных аудиторий. Разница — только в глубине пункта «что»: для инженеров — архитектурные детали и компромиссы, для руководителя — одна фраза уровня «как это сделано» и акцент на сроках/рисках.
