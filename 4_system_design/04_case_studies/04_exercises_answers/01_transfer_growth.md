# Упражнение 01: разбор

## 1. Идемпотентность периодических переводов

Ключ идемпотентности не может быть один на все повторы («ежемесячный перевод соседу») — если использовать один и тот же `Idempotency-Key` для каждого месяца, второй и все последующие месячные списания будут восприняты системой как повтор первого запроса и просто вернут сохранённый результат первого перевода, вообще не выполняя новых списаний. Правильный подход: ключ должен однозначно идентифицировать **конкретное выполнение** регулярного расписания, а не само расписание — например, `idempotency_key = f"{schedule_id}:{billing_period}"` (конкатенация ID регулярного правила и конкретного расчётного периода, скажем, `"schedule-42:2026-08"`). Это даёт нужное свойство: повторная попытка планировщика выполнить перевод за август 2026 (например, из-за сбоя и перезапуска джобы) идемпотентна и не задвоит списание, а переход к сентябрю 2026 естественно создаёт новый ключ и новый перевод.

## 2. Идемпотентность и частичные сбои с двумя провайдерами

Для каждого провайдера нужен собственный идемпотентный ключ, передаваемый именно ему (у каждого провайдера — свой API и свои гарантии идемпотентности, поэтому нельзя полагаться только на внутренний ключ системы). Практическая схема: до вызова провайдера транзакция внутри своей системы переводит перевод в статус `pending_provider`, сохраняя внешний идемпотентный ключ, специфичный для этого провайдера (например, `provider_a_key = f"txfer:{transfer_id}"`). При вызове провайдера с этим ключом: если ответ не пришёл (таймаут) — повторный вызов с тем же ключом безопасен, потому что провайдер либо ещё не обработал первый запрос (и обработает повторный как первый), либо уже обработал (и по идемпотентному ключу вернёт тот же результат, не выполнив операцию дважды на своей стороне). Дополнительно — обязателен процесс **reconciliation**: периодическая сверка списка переводов в статусе `pending_provider` дольше некоторого порога (например, 10 минут) с фактическим статусом у провайдера через отдельный API проверки статуса — это ловит редкие случаи, когда даже повторный вызов с идемпотентным ключом не прошёл из-за длительной недоступности провайдера, и требует ручного/автоматического разбора зависших операций.

## 3. Шардирование с учётом эффекта локальности

Раз 80% переводов происходят между счетами одной и той же страны, разумный ключ шардирования — составной, начинающийся со страны счёта: например, шардировать `ledger_entries` так, чтобы счета одной страны физически размещались на одном (или на предсказуемо малом наборе) шардов — например, ключ шардирования `country_id` в комбинации с хэшем `account_id` внутри страны для равномерности распределения нагрузки внутри неё (чтобы не получить один гигантский шард на страну с наибольшим числом пользователей). Тогда 80% переводов (внутри одной страны) остаются локальной транзакцией на одном наборе шардов — быстро и без кросс-шардовой сложности. Оставшиеся 20% межстрановых переводов становятся кросс-шардовой операцией по определению (счета физически на разных шардах) — для них нужен паттерн saga, как описано в разделе 8 разбора `01_money_transfers.md`: шаг резервирования списания на шарде страны-отправителя с компенсирующим действием при ошибке, затем шаг зачисления на шарде страны-получателя, с отслеживанием и докручиванием незавершённых саг.

## 4. Быстрая история пользователя при выбранном шардировании

Поскольку ключ шардирования привязан к стране счёта, а `GET /transfers` запрашивается по конкретному `account_id`, история конкретного пользователя всегда лежит на одном (или предсказуемо малом наборе, если сам пользователь имеет счета в разных странах) шарде — запрос не требует scatter-gather по всем шардам системы. Дополнительно можно денормализовать: хранить в отдельной таблице/материализованном представлении `account_transfer_history` (шардированной строго по `account_id`, а не по стране) сжатый список `transfer_id` для быстрой пагинации истории конкретного счёта — обновляемый асинхронно (аналогично `feed_cache` в разборе ленты новостей из соседнего Go-раздела базы), даже если основной журнал `ledger_entries` шардирован по стране ради типичных локальных переводов. Это классический компромисс: одна и та же логическая операция (перевод) порождает записи в двух представлениях, оптимизированных под разные типовые запросы — сам перевод и историю по счёту.
