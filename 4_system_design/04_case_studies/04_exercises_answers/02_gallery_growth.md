# Упражнение 02: разбор

## 1. Приватные альбомы вместо публичных CDN-ссылок

Прежний подход (публичный, кэшируемый на CDN URL по прямой ссылке) не подходит,
потому что публичный URL не проверяет права доступа — любой, кто узнал ссылку
(переслал кто-то из приглашённых, утечка через логи, реферер), получает доступ
к приватному контенту навсегда, вне зависимости от того, кто на самом деле
имеет право его видеть. Решение, сохраняющее выгоды CDN (см. также аналогичное
рассуждение в `02_performance_and_scaling/04_exercises_answers/`
про платное видео): сами байты изображения по-прежнему физически лежат в blob
storage и раздаются через CDN (это не персонализированные данные сами по себе),
но получить временную, подписанную и ограниченную по сроку действия (например,
5–15 минут) CDN-ссылку можно только через backend, который на каждый запрос
проверяет, что текущий пользователь — владелец альбома или явно приглашённый
участник. Клиентское приложение получает такую подписанную ссылку при открытии
альбома и подгружает по ней изображения, которые CDN всё ещё эффективно
кэширует по факту (кэш срабатывает на уровне самого объекта в CDN, если разные
подписанные ссылки на один и тот же объект нормализуются к общему кэш-ключу,
либо просто кэшируется на короткий TTL, совпадающий со сроком действия
подписи).

## 2. Живая совместная лента альбома

Механизм, адаптированный из паттерна доставки чата в реальном времени: участник
альбома, открывший приложение, устанавливает постоянное соединение (WebSocket,
либо long-polling как fallback) с gateway-сервером. При завершении асинхронной
обработки нового фото (см. разбор `02_image_gallery_in_python.md` — событие
`UploadCompleted` → пайплайн → готовые варианты) сервис публикует
дополнительное событие `PhotoReady` со ссылкой на `album_id`. Отдельный
компонент (аналог fanout-логики из разбора ленты новостей) читает это событие
из брокера и, используя реестр «какой участник альбома сейчас на каком
gateway-узле подключён» (аналогично карте `user_id → connection` в реестре из
разбора чата), доставляет уведомление о новом фото каждому подключённому в
данный момент участнику альбома. Участники, не подключённые сейчас (закрыто
приложение), просто увидят новое фото при следующем обычном запросе списка
альбома — не нужно ничего доставлять им «в реальном времени» постфактум, только
тем, кто сейчас активно смотрит на экран.

## 3. Раздельное масштабирование приёма байтов и обработки

Приём байтов загрузки (сам факт загрузки в blob storage через presigned URL)
практически не потребляет ресурсы вашего backend — клиент грузит напрямую в
blob storage, backend лишь выдаёт разрешение и фиксирует метаданные, поэтому
10-кратный всплеск именно *приёма* загрузок в основном нагружает blob storage
(который обычно уже спроектирован провайдером на такие пики) и БД метаданных
(запись новой строки `images` — дешёвая операция). Куда серьёзнее — нагрузка на
*асинхронную обработку*: генерация превью — CPU-bound задача (см.
`02_performance_and_scaling/01_theory/01_gil_bottlenecks_and_profiling.md` про
GIL), и синхронный по времени всплеск в вечерние часы одного часового пояса
создаёт резкий пик именно на пул воркеров-обработчиков. Решение: приём загрузок
и обработка разделены очередью (уже заложено в исходном дизайне как асинхронный
пайплайн) — очередь **сглаживает пик**, беря на себя роль буфера: даже если пул
воркеров не рассчитан мгновенно обработать весь всплеск, задачи просто
накапливаются в очереди и обрабатываются с небольшой задержкой, вместо того
чтобы ронять систему приёма загрузок. Отдельно можно горизонтально
автоматически масштабировать именно пул воркеров-обработчиков по глубине
очереди (метрика: число ожидающих задач) в часы пика, не трогая при этом
уровень приёма загрузок, который не является узким местом в этом сценарии.

## 4. Подсчёт просмотров без записи в БД на каждый просмотр

Раз точность не критична (плюс-минус несколько процентов приемлемо), а частота
обращений огромна, писать напрямую в реляционную БД на каждый просмотр — прямой
путь создать искусственное узкое место там, где его не было. Решение:
инкрементировать счётчик просмотров в L2-кэше (Redis, атомарный `INCR` по ключу
`views:{image_id}`) на каждый просмотр — Redis выдерживает на порядки более
высокую частоту записи, чем реляционная БД, именно для таких простых атомарных
операций. Периодически (например, раз в минуту) фоновый процесс считывает
накопленные значения из Redis батчами и одним пакетным `UPDATE` переносит их в
реляционную БД метаданных (`images.view_count += delta`), обнуляя счётчик в
Redis после переноса. Это даёт eventual consistency счётчика (отображаемое
число просмотров может отставать на минуту от реального) ценой кардинального
снижения нагрузки на основную БД — компромисс, явно допустимый согласно
требованию задачи о необязательной точности.
