# Разбор: система денежных переводов

Полный разбор системы целиком — от требований до эволюции по мере роста нагрузки. Задача уровня «переводы между счетами в банковском/финтех-приложении». Центральные решения здесь — **строгая консистентность, идемпотентность и двойная запись**, а не производительность как таковая.

## 1. Требования

### Функциональные
- Перевести сумму со счёта A на счёт B (внутри одной системы).
- Просмотр истории переводов и текущего баланса счёта.
- (Опционально) переводы во внешний банк через платёжного провайдера.

### Нефункциональные
- **Деньги нельзя терять и нельзя задваивать** — это доминирует над всеми остальными нефункциональными требованиями. Строгая консистентность обязательна для баланса и факта перевода.
- **Идемпотентность** — повторная отправка одного и того же перевода (по вине сети, ретрая клиента, двойного нажатия кнопки) не должна привести к повторному списанию.
- **Аудируемость** — каждое движение денег должно быть прослеживаемо постфактум (для споров, регуляторных проверок, поддержки).
- Доступность важна, но вторична по отношению к корректности: **лучше отклонить перевод и сообщить об ошибке, чем провести его некорректно.**
- Нагрузка обычно на порядки ниже, чем у ленты новостей или мессенджера — счёт по тысячам/десяткам тысяч операций в секунду на всю систему, а не сотни тысяч.

### Вне scope
Обнаружение мошенничества, комплаенс-проверки (AML/KYC), расчёт комиссий — упомянуть, что они существуют на пути перевода, но не проектировать подробно.

## 2. Центральное решение: идемпотентность

Клиент (мобильное приложение) при инициации перевода генерирует уникальный `idempotency_key` (например, UUID) и передаёт его с запросом. Сервер:

1. Проверяет, есть ли уже сохранённый результат для этого `idempotency_key`.
2. Если есть — возвращает **тот же самый** сохранённый результат, не выполняя перевод повторно.
3. Если нет — выполняет перевод и атомарно сохраняет результат под этим ключом.

```
Первый запрос:  client -> POST /transfer {idempotency_key: "abc-123", ...}
                server: ключа нет -> выполнить перевод -> сохранить результат под "abc-123" -> вернуть

Повторный запрос (ретрай из-за таймаута сети):
                client -> POST /transfer {idempotency_key: "abc-123", ...}  (тот же ключ!)
                server: ключ "abc-123" уже есть -> вернуть сохранённый результат, перевод НЕ повторять
```

Это обязательно, потому что сеть ненадёжна: клиент, не получивший ответ вовремя (таймаут), не может отличить «сервер не получил запрос» от «сервер выполнил перевод, но ответ потерялся» — и должен иметь возможность безопасно повторить запрос. Без идемпотентности повтор означал бы двойное списание.

## 3. Центральное решение: консистентность и double-entry bookkeeping

### Почему обычная ACID-транзакция — база, но не всё

Внутри одной БД операция «списать со счёта A, зачислить на счёт B» обязана быть одной ACID-транзакцией: либо обе части выполняются, либо ни одна. Изолированность (уровень `SERIALIZABLE` или как минимум корректная блокировка строк счетов) предотвращает гонку, при которой параллельный перевод с того же счёта A обработается на основе устаревшего баланса.

### Double-entry bookkeeping (двойная запись)

Профессиональный подход, используемый реальными финансовыми системами: каждая операция — это не одно изменение баланса, а **две записи в журнале движений**: дебет одного счёта и кредит другого на одну и ту же сумму.

```
transfer_id=T1, amount=500
  entry: account=A, direction=DEBIT,  amount=500
  entry: account=B, direction=CREDIT, amount=500

Баланс счёта = сумма всех его записей (агрегат), а не отдельное мутируемое поле.
```

- **Плюс:** сумма всех записей в системе всегда равна нулю (что списано с одного, зачислено другому) — это встроенный инвариант, который можно проверить в любой момент как аудит (sum(debits) == sum(credits)), а не только доверять текущему значению поля `balance`.
- **Плюс:** полная история движений «из коробки» — баланс на любой момент времени восстанавливается пересчётом записей журнала, что закрывает требование аудируемости.
- Хранить сам текущий баланс отдельным полем ради скорости чтения (не пересчитывать журнал на каждый запрос) — нормально, но это **производное, кэшируемое значение**, источник истины — журнал движений.

## 4. API

```
POST /api/v1/transfers
  headers: Idempotency-Key: <uuid>
  body:   { "from_account": "A", "to_account": "B", "amount_minor": 50000, "currency": "USD" }
  resp:   { "transfer_id": "T1", "status": "completed" | "failed" | "pending" }

GET /api/v1/accounts/{id}/balance
  resp:   { "balance_minor": 123456, "currency": "USD" }

GET /api/v1/accounts/{id}/transfers?cursor=...
  resp:   { "transfers": [...], "nextCursor": "..." }
```

Важная деталь типов: суммы **всегда целые минорные единицы** (центы/копейки — `amount_minor`), никогда `float`. Плавающая точка накапливает ошибки округления, недопустимые при работе с деньгами.

## 5. Модель данных

```
accounts:
  account_id   PK
  balance_minor  BIGINT   -- денормализованный, для быстрого чтения; источник истины - ledger_entries
  currency

ledger_entries:                       -- журнал движений (double-entry)
  entry_id      PK
  transfer_id   -- группирует пару DEBIT/CREDIT одной операции
  account_id
  direction     -- DEBIT | CREDIT
  amount_minor
  created_at

idempotency_keys:
  key           PK  (Idempotency-Key от клиента)
  transfer_id
  response_body  -- сохранённый результат для повторной отдачи
  created_at
```

## 6. High-level дизайн

```
Клиент ──▶ API ──▶ [ Transfer Service ]
                         │
                         ├─▶ проверка idempotency_keys (тот же ключ уже обработан?)
                         │
                         ├─▶ ACID-транзакция в основной БД:
                         │     - проверить баланс A (SELECT ... FOR UPDATE)
                         │     - записать ledger_entries (DEBIT A, CREDIT B)
                         │     - обновить денормализованный balance_minor
                         │     - сохранить результат в idempotency_keys
                         │
                         └─▶ [ Outbox ] ──▶ [ Брокер ] ──▶ уведомления, аналитика, внешний провайдер
```

**Поток перевода:**
1. Клиент отправляет запрос с `Idempotency-Key`.
2. Сервис проверяет ключ — если уже обработан, возвращает сохранённый результат немедленно.
3. Иначе — одна ACID-транзакция: заблокировать строку счёта A, проверить достаточность средств, записать пару `ledger_entries`, обновить `balance_minor` обоих счетов, сохранить запись в `idempotency_keys` — всё атомарно, либо всё целиком, либо ничего.
4. После коммита — событие `TransferCompleted` кладётся в outbox-таблицу той же транзакцией (см. ниже), затем асинхронно публикуется в брокер для уведомлений/аналитики — это уже не требует строгой консистентности.

## 7. Надёжные события: паттерн outbox

Если после ACID-транзакции сразу отдельным вызовом публиковать событие в брокер, возможна рассинхронизация: транзакция закоммитилась, а публикация в брокер упала (сетевой сбой) — событие потеряно, хотя перевод реально произошёл. Паттерн outbox решает это: событие записывается в таблицу `outbox` **в той же самой ACID-транзакции**, что и сам перевод, а отдельный фоновый процесс читает `outbox` и публикует события в брокер, помечая их отправленными. Так публикация события становится атомарной относительно самого перевода на уровне БД — либо оба закоммичены, либо ни один, а доставка в брокер — уже отдельная, отказоустойчивая задача с ретраями поверх надёжно сохранённой записи.

## 8. Развитие решения по мере роста нагрузки

- **Старт (низкая нагрузка, один регион).** Один PostgreSQL-кластер с ACID-транзакциями, синхронная запись, простая идемпотентность через уникальный индекс на `Idempotency-Key`. Этого достаточно для многих тысяч операций в сутки.
- **Рост нагрузки на чтение (баланс, история).** Read-реплики под `GET /balance` и `GET /transfers` — читать баланс для отображения можно с небольшой задержкой относительно последней записи (несколько сотен миллисекунд), но **сам перевод и проверка достаточности средств перед списанием всегда идут к мастеру**, не к реплике — здесь устаревшие данные означают риск провести перевод с недостаточным балансом.
- **Рост объёма данных (шардирование).** Если журнал движений вырастает до сотен миллионов/миллиардов записей, `ledger_entries` шардируется по `account_id` (см. `02_performance_and_scaling/01_theory/05_partitioning_sharding.md`) — так, чтобы вся история конкретного счёта лежала на одном шарде и не требовала scatter-gather при просмотре истории. Перевод между счетами на **разных** шардах становится кросс-шардовой операцией — здесь и нужен паттерн saga вместо локальной ACID-транзакции: шаг 1 — резервирование списания на шарде A с компенсирующим откатом при ошибке, шаг 2 — зачисление на шарде B, с чётким протоколом отслеживания незавершённых саг и их принудительного докручивания/компенсации.
- **Интеграция с внешним провайдером (перевод в другой банк).** Внешний вызов провайдера — по определению ненадёжная сеть с непредсказуемой задержкой. Здесь идемпотентность нужна вдвойне: свой `Idempotency-Key` внутри системы **и** передача его (или собственного эквивалента) провайдеру, чтобы повторный вызов к провайдеру после таймаута не привёл к повторному списанию уже на его стороне. Плюс отдельный процесс **reconciliation** (сверки) — периодическое сравнение записей своей системы с выпиской провайдера, чтобы обнаружить и вручную разобрать редкие расхождения (например, провайдер обработал перевод, но подтверждение потерялось на сетевом уровне и не дошло до вас).

## 9. Узкие места и trade-offs

| Узкое место | Риск | Решение |
|---|---|---|
| Блокировка строки счёта при высокой конкурентной нагрузке на один счёт | contention, рост latency на «горячих» счетах (например, счёт мерчанта, принимающий много платежей) | Короткие транзакции, очередь операций на конкретный счёт, при экстремальной нагрузке — разбиение логического счёта на несколько «подсчётов» с последующей консолидацией |
| Кросс-шардовые переводы | сложность саги, окно неопределённости между шагами | Явный статус `pending` на переходный период, воркер, докручивающий незавершённые саги, идемпотентность на каждом шаге саги |
| Потеря события при публикации в брокер | пропущенное уведомление/аналитика при физически состоявшемся переводе | Паттерн outbox — атомарная запись события в той же транзакции, что и сам перевод |
| Дублирующий вызов внешнего провайдера при ретрае | двойное списание на стороне провайдера | Idempotency-key, переданный и на сторону провайдера; reconciliation постфактум |

**Итоговые компромиссы:** строгая консистентность и идемпотентность здесь — не опциональная оптимизация, а обязательное требование, ради которого сознательно жертвуют доступностью (лучше временно отклонить операцию, чем выполнить её некорректно) и производительностью (короткие, но обязательно ACID-транзакции вместо максимально возможного параллелизма).

> Частый вопрос на собеседовании: почему для платёжной системы недостаточно просто ACID-транзакции, и зачем нужна идемпотентность отдельно? ACID-транзакция гарантирует атомарность **одного** запроса на сервере, но не защищает от повторной отправки **того же самого** запроса клиентом из-за ненадёжной сети (таймаут, не увидели ответ). Идемпотентность через уникальный ключ операции гарантирует, что повторный запрос с тем же ключом не выполнит операцию заново, а просто вернёт уже сохранённый результат — это защита на уровне выше отдельной транзакции.

> Частый вопрос на собеседовании: зачем нужна двойная запись (double-entry bookkeeping), если можно просто хранить поле `balance` у счёта и менять его при каждом переводе? Двойная запись даёт встроенный инвариант для аудита (сумма всех движений всегда равна нулю) и полную историю без дополнительных таблиц логов — баланс становится производным значением, которое всегда можно пересчитать и сверить с журналом движений. Хранение только мутируемого поля `balance` без журнала делает невозможным надёжный аудит и восстановление истории при расхождениях.
