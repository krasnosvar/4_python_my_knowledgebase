# Разбор: галерея изображений / медиа-хранилище

Полный разбор системы целиком (аналог упрощённого Instagram/Google Photos в части хранения и раздачи изображений). Центральное решение здесь — **разделение метаданных и байтов контента**, обработка загруженного изображения в несколько представлений и раздача через CDN.

## 1. Требования

### Функциональные
- Загрузить изображение (с телефона/браузера), привязав его к пользователю/альбому.
- Просмотреть свои изображения и изображения, которыми с тобой поделились.
- Изображение должно открываться быстро в разных местах интерфейса — превью в ленте, полноразмерное в открытом виде.

### Нефункциональные
- **Read-heavy**: изображение загружается один раз, а просматривается (в ленте, в профиле, при шаринге) многие сотни раз. Возьмём соотношение чтение/запись примерно 1000:1.
- **Низкая latency отдачи**, особенно превью в ленте (p99 в единицы–десятки миллисекунд с учётом CDN).
- Загрузка должна **выдерживать большие файлы** и нестабильную мобильную сеть — не терять весь загруженный прогресс при обрыве соединения.
- Хранение — **дёшево на терабайтных объёмах**, так как изображений много и почти все хранятся годами.

### Вне scope
Модерация контента, распознавание образов/лиц, полнотекстовый поиск по фото — упомянуть, что существуют на этом пути, но не проектировать.

## 2. Оценка нагрузки

Предположим: 10 млн новых изображений в сутки, среднее фото ~3 MB (одно оригинальное разрешение) плюс производные (превью), соотношение чтение/запись 1000:1.

```
write QPS  = 10^7 / 10^5 ≈ 100 QPS  (пик, с учётом всплесков загрузки, ~500)
read  QPS  = 10^7 * 1000 / 10^5 = 10^5 QPS  (сотни тысяч запросов на отдачу в сутки-пик)
```

Хранилище (оригинал ~3 MB + производные размеры ~500 KB суммарно):

```
10^7 в сутки × 3.5 MB ≈ 35 TB/сутки
× 365 ≈ 12.8 PB/год
```

**Выводы:** read настолько превышает write, что почти вся архитектура отдачи вращается вокруг кэширования и CDN. Петабайтные объёмы делают локальное файловое хранилище на диске сервера приложения бессмысленным с первого дня — нужен blob storage, спроектированный для такого масштаба (S3-совместимое хранилище).

## 3. API

```
POST /api/v1/uploads                 -- инициировать загрузку
  resp: { "uploadUrl": "https://...", "assetId": "..." }   -- предподписанный URL для прямой загрузки в blob storage

PUT <uploadUrl>                      -- клиент загружает байты НАПРЯМУЮ в blob storage, минуя ваш сервер

POST /api/v1/uploads/{assetId}/complete
  body: { "albumId": "...", "takenAt": "..." }
  resp: { "imageId": "...", "status": "processing" }

GET /api/v1/images/{imageId}
  resp: { "imageId": "...", "variants": { "thumbnail": "https://cdn/...", "medium": "https://cdn/...", "original": "https://cdn/..." }, "status": "ready" }
```

Ключевое проектное решение уже видно в API: клиент загружает байты **напрямую в blob storage** по предподписанному URL, а не через ваш backend-сервер — backend только выдаёт временное разрешение на загрузку (presigned URL) и потом узнаёт о её завершении. Это снимает с backend-серверов нагрузку по перекачке гигабайт трафика загрузок — они лишь координируют процесс.

## 4. Модель данных

```
images:
  image_id      PK
  owner_id
  album_id
  status        -- uploading | processing | ready | failed
  original_key  -- ключ объекта в blob storage
  created_at

image_variants:                 -- производные представления одного изображения
  image_id      FK
  variant       -- thumbnail | medium | original
  storage_key
  width, height
  size_bytes
```

Метаданные (небольшие, структурированные, с частыми запросами вида «все фото пользователя/альбома») — в обычной реляционной БД. Сами байты изображений — исключительно в blob storage, никогда не в реляционной БД (хранить большие бинарные объекты прямо в строках БД — типичная ошибка, которая раздувает БД и делает бэкапы/репликацию непропорционально дорогими).

## 5. Центральное решение: пайплайн обработки после загрузки

Оригинал, как он есть, редко годится для прямой отдачи (слишком велик для превью в ленте, может быть в неоптимальном формате). После завершения загрузки запускается асинхронный пайплайн:

```
Клиент завершил загрузку оригинала
        │
        ▼
[ Событие "UploadCompleted" ] ──▶ [ Брокер сообщений ]
        │
        ▼
[ Обработка (воркеры) ]:
  - сгенерировать thumbnail (маленький, для ленты)
  - сгенерировать medium (для просмотра в приложении)
  - перекодировать в веб-оптимизированный формат (например, WebP/AVIF)
  - извлечь и сохранить базовые метаданные (разрешение, EXIF при наличии)
        │
        ▼
[ Сохранить image_variants, обновить images.status = 'ready' ]
        │
        ▼
[ Инвалидация/прогрев CDN для готовых вариантов ]
```

Обработка — **асинхронная и не блокирует ответ клиенту** на загрузку: клиент видит статус `processing` сразу после завершения загрузки байтов, и получает уведомление (или опрашивает статус), когда варианты готовы. Это прямое применение роли брокера сообщений из `03_distributed_components/01_theory/03_message_brokers_role.md` — развязка между моментом загрузки и потенциально тяжёлой CPU-bound обработкой изображения (в Python — по тем же причинам, что и в `02_performance_and_scaling/01_theory/01_bottlenecks.md`: обработка изображений CPU-bound, GIL требует параллелизма через отдельные процессы-воркеры, а не потоки).

## 6. High-level дизайн

```
                     ┌──────────────┐
Клиент ──────────────▶│ API (метаданные) │
   │                  └──────┬───────────┘
   │ прямая загрузка byte'ов │
   ▼                          ▼
[ Blob Storage (S3) ]   [ Metadata DB (PostgreSQL) ]
   │                          │
   │ событие UploadCompleted  │
   ▼                          │
[ Брокер ] ──▶ [ Обработка: воркеры генерации вариантов ] ──▶ пишут variants обратно в Blob Storage + Metadata DB
   │
   ▼
[ CDN ] ──▶ отдаёт готовые варианты пользователям при чтении
```

**Поток загрузки:**
1. Клиент запрашивает у API presigned URL, получает временное разрешение на прямую загрузку в blob storage.
2. Клиент грузит байты напрямую в blob storage (поддерживает докачку по частям для больших файлов и нестабильной сети — chunked upload).
3. Клиент уведомляет API о завершении → создаётся запись `images` со статусом `processing`, событие уходит в брокер.
4. Воркеры асинхронно генерируют варианты, сохраняют их в blob storage и записи в `image_variants`, обновляют статус на `ready`.

**Поток чтения:**
1. `GET /images/{id}` возвращает ссылки на варианты — но по факту большинство чтений идёт не через API, а напрямую по CDN-ссылке на нужный вариант (thumbnail для ленты, medium для просмотра), уже закэшированной на edge.
2. Метаданные (какие альбомы, кто владелец) кэшируются на уровне приложения (L1/L2) при высокой частоте обращений — см. `02_performance_and_scaling/01_theory/03_caching_levels.md`.

## 7. Развитие решения по мере роста нагрузки

- **Старт.** Один blob storage bucket, один PostgreSQL для метаданных, синхронная простая генерация одного размера превью прямо в обработчике загрузки. Работает, пока объём небольшой.
- **Рост объёма загрузок.** Синхронная генерация превью в обработчике запроса становится узким местом (CPU-bound задача блокирует обработку HTTP-запросов) — выносится в асинхронный пайплайн через брокер и отдельный пул воркеров (см. раздел 5), что также решает проблему GIL за счёт параллельных процессов-воркеров.
- **Рост read-нагрузки.** CDN перед blob storage становится обязательным, а не опциональным — без него каждый просмотр в ленте бьёт по origin blob storage. Добавляется многоуровневое кэширование метаданных (L1 в приложении для самых горячих альбомов, L2 Redis для остального) — см. `03_caching_levels.md`.
- **Рост числа пользователей и общего объёма хранения (петабайты).** Метаданные (таблица `images`) шардируются по `owner_id` (см. `02_performance_and_scaling/01_theory/05_partitioning_sharding.md`) — типичный запрос «все фото этого пользователя» остаётся дешёвым на одном шарде. Blob storage к этому моменту обычно уже горизонтально масштабируется «из коробки» силами провайдера (S3-совместимые хранилища проектируются на такие объёмы изначально).
- **Требование дедупликации / экономии места.** Одинаковые загруженные файлы (пересланные скриншоты, репосты) занимают место многократно. Решение по аналогии с chunking из файловых хранилищ: адресация объекта по хэшу содержимого (content-addressed storage) — если хэш уже существует в blob storage, повторно не загружать байты, только добавить новую ссылку на существующий объект из метаданных нового изображения.
- **Требование приватности/платного контента.** Публичные CDN-ссылки на изображения больше не подходят, если доступ должен проверяться (например, платная подписка на приватный альбом) — переход на подписанные, ограниченные по времени CDN-URL, аналогично рассуждению в `02_performance_and_scaling/04_exercises_answers/04_cache_layers_design.md` про платное видео.

## 8. Узкие места и trade-offs

| Узкое место | Риск | Решение |
|---|---|---|
| Загрузка больших файлов через нестабильную сеть | обрыв соединения теряет весь прогресс | Chunked upload с докачкой; presigned URL напрямую в blob storage, минуя backend |
| Синхронная генерация превью в обработчике запроса | блокирует HTTP-обработку, не масштабируется под CPU-bound нагрузку | Асинхронный пайплайн через брокер + отдельные воркер-процессы |
| Отсутствие CDN | origin blob storage перегружен повторяющимися просмотрами одних и тех же файлов | CDN перед blob storage — центральный элемент архитектуры при read:write ≈ 1000:1 |
| Дублирующиеся загрузки одинакового контента | лишний расход хранилища на петабайтных объёмах | Content-addressed storage: адресация по хэшу содержимого, дедупликация на уровне blob storage |
| Рост таблицы метаданных | одна БД не выдерживает объём/QPS метаданных при миллиардах изображений | Шардирование `images` по `owner_id` |

**Итоговые компромиссы:** архитектура почти целиком выстроена вокруг экстремального перекоса read:write и вокруг того, что байты контента и метаданные о нём — принципиально разные по природе данные с разными требованиями к хранению, поэтому с первого дня разводятся по разным системам (blob storage и реляционная БД), а не пытаются жить в одной.

> Частый вопрос на собеседовании: почему изображения не хранят прямо в реляционной БД рядом с остальными данными? Большие бинарные объекты в БД раздувают её объём непропорционально полезной нагрузке, делают бэкапы и репликацию тяжелее и дороже, и не дают использовать специализированные для раздачи контента механизмы (CDN, объектное хранилище с встроенным версионированием/жизненным циклом). Правильное разделение — метаданные (маленькие, структурированные, часто с транзакционными требованиями) в реляционной БД, байты — в blob storage, спроектированном именно для этого.

> Частый вопрос на собеседовании: почему обработка изображения (генерация превью) должна быть асинхронной, а не происходить прямо в обработчике запроса на загрузку? Это CPU-bound задача, которая при синхронном выполнении держит HTTP-обработчик занятым надолго, снижая throughput сервиса приложений и создавая задержку ответа клиенту, пропорциональную числу и размеру генерируемых вариантов. Вынос в асинхронный пайплайн через очередь разрывает эту связь: клиент получает быстрый ответ о начале обработки, а сама генерация вариантов происходит в отдельном пуле воркеров, который можно масштабировать независимо от API-слоя.
