# Распределённый монолит — антипаттерн

Худший из миров: сервисы физически разнесены по сети (вы уже платите сетевую цену — задержки, частичные отказы, сериализацию), но остаются жёстко связанными, поэтому не получаете взамен независимости деплоя и масштабирования.

## Признаки

- **Совместный релиз.** Сервисы нельзя задеплоить по отдельности — версии API должны совпадать, релиз всегда идёт «пачкой» по чек-листу в нужном порядке.
- **Общая база данных.** Несколько сервисов читают и пишут в одни и те же таблицы. Формально это «разные сервисы», но по факту одна общая модель данных — границы данных не соблюдены.
- **Синхронные цепочки вызовов.** `A → B → C → D`, где отказ или задержка на самом нижнем уровне рушит весь запрос сверху. Каждый лишний синхронный HTTP-хоп в цепочке — это ещё один таймаут, который должен отработать корректно, а не «как получится».
- **Ломкие контракты.** Изменение поля в ответе одного сервиса ломает нескольких потребителей; координация релизов идёт через ручные согласования и таблицы «кто когда обновляется», а не через версионирование API.
- **Общие библиотеки с бизнес-логикой.** Если несколько сервисов подключают один и тот же internal-пакет с доменными правилами, то по сути это один и тот же код, размазанный по нескольким процессам, а не независимые сервисы.

```
   Клиент ──▶ Service A ──(sync HTTP)──▶ Service B ──(sync HTTP)──▶ Service C
                 │                            │                        │
                 └──────────── общая БД ──────┴────────────────────────┘

   Итог: сеть + сериализация ПЛЮС жёсткая связанность = хуже монолита
```

## Почему он возникает

Это не случайность, а типичный побочный эффект нескольких управленческих решений:

1. **Резать по техническим слоям, а не по домену.** Часто монолит распиливают на «UI-сервис», «сервис бизнес-логики», «сервис доступа к данным» — по архитектурным слоям, а не по бизнес-возможностям (bounded context из DDD). В итоге любой пользовательский сценарий всё равно проходит через все три «сервиса» синхронной цепочкой — просто раньше это были модули одного процесса, а теперь три сетевых хопа.
2. **Микросервисы «по моде», а не по причине.** Решение резать на сервисы принимается до того, как появилась реальная боль (нужно независимо масштабировать, нужна автономия команд). Домен ещё не понят — границы получаются случайными и почти гарантированно неверными.
3. **Организационная структура не совпадает с архитектурной (закон Конвея).** Если над «одной фичей» продолжают совместно работать несколько команд, физическое разделение на сервисы не даёт им автономии — релизы всё равно требуют координации между командами.
4. **Не решились разделить данные.** Разделить код проще, чем данные: перенос БД требует миграции, дедупликации ответственности за поля, иногда — временного дублирования данных. Отложили «на потом» — и осталась общая БД, которая цементирует связанность.
5. **Нет времени/приоритета на версионирование контрактов.** Контракты API проектируют «на скорую руку», без обратной совместимости, потому что это соседняя команда и «мы просто договоримся в Slack». Договорённости в чате не защищают от breaking change при следующем деплое.

## Чем это отличается от здоровых микросервисов

Ключевые маркеры реальной независимости — раздельный деплой и раздельные данные. Если хотя бы одно из этого не выполняется, сложность распределённой системы уже оплачена, а её выгоды (независимый релиз, независимое масштабирование, изоляция отказов) — нет.

| Свойство | Микросервисы | Распределённый монолит |
|---|---|---|
| Деплой | независимый, по одному сервису | совместный, версии должны совпасть |
| Данные | своя БД на сервис | общая БД у нескольких сервисов |
| Вызовы | асинхронные где можно, синхронные — с таймаутами/ретраями | длинные синхронные цепочки без защиты |
| Контракт API | версионируется, обратная совместимость | меняется без оглядки на потребителей |
| Отказ одного сервиса | остальные продолжают работать (деградация) | рушит всю цепочку запроса |

## Как не попасть в эту ловушку

- Резать границы сервисов по **bounded contexts** (доменным возможностям), а не по техническим слоям.
- У каждого сервиса — **своя БД**; доступ к чужим данным — через API или события, не через прямой SQL к чужой таблице.
- Синхронные вызовы — с таймаутами, ретраями и деградацией по умолчанию; длинные цепочки `A→B→C→D` заменять на асинхронность там, где это допустимо бизнес-логикой.
- Контракты API — версионировать и держать обратную совместимость; ломающие изменения — через параллельные версии эндпоинтов, а не «просто предупредили в чате».
- Начинать с модульного монолита с чёткими внутренними границами — тогда, если дозревает решение выделять сервисы, границы уже понятны и не случайны.

> Частый вопрос на собеседовании: чем распределённый монолит отличается от микросервисов? Формально это тоже несколько сервисов, общающихся по сети, но они жёстко связаны: общая БД, совместный деплой, ломкие контракты. Вы платите сетевую цену без выгод независимости. Ключевые маркеры настоящей независимости — раздельный деплой и раздельные данные.

> Частый вопрос на собеседовании: как на код-ревью/архитектурном ревью распознать, что система движется к распределённому монолиту? Смотреть на три вещи: приходится ли координировать релизы нескольких сервисов вручную; ходит ли больше одного сервиса в одну и ту же таблицу БД; есть ли синхронные цепочки из 3+ сервисов без таймаутов и без деградации при отказе нижнего звена.
