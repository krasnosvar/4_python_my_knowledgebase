# Architecture styles: практические применения

Сводка «когда что» без воды — как выбор архитектурного стиля всплывает в реальной инженерии и в задачах системного дизайна.

## Выбор стиля: пошагово

1. **Начинайте с модульного монолита**, если домен не устоялся, команда одна и небольшая, важна скорость итераций. Держите чёткие внутренние границы (пакеты Python без циклических импортов, явные интерфейсы между модулями) — это даёт большую часть пользы будущей декомпозиции почти бесплатно.
2. **Переходите к сервисам по конкретной причине**, а не по умолчанию: неравномерная нагрузка на часть системы, несколько независимых команд, требование изолировать отказы. См. `03_choosing_architecture.md`.
3. **Мигрируйте инкрементально**, через strangler fig и Expand–Migrate–Contract, а не переписыванием с нуля. См. `04_migration_and_strangler_fig.md`.
4. **Постоянно проверяйте себя на признаки распределённого монолита**: совместный релиз, общая БД, синхронные цепочки без защиты, ломкие контракты. См. `02_distributed_monolith.md`.

## Как это соотносится с другими разделами базы

- Границы сервисов на практике режут по bounded contexts (доменное моделирование) — это отдельная большая тема, здесь важно только то, что резать нужно по домену, а не по техническому слою.
- Компоненты, которые связывают уже выделенные сервисы (API Gateway, service discovery, брокеры сообщений, балансировщики), разобраны в `03_distributed_components`.
- Конкретные кейсы разбора системы целиком, где архитектурный стиль — часть решения, разобраны в `04_case_studies`.

## Типичные ошибки

- Резать монолит по техническим слоям («UI-сервис», «сервис бизнес-логики», «сервис БД») вместо доменных границ → мгновенный распределённый монолит.
- Резать «на всякий случай», до появления реальной причины — команда платит операционную цену микросервисов без единой их выгоды.
- Общая БД у нескольких сервисов, оставленная «на потом», — становится постоянной, а не переходной.
- Длинные синхронные цепочки вызовов между сервисами без таймаутов и деградации — любой отказ снизу рушит весь запрос.
- «Большой взрыв» вместо инкрементальной миграции — риск копится в одном релизе вместо того, чтобы размазаться на много маленьких.

## Мини-чеклист на собеседовании и в реальном проекте

- Кто владеет данными каждого модуля — один явный владелец, или несколько пишут в одну таблицу?
- Можно ли задеплоить этот модуль отдельно от остальных прямо сейчас?
- Что произойдёт с остальной системой, если этот модуль полностью откажет?
- Если мигрируем — какой конкретный первый кусок выносим и по какому критерию считаем перенос завершённым?

> Частый вопрос на собеседовании: как вы объясните человеку, далёкому от System Design, разницу между монолитом и микросервисами одной фразой? Монолит — один корабль с разными каютами; микросервисы — флотилия кораблей поменьше, каждый со своим экипажем и маршрутом, но им нужно согласованно приходить в один порт. Флотилией управлять сложнее, но шторм топит только один корабль, а не весь флот разом.
