# Монолит vs микросервисы

Два полярных способа разложить систему по границам процессов: один развёртываемый артефакт против набора независимо развёртываемых сервисов. Выбор — не вопрос моды, а компромисс между простотой разработки и независимостью масштабирования/деплоя.

## Монолит

Всё приложение — один процесс и один артефакт деплоя (например, один Django-проект или один FastAPI-сервис со всеми модулями внутри). Модули общаются обычными вызовами функций, данные обычно живут в одной БД.

- **Плюсы:**
  - Простой деплой — один образ, один pipeline CI/CD.
  - Простая отладка — весь путь запроса в одном процессе, обычный traceback, а не распределённый трейс через пять сервисов.
  - Нет сети и частичных отказов между модулями — вызов функции надёжен и синхронен.
  - Транзакции — одна БД, легко держать консистентность обычным `BEGIN/COMMIT` (в Django — `transaction.atomic()`, в SQLAlchemy — `Session`).
  - Дёшево на старте — не нужны service discovery, распределённый трейсинг, межсервисная аутентификация, брокер сообщений.
- **Минусы:**
  - Масштабируется целиком — нельзя отмасштабировать только «горячий» модуль (например, обработку изображений), реплицируется весь процесс.
  - Один язык и один набор зависимостей на всё — сложно поставить рядом NumPy/pandas-пайплайн и лёгкий CRUD с разными требованиями к рантайму.
  - Любое изменение в одном модуле требует передеплоя всего приложения — релизы становятся рискованнее с ростом кодовой базы.
  - При росте команды растёт связанность: без дисциплины границы модулей размываются, импорты начинают ходить «куда попало».

## Микросервисы

Система разбита на независимые сервисы, каждый со своей зоной ответственности, своим деплоем и, в идеале, своей БД. Общаются по сети — HTTP/REST, gRPC или через брокер сообщений (Kafka, RabbitMQ).

- **Плюсы:**
  - Независимый деплой и релизный цикл у каждой команды/сервиса.
  - Независимое масштабирование — держим 20 реплик сервиса обработки платежей и 2 реплики сервиса настроек профиля.
  - Технологии под задачу (polyglot): сервис ML-инференса — на FastAPI + PyTorch, сервис биллинга — на Django, воркер аналитики — вообще на другом языке.
  - Изоляция отказов — падение одного сервиса не обязано ронять всю систему при разумных таймаутах и предохранителях.
- **Минусы:**
  - Сетевые вызовы: задержки, таймауты, ретраи, частичные отказы (fallacies of distributed computing).
  - Нет распределённых ACID-транзакций «из коробки» — согласованность через саги, идемпотентность, eventual consistency.
  - Операционная сложность: service discovery, распределённый трейсинг, централизованные логи, версионирование контрактов API между сервисами.
  - Тяжелее локальная разработка и сквозное (end-to-end) тестирование — надо поднимать несколько сервисов сразу (docker-compose, тестовые окружения).

## Сравнение на схеме

```
         Монолит                        Микросервисы
   +--------------------+        +------+  +------+  +------+
   |  Orders            |        |Orders|  |Users |  |Bills |
   |  Users             |        |  DB  |  |  DB  |  |  DB  |
   |  Billing           |        +--+---+  +--+---+  +--+---+
   |  (одна БД)         |           |         |         |
   +--------------------+           +----сеть-+----+----+
   1 деплой, 1 процесс           N деплоев, N процессов, N БД
```

## Когда что оправдано

- **Монолит (в т.ч. «модульный монолит»)** — новый продукт, небольшая команда, домен ещё не устоялся, важна скорость итераций. Чёткие внутренние модули (пакеты Python с явными границами и без циклических импортов) дают значительную часть пользы микросервисов без сетевой цены.
- **Микросервисы** — большая организация с несколькими автономными командами, разные требования к масштабированию/надёжности у частей системы, домен уже понятен и устоялся.

Здоровый путь чаще всего: начать с модульного монолита и выделять сервисы по мере роста конкретной боли, когда границы уже понятны, а не «на всякий случай» с первого дня.

> Частый вопрос на собеседовании: с чего начинать — с монолита или микросервисов? Разумный ответ: с монолита (лучше модульного), потому что на старте границы домена неизвестны, а стоимость операционной сложности микросервисов реальна с первого дня. Сервисы выделяют по мере появления конкретных причин: независимое масштабирование, автономия команд, изоляция отказов.

> Частый вопрос на собеседовании: какая практическая метрика подсказывает, что пора резать монолит на сервисы? Не «код стал большим», а конкретная боль: один модуль требует радикально другого профиля масштабирования, разные команды блокируют друг друга общим релизным циклом, либо отказ одного модуля должен перестать ронять остальные.
