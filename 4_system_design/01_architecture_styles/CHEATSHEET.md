## Монолит vs микросервисы

Подробнее: [01_monolith_vs_microservices.md](./01_theory/01_monolith_vs_microservices.md)

| Свойство | Монолит | Микросервисы |
| :--- | :--- | :--- |
| Деплой | один артефакт, один pipeline | независимый у каждого сервиса |
| Вызовы между модулями | вызов функции: надёжно, синхронно | сеть: задержки, таймауты, частичные отказы |
| Транзакции | одна БД, `BEGIN/COMMIT`, `transaction.atomic()` | нет распределённого ACID: саги, идемпотентность, eventual consistency |
| Масштабирование | только целиком | по сервису (20 реплик платежей, 2 реплики настроек) |
| Технологии | один язык и один набор зависимостей | под задачу (polyglot) |
| Отказы | падение модуля роняет процесс | изоляция при таймаутах и предохранителях |
| Отладка | обычный traceback | распределённый трейсинг, централизованные логи |
| Операционная цена | низкая | service discovery, трейсинг, межсервисная аутентификация, версии контрактов |

## Когда что

| Ситуация | Выбор |
| :--- | :--- |
| Новый продукт, домен не устоялся, одна команда до ~8–10 человек | модульный монолит |
| Несколько независимых команд с разными релизными циклами | сервисы по границам команд (закон Конвея) |
| Десятки команд | микросервисы или монолит с независимыми пайплайнами по модулям |
| Одна часть нагружена на порядок сильнее (отчёты, обработка изображений) | вынести горячую часть в сервис / отдельный воркер |
| Сбой второстепенного модуля не должен ронять основной путь | изоляция в отдельный процесс с таймаутами |
| Нагрузка равномерная | масштабировать монолит репликами |

## Чек-лист выбора

Подробнее: [03_choosing_architecture.md](./01_theory/03_choosing_architecture.md).
Большинство ответов «нет» → модульный монолит; несколько явных «да» → сервисы.

1. Несколько независимых команд?
2. Границы домена устоялись?
3. Есть часть с резко другим профилем нагрузки?
4. Обязательна изоляция отказов конкретного модуля?
5. Команда готова нести операционную стоимость?

## Распределённый монолит: признаки

Подробнее: [02_distributed_monolith.md](./01_theory/02_distributed_monolith.md)

| Свойство | Здоровые микросервисы | Распределённый монолит |
| :--- | :--- | :--- |
| Деплой | по одному сервису | совместный, версии должны совпасть |
| Данные | своя БД на сервис | общая БД у нескольких сервисов |
| Вызовы | асинхронные где можно; синхронные — с таймаутами и ретраями | длинные синхронные цепочки `A→B→C→D` без защиты |
| Контракт API | версионируется, обратная совместимость | ломается без оглядки на потребителей |
| Общий код | инфраструктурные утилиты | общий internal-пакет с бизнес-логикой |
| Отказ сервиса | деградация, остальные работают | рушит всю цепочку |

Быстрая проверка на ревью: ручная координация релизов? больше одного сервиса
пишет в одну таблицу? синхронная цепочка из 3+ сервисов без таймаутов?

## Миграция монолит → сервисы

Подробнее: [04_migration_and_strangler_fig.md](./01_theory/04_migration_and_strangler_fig.md)

| Подход | Суть | Когда |
| :--- | :--- | :--- |
| Big bang rewrite ⚠️ | переписать всё, выкатить одним релизом | только маленькая некритичная система |
| Strangler fig | роутер/прокси перед монолитом, переносим по одному куску | система, которая приносит деньги |
| Expand → Migrate → Contract | добавить новое рядом → перевести потребителей → удалить старое | смена схемы/контракта без простоя |

| Что выносить первым | Что не выносить первым |
| :--- | :--- |
| ясные границы данных, наибольшая текущая боль, слабая связь с доменом | модуль, глубоко переплетённый с чужими данными |

| Этап разделения данных | Состояние |
| :--- | :--- |
| 1. Общая БД, отдельный код | распределённый монолит — держать осознанно и недолго |
| 2. Отдельная схема в той же БД | ответственность разделена, инфраструктура общая |
| 3. Отдельная БД | цель; переезд через dual write или outbox → consumer |

## Типичные ошибки

Подробнее: [05_use_cases.md](./01_theory/05_use_cases.md)

- ⚠️ Резать по техническим слоям (UI / логика / БД), а не по bounded context → распределённый монолит.
- ⚠️ Микросервисы «на всякий случай», без конкретной боли → цена без выгоды.
- ⚠️ Общая БД «на потом» → становится постоянной.
- ⚠️ Синхронные цепочки без таймаутов и деградации → один отказ рушит запрос.
- ⚠️ Нет измеримого критерия готовности перед выключением старого пути.
