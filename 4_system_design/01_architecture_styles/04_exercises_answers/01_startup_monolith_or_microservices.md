# Упражнение 01: разбор

## 1. Оценка предложения «сразу микросервисы»

По всем четырём критериям предложение не выдерживает проверки:

- **Размер команды.** 4 разработчика на 4+ сервиса — меньше одного человека на
  сервис. Любая работа поперёк «границ» (а на старте она будет постоянной —
  фичи режут через все модули) требует переключения контекста между несколькими
  репозиториями/деплоями для одних и тех же людей.
- **Зрелость домена.** PMF не найден, требования меняются еженедельно. Это
  прямо означает, что сегодняшние границы между «Бронированиями»,
  «Пользователями», «Уведомлениями» и «Биллингом» почти гарантированно неверны
  — через месяц выяснится, что, например, уведомления должны знать детали
  бронирования, которые казались чужой ответственностью.
- **Требования к масштабированию.** Пара сотен запросов в минуту — это
  нагрузка, которую без всяких проблем держит один процесс на одной машине.
  Неравномерности нагрузки между модулями, оправдывающей раздельное
  масштабирование, нет и не предвидится в обозримом будущем.
- **Изоляция отказов.** Для MVP на ранней стадии куда важнее скорость
  разработки, чем то, что сбой уведомлений не уронит бронирования, — а такую
  изоляцию несложно обеспечить и внутри одного процесса (`try/except` вокруг
  отправки, очередь на потом).

Итог: предложение путает «правильно» с «дорого прямо сейчас без выгоды».
Стоимость координации четырёх сервисов на команде из четырёх человек выше
любой теоретической пользы независимого масштабирования, которое не
понадобится ещё очень долго.

## 2. Рекомендуемая архитектура

Модульный монолит на Django/FastAPI с явными внутренними модулями:

```
booking_platform/
  bookings/       # бронирования комнат — ядро домена
  accounts/       # пользователи и организации
  notifications/  # e-mail/push уведомления (через очередь задач, напр. Celery)
  billing/        # тарифы, оплата подписки
```

Правила: модули общаются только через явные Python-интерфейсы (функции/классы,
выделенные как публичный API модуля), без прямых импортов внутренних моделей
друг друга и без циклических зависимостей (контролируется через `import-linter`
или `tach` в CI). Один процесс, одна БД, один деплой — но при этом уже сейчас
видно, где будущие границы сервисов, если они понадобятся.

## 3. Сигналы к выделению сервиса

- Один из модулей начинает создавать нагрузку на порядок выше остальных
  (например, `notifications` при резком росте числа офисов и рассылок).
- Одному модулю требуется технология, которую неудобно тащить в основной
  процесс (полнотекстовый поиск с отдельным индексом, ML-инференс).
- Команда вырастает до нескольких независимых подкоманд, и им нужен раздельный
  релизный цикл.
- Регуляторные/аудиторские требования к `billing` требуют физической изоляции
  его данных и доступа.

## 4. Наиболее вероятный первый кандидат

`billing` — по двум причинам сразу: это модуль с наиболее чёткими и
независимыми границами данных (тарифы и платежи почти не пересекаются по схеме
с бронированиями), и это модуль, к которому раньше остальных обычно приходят
внешние требования (интеграция с платёжным провайдером, аудит,
PCI-совместимость), создающие конкретную, а не гипотетическую причину для
выделения.
