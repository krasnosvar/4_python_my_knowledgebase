# Упражнение 03: разбор

## 1. Порядок выноса модулей

Рекомендуемый порядок: **1) `search`, 2) `billing`, 3) `reviews`, 4)
`catalog`+`orders` остаются в монолите (или выносятся вместе, последними, если
вообще есть смысл).**

Обоснование:

- **`search` — первым.** Наиболее ясные границы данных (это, по сути,
  производный индекс поверх каталога, а не источник истины) и максимально
  острая конкретная боль прямо сейчас (нужна специализированная технология и
  отдельное масштабирование по чтению). Слабая связанность с остальным доменом
  — поиск только читает данные каталога, не участвует в записи бизнес-логики
  заказов.
- **`billing` — вторым.** Тоже достаточно ясные границы (платежи и тарифы —
  обособленная модель), острая организационная причина (отдельная команда,
  требования аудита). Более рискованно, чем `search`, потому что требует
  настоящей строгой консистентности при переносе денежных данных.
- **`reviews` — третьим, если вообще стоит.** Ясные границы данных, но низкий
  приоритет — модуль почти не меняется и не создаёт нагрузки, поэтому
  конкретной боли, оправдывающей вынос, нет. Его можно оставить в монолите
  бесконечно долго без вреда — вынос ради «полноты миграции» не создаёт
  ценности.
- **`catalog` и `orders` — не трогать первыми.** Тесно переплетены общими
  таблицами и часто меняются вместе — это ровно тот случай, когда вынос будет
  сложнее всего (нужно решать проблему разделения данных между двумя активно
  эволюционирующими моделями) и рискованнее всего (максимальная частота
  изменений = максимальный шанс сломать что-то на переходном периоде).

## 2. Таблица маршрутов на промежуточном этапе

```
prefix          -> handler
/search         -> search_service      (вынесен)
/billing        -> billing_service     (вынесен)
(остальное)     -> monolith            (catalog, orders, reviews)
```

Аналогично примеру `02_examples/01_strangler_fig_router`: роутер регистрирует
префиксы `/search` и `/billing` на новые сервисы, всё остальное продолжает идти
в монолит без единой строчки изменений в клиентском коде.

## 3. Expand–Migrate–Contract для `billing`

- **Expand.** Развернуть `billing-service` с собственной БД параллельно
  монолиту. На запись — временно писать в обе БД (dual write: сначала в
  монолитную БД как раньше, затем событием/синхронным вызовом дублировать в
  новую БД `billing-service`), либо публиковать событие `PaymentProcessed` из
  монолита, которое `billing-service` потребляет и строит свою копию данных.
- **Migrate.** Постепенно переключать чтения на `billing-service` (сначала
  некритичные — например, история платежей в личном кабинете), сверяя ответы
  старого и нового пути на расхождения. Когда уверенность набрана — переключить
  прямой приём новых платежей на `billing-service` как источник истины, а
  монолит начинает читать баланс/статусы через API `billing-service`, а не из
  своей таблицы.
- **Contract.** Убрать таблицы платежей из монолитной БД и прямой доступ к ним,
  оставить только вызовы API `billing-service`. Убрать dual write.

Ключевое: ни на одном шаге прод не останавливается, и на каждом шаге есть
возможность откатиться на предыдущий, если сверка покажет расхождения.

## 4. Почему `catalog` и `orders` не выносятся первыми

Частота изменений — не аргумент «в пользу» раннего выноса, а аргумент
«против». Модуль, который часто меняется и тесно связан с другим часто
меняющимся модулем, требует решить сразу две сложные задачи одновременно:
разделить данные (кто владеет какими полями, как `orders` будет ссылаться на
товары `catalog` после разделения БД — по ID через API, с локальным кэшем?) и
делать это на нестабильной, продолжающей активно эволюционировать модели.
Выносить стоит сначала на модулях с низкой связанностью и высокой стабильностью
границ (`search`, затем `billing`), чтобы отработать сам процесс миграции
(роутер, Expand-Migrate-Contract, мониторинг расхождений) на менее рискованном
материале, прежде чем браться за самый сложный узел системы.
