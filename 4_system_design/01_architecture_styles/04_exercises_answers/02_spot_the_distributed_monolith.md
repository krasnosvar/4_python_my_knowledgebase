# Упражнение 02: разбор

## 1. Признаки по каждому пункту

- **Прямой `SELECT` в чужую таблицу `prices`.** Это признак «общая база данных»
  — граница владения данными не соблюдена: `orders-service` не просто
  пользуется чужим API, а знает внутреннюю схему `pricing-service` и завязан на
  неё напрямую.
- **Синхронная цепочка без таймаутов `orders → pricing → notifications`.**
  Прямой пример признака «синхронные цепочки вызовов», где отказ или задержка в
  самом нижнем звене рушит верхние — ровно то, что показано в примере
  `02_examples/02_distributed_monolith_chain`.
- **Совместный релиз `orders-service` и `pricing-service`.** Классический
  признак «совместный релиз» — версии двух формально независимых сервисов
  должны совпадать, то есть по факту это один деплой, разбитый на два
  репозитория.
- **`notifications-service` роняет весь запрос при недоступности `shared_db`.**
  Это следствие как общей БД (отказ инфраструктуры одной базы затрагивает все
  «сервисы» сразу), так и синхронной цепочки без деградации: логически
  необязательный шаг (уведомление) сделан блокирующим для обязательного
  (оформление заказа).

## 2. Вероятная причина

Судя по описанию, система была распилена по историческим/организационным
линиям, а не по доменным границам: похоже, что `pricing-service` выделили
технически (вынесли код ценообразования в отдельный процесс), но не успели или
не решились по-настоящему разделить данные — прямой `SELECT` в чужую таблицу
выглядит как «временное» решение, которое осталось постоянным, потому что не
было явного давления его убрать, пока всё работало. Совместные релизы и
синхронная цепочка без таймаутов говорят о том, что контракты между сервисами
никогда не проектировались как независимые API — сервисы изначально
задумывались как модули одного приложения, которые впоследствии просто
физически разнесли по разным Docker-образам без изменения способа их
взаимодействия.

## 3. Предложения по каждому пункту

- Заменить прямой `SELECT` в `prices` на явный API-эндпоинт `pricing-service`
  (или событие `PriceChanged`, которое `orders-service` кэширует у себя) —
  граница данных должна проходить через контракт, а не через общую схему.
- Добавить таймауты и fallback на каждый межсервисный вызов: если
  `pricing-service` не отвечает за N мс — либо использовать последний
  закэшированный тариф, либо явно отклонить запрос с понятной ошибкой, не
  подвешивая клиента на неопределённый срок.
- Ввести версионирование API между `orders-service` и `pricing-service`
  (например, `/v1/`, `/v2/` эндпоинты) с политикой обратной совместимости,
  чтобы релизы можно было разносить по времени.
- Сделать отправку уведомления асинхронной (через очередь) относительно
  основного потока оформления заказа — недоступность `notifications-service` не
  должна блокировать подтверждение заказа, только откладывать уведомление.

## 4. С чего начать

С разделения синхронной цепочки на асинхронную часть, где это возможно (в
первую очередь `notifications`, так как логически это уведомление после факта,
а не часть критического пути) — это самое дешёвое по риску изменение с
немедленным эффектом на надёжность, и оно не требует миграции данных. Замену
прямого доступа к `prices` на API стоит делать следом, так как это требует
координации с командой `pricing-service` и, вероятно, временного периода, когда
работают оба способа доступа (по аналогии с Expand–Migrate–Contract).
