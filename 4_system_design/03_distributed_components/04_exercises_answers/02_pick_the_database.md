# Упражнение 02: разбор

## 1. Выбор БД по сервисам

| Сервис | Тип БД | Обоснование |
|---|---|---|
| `listings-service` | Реляционная (PostgreSQL) | Нужны ACID-транзакции при смене статуса объявления, данные структурированы и стабильны по схеме, важна целостность (продавец существует, категория валидна). |
| `search-service` | Поисковый индекс (Elasticsearch/OpenSearch) | Полнотекстовый и фасетный поиск — специализированная задача, для которой реляционная БД плохо подходит по производительности при таком паттерне запросов; не является источником истины, а производной проекцией. |
| `chat-service` | Широко-колоночная или документная с моделью «одна партиция на диалог» (например, Cassandra, либо MongoDB с шардированием по `chat_id`) | Огромный объём непрерывной записи, паттерн доступа предсказуем и почти всегда один и тот же («последние сообщения этого диалога») — это ровно случай, где широко-колоночная модель с партиционированием по ключу диалога даёт лучшую производительность записи и чтения последних сообщений, чем реляционная модель общего назначения. |
| `pricing-analytics-service` | Колоночная аналитическая БД (например, ClickHouse) | Тяжёлые агрегации по историческим данным за длительные периоды — колоночное хранение на порядок эффективнее для таких запросов (сканирование только нужных колонок), чем строковая реляционная модель. |
| `session-service` | Key-value (Redis) | Простой доступ по ключу (токен → user_id), нужен TTL сессии из коробки, экстремальная скорость чтения/записи — классический сценарий key-value кэша/хранилища. |

## 2. Синхронизация `search-service` с `listings-service`

`search-service` не должен читать напрямую из БД `listings-service` (это
создало бы связанность на уровне БД, антипаттерн из
`01_architecture_styles/01_theory/01_monolith_and_microservices_in_python.md`).
Механизм: `listings-service` при создании/изменении/удалении объявления
записывает событие (`ListingCreated`, `ListingUpdated`, `ListingDeleted`) в
таблицу Transactional Outbox и публикует в брокер сообщений; `search-service`
подписан на эти события и асинхронно обновляет свой индекс. Консистентность
между ними — eventual: между сохранением объявления в PostgreSQL и его
появлением в поисковой выдаче пройдёт короткое время (обычно доли секунды —
единицы секунд), что абсолютно приемлемо для поиска (в отличие от самого факта
продажи объявления, который должен быть строго консистентен в
`listings-service`).

## 3. Оправдана ли полиглот-персистентность здесь

Да, в данном случае оправдана — у каждого выбранного хранилища есть конкретная,
отличная от остальных причина (транзакционность у `listings`, полнотекстовый
поиск у `search`, write-heavy последовательный доступ у `chat`, тяжёлые
агрегации у `pricing-analytics`, TTL и скорость у `session`). Порог, за которым
разнообразие технологий перестаёт окупаться, — когда для двух хранилищ выбраны
разные технологии без реальной разницы в профиле нагрузки (например, если бы
`session-service` тоже хранился в PostgreSQL наравне с key-value — это было бы
избыточным усложнением в обратную сторону, отказом от полиглота там, где он был
бы оправдан). Признак «слишком много»: если команда не может обеспечить
операционную зрелость (бэкапы, мониторинг, экспертиза) по каждой из технологий
— тогда часть выборов стоит унифицировать в пользу простоты, даже ценой
небольшой потери производительности на конкретном паттерне доступа.

## 4. Операция, требующая строгой ACID-транзакции

Смена статуса объявления с «активно» на «зарезервировано» (и далее на
«продано») требует строгой ACID-транзакции внутри `listings-service`: если два
покупателя одновременно попытаются зарезервировать одно и то же объявление,
необходимо гарантированно разрешить это состояние гонки (например, через
`UPDATE ... WHERE status = 'active'` с проверкой числа изменённых строк внутри
транзакции) — иначе объявление можно «продать» дважды. Это принципиально
отличается от синхронизации с `search-service`: там устаревание индекса на
секунду не создаёт противоречия в бизнес-смысле (пользователь просто увидит
объявление в поиске на секунду дольше/позже), тогда как двойная продажа одного
товара — прямая потеря денег и доверия, что требует именно строгой
консистентности в момент самой операции, а не «когда-нибудь потом».
