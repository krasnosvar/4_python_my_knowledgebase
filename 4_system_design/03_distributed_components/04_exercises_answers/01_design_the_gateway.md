# Упражнение 01: разбор

## 1. Скидка партнёрам в Gateway

Не стоит. Это классический пример бизнес-логики, просачивающейся в шлюз просто
потому, что «он всё видит». Проблема в том, что это правило (5% скидка по стажу
партнёрства) относится к домену биллинга/ценообразования, а не к маршрутизации
или периметру безопасности — оно будет меняться по бизнес-причинам (условия
скидки, новые уровни партнёрства) независимо от инфраструктурных изменений
шлюза, и каждое такое изменение потребует деплоя и тестирования компонента,
который в теории должен быть тонким и стабильным. Хуже того, если завтра
появится второй способ доступа к `orders-service` в обход Gateway (например,
внутренний вызов от `chat-service` при создании заказа через ассистента),
скидка не применится, потому что правило живёт только в шлюзе, а не в самом
домене заказов/цен. Правильное место — в `orders-service` или отдельном
`pricing-service`, где это доменное правило и его тесты естественно живут
вместе с остальной логикой ценообразования.

## 2. Доверие `X-User-Id` без проверки

Работоспособно как оптимизация, но рискованно для платёжного сервиса конкретно.
Общая идея «проверить один раз на периметре» разумна для большинства внутренних
сервисов — но `payments-service` имеет дело с деньгами, а значит цена ошибки
при компрометации или неправильной настройке шлюза (например, баг
маршрутизации, из-за которого заголовок случайно не устанавливается или
устанавливается неверно для части запросов) — прямая финансовая потеря или
несанкционированный доступ к чужим платёжным данным. Для критичных операций
разумно применять принцип defense in depth (согласуется с подходом zero trust):
`payments-service` может доверять заголовку для быстрого пути, но обязан хотя
бы минимально валидировать его формат/подпись и логировать несоответствия, а
для самых чувствительных операций (списание, возврат) — независимо проверять
права доступа, а не полагаться исключительно на то, что «Gateway уже проверил».
Компромисс — чуть больше кода в `payments-service`, но кардинально меньший
blast radius при сбое или ошибке конфигурации периметра.

## 3. Разный формат ответов для мобильного и партнёров

Решать через параметр запроса в самом Gateway — плохая идея: это будет
означать, что Gateway должен знать бизнес-логику агрегации и трансформации
данных под каждый тип клиента, то есть содержать логику, которая по определению
принадлежит клиент-специфичному слою (это ровно то, для чего существует BFF,
см. `01_architecture_styles/01_theory/`).
Рекомендация: единый API Gateway на периметре берёт на себя общие cross-cutting
concerns (auth, rate limiting, TLS) для обоих типов клиентов, а за ним — два
отдельных BFF: `mobile-bff` (компактные агрегированные ответы, минимум полей) и
`partner-bff` (полный, версионированный по официальному контракту формат, с
обратной совместимостью, так как внешние партнёры интегрируются по договору и
не могут обновляться мгновенно вместе с вами).

## 4. Итоговый список задач Gateway

Gateway в этой системе должен решать:
1. Терминация TLS для всех входящих соединений.
2. Аутентификация (проверка токена) на входе для обоих типов клиентов.
3. Маршрутизация к `catalog-service`, `orders-service`, `payments-service` (или
   к соответствующим BFF, если они введены).
4. Rate limiting/квоты, отдельные политики для мобильных пользователей и
   партнёров (у партнёров по контракту может быть другой лимит).
5. Логирование, метрики и старт трейсинга на границе системы.
6. Базовая защита от злоупотреблений (например, отсечение аномального трафика)
   — но не бизнес-правила.

Намеренно вне Gateway: расчёт скидок и любые правила ценообразования (в
`orders-service`/`pricing-service`), детальная авторизация по бизнес-ролям
внутри платёжных операций (частично дублируется и внутри `payments-service`,
см. пункт 2), агрегация и подгонка формата ответа под конкретного клиента (в
BFF, а не в самом Gateway).
