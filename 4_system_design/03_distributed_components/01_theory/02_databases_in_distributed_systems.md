# Базы данных в распределённой системе

В монолите вопрос обычно один: «какую БД взять». В распределённой системе он
превращается в несколько: какую БД взять для *каждого* сервиса, и можно ли — и
нужно ли — использовать разные БД для разных сервисов одной системы.

## SQL vs NoSQL: когда что

Это не вопрос «что лучше», а вопрос, какой модели данных и какого профиля
нагрузки требует конкретный сервис.

### Когда SQL (реляционная БД: PostgreSQL, MySQL)

- Данные естественно **реляционные** — много связей между сущностями, нужны
  JOIN'ы, целостность ссылок (foreign keys).
- Требуется **строгая консистентность и ACID-транзакции** — деньги, остатки на
  складе в момент оплаты, любые операции, где недопустимо потерять или
  задвоить изменение.
- Схема данных достаточно **стабильна** и известна заранее — реляционная
  модель менее гибка к частым изменениям структуры на лету, чем документная.
- Нужны сложные запросы с агрегациями, фильтрацией по многим полям, отчётность.

### Когда NoSQL

- **Key-value (Redis, DynamoDB)** — простой доступ по ключу, нужна
  экстремальная скорость чтения/записи, данные не требуют сложных связей.
  Кэши, сессии, счётчики.
- **Документная (MongoDB)** — данные естественно древовидные/вложенные, схема
  часто меняется или различается между записями (полиморфные сущности), не
  требуется много JOIN'ов между коллекциями.
- **Широко-колоночная (Cassandra, HBase)** — огромный объём записи
  (write-heavy), линейное горизонтальное масштабирование важнее сложных
  запросов, модель доступа известна заранее (запрос почти всегда по одному и
  тому же ключу партиционирования).
- **Графовая (Neo4j)** — данные и связи между ними одинаково важны для
  запросов (социальные графы, рекомендации, обнаружение мошенничества по
  связям).

Общее следствие: NoSQL почти всегда жертвует чем-то ради масштабирования и
гибкости схемы — чаще всего JOIN'ами (приходится денормализовывать данные и
дублировать) и/или строгой консистентностью.

### CAP-теорема и eventual consistency простыми словами

Когда данные хранятся на нескольких серверах (узлах), между ними может
пропасть сеть — это называется **сетевым разделением** (partition).
CAP-теорема утверждает: в момент такого разделения система может гарантировать
только одно из двух:

- **C — Consistency (согласованность):** любое чтение возвращает самую свежую
  запись. Ради этого узел, отрезанный от остальных, должен отказывать в ответе
  (иначе он может отдать устаревшие данные).
- **A — Availability (доступность):** каждый работающий узел отвечает на
  запрос — пусть даже данными, которые могли устареть.

**P — Partition tolerance** (устойчивость к разделению) выбирать не
приходится: сеть в распределённой системе рано или поздно рвётся, поэтому
реальный выбор — между C и A *на время сбоя*. Классические реляционные БД с
синхронной репликацией и банковские системы обычно выбирают C (лучше ошибка,
чем неверный баланс), многие NoSQL-хранилища (Cassandra, DynamoDB) по
умолчанию выбирают A.

**Eventual consistency (согласованность в конечном счёте)** — обещание
системы, выбравшей A: если новые записи прекратятся, через некоторое время все
узлы сойдутся к одному значению. Пока этого не произошло, два пользователя
могут увидеть разные данные (например, лайк уже засчитан на одном узле, но ещё
не виден на другом). Для ленты новостей это приемлемо, для остатка на счёте —
нет.

## Полиглот-персистентность (polyglot persistence)

В распределённой системе из нескольких сервисов нет причины заставлять все
сервисы использовать одну и ту же БД — у каждого сервиса свой профиль нагрузки
и своя модель данных, и выбор БД делается на уровне сервиса, а не на уровне
всей системы.

```
Orders Service     -> PostgreSQL   (реляционные данные, нужны транзакции)
Search Service     -> Elasticsearch (полнотекстовый поиск)
Session Store      -> Redis         (key-value, TTL, скорость)
Analytics Service  -> ClickHouse    (колоночная аналитика, огромные агрегации)
Recommendations    -> Neo4j         (граф связей "кто что купил/просмотрел")
```

Это прямое следствие микросервисной архитектуры: если у каждого сервиса своя
БД (обязательное условие настоящей независимости, см.
`01_architecture_styles`), то и технология этой БД — внутренняя деталь
реализации сервиса, которую можно выбирать под конкретную задачу.

- **Плюсы:** каждый сервис получает БД, оптимальную именно под его профиль
  нагрузки, вместо компромисса «одна БД на всех, устраивающая никого
  полностью».
- **Минусы:** операционная цена — команде нужно поддерживать экспертизу сразу
  по нескольким технологиям хранения (бэкапы, мониторинг, тюнинг для каждой),
  а не по одной. Данные, которые логически связаны, но живут в разных БД,
  требуют синхронизации через API/события, а не через прямой JOIN — это удобно
  архитектурно (границы сервисов), но добавляет работы по поддержанию
  консистентности между копиями.

## Согласованность между БД разных сервисов

Если `Orders Service` (PostgreSQL) публикует событие о заказе, а `Search
Service` (Elasticsearch) должен обновить свой поисковый индекс — это два
разных хранилища, обновляемых асинхронно через событие. Здесь неизбежна
eventual consistency: поисковый индекс на короткое время отстаёт от источника
истины в PostgreSQL. Для данных, требующих строгой консистентности (сама
транзакция заказа), полиглот-персистентность не применяется — эти данные
остаются в одной транзакционной БД, а производные копии в других хранилищах
(поиск, аналитика, кэш) осознанно принимают роль вторичных, устаревающих
представлений.

## Практический выбор для сервиса

1. Нужна ли ACID-транзакция над этими данными прямо сейчас, в рамках одного
   сервиса? Если да — реляционная БД почти всегда правильный выбор по
   умолчанию.
2. Известен ли заранее и стабилен ли паттерн доступа (почти всегда по одному
   ключу)? Тогда key-value/широко-колоночная модель может быть проще и
   быстрее.
3. Насколько важны сложные запросы и отчётность по этим данным? Реляционная
   модель или колоночное хранилище для аналитики.
4. Схема данных стабильна, или сущности сильно различаются по структуре и
   часто меняются? Документная модель снимает миграции схемы.

> Частый вопрос на собеседовании: что такое полиглот-персистентность и зачем
> она нужна? Использование разных типов БД для разных сервисов/подсистем одной
> системы, каждая — под свой профиль нагрузки и модель данных, вместо одной
> универсальной БД на всё. Цена — операционная сложность поддержки нескольких
> технологий хранения и необходимость синхронизировать логически связанные
> данные, живущие в разных БД, через API/события, а не через прямой JOIN.

> Частый вопрос на собеседовании: можно ли использовать NoSQL там, где раньше
> использовали SQL, просто ради масштабируемости? Можно, но это осознанный
> компромисс, а не бесплатное улучшение: почти всегда придётся отказаться от
> удобных JOIN'ов (денормализовать и дублировать данные под конкретные
> паттерны чтения) и, возможно, от строгой консистентности — оправдано это
> только тогда, когда реальный профиль нагрузки (объём, паттерн доступа)
> действительно требует того, что даёт конкретная NoSQL-модель.
