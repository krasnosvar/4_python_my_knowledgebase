# Distributed components: практические применения

Сводка того, как компоненты этого раздела складываются в единый путь запроса распределённой системы.

## Типичная сборка запроса

```
клиент ─▶ [ API Gateway ]           auth, rate limit, TLS, маршрутизация
              │
              ▼
     [ Service Discovery ]          "куда отправить" - здоровые инстансы svc-a
              │
              ▼
     [ Load Balancer: least conn ]  "какой из здоровых инстансов выбрать"
              │
              ▼
        svc-a instance ──▶ своя БД (полиглот-персистентность: своя технология под задачу)
              │
              ▼ (асинхронно, не блокируя ответ клиенту)
       [ Message Broker ] ──▶ svc-b, svc-c потребляют событие независимо
```

Каждый компонент решает свою узкую задачу: шлюз — периметр и cross-cutting concerns, discovery — актуальный список живых адресов, балансировщик — выбор конкретного адреса, брокер — развязку между сервисом-источником события и его потребителями. Вместе они и образуют «инфраструктурный клей» между независимыми сервисами, который отличает набор сервисов от простого набора процессов, кое-как обращающихся друг к другу напрямую.

## Как выбирать БД и связи между сервисами на практике

- Каждый сервис выбирает свою БД под свой профиль нагрузки (`02_databases_in_distributed_systems.md`) — единой БД на всю систему в здоровой микросервисной архитектуре не должно быть в принципе.
- Синхронный вызов между сервисами — только когда вызывающей стороне действительно нужен немедленный ответ для продолжения своей логики; всегда с таймаутом и осмысленной деградацией.
- Асинхронная связь через брокер — когда немедленный ответ не нужен бизнес-логике; разрывает потенциальную синхронную цепочку и связанную с ней хрупкость (`01_architecture_styles/02_distributed_monolith.md`).

## Частые ошибки

- API Gateway обрастает бизнес-логикой и становится узким местом и точкой отказа для всей системы — держите его тонким.
- Смешивание liveness и readiness проверок в одну — приводит к бессмысленным перезапускам процессов при временных проблемах с зависимостями.
- Sticky sessions (IP hash) вводятся «на всякий случай» вместо того, чтобы сделать сервис по-настоящему stateless и вынести состояние во внешнее хранилище.
- Полиглот-персистентность применяется бездумно («у нас будет 5 разных БД, потому что это модно») без реальной причины, соответствующей профилю нагрузки конкретного сервиса — это чистая операционная цена без выгоды.
- Round Robin используется там, где запросы сильно различаются по длительности обработки — приводит к перекосу нагрузки, который решался бы Least Connections почти без дополнительных затрат.

## Мини-чеклист

1. Где заканчивается ответственность API Gateway и начинается ответственность самого сервиса — не размыты ли границы?
2. Как сервис узнаёт актуальный список живых адресов зависимостей — через явный реестр, через платформу (Kubernetes Service), или захардкожен адрес?
3. Отличается ли liveness-проверка от readiness-проверки для каждого сервиса, или используется одна и та же на оба случая?
4. Какой алгоритм балансировки используется, и соответствует ли он реальному профилю длительности запросов?
5. Каждый ли сервис владеет своей БД, или есть скрытые общие таблицы между «независимыми» сервисами?

> Частый вопрос на собеседовании: как эти компоненты (Gateway, discovery, балансировка, брокер, БД) связаны между собой в одну картину? Gateway и discovery/балансировка вместе решают задачу «довести синхронный запрос до правильного живого инстанса нужного сервиса»; брокер — альтернативный, асинхронный путь связи там, где немедленный синхронный ответ не нужен; выбор БД — внутренняя деталь каждого сервиса, не видимая снаружи. Вместе они образуют инфраструктуру, которая делает набор независимо задеплоенных сервисов согласованно работающей системой, а не просто россыпью процессов.
