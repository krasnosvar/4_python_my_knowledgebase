# Health checks и service discovery

Два взаимосвязанных механизма: как система узнаёт, что конкретный инстанс сервиса жив и готов принимать трафик (health checks), и как один сервис находит сетевой адрес другого сервиса, когда инстансы динамически появляются и исчезают (service discovery).

## Health checks

### Liveness vs readiness

Это два разных вопроса, которые часто путают:

- **Liveness («жив ли процесс»)** — отвечает ли процесс вообще, не завис ли он намертво (deadlock, бесконечный цикл). Провал liveness-проверки — сигнал «нужно перезапустить процесс», потому что сам он уже не восстановится.
- **Readiness («готов ли принимать трафик именно сейчас»)** — процесс жив, но временно не готов обслуживать запросы: ещё не прогрелся, идёт миграция данных, потерял соединение с БД. Провал readiness-проверки — сигнал «временно убрать из пула балансировщика, но не перезапускать» — инстанс может сам восстановиться (например, когда восстановится соединение с БД) и снова начать проходить проверку.

Смешение этих двух проверок в одну — частая ошибка: если readiness-проблему (временная потеря связи с БД) обрабатывать как liveness-провал, инстанс будет без нужды перезапускаться, хотя проблема была не в нём самом, а в зависимости, и перезапуск её не решит.

### Как это выглядит на практике

Обычно — HTTP-эндпоинт (`/healthz`, `/readyz`), который периодически опрашивает балансировщик/оркестратор (Kubernetes, например, различает `livenessProbe` и `readinessProbe` буквально как две настройки). Readiness-проверка обычно чуть более содержательная — может проверять доступность критичных зависимостей (БД, кэш), тогда как liveness чаще всего — минимальная проверка «процесс отвечает на HTTP вообще».

## Service Discovery

Проблема: в динамической инфраструктуре (автоскейлинг, рестарты, контейнеры с новыми IP при каждом развёртывании) адреса инстансов сервиса постоянно меняются. Клиенту (или балансировщику) нужен способ узнать актуальный список живых адресов, а не хардкодить IP.

### Client-side discovery

Клиент сам спрашивает реестр сервисов (service registry) о списке живых инстансов нужного сервиса и сам выбирает один из них (применяя один из алгоритмов балансировки из `04_load_balancing.md`) — балансировка происходит на стороне клиента.

```
Client ──▶ [ Registry ] ──▶ список живых адресов svc-a
Client сам выбирает один и обращается напрямую
```

- **Плюс:** нет дополнительного сетевого хопа через промежуточный балансировщик.
- **Минус:** логика обнаружения и балансировки размазывается по каждому клиенту — каждый клиентский сервис должен знать протокол реестра и уметь балансировать.

### Server-side discovery

Клиент обращается к стабильному адресу (балансировщику/прокси), а тот сам находит живой инстанс через реестр и перенаправляет запрос.

```
Client ──▶ [ Стабильный адрес: LB/прокси ] ──▶ (сам находит живой инстанс) ──▶ svc-a instance
```

- **Плюс:** клиент максимально прост — просто обращается к одному стабильному адресу, вся сложность обнаружения инкапсулирована в инфраструктуре.
- **Минус:** дополнительный сетевой хоп через прокси/балансировщик.

### Реестр сервисов

База «имя сервиса → адреса живых инстансов», наполняемая либо через явную регистрацию инстанса при старте (self-registration), либо через внешний наблюдатель, который сам обнаруживает новые инстансы (например, в оркестраторе). Реестр обязательно связан с health checks — из списка отдаются только инстансы, прошедшие проверку готовности, иначе discovery будет направлять трафик на нерабочие инстансы.

Примеры механизма: Consul, etcd как универсальные реестры с health checks; в Kubernetes эта роль в основном закрыта «бесплатно» — `Service` даёт стабильное DNS-имя и виртуальный IP, а платформа сама поддерживает список здоровых подов на основе readiness-проб, реализуя фактически server-side discovery без необходимости писать собственный код обнаружения.

```
Инстансы регистрируются/обнаруживаются:      Клиент резолвит имя сервиса:
svc-a: 10.0.0.1 (healthy)  ─┐                  "svc-a" ──▶ [Registry/DNS] ──▶ 10.0.0.2
svc-a: 10.0.0.2 (healthy)  ─┼─▶ [ Registry ]   (отдаёт только здоровые инстансы,
svc-a: 10.0.0.3 (unhealthy)─┘  + health checks  10.0.0.3 исключён по health check)
```

## Как это связано с балансировкой и API Gateway

Service discovery отвечает на вопрос «куда вообще можно отправить запрос», балансировка (`04_load_balancing.md`) — «какой из доступных адресов выбрать для конкретного запроса», API Gateway (`01_api_gateway.md`) часто объединяет обе задачи на периметре системы плюс добавляет cross-cutting concerns поверх. Это не взаимоисключающие компоненты, а слои одной и той же задачи «довести запрос до живого, готового инстанса нужного сервиса».

> Частый вопрос на собеседовании: в чём разница liveness и readiness проверки? Liveness отвечает, жив ли сам процесс (провал — нужен перезапуск, сам он не восстановится). Readiness отвечает, готов ли инстанс принимать трафик прямо сейчас (провал — временно убрать из пула балансировки, но не обязательно перезапускать, инстанс может восстановиться сам, например когда вернётся соединение с зависимой БД).

> Частый вопрос на собеседовании: client-side или server-side discovery — что используется в Kubernetes? Server-side: клиент обращается к стабильному DNS-имени/виртуальному IP объекта Service, а платформа сама поддерживает список здоровых подов на основе readiness-проб и направляет трафик — вся сложность обнаружения и здоровья инстансов инкапсулирована в платформе, а не в коде клиентского сервиса.
