# API Gateway

Единая точка входа для внешних клиентов перед набором внутренних сервисов.
Клиент общается только со шлюзом и не знает о внутренней топологии системы за
ним.

```
                    +-------------+     +-----------------+
   клиенты  ───────▶|             |────▶| Orders Service  |
  (web/mobile)      | API Gateway |────▶| Users Service   |
                     |             |────▶| Billing Service |
                     +-------------+     +-----------------+
```

## Роль шлюза: cross-cutting concerns

Шлюз берёт на себя сквозные задачи, общие для всех запросов, чтобы не
дублировать их в каждом внутреннем сервисе:

- **Маршрутизация** запросов к нужному внутреннему сервису по
  пути/заголовку/версии API.
- **Аутентификация и авторизация на входе** — проверка токена один раз на
  периметре, а не в каждом сервисе заново (внутренние сервисы могут доверять
  уже провалидированному контексту от шлюза).
- **Rate limiting и квоты** — защита внутренних сервисов от перегрузки на
  самой границе системы, до того как запрос вообще потратит их ресурсы.
- **Терминация TLS** — TLS это шифрование соединения (то, что превращает
  `http://` в `https://`). «Терминация» означает, что шифрованное соединение
  от клиента заканчивается на шлюзе: он расшифровывает трафик, а дальше внутри
  периметра запросы могут идти без шифрования (или тоже шифроваться, если
  компания следует модели **zero trust** — «не доверять никому, даже внутри
  собственной сети», когда каждый сервис заново проверяет каждого, кто к нему
  обращается).
- **CORS** (Cross-Origin Resource Sharing) — правила, которые сервер сообщает
  браузеру: JavaScript с каких сайтов может обращаться к этому API. Браузер по
  умолчанию запрещает странице с одного домена читать ответы API другого
  домена, и CORS-заголовки ослабляют этот запрет точечно. Это и прочие
  HTTP-специфичные политики для браузерных клиентов удобно настраивать в одном
  месте — на шлюзе.
- **Агрегация ответов** нескольких сервисов в один ответ клиенту и
  **трансляция протоколов** (например, наружу — простой REST/JSON, внутрь —
  gRPC между сервисами).
- **Наблюдаемость на границе** — единая точка для логирования, метрик и старта
  трейсинга запроса, до того как он разошёлся по внутренним сервисам.

## Риски

Шлюз легко превращается в «толстую» точку с собственной бизнес-логикой —
искушение велико, ведь он и так видит весь трафик. Это плохо по двум причинам:
во-первых, он становится ещё одним местом, которое нужно понимать и
тестировать при любом изменении бизнес-правил; во-вторых, он превращается в
единую точку отказа и в узкое место для всей системы — если шлюз не
масштабируется вместе с трафиком или падает, ложится всё, что за ним, вне
зависимости от того, насколько здоровы сами внутренние сервисы. Держать шлюз
тонким — намеренное архитектурное решение, а не забывчивость.

## API Gateway на практике в Python-стеке

Шлюз необязательно писать с нуля — часто это готовое решение (Kong, Envoy,
Traefik, облачный API Gateway) перед набором Python-сервисов (FastAPI/Django).
Иногда лёгкий шлюз пишут поверх ASGI (например, тонкий FastAPI-сервис, который
только маршрутизирует и агрегирует, не имея собственной модели данных) — тогда
особенно важно дисциплинированно не давать ему обрастать бизнес-логикой.

## Отличие от BFF (Backend for Frontend)

API Gateway — универсальная точка входа с общими для всех клиентов
cross-cutting concerns. **BFF** — отдельный бэкенд-шлюз под конкретный тип
клиента (свой для web, свой для мобильного приложения), задача которого —
агрегировать и подгонять данные под нужды именно этого клиента (мобильному
нужен компактный ответ с меньшим числом полей и раундтрипов, web — другой
набор данных). Часто применяются вместе: единый API Gateway на периметре берёт
на себя auth/rate limiting/TLS, а за ним стоят несколько BFF под разных
клиентов, которые уже занимаются агрегацией под конкретную форму ответа.

```
   Web    ───▶ [ API Gateway ] ──▶ [ BFF-web ]    ──┐
                                                      ├──▶ внутренние сервисы
   Mobile  ───▶ [ API Gateway ] ──▶ [ BFF-mobile ] ──┘
```

> Частый вопрос на собеседовании: чем API Gateway отличается от простого
> reverse proxy (nginx перед сервисами)? Reverse proxy в базовой конфигурации
> — это в основном маршрутизация и терминация TLS. API Gateway берёт на себя
> более широкий набор задач уровня приложения: аутентификацию/авторизацию,
> rate limiting с бизнес-семантикой (лимиты на пользователя/ключ, а не просто
> на IP), агрегацию ответов нескольких сервисов, трансляцию протоколов. На
> практике грань размыта — многие reverse proxy умеют почти всё то же самое
> через плагины.

> Частый вопрос на собеседовании: почему нельзя просто дать каждому
> внутреннему сервису самому проверять аутентификацию? Можно, и в моделях zero
> trust так и делают дополнительно (проверка на каждом сервисе, а не только на
> периметре). Но проверка один раз на шлюзе снимает дублирование логики
> авторизации в каждом сервисе и даёт единую точку, где меняется политика
> аутентификации при необходимости — компромисс в том, что шлюз становится
> критичным звеном, отказ которого блокирует доступ вообще ко всему периметру.
