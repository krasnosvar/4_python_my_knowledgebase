# Балансировщики нагрузки: алгоритмы

Балансировщик распределяет входящие запросы между несколькими инстансами сервиса. Выбор алгоритма определяет, насколько равномерно распределится нагрузка и насколько балансировщик учитывает реальное состояние инстансов, а не просто их количество.

## Round Robin

Запросы раздаются инстансам по кругу, по очереди: 1, 2, 3, 1, 2, 3, ...

- **Плюс:** предельно простой, не требует никакого состояния о загрузке инстансов.
- **Минус:** не учитывает, что инстансы могут быть загружены по-разному (один уже обрабатывает медленный запрос, другой свободен) — новый запрос всё равно уйдёт по кругу следующему инстансу, даже если тот уже перегружен.

## Weighted Round Robin

То же самое, но с весами: более мощный инстанс получает пропорционально больше запросов (например, вес 3 против веса 1 у более слабого инстанса — на каждые 3 запроса первому один достаётся второму).

- Полезен при неоднородном парке инстансов (разные размеры машин, например, при поэтапном обновлении инфраструктуры).

## Least Connections

Запрос уходит инстансу с наименьшим числом **сейчас обрабатываемых** соединений/запросов.

- **Плюс:** учитывает реальную текущую загрузку, а не просто очередь по кругу — лучше подходит, когда запросы существенно различаются по времени обработки (иначе один инстанс с несколькими медленными запросами продолжал бы получать новые порции по round robin, только усугубляя перекос).
- **Минус:** требует, чтобы балансировщик отслеживал состояние (число активных соединений на каждый инстанс) — чуть сложнее, чем round robin.

## Least Response Time

Комбинация Least Connections и учёта средней латентности ответа инстанса: запрос уходит инстансу с наименьшим числом активных соединений **и** наименьшей недавней латентностью.

- Точнее отражает реальную способность инстанса быстро обработать ещё один запрос, но требует сбора и поддержания метрики латентности по каждому инстансу.

## IP Hash / Consistent Hash

Инстанс выбирается по хэшу от IP-адреса клиента (или другого ключа сессии) — один и тот же клиент почти всегда попадает на один и тот же инстанс.

- **Плюс:** даёт «липкость» сессии (sticky session) без необходимости хранить состояние сессии централизованно — полезно, если инстанс кэширует что-то про конкретного клиента локально в памяти.
- **Минус:** привязка к конкретному клиенту нарушает равномерность распределения нагрузки, если у клиентов сильно разное поведение (один клиент шлёт на порядок больше запросов, чем другие) — весь этот трафик оседает на одном инстансе. При выходе инстанса из строя все «прилипшие» к нему клиенты теряют своё состояние (если оно не вынесено во внешнее хранилище — см. `03_distributed_components` и обсуждение stateless-компонентов в `02_performance_and_scaling`).

## Random / Power of Two Choices

Случайный выбор инстанса, иногда — с улучшением «power of two choices»: выбрать случайно два инстанса, отправить запрос тому, у кого сейчас меньше активных соединений. Простая эвристика, дающая на практике распределение почти такое же ровное, как полный Least Connections, но при существенно меньших накладных расходах на учёт состояния всех инстансов.

## Сравнение

| Алгоритм | Учитывает текущую загрузку | Требует состояния | Типичное применение |
|---|---|---|---|
| Round Robin | нет | нет | однородные инстансы, схожие по времени запросы |
| Weighted Round Robin | нет (кроме статичного веса) | минимальное | неоднородный парк инстансов |
| Least Connections | да | среднее | запросы сильно различаются по времени обработки |
| Least Response Time | да, точнее | больше | latency-критичные сервисы с неоднородной нагрузкой |
| IP Hash / Consistent Hash | нет | нет (детерминирован по ключу) | sticky-сессии, локальный кэш на инстансе |
| Power of Two Choices | частично | минимальное | компромисс простоты и равномерности при большом числе инстансов |

## Уровень балансировки: L4 vs L7

- **L4 (транспортный уровень)** — балансировка на основе IP/порта/TCP-соединения, не заглядывая внутрь содержимого запроса. Быстрее, но не может маршрутизировать по пути URL, заголовкам, содержимому запроса.
- **L7 (уровень приложения)** — балансировщик понимает HTTP и может маршрутизировать по пути (`/api/orders` → один набор инстансов, `/api/users` → другой), заголовкам, cookie. Это то, что фактически делает и API Gateway в части простой маршрутизации — грань между «L7-балансировщиком» и «шлюзом» размыта и определяется тем, сколько дополнительных cross-cutting concerns взято на себя.

## Практический выбор

Для большинства stateless HTTP API сервисов с относительно однородным временем обработки запросов достаточно round robin или least connections — оба просты и хорошо предсказуемы. Least connections предпочтительнее, когда время обработки запросов существенно варьируется (например, часть запросов — простой CRUD, часть — тяжёлые агрегации). Sticky-сессии (IP hash) стоит вводить только по конкретной причине (локальное состояние на инстансе, которое дорого/сложно вынести вовне) — если такой причины нет, лучше держать сервис полностью stateless и не привязывать клиента к конкретному инстансу вовсе.

> Частый вопрос на собеседовании: чем Round Robin хуже Least Connections и когда это действительно имеет значение? Round Robin не учитывает текущую загрузку инстансов — если время обработки запросов сильно варьируется, инстанс, уже занятый долгим запросом, всё равно получит следующий по очереди, увеличивая перекос. Least Connections распределяет новый запрос туда, где сейчас меньше всего активной работы, что точнее отражает реальную свободную мощность — разница особенно заметна при неоднородных по длительности запросах, и почти незаметна, если все запросы примерно одинаковы по времени обработки.

> Частый вопрос на собеседовании: почему sticky sessions (привязка клиента к инстансу через IP hash) — компромиссное, а не идеальное решение? Она нарушает равномерность распределения нагрузки при неравномерном поведении клиентов и превращает потерю инстанса в потерю состояния для всех «прилипших» к нему клиентов, если это состояние не продублировано во внешнем хранилище. Более здоровый путь — держать сервис stateless и хранить состояние сессии в общем внешнем хранилище (Redis), которое доступно любому инстансу, тогда балансировка может быть свободной (round robin/least connections) без потери данных при выходе инстанса из строя.
