# Партиционирование и шардирование данных (концептуально)

Когда объём данных или нагрузка на запись превышают то, что может выдержать один узел БД (даже вертикально масштабированный до предела), данные разбивают на части, распределённые по нескольким узлам. Здесь — концептуальный уровень: что это такое и какие есть стратегии; механика конкретных СУБД (репликация, консистентность, транзакции между шардами) разбирается подробно в разделе про данные (`2_data_and_messaging`).

## Партиционирование vs шардирование: в чём разница

- **Партиционирование** — разбиение данных на части (партиции) в рамках, как правило, одного логического хранилища/узла (например, партиционирование таблицы по диапазону дат в PostgreSQL). Упрощает управление большими таблицами (быстрое удаление старых партиций, более узкие индексы), но необязательно распределяет данные по разным физическим машинам.
- **Шардирование** — разбиение данных на части (шарды), физически расположенные на **разных узлах**. Это партиционирование, применённое ради горизонтального масштабирования — каждый шард может обслуживаться отдельным сервером БД.

На практике эти термины часто используют как синонимы, но шардирование всегда подразумевает распределение по разным машинам, а партиционирование — не обязательно.

## Зачем шардировать

- **Объём данных** превышает то, что помещается на диск/в память одного узла с приемлемой производительностью.
- **Write QPS** превышает то, что может обработать один узел на запись (у БД обычно один узел-мастер принимает запись; реплики решают проблему масштабирования чтения, но не записи).
- Желание **изолировать нагрузку** — например, данные одного крупного клиента (tenant) не должны замедлять запросы остальных клиентов.

## Стратегии выбора ключа шардирования

### Range-based (по диапазону)

Данные распределяются по диапазонам значений ключа (например, пользователи с ID 1–1000000 — шард A, 1000001–2000000 — шард B).

- **Плюс:** простые range-запросы («все заказы за последний месяц») остаются эффективными — данные диапазона лежат на одном шарде.
- **Минус:** легко получить **hot shard** — если новые данные всегда попадают в один и тот же (обычно последний, «свежий») диапазон, вся нагрузка записи концентрируется на одном шарде, а остальные простаивают.

### Hash-based (по хэшу ключа)

Ключ шардирования (например, `user_id`) хэшируется, и результат хэша определяет шард (`hash(key) % N`).

- **Плюс:** равномерное распределение нагрузки по шардам при достаточно случайном ключе — hot shard маловероятен.
- **Минус:** range-запросы становятся дорогими — соседние по логике данные (например, диапазон дат) размазаны по всем шардам случайным образом, и такой запрос требует опроса всех шардов (scatter-gather) вместо одного.
- **Проблема простого `mod N`:** при добавлении/удалении шарда (изменении `N`) результат `hash(key) % N` меняется почти для всех ключей — требуется массовая перебалансировка данных. Решение — **consistent hashing**: кольцо хэшей, где добавление узла переносит только часть ключей (в среднем `K/N` из `K` ключей), а не пересчитывает всё заново.

### По географии / tenant (клиенту)

Данные каждого крупного клиента или каждого региона — на своём шарде. Естественная изоляция нагрузки и данных (полезно и для требований резидентности данных — data residency), но неравномерность неизбежна: у одного клиента данных может быть на порядки больше, чем у другого («шумный сосед» на уровне шарда).

## Последствия шардирования, которые нужно осознанно принять

- **Кросс-шардовые запросы дорогие.** JOIN между данными на разных шардах либо невозможен на уровне БД, либо требует scatter-gather (запросить каждый шард и смержить в приложении) — существенно медленнее одного запроса на одном узле.
- **Кросс-шардовые транзакции сложны.** Изменение данных, затрагивающее сразу два шарда, требует распределённой транзакции (двухфазный коммит) или паттерна saga — обычная ACID-транзакция одной БД здесь не работает напрямую. Именно поэтому ключ шардирования стоит выбирать так, чтобы данные, которые часто изменяются в одной транзакции, оказывались на одном шарде.
- **Ресурсинг («resharding»)** — добавление нового шарда при росте данных — операционно сложная задача: нужно перенести часть данных без простоя и без потери записей на переходный период.

## Как выбирать ключ шардирования на практике

1. Определить самый частый и самый критичный по производительности паттерн доступа (обычно — по ID пользователя/сущности, владеющей большинством данных).
2. Убедиться, что этот ключ даёт достаточно равномерное распределение (не должно быть 80% данных у 1% значений ключа — это прямой путь к hot shard).
3. Проверить, какие операции требуют кросс-шардовых запросов при выбранном ключе, и оценить, насколько они частые и насколько допустима их более высокая стоимость.
4. Предпочитать ключ, при котором данные одной транзакционной единицы (например, всё, что касается одного заказа) оказываются на одном шарде.

> Частый вопрос на собеседовании: чем плох простой `hash(key) % N` при масштабировании числа шардов? При изменении `N` (добавлении/удалении шарда) результат операции меняется почти для всех ключей — это требует пересчитать и перенести практически весь датасет. Consistent hashing решает эту проблему: узлы и ключи размещаются на одном кольце хэшей, и добавление узла переносит только часть ключей (примерно `K/N`), а не весь датасет заново.

> Частый вопрос на собеседовании: как выбрать ключ шардирования для системы заказов интернет-магазина? Скорее всего — по `user_id` или по `shop_id`, в зависимости от того, какие запросы важнее: если типичный запрос — «все заказы этого пользователя», шардировать по `user_id`, чтобы такой запрос не требовал scatter-gather по всем шардам. Важно, чтобы данные, участвующие в одной транзакции (заказ и его позиции), лежали на одном шарде.
