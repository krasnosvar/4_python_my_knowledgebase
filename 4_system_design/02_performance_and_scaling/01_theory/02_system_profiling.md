# Методология профилирования системы

Речь не о профилировании кода (`cProfile`, flame graphs одной функции) — это задача другого уровня. Здесь — профилирование **системы в целом**: где и что мерить на уровне архитектуры, чтобы понять, что на самом деле происходит с запросом, пока он идёт через десяток компонентов.

## Где мерить: на границах компонентов

Каждый переход через границу компонента (сеть, процесс, очередь) — потенциальное место потери времени, которое не видно изнутри одного компонента. Правило: мерить время **входа** и **выхода** на каждой границе пути запроса, а не только «сколько всего заняло».

```
Клиент → [LB] → [App] → [Cache] → [DB]
   t0      t1     t2       t3       t4

время в App        = t2 - t1
время в Cache/DB    = t3 - t2  (или дальше t4 - t3, если miss)
время в очереди LB  = разница между "запрос пришёл" и "запрос ушёл в App"
```

Если измерять только «общее время ответа App» (t2 - t1 в терминах самого приложения), легко упустить, что запрос ждал в очереди перед приложением 200 мс до того, как обработка вообще началась — а это тоже часть латентности, которую видит пользователь.

## Что мерить: золотые сигналы

Универсальный минимальный набор метрик для любого звена системы (согласуется с подходами RED/USE, разбираемыми подробнее в разделе наблюдаемости):

- **Latency** — распределение времени ответа, обязательно с перцентилями (p50, p95, p99), а не только среднее. Среднее скрывает «длинный хвост»: p50 может быть 20 мс, а p99 — 2 секунды, и именно p99 определяет опыт заметной доли пользователей.
- **Traffic / Rate** — сколько запросов в секунду проходит через звено.
- **Errors** — доля запросов, завершившихся ошибкой (включая таймауты).
- **Saturation / Utilization** — насколько близко звено к пределу своей пропускной способности (загрузка CPU, глубина очереди, число занятых соединений в пуле).

Узкое место почти всегда выдаёт себя ростом latency (особенно p99) и saturation при неизменном или чуть растущем traffic — это и есть сигнал «звено на пределе».

## Распределённый трейсинг: как увидеть путь запроса целиком

Один запрос пользователя на бэкенде часто превращается в дерево вызовов через несколько сервисов. Профилировать такой запрос по логам каждого сервиса отдельно — трудоёмко и не даёт цельной картины. Распределённый трейсинг (например, OpenTelemetry) присваивает запросу единый `trace_id`, а каждому шагу обработки — `span` с началом/концом и родительским span'ом, формируя дерево вызовов с точными длительностями.

```
trace_id=abc123
├─ span: API Gateway           (5 мс)
│  └─ span: Orders Service      (120 мс)
│     ├─ span: DB query          (15 мс)
│     └─ span: Pricing Service   (95 мс)   <- держит большую часть времени
│        └─ span: DB query        (90 мс)  <- и внутри неё — почти всё время в БД
```

Такое дерево сразу показывает, что 95 мс из 120 мс в `Orders Service` уходит на вызов `Pricing Service`, и почти всё это время, в свою очередь, — на запрос к БД внутри него. Без трейсинга по границам сервисов пришлось бы сопоставлять логи вручную по времени, что медленно и ненадёжно при высокой нагрузке.

## Профилирование под нагрузкой, а не в вакууме

Узкое место часто проявляется только при определённом уровне конкурентной нагрузки (contention на блокировках, исчерпание пула соединений, насыщение очереди), которого не видно при единичном запросе в тестовом окружении. Практика:

- **Нагрузочное тестирование** (например, Locust — написан на Python и позволяет описывать сценарии нагрузки обычным Python-кодом) со ступенчатым увеличением RPS, пока не начнёт расти латентность/ошибки — это точка предела текущей конфигурации.
- **Профилирование в проде на семпле трафика**, а не только в синтетическом тесте — синтетический тест часто не воспроизводит реальные паттерны доступа (hot keys, неравномерное распределение запросов по эндпоинтам).

## Порядок действий при расследовании

1. Собрать p50/p95/p99 latency и error rate по каждому звену пути запроса за интересующий период.
2. Найти звено с наибольшим вкладом в p99 через трейсы конкретных медленных запросов.
3. Проверить saturation этого звена (утилизация CPU, глубина очереди, занятость пула соединений) — подтверждает ли это узкое место, или проблема разовая (например, единичный медленный внешний вызов, GC-пауза).
4. Только после этого принимать решение о масштабировании/кэшировании/шардировании конкретно этого звена, а не всей системы целиком.

> Частый вопрос на собеседовании: почему для профилирования системы недостаточно смотреть на среднюю латентность? Среднее скрывает длинный хвост распределения — небольшая, но значимая доля запросов может отрабатывать в разы медленнее среднего, и именно она определяет пользовательский опыт и часто указывает на узкое место, которое проявляется не всегда, а при определённых условиях (hot key, конкретный тяжёлый запрос, contention под нагрузкой).

> Частый вопрос на собеседовании: как распределённый трейсинг помогает искать узкие места, которые не видны в логах отдельных сервисов? Трейсинг связывает все span'ы одного запроса единым trace_id в дерево вызовов с точными длительностями каждого шага, показывая, где именно запрос провёл время — включая вложенные вызовы других сервисов, — вместо того чтобы вручную сопоставлять разрозненные логи по временным меткам.
