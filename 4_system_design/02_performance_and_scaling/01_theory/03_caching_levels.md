# Кэширование на уровне архитектуры

Механика конкретных паттернов кэша (cache-aside, TTL, eviction, Redis) — тема отдельного раздела базы (`2_data_and_messaging`). Здесь — более высокий уровень: где именно в архитектуре системы стоят кэши, что каждый уровень даёт и почему они почти всегда работают вместе, а не по отдельности.

## Путь запроса и уровни кэша

```
Клиент → CDN → Reverse proxy → Приложение (L1) → Redis (L2) → БД (буферный кэш)
  │        │          │              │                │              │
браузер  edge      кэш ответов   локальный кэш   распределённый    страницы БД
кэш      кэш       nginx/varnish  процесса        кэш               в памяти
```

Каждый уровень решает свою задачу и разгружает следующий за собой уровень — узкое место конкретной системы определяет, какой из уровней даёт наибольшую выгоду.

## CDN (Content Delivery Network)

Сеть edge-серверов, географически распределённых близко к пользователям. Кэширует статический и полустатический контент (изображения, JS/CSS-бандлы, иногда целые HTML-страницы или API-ответы с явным `Cache-Control`) прямо на границе сети, до того как запрос вообще доходит до вашей инфраструктуры.

- **Что даёт:** резко снижает латентность для географически удалённых пользователей (запрос обслуживается edge-узлом в соседнем городе, а не origin-сервером на другом континенте) и полностью снимает нагрузку с origin для кэшированного контента — CDN-запрос вообще не доходит до бэкенда.
- **Когда уместен:** контент одинаков для многих пользователей (статика, публичные страницы, изображения) и допускает управляемую задержку обновления через TTL или явную инвалидацию.
- **Когда бесполезен:** персонализированный контент, уникальный на каждого пользователя (личный кабинет с приватными данными) — кэшировать нечего, разве что общие для всех части ответа.

## Reverse proxy / кэш HTTP-ответов

Слой перед приложением (nginx, Varnish), кэширующий целиком HTTP-ответы по ключу (URL + заголовки) на короткое время. Ближе к origin, чем CDN, но всё ещё перед самим приложением — снимает повторяющиеся одинаковые запросы, не давая им дойти до кода приложения и БД.

- Хорошо подходит для read-heavy эндпоинтов с одинаковым ответом на множество запросов в короткий промежуток времени (например, список популярных товаров, обновляемый раз в минуту).
- В экосистеме Python часто эту же роль на уровне приложения берёт HTTP-кэширование через заголовки (`ETag`, `Cache-Control`), которое затем понимают клиент, CDN и reverse proxy без специального серверного кода.

## Кэш приложения (L1, in-process)

Локальный кэш внутри процесса приложения (простой `dict`/`functools.lru_cache` или библиотека вроде `cachetools`). Самый быстрый уровень — нет сети, только память процесса.

- **Плюс:** минимальная латентность (микросекунды), нет сетевого round-trip.
- **Минус:** свой для каждого инстанса приложения — при нескольких репликах данные не согласованы между ними, и при рестарте процесса кэш пропадает.
- Хорош для данных, которые почти не меняются и одинаковы для всех (справочники, конфигурация, feature flags), либо как первый уровень перед распределённым кэшем (L1 гасит самые горячие ключи и сеть до L2).

## Распределённый кэш приложения (L2, Redis/Memcached)

Общий кэш для всех инстансов приложения — отдельный сетевой сервис. Разобран подробно в разделе про Redis (`2_data_and_messaging`); здесь важно только его место в общей картине: между приложением и БД, общий для всех реплик приложения, переживает рестарт отдельного инстанса приложения.

- Даёт согласованность между репликами приложения (в отличие от L1) ценой сетевого round-trip (доли миллисекунды вместо микросекунд).
- Именно этот уровень чаще всего снимает основную нагрузку с БД в типичном веб-бэкенде.

## Кэш на уровне БД (буферный пул)

Сама СУБД держит часто используемые страницы данных в оперативной памяти (buffer pool в PostgreSQL/MySQL), не читая их каждый раз с диска. Это последний уровень кэша перед физическим хранилищем — им управляет сама БД, а не код приложения, но его размер и поведение (например, `shared_buffers` в PostgreSQL) — тоже архитектурное решение, влияющее на производительность всей системы.

## Как выбирать, где ставить кэш

1. **Определить, на каком уровне пути запроса находится текущее узкое место** (см. `01_bottlenecks.md`) — кэшировать нужно перед этим звеном, а не «везде подряд».
2. **Оценить, насколько контент общий для многих пользователей.** Чем более общий — тем ближе к клиенту (CDN) можно и нужно кэшировать. Чем более персонализирован — тем ближе к БД (L2/L1) единственно возможное место.
3. **Оценить допустимую устареваемость.** Публичная статика допускает часы TTL; данные, влияющие на баланс/остатки, — секунды или вообще не кэшируются на этом уровне.
4. **Помнить, что уровни работают вместе, а не взаимоисключающе.** Типичный высоконагруженный сервис использует все уровни одновременно: CDN снимает трафик по статике, L2 — по динамическим, но не персональным данным, L1 — по самым горячим ключам внутри L2-периметра, буферный пул БД — по всему, что не попало в приложенческий кэш.

## Итоговая картина по уровням

| Уровень | Латентность | Общий между инстансами | Переживает рестарт | Типичный контент |
|---|---|---|---|---|
| CDN | доли мс (edge) | да, глобально | да | статика, публичные страницы |
| Reverse proxy | ~1 мс | на своём узле | обычно нет | одинаковые HTTP-ответы на короткое TTL |
| L1 (in-process) | микросекунды | нет | нет | справочники, конфигурация, самые горячие ключи |
| L2 (Redis/Memcached) | доли мс | да | да (частично, с persistence) | результаты запросов, сессии, счётчики |
| Буферный пул БД | микросекунды–мс | на узле БД | нет (греется заново) | горячие страницы данных |

> Частый вопрос на собеседовании: где в типичном веб-стеке находятся кэши, и почему их несколько, а не один большой? На всём пути запроса: CDN, reverse proxy, L1 в приложении, L2 распределённый, буферный пул БД. Их несколько, потому что у каждого уровня свой компромисс между близостью к клиенту (низкая латентность, высокая разгрузка origin) и возможностью хранить персонализированные/часто меняющиеся данные — один уровень не может одновременно быть предельно быстрым, глобально распределённым и мгновенно согласованным.

> Частый вопрос на собеседовании: почему нельзя просто кэшировать всё на CDN и не думать про остальные уровни? Потому что CDN эффективен только для контента, одинакового для многих пользователей и допускающего управляемую задержку обновления — персонализированные ответы (личный кабинет, баланс, лента конкретного пользователя) кэшировать там нечего или почти нечего, для них нужны уровни ближе к бэкенду.
