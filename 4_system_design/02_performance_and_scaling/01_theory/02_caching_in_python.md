# Многоуровневое кэширование в Python: L1, L2 Redis и защита от Stampede

## О чём эта тема (краткий контекст)

Кэширование разгружает медленные хранилища (прежде всего реляционные БД) и
снижает латентность чтения за счёт сохранения часто запрашиваемых результатов в
быстрой памяти. В реальной архитектуре кэш работает каскадом на нескольких
уровнях: от CDN и Reverse Proxy на границе сети до локального кэша в памяти
процесса (L1) и распределённого кэша в Redis/Memcached (L2). При этом любая
система кэширования должна решать три фундаментальные проблемы: инвалидацию
устаревших данных, ограничение потребления памяти (LRU/LFU/TTL) и защиту от
«эффекта толпы» (cache stampede), когда одновременное истечение горячего ключа
пробивает кэш сотнями параллельных запросов в базу.

> **Базовая теория и инфраструктурный фундамент (DevOps / SRE):**

>

> исключительно особенности реализации и эксплуатации в экосистеме
> **Python** (рантайм CPython и GIL, память, WSGI/ASGI, стандартная
> библиотека и популярные фреймворки). Базовая работа с Redis разобрана в

## 1. Локальный L1-кэш в Python (`lru_cache`, `cachetools`) и его ловушки

Локальный in-process кэш (L1) хранит объекты Python прямо в оперативной памяти
воркера. Чтение из него занимает сотни наносекунд (0 сетевых походов и 0 затрат
на десериализацию JSON/pickle), но в Python у него есть четыре опасные ловушки.

### Ловушка 1: Размножение памяти и рассинхрон между воркерами Gunicorn

Из-за GIL Python-приложение в продакшене почти всегда работает как $N$
независимых процессов-воркеров (`gunicorn -w 8` или 8 подов в Kubernetes). У
каждого процесса — **собственное изолированное адресное пространство**:

```text
Балансировщик (Round Robin)
  ├──▶ Worker 1 (PID 101): свой L1 dict (250 МБ)  ──┐
  ├──▶ Worker 2 (PID 102): свой L1 dict (250 МБ)  ──┼──▶ общий L2 Redis
  └──▶ ...                                          │    (единый для всех)
  └──▶ Worker 8 (PID 108): свой L1 dict (250 МБ)  ──┘
```

Следствия:
1. **Умножение памяти на $N$:** кэш весом 250 МБ в одном процессе превращается
   в $8 \times 250\text{ МБ} = 2\text{ ГБ}$ RAM на хосте и легко приводит к
   `OOMKilled` контейнера.
2. **Холодный прогрев и низкий Hit Ratio:** первый запрос на ключ `"tariff_1"`
   прогреет только `Worker 1`; следующие 7 запросов по Round Robin попадут на
   воркеры 2..8 и получат `Cache Miss`.
3. **Невозможна точечная инвалидация без Pub/Sub:** если `Worker 1` обновил
   запись в БД и очистил свой `lru_cache`, воркеры 2..8 продолжат отдавать
   старое значение до истечения TTL. Поэтому в L1-кэше Python-сервиса держат
   только небольшие справочники/конфиги с коротким TTL (5–60 секунд) через
   `cachetools.TTLCache(maxsize=1024, ttl=30)`.

### Ловушка 2: Утечка памяти при `@lru_cache` на методах класса

Декоратор `functools.lru_cache` хранит сильные ссылки на все аргументы вызова в
глобальном словаре функции, **включая первый аргумент `self`**. Если навесить
`@lru_cache` на метод экземпляра класса, создаваемого на каждый запрос (к
примеру, сервиса или репозитория), сборщик мусора никогда не удалит эти
экземпляры!

### Ловушка 3: `@lru_cache` не работает корректно с `async def`

Если обернуть `async def get_config()` в стандартный `@functools.lru_cache`, в
кэше сохранится **объект корутины (`coroutine object`)**, который можно
ожидать (`await`) только один раз — второй вызов упадёт с `RuntimeError: cannot
reuse already awaited coroutine`. Для асинхронных функций используют явный
`TTLCache` из `cachetools` или библиотеку `async-lru` (`@alru_cache(ttl=30)`).

### Ловушка 4: Мутация закэшированного объекта по ссылке

L1-кэш в Python возвращает ссылку на тот же самый `dict` или `list` в памяти.
Если вызывающий код сделает `data["extra"] = 1`, он незаметно испортит данные в
кэше для всех последующих запросов в этом воркере. Возвращайте из L1-кэша
неизменяемые типы (`tuple`, `@dataclass(frozen=True)`) или копию.

## 2. Двухуровневый кэш (L1 + L2 Redis) и защита от Cache Stampede

Когда истекает TTL популярного ключа (например, главной страницы каталога при
5000 RPS), сотни корутин внутри каждого воркера одновременно получают `Miss` в
Redis и лавиной устремляются в PostgreSQL — это **Cache Stampede (Thundering
Herd)**.

В Python защита строится на двух уровнях:
1. **Внутри одного `asyncio`-воркера (Singleflight на `asyncio.Lock`):** если
   100 корутин в одном процессе одновременно запросили ключ `k`, только первая
   идёт в Redis/БД, а остальные 99 ждут на `asyncio.Lock` для этого ключа.
2. **Между разными воркерами/подами (распределённый лок в Redis или Early
   Expiration):** чтобы в БД пошёл только один из 8 воркеров.

```python
import asyncio
import json
from collections import defaultdict
from cachetools import TTLCache
import redis.asyncio as redis


class TwoLevelCache:
    def __init__(self, redis_client: redis.Redis) -> None:
        self._l1 = TTLCache(maxsize=2000, ttl=5.0)   # L1: 5 секунд в RAM
        self._l2 = redis_client                      # L2: Redis
        self._key_locks: dict[str, asyncio.Lock] = defaultdict(asyncio.Lock)

    async def get_or_load(
        self, key: str, loader_coro, l2_ttl: int = 60
    ) -> dict:
        # 1. Быстрая проверка в памяти процесса (L1, ~0.5 мкс)
        if key in self._l1:
            return self._l1[key]

        # 2. Singleflight в воркере: только одна корутина на ключ идёт в сеть
        async with self._key_locks[key]:
            if key in self._l1:
                return self._l1[key]

            # 3. Проверяем распределённый кэш L2 (Redis, ~0.5–1 мс)
            raw = await self._l2.get(key)
            if raw is not None:
                data = json.loads(raw)
                self._l1[key] = data
                return data

            # 4. Промах в L1 и L2 — загружаем из БД и прогреваем оба уровня
            data = await loader_coro()
            await self._l2.set(key, json.dumps(data), ex=l2_ttl)
            self._l1[key] = data
            return data
```

> **Почему в Redis никогда не стоит класть `pickle`:** модуль `pickle` в Python
> медленнее `orjson`/`msgspec`, нечитаем из сервисов на других языках и ломается
> при переименовании Python-классов между релизами, а при компрометации Redis
> позволяет выполнить произвольный код (`RCE`) при десериализации. Используйте
> JSON (`orjson`), `msgpack` или Protobuf.

## 3. Типовые вопросы на собеседовании (Python System Design)

> **Вопрос:** Разработчик добавил `@lru_cache(maxsize=100_000)` для кэширования
> карточек товаров в Django/FastAPI приложении, которое запускается под
> `gunicorn --workers 8`. На стенде с 1 воркером всё летало, а в продакшене
> контейнер падает по `OOMKilled`, причём пользователи иногда видят старую цену
> товара после её обновления. Почему?
>
> **Ответ:** Из-за модели pre-fork у каждого из 8 воркеров Gunicorn своя копия
> памяти и свой независимый словарь `@lru_cache`. Во-первых, потребление памяти
> под кэш умножилось на 8. Во-вторых, у `@lru_cache` нет TTL: карточки остаются
> в памяти воркера навечно, а инвалидация в одном воркере при обновлении цены
> никак не очищает память остальных 7 воркеров. Решение: вынести основной кэш
> карточек в общий L2 Redis, а в процессе оставить маленький `TTLCache` (на
> 1000 самых горячих ключей с TTL 5–10 секунд) или инвалидировать L1 через
> Redis Pub/Sub.

> **Вопрос:** Как в `asyncio`-приложении предотвратить ситуацию, когда при
> истечении ключа в Redis 200 одновременных запросов в рамках одного воркера
> отправляют 200 одинаковых тяжёлых `SELECT` в PostgreSQL?
>
> **Ответ:** Использовать паттерн Singleflight (Request Coalescing) на базе
> словаря локов `dict[str, asyncio.Lock]` по ключу кэша и двойной проверки
> (Double-Checked Locking). Первая корутина захватывает `lock` для конкретного
> ключа, делает запрос в БД и записывает ответ в кэш; остальные 199 корутин
> ждут освобождения этого лока, после чего во второй проверке сразу забирают
> свежее значение из кэша без обращения к БД.
