# Упражнение 02: разбор

## 1. API-сервис: горизонтально

API-сервис явно stateless — нет состояния между запросами в памяти процесса, значит любой инстанс может обработать любой запрос. Это ровно тот случай, когда горизонтальное масштабирование почти бесплатно: добавление реплик за балансировщиком не требует решения проблем согласованности состояния между узлами. При этом текущая утилизация всего ~30% при 2 инстансах говорит, что до вертикального потолка ещё далеко, но горизонталь всё равно предпочтительнее вертикали здесь по совокупности причин: она даёт отказоустойчивость (не одна точка отказа) практически без дополнительной сложности, и линейно дешевле масштабируется дальше, если нагрузка продолжит расти сверх удвоения.

## 2. Транскодер: почему важен GIL и как масштабировать

Транскодирование видео — классическая CPU-bound задача. Если транскодер реализован как один Python-процесс с несколькими потоками, GIL не даст этим потокам параллельно использовать несколько ядер для самого процесса кодирования (лок отпускается на I/O-ожиданиях, но не на плотных вычислениях) — 32 ядра сервера в таком случае используются в лучшем случае одним потоком за раз для CPU-bound части, а остальные 31 ядро простаивают на этой задаче. Поэтому горизонтальность внутри одного сервера здесь достигается не потоками, а несколькими независимыми процессами (`multiprocessing`, либо отдельные worker-процессы, каждый берёт задачу из общей очереди) — по одному процессу на ядро (или чуть меньше, оставляя запас), что даёт настоящий параллелизм по CPU. Дальше — горизонтально между серверами: несколько таких серверов-транскодеров, каждый со своим пулом процессов, тянущих задачи из общей очереди (например, Celery поверх Redis/RabbitMQ), а не одна очередь FIFO строго на один сервер.

## 3. Признак приближения к вертикальному потолку

Да, признак уже есть: утилизация CPU транскодера — 85% в часы пик на сервере с уже максимальным для практических целей числом ядер (32) для отдельного сервера. Продолжать наращивать мощность одного сервера транскодера дальше означает упираться в нелинейно растущую стоимость топовых конфигураций (см. `04_horizontal_vs_vertical_scaling.md`) и рано или поздно — в физический потолок доступных конфигураций у облачного провайдера. При этом весь транскодинг проходит через один сервер — это единая точка отказа: если сервер ляжет, обработка видео полностью остановится, а очередь необработанных видео будет расти без ограничений (по Little's Law), пока сервер не восстановится.

## 4. Итоговая архитектура

- API-сервис — горизонтальное масштабирование: увеличить число stateless-реплик за балансировщиком пропорционально ожидаемому росту трафика запросов (не самой обработки видео — эти нагрузки разделены).
- Транскодер — заменить единственный сервер на несколько серверов-воркеров умеренной мощности (не обязательно по 32 ядра каждый), каждый — с пулом процессов (`multiprocessing`) под число своих ядер, вытягивающих задачи из общей распределённой очереди задач. Очередь перед транскодерами становится общей точкой развязки: она сглаживает всплески (видео копится в очереди, а не теряется и не роняет систему при кратковременном превышении мощности), и добавление нового сервера-воркера линейно увеличивает пропускную способность обработки видео без изменения остального кода — то есть именно горизонталь, а не дальнейшая вертикаль, даёт путь к плановому удвоению throughput.
