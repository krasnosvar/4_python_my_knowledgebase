# Упражнение 04: разбор

## 1. Уровни кэша по типу контента

| Контент | Уровень | Обоснование |
|---|---|---|
| Страница описания курса | CDN + reverse proxy, с TTL часы | Одинакова для всех, меняется редко — идеальный кандидат для максимально близкого к клиенту кэша с длинным TTL и явной инвалидацией при редактировании курса преподавателем. |
| Видео уроков | CDN | Статичные большие файлы, не меняются после публикации — классический сценарий раздачи через CDN, снимает всю нагрузку с origin. |
| Личный прогресс пользователя | Не кэшировать на общих уровнях (CDN/reverse proxy); максимум — короткоживущий L1/L2 с точечной инвалидацией по user_id | Полностью персонализирован и меняется на каждое действие — CDN/reverse proxy кэшировать нечего (ключ кэша был бы уникален на пользователя и запрос, hit ratio около нуля), а если и кэшировать в L2 (например, чтобы не бить лишний раз по БД при частом опросе прогресса), то с немедленной инвалидацией по конкретному user_id при каждом обновлении, а не по TTL. |
| Список «рекомендованные курсы» | L2 (Redis), TTL порядка часов | Персонализирован, но источник данных сам обновляется только раз в 6 часов — кэшировать на CDN бессмысленно (персонализация), но L2 с TTL, синхронизированным с частотой пересчёта, полностью оправдан. |
| Количество свободных мест | L2 с очень коротким TTL для отображения, но НЕ для решения о продаже | См. пункт 3 — разделяем «читать для отображения» и «читать для критического решения». |

## 2. TTL для «рекомендованных курсов»

TTL стоит выставить чуть меньше интервала пересчёта источника — например, 5–6
часов, с небольшим jitter (± 15–30 минут), чтобы не создавать синхронный
всплеск перезагрузки кэша у всех пользователей одновременно сразу после
очередного batch-пересчёта. Смысл: TTL длиннее интервала пересчёта не даёт
выгоды (данные всё равно обновляются реже, чем текущий TTL позволял бы отдавать
свежее), а заметно короче — создаёт лишние обращения к дорогому источнику
(пересчитанный batch-результат) без пользы, так как между пересчётами данные
физически не меняются.

## 3. Свободные места: отображение vs решение о продаже

Кэшировать количество свободных мест с TTL в минуту для **отображения** на
странице курса — нормально: пользователь видит примерное, слегка устаревшее
число «осталось 3 места», и небольшая неточность в отображении не создаёт
вреда. Но использовать это же кэшированное значение как основание для **решения
«можно ли продать ещё одно место»** в момент оплаты — прямой путь к перепродаже
мест: два покупателя увидят «1 место осталось» одновременно из кэша и оба
получат подтверждение оплаты, хотя место одно. Поэтому путь оплаты обязан
читать актуальное значение напрямую из источника истины (БД) в момент списания,
как правило через атомарную операцию с проверкой условия (`UPDATE ... SET
seats_left = seats_left - 1 WHERE seats_left > 0`, с проверкой числа изменённых
строк) — то есть не полагаться на кэш вообще для этого конкретного пути,
оставляя кэш только для некритичного отображения на остальных страницах.

## 4. Изменение при платной подписке

Если доступ к видео требует проверки статуса подписки на каждый запрос,
публично кэшировать сами видеофайлы на CDN по прямой публичной ссылке уже
нельзя — иначе подписку можно обойти, просто зная URL. Практическое решение,
сохраняющее выгоды CDN: видео по-прежнему физически хранится и раздаётся через
CDN, но доступ выдаётся через подписанные, ограниченные по времени URL (signed
URL / токен с коротким сроком действия), которые генерируются бэкендом только
после проверки активной подписки конкретного пользователя. Сам байтовый контент
видео всё ещё кэшируется на CDN (он не персонализирован), но право получить
временную ссылку на него — персонализированная и непубличная операция,
выполняемая на каждый запрос через бэкенд, а не через прямое кэширование
финального URL.
