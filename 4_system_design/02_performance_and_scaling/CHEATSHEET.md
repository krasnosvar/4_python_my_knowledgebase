## Узкие места

Подробнее: [01_bottlenecks.md](./01_theory/01_bottlenecks.md)

| Формула / правило | Смысл |
| :--- | :--- |
| throughput системы = throughput самого слабого звена | не сумма и не среднее |
| `L = λ × W` (закон Литтла) | очередь растёт без остановки → `λ` выше пропускной способности звена |
| Предел звена | точка, где при росте RPS растёт латентность, а не throughput |
| Утилизация важнее средней латентности | 5 мс при 95% загрузки опаснее, чем 50 мс при 10% |

| Звено | Частая причина |
| :--- | :--- |
| БД (запись) | один мастер, диск/CPU, локи на горячих строках |
| БД (чтение) | мало реплик, нет кэша |
| Внешний API | лимиты провайдера, синхронные вызовы без пула соединений |
| CPU-bound Python | GIL: нужны процессы (`multiprocessing`, несколько воркеров) |
| I/O-bound Python | GIL не мешает: потоки или `asyncio` |
| Пул соединений | мал — запросы ждут соединение |
| Сеть/DNS | резолвинг на каждый запрос, нет keep-alive |

## Профилирование системы

Подробнее: [02_system_profiling.md](./01_theory/02_system_profiling.md)

| Сигнал | Что мерить | Методика |
| :--- | :--- | :--- |
| Latency | p50 / p95 / p99, не среднее | RED: Duration |
| Traffic / Rate | запросов в секунду | RED: Rate |
| Errors | доля ошибок, включая таймауты | RED и USE |
| Saturation / Utilization | CPU, глубина очереди, занятость пула | USE |

| Инструмент | Для чего |
| :--- | :--- |
| Тайминги на границах (вход/выход) | увидеть время в очереди перед компонентом |
| Распределённый трейсинг (OpenTelemetry): `trace_id` + дерево `span` | где запрос провёл время через несколько сервисов |
| Нагрузочный тест (Locust) со ступенчатым RPS | точка предела текущей конфигурации |
| Профилирование в проде на семпле | реальные hot keys и распределение по эндпоинтам |

Расследование: p99 и error rate по звеньям → трейсы медленных запросов →
saturation звена → только потом решение.

## Уровни кэша

Подробнее: [03_caching_levels.md](./01_theory/03_caching_levels.md)

| Уровень | Латентность | Общий между инстансами | Переживает рестарт | Типичный контент |
| :--- | :--- | :--- | :--- | :--- |
| CDN | доли мс (edge) | да, глобально | да | статика, публичные страницы |
| Reverse proxy (nginx, Varnish) | ~1 мс | на своём узле | обычно нет | одинаковые HTTP-ответы, короткий TTL |
| L1 in-process (`lru_cache`, `cachetools`) | микросекунды | нет | нет | справочники, конфиг, самые горячие ключи |
| L2 (Redis/Memcached) | доли мс | да | частично (persistence) | результаты запросов, сессии, счётчики |
| Буферный пул БД (`shared_buffers`) | микросекунды–мс | на узле БД | нет | горячие страницы данных |

| Контент | Где кэшировать |
| :--- | :--- |
| Общий для многих, допускает задержку обновления | ближе к клиенту: CDN, reverse proxy |
| Персонализированный | ближе к БД: L2 / L1 |
| Баланс, остатки | секунды TTL или не кэшировать |

## Вертикаль vs горизонталь

Подробнее: [04_horizontal_vs_vertical_scaling.md](./01_theory/04_horizontal_vs_vertical_scaling.md)

| | Вертикаль (scale up) | Горизонталь (scale out) |
| :--- | :--- | :--- |
| Суть | тот же узел мощнее | больше узлов за балансировщиком |
| Архитектура | без изменений | балансировка, discovery, согласование |
| Потолок | физический | практически нет (упирается в координацию, БД) |
| Стоимость | нелинейная | ближе к линейной |
| Отказ | единая точка отказа | отказ одного из N не останавливает систему |
| Простой | часто нужен рестарт | узлы добавляются без остановки |
| Подходит | монолит, БД на запись | stateless-приложение, воркеры очереди, read-реплики |

Закон Амдала — предел ускорения при последовательной доле `1 - p`:

```python
def speedup(p, n):
    return 1 / ((1 - p) + p / n)

print(round(speedup(0.9, 10), 2), round(speedup(0.9, 100), 2), round(speedup(0.9, 10**6), 2))
# 5.26 9.17 10.0  — при p = 0.9 больше 10x не получить
```

## Партиционирование и шардирование

Подробнее: [05_partitioning_sharding.md](./01_theory/05_partitioning_sharding.md)

| Стратегия | Плюс | Минус |
| :--- | :--- | :--- |
| Range (диапазон ключа) | range-запросы на одном шарде | hot shard на «свежем» диапазоне |
| Hash (`hash(key) % N`) | равномерная нагрузка | range-запросы → scatter-gather; смена `N` переносит почти все ключи |
| Consistent hashing | при добавлении узла переезжает ~`K/N` ключей | сложнее реализации |
| Гео / tenant | изоляция, data residency | неравномерность, «шумный сосед» |

```python
# hash % N: доля ключей, сменивших шард при N=4 → N=5
moved = sum(1 for k in range(100_000) if k % 4 != k % 5)
print(moved / 100_000)  # 0.8
```

Выбор ключа: самый частый паттерн доступа → равномерность → какие запросы
станут кросс-шардовыми → данные одной транзакции на одном шарде.

## Типичные ошибки

- ⚠️ Добавлять реплики приложения, когда узкое место в БД или внешнем API.
- ⚠️ Смотреть на среднюю латентность вместо p99.
- ⚠️ Кэш для уникальных данных или данных со строгой консистентностью → низкий hit ratio.
- ⚠️ Хранить сессии в памяти процесса и масштабироваться горизонтально (sticky sessions — паллиатив).
- ⚠️ Ключ шардирования без учёта паттерна доступа → hot shard или scatter-gather.
- ⚠️ Кросс-шардовые транзакции: нужен 2PC или сага, обычный ACID не работает.
- ⚠️ Тянуть вертикаль БД до упора, не планируя шардирование заранее.
